# Docker для автотестов — практический гайд

Как собирать образы, запускать контейнеры и гонять автотесты (Playwright + TypeScript; вариант для Python — в конце). Заточено под реальную легенду: тесты в Docker-контейнерах с зафиксированными зависимостями и версиями, прогон в CI, поднятие зависимостей (приложение + БД + mock) через `docker-compose`.

---

## 1. Зачем Docker в автотестах

**Проблема без Docker:** «у меня локально проходит, в CI падает». Причины — разные версии Node/браузеров/ОС-библиотек, разные зависимости, разное окружение.

**Что даёт Docker:**

- **Воспроизводимость** — образ фиксирует ОС, Node, браузеры и зависимости: у всех и в CI одно и то же окружение.
- **Изоляция** — тесты не зависят от того, что установлено на машине.
- **Портируемость** — один и тот же образ гоняется локально, в CI и на любом сервере.
- **Поднятие всего стека одной командой** — приложение, БД, mock-сервер, тесты — через `docker-compose up`.

**Ключевые термины (чтобы не путать):**

- **Образ (image)** — «слепок» окружения: неизменяемый шаблон (ОС + Node + браузеры + твой код + зависимости).
- **Контейнер (container)** — запущенный экземпляр образа (живой процесс). Из одного образа можно поднять сколько угодно контейнеров.
- **Dockerfile** — рецепт сборки образа.
- **docker-compose** — оркестрация нескольких контейнеров (тесты + их зависимости) одним файлом.
- «Скомпилировать/создать» контейнер = **собрать образ** (`docker build`), а потом **запустить** (`docker run`).

## 2. Dockerfile для Playwright-тестов

Playwright даёт **официальный образ**, где уже установлены браузеры (Chromium/Firefox/WebKit) и все системные библиотеки — это критично, вручную их ставить больно. Версия образа **должна совпадать** с версией Playwright в `package.json` (иначе рассинхрон браузеров).

`Dockerfile`:

```dockerfile
# 1. Базовый образ: браузеры + системные зависимости уже внутри.
#    Тег версии = версия playwright в package.json (фиксируем!)
FROM mcr.microsoft.com/playwright:v1.48.0-jammy

# 2. Рабочая директория внутри контейнера
WORKDIR /tests

# 3. Сначала копируем только манифесты зависимостей — ради кеша слоёв.
#    Пока package*.json не менялись, npm ci не переустанавливается.
COPY package.json package-lock.json ./

# 4. Ставим зависимости строго по lock-файлу (детерминированно)
RUN npm ci

# 5. Теперь копируем весь код тестов
COPY . .

# 6. Команда по умолчанию — запуск тестов
CMD ["npx", "playwright", "test"]
```

**Про «компиляцию»:** Playwright исполняет TypeScript «на лету» (через встроенный транспайлер), отдельный `tsc` для прогона не нужен. Но типы полезно проверять — добавляют шаг `npx tsc --noEmit` в CI как отдельную проверку.

**`.dockerignore`** (чтобы не тащить лишнее в образ и не ломать кеш):

```
node_modules
test-results
playwright-report
allure-results
.git
Dockerfile
```

## 3. Сборка образа (build) и запуск (run)

**Собрать образ** (`-t` — имя/тег):

```bash
docker build -t aqa-tests:local .
```

**Запустить тесты в контейнере:**

```bash
docker run --rm aqa-tests:local
```

- `--rm` — удалить контейнер после завершения (не копить мусор).

**Забрать отчёты наружу через volume** (`-v` монтирует папку хоста в контейнер):

```bash
docker run --rm \
  -v "$(pwd)/playwright-report:/tests/playwright-report" \
  -v "$(pwd)/allure-results:/tests/allure-results" \
  aqa-tests:local
```

Так HTML-отчёт Playwright и результаты Allure окажутся на твоей машине после прогона.

**Прокинуть переменные окружения** (base URL, креды, теги):

```bash
docker run --rm \
  -e BASE_URL=https://staging.example.com \
  -e CI=true \
  aqa-tests:local \
  npx playwright test --grep @smoke
```

Аргументы после имени образа **переопределяют** `CMD` — удобно гонять подмножество (`@smoke`).

**Запустить конкретный файл/проект:**

```bash
docker run --rm aqa-tests:local npx playwright test tests/checkout.spec.ts --project=chromium
```

## 4. docker-compose: тесты + их зависимости

Обычно тестам нужно не только браузер, но и **тестируемое приложение, БД, mock-сервер**. Поднимаем всё вместе `docker-compose`:

`docker-compose.yml`:

```yaml
services:
  # Тестируемое приложение (или его образ из registry)
  app:
    image: registry.example.com/app:latest
    environment:
      DB_HOST: db
    depends_on:
      db:
        condition: service_healthy
    ports:
      - "3000:3000"

  # Реляционная БД для приложения
  db:
    image: postgres:16
    environment:
      POSTGRES_PASSWORD: test
    healthcheck:                       # ждём, пока БД реально готова
      test: ["CMD-SHELL", "pg_isready -U postgres"]
      interval: 3s
      retries: 10

  # Standalone mock-сервер для нестабильных внешних сервисов
  mock:
    image: wiremock/wiremock:latest
    volumes:
      - ./mocks:/home/wiremock/mappings   # JSON-правила ответов

  # Контейнер с автотестами
  tests:
    build: .                             # собрать из нашего Dockerfile
    environment:
      BASE_URL: http://app:3000          # по имени сервиса внутри сети compose
      MOCK_URL: http://mock:8080
    depends_on:
      - app
      - mock
    volumes:
      - ./playwright-report:/tests/playwright-report
      - ./allure-results:/tests/allure-results
```

**Запуск всего стека и выход по коду тестов:**

```bash
docker compose up --build --abort-on-container-exit --exit-code-from tests
```

- `--build` — пересобрать образ тестов;
- `--abort-on-container-exit` — остановить всё, когда тесты завершились;
- `--exit-code-from tests` — вернуть наружу код выхода контейнера с тестами (для CI-гейта: упали тесты → упал пайплайн).

**Погасить и почистить:**

```bash
docker compose down -v      # -v удалить и volume (данные БД)
```

**Важный момент — сеть:** внутри `docker-compose` контейнеры видят друг друга **по имени сервиса** (`app`, `db`, `mock`), а не по `localhost`. Поэтому `BASE_URL=http://app:3000`, а не `127.0.0.1`.

## 5. Прогон в CI

**GitLab CI** (`.gitlab-ci.yml`) — самый частый вариант, когда тесты в Docker:

```yaml
e2e:
  stage: test
  image: mcr.microsoft.com/playwright:v1.48.0-jammy
  script:
    - npm ci
    - npx playwright test
  artifacts:
    when: always
    paths:
      - playwright-report/
      - allure-results/
    expire_in: 1 week
```

Здесь CI сам берёт образ Playwright как окружение раннера — Dockerfile для этого не обязателен. А `docker-compose`-вариант нужен, когда надо поднять ещё и приложение+БД.

**Jenkins** — либо агент на Docker, либо шаг:

```groovy
sh 'docker compose up --build --abort-on-container-exit --exit-code-from tests'
```

## 6. Тонкости, которые отличают «работает» от «стабильно»

- **Фиксируй версии.** Тег образа Playwright = версия в `package.json`; `npm ci` (не `npm install`) — по lock-файлу. Иначе «поплыли» браузеры/зависимости.
- **Кеш слоёв.** Сначала `COPY package*.json` + `npm ci`, потом `COPY . .` — тогда переустановка зависимостей не происходит на каждое изменение теста (сборка быстрее).
- **`--rm`** на разовых прогонах, чтобы не плодить мёртвые контейнеры.
- **Volumes для отчётов** — иначе Allure/HTML-отчёт останутся внутри контейнера и пропадут.
- **Ждать готовности зависимостей** — `healthcheck` + `depends_on: condition: service_healthy`, иначе тесты стартуют раньше, чем поднялась БД/приложение → флак.
- **`--ipc=host`** для Chromium в Docker (уменьшает падения из-за нехватки shared memory): `docker run --ipc=host ...`.
- **Ресурсы.** Браузерам нужна память; в CI закладывай лимиты.

## 7. Шпаргалка команд

```bash
docker build -t aqa-tests:local .              # собрать образ
docker run --rm aqa-tests:local                # запустить тесты
docker run --rm -v $(pwd)/report:/tests/report aqa-tests:local   # с отчётом
docker run -it --rm --entrypoint bash aqa-tests:local            # зайти внутрь, отладить
docker images                                  # список образов
docker ps -a                                   # список контейнеров
docker compose up --build --exit-code-from tests   # весь стек + код выхода
docker compose down -v                         # погасить и почистить
docker system prune -af                        # очистить всё лишнее (осторожно)
```

## 8. Вариант для Python (Selenide/pytest-playwright)

Если стек Python:

```dockerfile
FROM mcr.microsoft.com/playwright/python:v1.48.0-jammy
WORKDIR /tests
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt
COPY . .
CMD ["pytest", "-n", "auto", "--alluredir=allure-results"]
```

`-n auto` (pytest-xdist) — параллельный прогон по ядрам. Остальное (compose, volumes, CI) — идентично.

*(Примечание: Selenide — Java-инструмент; если речь про Java-стек, базовый образ — с JDK + Maven/Gradle, а не playwright/python. Пример выше — для Python + Playwright.)*

## 9. Как рассказать на собесе (одним блоком)

> «Тесты у меня гоняются в Docker ради воспроизводимости: образ на базе официального `mcr.microsoft.com/playwright` с зафиксированной версией под браузеры, зависимости через `npm ci` по lock-файлу. Собираю `docker build`, запускаю `docker run` с volume под отчёты Allure. Когда нужно поднять приложение, БД и mock-сервер — оркеструю `docker-compose` с `healthcheck` и `depends_on`, а `--exit-code-from tests` отдаёт код выхода в CI-гейт. В CI (GitLab) образ Playwright — это окружение раннера; артефакты — отчёты. Ключевое, что держу под контролем: фиксация версий, кеш слоёв, готовность зависимостей перед стартом и volumes под отчёты — иначе получаешь флак и “у меня локально работает”».

## 10. Мой день с Docker (по легенде, от первого лица)

Как это реально выглядит в ежедневной работе на T-бизнес — готовый рассказ для собеса.

**Базовый режим: образ уже собран, я просто гоняю тесты.**
В обычный день образ не пересобираю — он собран и лежит. Разрабатываю или чиню тест и прогоняю его в контейнере, чтобы окружение было ровно как в CI. Обычно это подмножество, а не вся сюита:

```bash
docker run --rm -v "$(pwd)/playwright-report:/tests/playwright-report" \
  aqa-tests:local npx playwright test tests/installment.spec.ts --project=chromium
```

Отчёт через volume падает на машину, смотрю trace на падении — самодиагностируемые падения (trace, скрин, запрос/ответ) экономят время разбора.

**Когда пересобираю образ.**
Только при смене окружения, а не кода теста: обновил зависимость в `package.json`, поднял версию Playwright, добавил системную либу.

```bash
docker build -t aqa-tests:local .
```

Если поменял только тесты — `npm ci` берётся из кеша слоёв, сборка занимает секунды. Версию образа Playwright держу строго равной версии в `package.json` — иначе браузеры разъезжаются и ловишь флак.

**Полный стек через docker-compose.**
Когда тесту нужно приложение + БД + mock — поднимаю разом:

```bash
docker compose up --build --abort-on-container-exit --exit-code-from tests
```

Держу под контролем **готовность зависимостей**: `healthcheck` на БД и `depends_on: condition: service_healthy`, чтобы тесты не стартовали раньше, чем поднялся бэк. Контейнеры внутри compose видят друг друга по имени сервиса (`http://app:3000`), а не по localhost.

**Параллелизм.**
Тесты гоняются на нескольких воркерах внутри контейнера — работает, потому что данные изолированы (авторизация в worker-scoped `storageState`, состояние под роль через эндпоинты персонификации с teardown). Для Chromium в докере обязательно `--ipc=host`.

**Отладка внутри контейнера.**
Если падает только в контейнере, а локально зелёный — захожу внутрь:

```bash
docker run -it --rm --entrypoint bash aqa-tests:local
# внутри: версии, переменные, доступность mock/app, npx playwright test --debug
```

**CI — основной прогон.**
Мой личный докер-прогон — проверка перед пушем. Настоящий регресс идёт в GitLab CI: пуш ветки → пайплайн поднимает образ Playwright как окружение раннера, ставит зависимости по lock-файлу, гоняет тесты, складывает артефакты (Allure + HTML). На merge критичные тесты — гейт. Smoke на каждый PR, полный регресс — по расписанию/на релиз.

**Что держу в голове каждый день (отличает «работает» от «стабильно»):**

- версии зафиксированы (тег образа = версия Playwright, `npm ci`, а не `install`);
- кеш слоёв — зависимости отдельным слоем;
- готовность зависимостей через `healthcheck` перед стартом;
- volumes под отчёты — иначе Allure остаётся внутри контейнера;
- `--rm` на разовых прогонах — не копить мёртвые контейнеры;
- `--exit-code-from tests` — код выхода честно уходит в CI-гейт.

**Одной фразой для собеса:**

> «Ежедневно тесты гоняю в Docker: локально в контейнере прогоняю подмножество перед пушем, образ пересобираю только при смене зависимостей (кеш слоёв + фиксированная версия Playwright), полный стек с приложением/БД/mock поднимаю через docker-compose с healthcheck, а настоящий регресс — в GitLab CI с артефактами Allure и гейтом на критичных тестах. Держу под контролем версии, готовность зависимостей и volumes под отчёты — это убирает флак и “у меня локально работает”».

## 11. CI/CD в GitLab: контейнеры и параллелизм

### 11.1. Как GitLab CI вообще связан с Docker

GitLab CI гоняет задачи (jobs) на **раннерах (runners)**. Самый частый режим — **Docker executor**: раннер под каждую job **поднимает контейнер из указанного образа** и выполняет `script` внутри него. То есть в CI Docker работает сам, неявно:

- `image:` — образ, в котором крутится job (это и есть окружение теста);
- `services:` — вспомогательные контейнеры (БД, mock), которые GitLab поднимает рядом и линкует в сеть job;
- твой `script` выполняется внутри контейнера `image`.

Ключевая мысль для собеса: **`image` в GitLab CI = тот же Docker-образ, что я гоняю локально**. Поэтому official `mcr.microsoft.com/playwright` — идеальный `image`: браузеры и системные либы уже внутри, ничего доустанавливать не надо.

### 11.2. Базовый пайплайн

`.gitlab-ci.yml`:

```yaml
stages:
  - typecheck
  - test
  - report

variables:
  npm_config_cache: "$CI_PROJECT_DIR/.npm"     # кеш npm внутри проекта

# кеш зависимостей между запусками
.cache: &cache
  cache:
    key:
      files: [package-lock.json]                # инвалидируется при смене lock
    paths:
      - .npm/
      - node_modules/

typecheck:
  stage: typecheck
  image: node:20
  <<: *cache
  script:
    - npm ci
    - npx tsc --noEmit                          # проверка типов TS

e2e:
  stage: test
  image: mcr.microsoft.com/playwright:v1.48.0-jammy   # браузеры уже внутри
  services:
    - name: postgres:16
      alias: db
    - name: wiremock/wiremock:latest
      alias: mock
  variables:
    BASE_URL: "http://app:3000"
    DB_HOST: "db"
  <<: *cache
  script:
    - npm ci
    - npx playwright test
  artifacts:
    when: always
    paths:
      - playwright-report/
      - allure-results/
    reports:
      junit: results.xml
    expire_in: 1 week
```

`services` — это отдельные контейнеры БД и mock, которые GitLab поднимает вместе с job; обращаешься к ним по `alias` (`db`, `mock`), как в docker-compose по имени сервиса.

### 11.3. Два уровня параллелизма (это главное)

Параллелизм в связке «Playwright + GitLab» работает **на двух уровнях одновременно** — важно их не путать:

**Уровень 1 — воркеры внутри одного контейнера (`--workers`).**
Playwright внутри одной job запускает несколько **worker-процессов** (по умолчанию — по числу ядер, в CI обычно ограничивают). Каждый воркер гонит свои тесты в своём browser-context параллельно. Это параллелизм **внутри одного контейнера/раннера**, ограничен его CPU.

```bash
npx playwright test --workers=4
```

Работает это только потому, что тесты **изолированы по данным** — иначе воркеры мешают друг другу. У меня изоляция обеспечена: авторизация в worker-scoped `storageState`, состояние под роль через backend-эндпоинты персонификации с teardown.

**Уровень 2 — шардирование по нескольким контейнерам (`parallel` + `--shard`).**
`parallel: N` в GitLab **клонирует job в N параллельных job**, каждая — в своём контейнере на (возможно) разных раннерах. GitLab прокидывает переменные `CI_NODE_INDEX` (1..N) и `CI_NODE_TOTAL` (N), а Playwright умеет делить сюиту на шарды `--shard=i/n`:

```yaml
e2e:
  stage: test
  image: mcr.microsoft.com/playwright:v1.48.0-jammy
  parallel: 4                                    # 4 параллельных контейнера
  script:
    - npm ci
    - npx playwright test --shard=$CI_NODE_INDEX/$CI_NODE_TOTAL --workers=4
  artifacts:
    when: always
    paths:
      - blob-report/                             # промежуточный blob каждого шарда
    expire_in: 1 day
```

**Итого:** 4 контейнера (шарды) × 4 воркера = до 16 тестов одновременно. Первый уровень масштабируется CPU одного раннера, второй — числом раннеров. Это и есть ответ на «как ускорили регресс»: не только воркеры в одном контейнере, но и распараллеливание по контейнерам в CI.

Есть и третий приём — **`parallel:matrix`**: запуск job матрицей переменных (например, по браузерам/проектам):

```yaml
e2e:
  parallel:
    matrix:
      - PROJECT: [chromium, firefox, webkit]
  script:
    - npx playwright test --project=$PROJECT
```

### 11.4. Сборка отчёта из шардов (merge)

При шардировании каждый контейнер даёт **свой кусок отчёта** — их надо слить в один. Playwright для этого имеет **blob-репортер** и `merge-reports`:

```yaml
merge-report:
  stage: report
  image: mcr.microsoft.com/playwright:v1.48.0-jammy
  needs: ["e2e"]                                 # ждёт все шарды e2e
  when: always
  script:
    - npx playwright merge-reports --reporter html ./blob-report
  artifacts:
    paths:
      - playwright-report/
    expire_in: 1 week
```

`needs` собирает артефакты (blob'ы) со всех параллельных шардов, а `merge-reports` склеивает их в единый HTML. Для Allure аналогично: каждый шард пишет `allure-results`, отдельная job их объединяет и генерит отчёт.

### 11.5. Кеширование (чтобы CI не тормозил)

- **`cache` по `package-lock.json`** — не переустанавливать `node_modules` на каждый запуск, инвалидировать только при смене lock.
- **Браузеры** — в official playwright-образе они уже внутри, отдельно кешировать не нужно (это плюс образа против голого `node`).
- Кеш `.npm` ускоряет `npm ci`.

### 11.6. Гейты и правила запуска

- **Quality gate:** если e2e (критичные) падают — pipeline красный и merge заблокирован. Это делается тем, что job **не** `allow_failure`.
- **`rules`/`only`** — smoke на каждый MR, полный регресс — по расписанию (`schedule`) или на релизную ветку:

```yaml
smoke:
  script: [npx playwright test --grep @smoke]
  rules:
    - if: '$CI_PIPELINE_SOURCE == "merge_request_event"'

full-regress:
  script: [npx playwright test]
  rules:
    - if: '$CI_PIPELINE_SOURCE == "schedule"'
```

- **`needs`** (DAG) — строит зависимости между job, чтобы merge-report ждал шарды, а не всю стадию.
- **Ретраи флака** — `retry: 2` на job + Playwright `retries` в конфиге; но флак держу в карантине, а не маскирую ретраями.

### 11.7. Как рассказать на собесе (CI/CD + параллелизм)

> «В GitLab CI Docker работает сам: `image` job — это тот же playwright-образ, что я гоняю локально, а БД и mock поднимаются как `services`. Параллелизм двухуровневый: внутри контейнера Playwright гонит несколько `--workers` (ограничено CPU раннера), а поверх — `parallel: N` в GitLab клонирует job на N контейнеров, и Playwright делит сюиту `--shard=$CI_NODE_INDEX/$CI_NODE_TOTAL`. Получается N шардов × M воркеров одновременно — так и сократили регресс. Изоляция данных (storageState + эндпоинты персонификации) — обязательное условие, иначе параллель ломается. Отчёты со всех шардов собираю через blob + `merge-reports` в отдельной job по `needs`. Критичные тесты — гейт на merge, smoke на каждый MR, полный регресс по расписанию».

## 12. Инженерная расшивка + SMART (Docker / CI-CD)

По каждому инженерному вопросу — матрица «проблема → если проигнорировать → куда копать дальше → что даёт», затем SMART-ответ по легенде. Формат для устного разбора на собесе.

### Вопрос 1. Зачем гонять тесты в Docker, а не просто локально/на раннере?

| Проблема | Если проигнорировать | Куда копать дальше | Что даёт, если решить |
|---|---|---|---|
| Разное окружение (Node, браузеры, ОС-либы) у людей и в CI | «Локально проходит, в CI падает»; ложные баги, потеря доверия | Зафиксировать окружение в образе (official playwright-image, версия = версии в package.json) | Один и тот же прогон везде — воспроизводимость |
| Ручная установка браузеров/зависимостей | Долгий и хрупкий setup, «у меня не ставится» | Готовый образ с браузерами + `npm ci` по lock | Нулевой setup, детерминированные зависимости |
| Тесты зависят от того, что стоит на машине | Скрытые связи, флак от окружения | Изоляция в контейнере | Тесты не трогают хост, чистое окружение |

**SMART-ответ:**
> **S:** тесты гоняю в Docker на базе `mcr.microsoft.com/playwright` с версией образа, равной версии Playwright в `package.json`, зависимости — `npm ci` по lock-файлу. **M:** цель — убрать класс «локально проходит, в CI падает»: один и тот же образ локально, в CI и на сервере. **A:** реализуемо сразу — образ официальный, браузеры внутри. **R:** прямо снижает флак от окружения и ускоряет онбординг (новый человек не ставит браузеры руками). **T:** образ и Dockerfile завёл на старте проекта, дальше только обновляю версию при апгрейде Playwright.

### Вопрос 2. Как обеспечить, что параллельные тесты не мешают друг другу?

| Проблема | Если проигнорировать | Куда копать дальше | Что даёт, если решить |
|---|---|---|---|
| Общие/грязные данные между тестами | Тесты влияют друг на друга, падают при параллели | Изоляция данных: свежее состояние на тест | Детерминированность, безопасный параллелизм |
| Общая сессия/пользователь | Гонки за состоянием, флак | Авторизация в worker-scoped storageState | Скорость + независимость |
| Долгая подготовка состояния | Параллель не окупается | Генерация состояния через backend-эндпоинты | Подготовка за секунды, а не минуты |

**SMART-ответ:**
> **S:** изоляцию строю на двух опорах — авторизация через API в worker-scoped `storageState` (одна сессия на воркер) и состояние под роль через backend-эндпоинты персонификации в test-scoped фикстуре с teardown (свежие данные на каждый тест). **M:** результат — подготовка данных с 4–5 минут до 3–5 секунд и **полный параллелизм** без пересечений. **A:** эндпоинты собрали девопсы с бэкендерами, дальше это просто фикстура. **R:** без изоляции параллель невозможна — а именно она даёт скорость регресса. **T:** прошли эволюцию хардкод → фабрики → эндпоинты за первые месяцы проекта.

### Вопрос 3. Как ускорить регресс в CI, а не просто «добавить воркеров»?

| Проблема | Если проигнорировать | Куда копать дальше | Что даёт, если решить |
|---|---|---|---|
| Один контейнер упирается в CPU раннера | Воркеров больше не добавишь, регресс тормозит | Второй уровень — шардирование по контейнерам (`parallel` + `--shard`) | Масштаб числом раннеров, а не только ядрами |
| Тяжёлые вечнозелёные тесты в прогоне | Прогон раздут без пользы | Чистка corner-case (парадокс пестицида) + пирамида | Быстрый прогон, дешёвые проверки вниз |
| Отчёт разбит по шардам | Непонятно, что упало в целом | blob + `merge-reports` по `needs` | Единый отчёт со всех шардов |

**SMART-ответ:**
> **S:** ускоряю двухуровнево — `--workers` внутри контейнера (по CPU раннера) плюс `parallel: N` в GitLab с `--shard=$CI_NODE_INDEX/$CI_NODE_TOTAL`, то есть N контейнеров × M воркеров. Плюс держу прогон острым: чищу тяжёлые вечнозелёные corner-case и спускаю дешёвые проверки на API/юнит-уровень. **M:** так регресс, который вручную занимал часы, в авто укладывается в десятки минут. **A:** на стандартном GitLab + playwright-образе, отчёты сливаю `merge-reports`. **R:** держит темп релизов при растущей сюите. **T:** шардирование включаю по мере роста числа тестов, когда одного контейнера уже мало.

### Вопрос 4. Как не пустить сломанный билд (quality gate)?

| Проблема | Если проигнорировать | Куда копать дальше | Что даёт, если решить |
|---|---|---|---|
| Красные тесты не блокируют merge | Сломанный критичный путь уезжает в прод | Gate: критичные job не `allow_failure` | Денежный путь защищён автоматически |
| Всё гоняется на каждый чих | Пайплайн долгий, разработчики ждут | `rules`: smoke на MR, регресс по расписанию | Быстрый фидбэк + полнота отдельно |
| Флак обесценивает gate | Команда игнорирует «красное» | Карантин флака, а не маскировка ретраями | Gate остаётся значимым |

**SMART-ответ:**
> **S:** ставлю quality gate — job с `@critical` тестами не `allow_failure`, её падение делает pipeline красным и блокирует merge; `rules` разводят smoke на каждый MR и полный регресс по расписанию/на релиз. **M:** цель — ни один сломанный критичный путь не проходит в прод без ручного вмешательства; флак держу <2%, чтобы gate не обесценивался. **A:** стандартный GitLab (`rules`, `needs`, artifacts). **R:** прямо защищает релиз при частых мержах. **T:** smoke-gate поднимается в первые недели, полный регресс с расписанием — по мере роста сюиты.

### Вопрос 5. Как держать пайплайн быстрым и дешёвым?

| Проблема | Если проигнорировать | Куда копать дальше | Что даёт, если решить |
|---|---|---|---|
| `npm install` на каждый запуск | CI тормозит, лишние минуты | Кеш по `package-lock.json`, `npm ci` | Зависимости не ставятся заново |
| Пересборка образа на каждое изменение | Долгие сборки | Кеш слоёв: зависимости отдельным слоем | Пересборка секунды, а не минуты |
| Тесты стартуют раньше зависимостей | Флак на старте | `healthcheck` + `depends_on`/`services` | Стабильный старт |

**SMART-ответ:**
> **S:** держу пайплайн быстрым за счёт кеша (`cache` по lock-файлу, `npm ci`), кеша слоёв Docker (COPY package*.json → npm ci → COPY код), готового образа с браузерами и `healthcheck` перед стартом тестов. **M:** цель — минимизировать «пустое» время CI (установка, пересборка, ожидание) и не ловить флак на старте зависимостей. **A:** всё стандартными механизмами GitLab и Docker. **R:** быстрый пайплайн = разработчики не ждут, гейт не раздражает. **T:** заложил при настройке пайплайна, поддерживаю при апгрейдах.

### Вопрос 6. Как бороться с флаком в CI, не пряча его ретраями?

| Проблема | Если проигнорировать | Куда копать дальше | Что даёт, если решить |
|---|---|---|---|
| Флак маскируется постоянными ретраями | Проблема гниёт под ковром, база деградирует | Ретраи — только сеть безопасности + карантин + разбор причины | Флак реально снижается |
| Причина флака не классифицирована | Чинят симптом, не причину | Разбор: гонки/ожидания, данные, окружение, локаторы | Точечные архитектурные фиксы |
| Нет метрики флака | Спорят на ощущениях | flaky-rate + тренд в отчёте | Управляемость |

**SMART-ответ:**
> **S:** флак бью по причине: `sleep` → auto-waiting и `expect.poll`, для eventual consistency — polling по статусу через Kafka; изоляция данных под параллель; иерархия локаторов вместо индексов/текста. Ретраи оставляю как страховку + карантин с обязательным разбором, а не как костыль. **M:** довёл flaky-rate с 12–15% до <2% и держу метрику в отчёте. **A:** архитектурные решения, не костыли, поэтому эффект устойчивый. **R:** низкий флак — условие и для параллели, и для значимости quality-gate. **T:** основная стабилизация — за первые месяцы, дальше поддержание карантином и метрикой.
