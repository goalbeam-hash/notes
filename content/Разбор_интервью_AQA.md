## Общая оценка интервью

**Вердикт: скорее провален.** Кандидат демонстрирует реальный практический опыт (видно по рассказу о проекте, фабрике фикстур, POM, стабах данных), но:

- **Не владеет терминологией.** Почти на каждый теоретический вопрос отвечает «вокруг да около», не называя ключевое слово, которое ждёт интервьюер (fluent wait, sharding, consumer group, query parameters, stages, `page.route`, `storageState`, saturation point).
- **Путает базовые концепции:** фикстуры ≠ параметризация, тестовые данные ≠ «импорт из файла», INNER JOIN объясняет неверно с первой попытки, идемпотентность путает (называет PATCH, забывает GET), Kafka у него «push», хотя она pull.
- **Речь неструктурирована:** обилие «ну», «получается», «э-э», уходы в сторону, ответы через наводящие вопросы интервьюера. Интервьюеру приходилось по 3–4 раза переспрашивать один и тот же вопрос.
- **Плохо работает с незнанием:** вместо честного короткого «не знаю, но предполагаю что...» — долгие попытки угадать, что снижает впечатление сильнее, чем честный скип.

Сильные стороны: реальный опыт с Playwright-фикстурами и POM, понимание проблем eventual consistency, понимание изоляции тестов при параллелизации, адекватный ответ про эмулятор/симулятор и метрики сервера (с подсказками).

### Вопрос 3. Как подготавливались тестовые данные для теста?

🗣 **Ответ кандидата:**
Сначала не понял вопрос («ты имеешь в виду, как падала задача?»), потом рассказал про пакет с ролями и статусами клиентов и слой обращения к бэкенду. На повторное уточнение ответил: **«через импорт из папки с бизнес-ролями... импорт класса из файла»**.

⚠️ **Анализ ошибок:**
1. **Ключевой провал интервью.** Интервьюер трижды задал вопрос, ожидая слово **«фикстуры»** — механизм создания и передачи данных в тест. Кандидат ответил «через импорт», что концептуально неверно: импорт — это механизм языка для подключения кода, а не механизм подготовки/внедрения тестовых данных.
2. Кандидат сам чуть раньше описывал фикстуры и даже фабрику фикстур — то есть знание есть, но он **не связал вопрос с ответом**. Это выглядит как непонимание собственного инструментария.
3. Когда интервьюер прямо сказал «мы же делаем это через фикстуры», кандидат начал спорить («ну понятно, что через фикстуры, но мы же должны их прописать...»), вместо того чтобы согласиться и чётко переформулировать.

✅ **Идеальный ответ:**

> «Тестовые данные готовятся **через фикстуры** — это и есть механизм setup/teardown в Playwright.
> Конкретно: у нас есть API-слой подготовки данных. Фикстура перед тестом через API-запросы создаёт нужное состояние — пользователя с нужной бизнес-ролью, статусами, ограничениями, транзакции. Данные внедряются в тест через **dependency injection**: тест объявляет фикстуру параметром, Playwright её создаёт и передаёт.
> После `await use()` фикстура выполняет **teardown** — удаляет созданные сущности, чтобы окружение оставалось чистым и тесты были изолированы для параллельного запуска.
> Статичные справочные данные (роли, конфиги) лежат отдельным пакетом, параметризованные наборы — через параметризацию тестов/фикстур.»

### Вопрос 4. Зачем нужны фикстуры в автотестах?

🗣 **Ответ кандидата:**
«Для параметризации». На уточнение — «параметризация данных пользовательских и средовых, предусловия среды, версия билда, версия системы». Про очистку данных сказал только после прямой подсказки интервьюера («мы же их ещё очищать должны») — «ну да, под капотом в функции use очищается, через garbage collector».


⚠️ **Анализ ошибок:**
1. **«Параметризация» — неверный ответ.** Фикстуры и параметризация — разные механизмы. Фикстура — это управление жизненным циклом ресурсов (setup → предоставление → teardown). Параметризация — прогон одного теста с разными данными.
2. **Не назвал teardown/очистку самостоятельно** — интервьюер прямо сказал: «это надо проговаривать». Это половина смысла фикстур.
3. **«Очистилась через garbage collector» — грубая ошибка.** GC освобождает память в рантайме JS и не имеет отношения к очистке тестовых данных. Очистка происходит в коде фикстуры **после** `await use()` — это явный teardown, который пишет разработчик тестов.

✅ **Идеальный ответ:**

> «Фикстуры решают три задачи:
> 1. **Setup — подготовка предусловий:** создание тестовых данных, авторизация, открытие страницы, инициализация Page Object'ов, API-клиентов.
> 2. **Teardown — гарантированная очистка:** всё, что написано в фикстуре после `await use()`, выполнится после теста даже при его падении. Так мы удаляем созданные данные и держим окружение чистым — это критично для изоляции и параллельного запуска.
> 3. **Dependency Injection и переиспользование:** тест запрашивает только нужные ему фикстуры параметрами, не зная, как они создаются. Это убирает дублирование кода и boilerplate вида before/after в каждом тесте.
> В Playwright кастомные фикстуры создаются через `test.extend({...})`; они ленивые (создаются только если запрошены) и имеют скоупы — `test` и `worker`.»

```typescript
export const test = base.extend<{ user: User }>({
  user: async ({ request }, use) => {
    const user = await createUserViaApi(request);   // setup
    await use(user);                                 // тест работает
    await deleteUserViaApi(request, user.id);        // teardown — а не GC!
  },
});
```

### Вопрос 5. Основные преимущества Playwright (в т.ч. по сравнению с Selenium)

🗣 **Ответ кандидата:**
ARIA/accessibility-селекторы (`getByRole`), лаконичный синтаксис; плагин VS Code с codegen («натыкать тест через UI»); «меньше бойлерплейта из коробки»; после наводки вспомнил автоожидания («да, ожидания»); «наслышан, что более гибкая работа с воркерами».

⚠️ **Анализ ошибок:**
1. **Главное преимущество — auto-waiting — кандидат вспомнил только с подсказкой**, хотя интервьюер прямо намекал («есть очень хорошее преимущество, из-за которого его сейчас много где используют»). Для человека, ежедневно пишущего на Playwright, это должно отлетать от зубов.
2. Ответ бессистемный: перечислил 2–3 второстепенных пункта, не назвав архитектурные преимущества.
3. «Наслышан про воркеры» — при том, что сам работает с параллелизацией (см. вопрос 7). Неуверенная подача обесценивает реальный опыт.

✅ **Идеальный ответ:**

> «Ключевые преимущества Playwright:
> 1. **Auto-waiting и web-first assertions** — Playwright сам ждёт actionability элемента (visible, stable, enabled) перед действием, а `expect(locator).toBeVisible()` перезапрашивает состояние до таймаута. Это убирает флаки и ручные sleep'ы, которые были бичом Selenium.
> 2. **Встроенный test runner** с параллелизацией через воркеры из коробки, ретраями, шардингом, проектами под разные браузеры/конфигурации.
> 3. **Browser contexts** — изоляция уровня «инкогнито-профиля» за миллисекунды, вместо тяжёлого поднятия нового браузера; на одном инстансе браузера — много изолированных контекстов.
> 4. **Перехват сети** — `page.route()` для моков, блокировки и модификации запросов; плюс встроенный `APIRequestContext` для API-тестов.
> 5. **Архитектура:** общение с браузером по WebSocket/CDP-протоколу напрямую, а не через HTTP-посредника WebDriver, — быстрее и стабильнее.
> 6. **Tooling:** trace viewer (пошаговая запись упавшего теста со скриншотами, сетью, DOM), codegen, UI mode, скриншоты/видео из коробки.
> 7. Один API для Chromium, Firefox, WebKit; поддержка нескольких языков (TS/JS, Python, Java, .NET).»

### Вопрос 6. Какие бывают виды ожиданий? (явные, неявные и третий)

🗣 **Ответ кандидата:**
«Явные, неявные». Третий вид вспомнить не смог: «не слышал... это по сути явный, ещё более накрученный».

⚠️ **Анализ ошибок:**
1. Третий вид — **fluent wait** (плавное/текучее ожидание) — классика собеседований по Selenium. Кандидат его не знает.
2. Формулировка «это по сути явный, ещё более накрученный» — по смыслу близко (fluent действительно является настраиваемым вариантом явного), но без названия и деталей ответ не засчитывается.

✅ **Идеальный ответ:**

> «Классически выделяют три вида ожиданий (терминология из Selenium):
> 1. **Неявные (implicit wait)** — глобальная настройка: при поиске любого элемента драйвер ждёт до N секунд, прежде чем бросить исключение. Задаётся один раз, действует на все `findElement`.
> 2. **Явные (explicit wait)** — ожидание конкретного условия для конкретного элемента: `WebDriverWait` + `ExpectedConditions` (elementToBeClickable, visibilityOf и т.д.).
> 3. **Fluent wait** — расширенное явное ожидание с тонкой настройкой: свой интервал опроса (polling), общий таймаут и список игнорируемых исключений (например, игнорировать `NoSuchElementException` во время опроса).
> Важно: implicit и explicit смешивать нельзя — получаются непредсказуемые таймауты.
> В Playwright эта проблема решена архитектурно — **auto-waiting**: каждое действие само ждёт actionability, а web-first assertions ретраятся до таймаута. Явные ожидания (`waitForSelector`, `waitForResponse`, `waitForLoadState`) нужны редко, для специфических случаев.»

### Вопрос 7. Работал с параллелизацией тестов? Как?

🗣 **Ответ кандидата:**
«Да, это тема воркеров». Далее — про инкапсуляцию тестов через фабрику фикстур: «одна страница — один класс», автоматические фикстуры «под коробкой», снижается вероятность «наслаивания тестов» и обращения к методам чужой страницы.

⚠️ **Анализ ошибок:**
1. **Подмена ответа.** Вопрос был про механику параллелизации (воркеры, конфигурация, изоляция), а кандидат рассказал про Page Object и фикстуры — это про изоляцию кода, а не про параллельный запуск.
2. «Снижается вероятность обратиться к методам с другой страницы» — это не про параллелизацию вообще; параллельные тесты мешают друг другу через **общие данные и окружение**, а не через методы классов.
3. Не назвал ни одного конкретного механизма: `workers` в конфиге, `fullyParallel`, worker-scoped фикстуры, `test.describe.configure({ mode: 'parallel' })`, шардинг.

✅ **Идеальный ответ:**

> «Да. В Playwright параллелизация встроена в test runner:
> - Тесты запускаются **воркерами** — отдельными процессами ОС. Количество задаётся `workers` в конфиге или `--workers` в CLI (по умолчанию ~половина ядер CPU).
> - По умолчанию параллелятся **файлы** тестов; тесты внутри файла идут последовательно в одном воркере. Флаг `fullyParallel: true` (или `test.describe.configure({ mode: 'parallel' })`) распараллеливает и тесты внутри файла.
> - Каждый воркер имеет свой изолированный контекст: свой инстанс браузера, свои worker-scoped фикстуры. Между воркерами нет общей памяти.
> - Для масштабирования на несколько машин CI — **шардинг** (`--shard=1/4`).
> - Главное условие параллелизации — **изоляция тестов**: уникальные тестовые данные на тест (создаются и удаляются фикстурами), никакого общего мутируемого состояния, независимость от порядка выполнения.»

### Вопрос 8. Что такое worker?

🗣 **Ответ кандидата:**
«Один тред, один инстанс теста, который запущен... существует для параллельного выполнения».

⚠️ **Анализ ошибок:**
1. **Неточно:** воркер в Playwright — это не «тред» и не «инстанс теста», а **отдельный процесс ОС**, который последовательно выполняет назначенные ему тесты. Разница тред/процесс — важна: процессы полностью изолированы по памяти.

### Вопрос 11. Какие проблемы могут быть при параллельном выполнении тестов?

🗣 **Ответ кандидата:**
«Тесты будут есть друг друга» — обращение к одним сущностям в БД, общее пространство, тесты мешают и ломают друг друга. Нечистая тестовая среда, нужны чистые фикстуры. Упомянул нагрузку («много воркеров — много нагрузки»), разведение тестов по разным подам/окружениям.

⚠️ **Анализ ошибок:**
1. По сути ответ **в основном верный** — конкуренция за данные, грязная среда, нагрузка. Это один из лучших ответов кандидата.
2. Минусы: жаргон («тесты едят друг друга») вместо терминов (race condition, shared state, флакинес), нет упоминания порядка/зависимости тестов и проблем с лимитами внешних систем (rate limits, пул соединений БД).

✅ **Идеальный ответ:**

> «Основные проблемы:
> 1. **Гонки за общие данные (race conditions):** два теста одновременно читают/изменяют одну сущность — одного пользователя, одну запись БД, один файл. Результат — флакающие падения, которых нет при одиночном запуске. Решение — уникальные данные на тест (генерация через фикстуры, uuid/timestamp в идентификаторах).
> 2. **Общее мутируемое состояние окружения:** тест A меняет конфиг/фичефлаг/баланс — тест B это видит. Решение — изоляция данных, а глобальные настройки не трогать в параллельных тестах (или выносить в serial-группу).
> 3. **Зависимость тестов от порядка выполнения:** при параллелизации порядок недетерминирован — тесты, неявно зависящие друг от друга, начинают падать. Тесты должны быть атомарными и независимыми.
> 4. **Нагрузка на стенд:** N воркеров — N-кратная нагрузка на тестовое окружение; оно может деградировать и давать таймауты, которые выглядят как баги. Плюс лимиты: пул соединений БД, rate limit API.
> 5. **Ресурсы CI-агента:** каждый воркер — процесс с браузером; нехватка CPU/RAM ведёт к таймаутам и флакам.
> Всё это лечится дисциплиной изоляции: данные создаются и удаляются фикстурами, тесты не разделяют состояние, тяжёлые/конфликтные сценарии — в serial mode.»

### Вопрос 13. SQL: чем LEFT JOIN отличается от INNER JOIN?

🗣 **Ответ кандидата:**
Путано: «результирующая таблица получит лишь те значения... которые есть в левой таблице», INNER JOIN — «наверное, в правом... наоборот, то, что в правой таблице». После наводки («ты же видел кружочки») — INNER это «внутреннее пересечение», «те значения, которые общие для двух таблиц». Про LEFT так и не дал чёткой финальной формулировки.

⚠️ **Анализ ошибок:**
1. **INNER JOIN назвал «правым» — грубая ошибка.** «Наоборот к LEFT» — это RIGHT JOIN, а не INNER.
2. К правильному «пересечению» пришёл только через подсказки интервьюера.
3. Не сказал главного отличия LEFT JOIN: строки левой таблицы **без совпадений тоже попадают в результат, с NULL в колонках правой**. Без этого определение LEFT JOIN неполно.
4. Это базовый вопрос уровня junior — на скрининге ответ должен быть мгновенным.

✅ **Идеальный ответ:**

> «**INNER JOIN** возвращает только строки, у которых есть совпадение по условию соединения **в обеих таблицах** — пересечение.
> **LEFT JOIN** возвращает **все строки левой таблицы**, и если совпадение в правой найдено — данные правой, если нет — **NULL** в её колонках.
> Пример: таблицы `users` и `orders`.
> - `users INNER JOIN orders` — только пользователи, у которых есть заказы;
> - `users LEFT JOIN orders` — все пользователи; у тех, кто без заказов, поля заказа будут NULL.
> Классический приём — найти пользователей без заказов: `LEFT JOIN ... WHERE orders.id IS NULL`.
> Для полноты: RIGHT JOIN — зеркально (все строки правой), FULL OUTER JOIN — все строки обеих таблиц, CROSS JOIN — декартово произведение.»

### Вопрос 14. RabbitMQ: работал? Чем отличается от Kafka?

🗣 **Ответ кандидата:**
«С Rabbit нет, MQ не работал... в теории даже так не скажу, чем они отличаются».

⚠️ **Анализ ошибок:**
1. Честное «не работал» — нормально. Но полное отсутствие даже теоретического представления о втором по популярности брокере — минус для мидл-уровня, особенно когда Kafka заявлена в опыте: сравнение Kafka vs RabbitMQ — топ-вопрос собеседований.

✅ **Идеальный ответ:**

> «Практического опыта с RabbitMQ нет, но концептуальную разницу знаю:
> - **Модель доставки:** RabbitMQ — **push**: брокер сам заталкивает сообщения консюмерам. Kafka — **pull**: консюмер сам опрашивает брокер.
> - **Хранение:** RabbitMQ — классическая очередь: сообщение после подтверждения (ack) **удаляется**. Kafka — **распределённый лог**: сообщения хранятся заданный retention-период независимо от того, прочитаны ли; их можно **перечитать заново** (сдвинув offset) — удобно для повторной обработки и отладки.

> - **Назначение:** RabbitMQ — очереди задач, RPC, сложная маршрутизация при умеренном объёме. Kafka — стриминг событий, event sourcing, высокая пропускная способность (миллионы сообщений/сек), несколько независимых групп читателей одного потока.»

### Вопрос 16. Как работает Kafka?

🗣 **Ответ кандидата:**
«Kafka слушает за другими микросервисами, подписана на события, как только происходит триггер — пишет в общий лог, что произошёл триггер... по этим логам через ELK удобно отследить, что происходило».

⚠️ **Анализ ошибок:**
1. **Модель перевёрнута.** Kafka ни за кем «не слушает» и ни на что «не подписана» — она **пассивный брокер**. **Продюсеры** сами отправляют сообщения в топики, консюмеры сами их читают. У кандидата Kafka выступает активным наблюдателем — это неверно.
2. Смешал Kafka-лог с логами приложений и ELK — разные вещи (хотя ELK может использоваться рядом, к механике Kafka это не относится).
3. Не назвал ни одного термина: producer, topic, partition, offset, broker, consumer group.

✅ **Идеальный ответ:**

> «Kafka — распределённый брокер сообщений, построенный как **журнал (commit log)**.
> Механика:
> - **Продюсеры** пишут сообщения в **топики**. Топик разбит на **партиции** — упорядоченные append-only журналы; порядок гарантируется только внутри партиции. Ключ сообщения определяет партицию (одинаковый ключ — одна партиция — сохранение порядка для сущности).
> - Сообщения **не удаляются после чтения** — хранятся retention-период (по времени или размеру).
> - **Консюмеры** читают сообщения, самостоятельно опрашивая брокер (**pull**), и трекают свою позицию — **offset**. Offset коммитится, поэтому после рестарта консюмер продолжает с места остановки, а можно и перечитать историю, сдвинув offset назад.
> - Кластер состоит из **брокеров**; партиции реплицируются между ними для отказоустойчивости (лидер + реплики).
> - Консюмеры объединяются в **consumer groups** для масштабирования (см. следующий вопрос).»

### Вопрос 17. Как консюмер получает данные: он приходит к Kafka или она ему отдаёт (pull vs push)?

🗣 **Ответ кандидата:**
Слово «консюмер» вспомнил только с подсказкой («слушатель... как спикер» → интервьюер: «консюмер»). На ключевой вопрос ответил: **«скорее она ему даёт, она же пишет сообщение»** — т.е. push.

⚠️ **Анализ ошибок:**
1. **Неправильный ответ на главный вопрос.** Kafka — это **pull-модель**: консюмер сам приходит за данными (метод `poll()`). Это фундаментальное отличие Kafka от push-брокеров и одна из причин её масштабируемости.
2. Не вспомнил слово «consumer» самостоятельно — при заявленном опыте работы с Kafka на текущем проекте это выглядит плохо.

✅ **Идеальный ответ:**

> «Потребитель называется **consumer**, и Kafka использует **pull-модель**: консюмер **сам опрашивает** брокер — в цикле вызывает `poll()`, забирает пачку сообщений начиная со своего offset, обрабатывает и коммитит offset.
> Преимущества pull:
> - консюмер сам управляет темпом чтения — брокер не завалит медленного потребителя (естественный backpressure);
> - эффективное батчирование — можно забирать сообщения крупными пачками;
> - легко перечитывать историю: offset — под контролем консюмера.
> Чтобы pull не превращался в бесполезный опрос пустого топика, `poll` поддерживает long polling — запрос ждёт появления данных до таймаута.»

### Вопрос 18. Что такое Consumer Group? Чем отличается от консюмера?

🗣 **Ответ кандидата:**
«Затрудняюсь ответить. Ну это группа, наверное, те, кто считывает информацию». На уточнение: «тут скип, не отвечу».

⚠️ **Анализ ошибок:**
1. Тавтология «consumer group — это группа консюмеров» ответом не является, кандидат это сам признал и скипнул.
2. Для человека, у которого Kafka в текущем проекте, — серьёзный пробел: consumer group — центральное понятие масштабирования чтения в Kafka.
3. Плюс кандидату: честно скипнул, не стал долго мучить угадывание. И хорошо, что в конце интервью **сам спросил** правильный ответ — это выглядит как интерес к теме.

✅ **Идеальный ответ:**

> «**Consumer group** — это набор консюмеров, объединённых общим `group.id`, которые **совместно** читают топик, разделяя между собой партиции.
> Правила:
> - каждая партиция топика в любой момент читается **ровно одним** консюмером внутри группы — сообщение обработается группой один раз (распределение нагрузки);
> - **разные группы независимы**: каждая группа получает весь поток сообщений целиком со своими offset'ами (широковещание между группами). Пример: топик `payments` читают группа `fraud-detection` и группа `notifications` — обе получают все события;
> - если консюмер падает или добавляется новый — происходит **rebalance**: партиции перераспределяются между живыми членами группы (отказоустойчивость);
> - консюмеров в группе больше, чем партиций, — лишние простаивают; поэтому число партиций задаёт предел параллелизма чтения.
> Итого: один консюмер — один читатель; consumer group — механизм горизонтального масштабирования и отказоустойчивости чтения.»

### Вопрос 20. Какие методы идемпотентны по умолчанию?

🗣 **Ответ кандидата:**
«Наверное, PUT, DELETE». Потом добавил **PATCH** («патч меняет часть в запросе»), интервьюер усомнился — кандидат отказался от PATCH. **GET вспомнил только после прямой подсказки** («ничего не забыл?... самое первое»).

⚠️ **Анализ ошибок:**
1. **PATCH назван идемпотентным — ошибка.** По спецификации PATCH не является идемпотентным по умолчанию: patch-документ может описывать относительные изменения (например, «добавить элемент в массив», инкремент) — повтор даст другой результат.

3. Не названы HEAD и OPTIONS.

✅ **Идеальный ответ:**

> «**Идемпотентный метод** — повторное выполнение одинакового запроса приводит систему к тому же состоянию, что и однократное (состояние сервера не отличается после 1 и после N одинаковых вызовов).

### Вопрос 26. Чем merge отличается от rebase? Как выглядит история коммитов?

🗣 **Ответ кандидата:**
Про merge: «сольёт все изменения в одну ветку... нужно будет выбрать... сравнить репозитории... что-то может выпасть». Про rebase с примером интервьюера (A-B-C в main, D-E в ветке): согласился, что получится «A B C D E вертикально». Про merge внятно не ответил: «сохранится ветка dev, перейдёшь в основную с новым коммитом... если захочешь остаться с файлами локально, придётся создать новый коммит».

⚠️ **Анализ ошибок:**
1. **Про rebase** — с подсказками ответил верно (коммиты переносятся поверх целевой ветки, история линейная), но сам механизм не объяснил.
2. **Про merge — ответ развалился.** Кандидат смешал merge с checkout/переключением веток и локальными файлами. Не сказал главного: merge создаёт **merge-коммит** с двумя родителями, история сохраняет ветвление.
3. Не упомянуты ключевые следствия: rebase **переписывает историю** (новые хэши коммитов), поэтому его нельзя делать на общих ветках; merge историю сохраняет.

✅ **Идеальный ответ:**

> «Обе команды интегрируют изменения одной ветки в другую, разница — в форме итоговой истории.
> **Merge:** создаётся **merge-коммит** с двумя родителями — вершинами обеих веток. История сохраняет реальную картину ветвления (граф с «ромбами»). Исходные коммиты не меняются.
> **Rebase:** мои коммиты **переносятся поверх** целевой ветки — Git по очереди повторно применяет их на новую базу. История становится **линейной**, как будто я начал работу от последнего коммита main. Важно: это **новые коммиты с новыми хэшами** — история переписана.
> На примере: main = A–B–C, моя ветка от B = D–E.
> - rebase на main: A–B–C–D'–E' — одна прямая линия;
> - merge в main: A–B–C–M, где M — merge-коммит, объединяющий C и E; ветка D–E остаётся видимой в графе.
> **Правило:** rebase — только для своих локальных/личных веток (актуализировать перед MR, красивая история); на общих ветках — merge, потому что переписывание опубликованной истории ломает работу коллег.
> Конфликты возможны в обоих случаях; при rebase они разрешаются по каждому переносимому коммиту.»

### Вопрос 29. Чем load testing отличается от stress testing?

🗣 **Ответ кандидата:**
Путано: «стресс-тест хочет выделить пределы системы, проверить отказоустойчивость... стресс-тест — это как смок-тест по вопросу нагрузки... а нагрузочное тестирование выявляет, какие элементы страницы грузятся дольше всех, слабые места по скорости».

⚠️ **Анализ ошибок:**
1. **«Стресс-тест — это как смок-тест» — неверная аналогия**, только запутала ответ.
2. Определение load testing через «какие элементы страницы грузятся дольше» — это скорее про client-side performance (фронтенд-профилирование), а не про нагрузочное тестирование сервера.
3. Главный дифференциатор — **уровень нагрузки относительно ожидаемой** — так и не был назван чётко, хотя интервьюер прямо подсказывал: «у них один параметр, по сути, основной».
4. Половина мысли верная (стресс = пределы системы), но утоплена в каше.

✅ **Идеальный ответ:**

> «Различие — в **уровне подаваемой нагрузки** относительно ожидаемой (это и есть тот самый один основной параметр):
> - **Load testing** — нагрузка **в пределах ожидаемой** (обычной или пиковой прогнозируемой). Цель — убедиться, что система выполняет SLA при штатной нагрузке: время ответа, error rate, стабильность. Ответ на вопрос: "выдержим ли мы наш обычный и пиковый трафик?"
> - **Stress testing** — нагрузка **выше ожидаемой**, растим до предела и за него. Цели: найти точку отказа (сколько система выдержит максимум), посмотреть, **как** она деградирует (плавно или падает целиком) и **восстанавливается ли** после снятия нагрузки. Ответ на вопрос: "что будет, если трафик в разы превысит расчётный?"
> Смежные виды: **soak/endurance** — умеренная нагрузка длительное время (ищем утечки памяти, деградацию), **spike testing** — резкие скачки нагрузки, **capacity/scalability** — поиск максимальной ёмкости при соблюдении SLA.»

### Вопрос 30. Подходы к аутентификации в Playwright? Что такое storage state?

🗣 **Ответ кандидата:**
«Можно сохранить данные аутентификации залогиненного пользователя в кэш браузера... можно с токенами работать... токены хранить в слое, где хранишь другие данные, с ролями». Про storage state: «кэш браузера... куки... local storage, session storage». Третье хранилище (IndexedDB) не вспомнил.

⚠️ **Анализ ошибок:**
1. **«Кэш браузера» — неточный термин.** Кэш — это хранилище ресурсов (картинки, скрипты), а сессия живёт в **cookies и localStorage**. Playwright сохраняет их через **`storageState`** — этого ключевого слова кандидат не назвал (интервьюеру пришлось самому спросить «что такое storage state»).
2. «Токены хранить в слое с ролями» — размытый ответ; в Playwright токены хранятся в том же storageState-файле или подставляются в заголовки API-контекста.
3. IndexedDB не вспомнил — простительно (интервьюер сам сказал, что про него часто забывают), но паттерн «не помню точные названия» повторяется весь скрининг.

✅ **Идеальный ответ:**

> «Стандартный подход — **переиспользование состояния аутентификации через `storageState`**:
> 1. В **setup-проекте** (dependency в конфиге) один раз логинимся — через UI или, лучше, через API (быстрее и стабильнее);
> 2. Сохраняем состояние: `await context.storageState({ path: 'auth.json' })`;
> 3. Все тестовые проекты используют его: `use: { storageState: 'auth.json' }` — каждый тест стартует уже залогиненным, экономим минуты на каждом прогоне.
> **storageState** — это снапшот состояния браузерного контекста: **cookies, localStorage** и, в свежих версиях, **IndexedDB** (важно для MSAL-подобных auth-библиотек, которые хранят токены именно там). SessionStorage в storageState **не** сохраняется — при необходимости его переносят вручную через init-скрипты.
> Вариации: несколько ролей — несколько файлов состояния (admin.json, user.json) и разные проекты/фикстуры; для API-тестов — токен в `extraHTTPHeaders` у `APIRequestContext`; для мультипользовательских сценариев — разные контексты с разными storageState в одном тесте.»

###Вопрос 31. Параметризация: что можем параметризовать? Чем параметризация фикстур отличается от параметризации тестов?

🗣 **Ответ кандидата:**
«Данные: логин, пароль, окружение... итерируемый список». На вопрос о разнице: «если какой-то триггер происходит в тесте, можешь с одними данными зайти или с другими... фикстуры определяют предусловие теста, а параметризация теста определяет логику теста: пойти по пути А, если нет — по пути Б». На вопрос «сколько будет тестов при параметризации» — «смотря какая логика... я всё пишу в рамках одного теста», затем ушёл в рассуждение про флаги и падение коллекции тестов.

⚠️ **Анализ ошибок:**
1. **Определение параметризации теста через «if/else внутри теста» — концептуально неверно.** Условная логика внутри теста — это антипаттерн (тест должен быть линейным и детерминированным). Параметризация — это прогон **одного и того же теста с разными входными данными**, где каждый набор данных = **отдельный тест в отчёте**.
2. На прямой вопрос «сколько будет тестов» правильный ответ — «несколько, по одному на каждый набор параметров». Кандидат ответил «я всё пишу в рамках одного теста» — прямо противоположно.
3. Рассуждение про «флаги, чтобы коллекция не переставала прогоняться» — не по теме (похоже на путаницу с `test.fail()`/`continue-on-error`).
4. Разницу тест- и фикстур-параметризации не раскрыл.

✅ **Идеальный ответ:**

> «**Параметризация** — прогон одной тестовой логики с разными входными данными без дублирования кода.
> **Параметризация теста** — цикл по массиву данных с генерацией тестов:
>
> ```typescript
> for (const role of ['admin', 'manager', 'viewer']) {
>   test(`доступ к отчётам для роли ${role}`, async ({ page }) => { ... });
> }
> ```
>
> Каждый набор данных — **отдельный тест** в отчёте: 3 роли = 3 теста, падают и ретраятся независимо. В pytest это `@pytest.mark.parametrize`.
> **Параметризация фикстур** — разные конфигурации **окружения/предусловий**, с которыми прогоняется весь набор тестов: option-фикстуры (`test.extend` + значение из конфига) и **projects** в `playwright.config.ts` — один и тот же набор тестов гоняется в Chromium/Firefox/WebKit, на разных стендах, с разными ролями. В pytest — `params` у `@pytest.fixture`.
> **Разница:** параметризация теста множит тесты по **данным** («один сценарий × N наборов данных»), параметризация фикстур множит прогоны по **окружениям/конфигурациям** («все сценарии × N окружений»). И в обоих случаях в отчёте получается несколько независимых тестов — а не один тест с ветвлением if/else внутри: условная логика в тесте — антипаттерн, тест должен быть линейным.»

### Вопрос 32. Что такое multi-page сценарий? Контекст один или разные?

🗣 **Ответ кандидата:**
«Сценарий, в котором проходишься по методам классов разных страниц, переходишь на одну страницу, другую». Про контекст: путано — «может быть и один, и не один... если использовать page в целом, контекст не будет инкапсулирован...».

⚠️ **Анализ ошибок:**
1. **Суть не понята.** Multi-page сценарий — это не «переходы между страницами приложения» (это обычный тест), а тест с **несколькими вкладками/окнами или несколькими браузерными контекстами одновременно**: например, два пользователя в чате, попап окна, оплата в новой вкладке.
2. Ответ про контексты вышел бессвязным, потому что кандидат не различает `Page` (вкладка) и `BrowserContext` (изолированная сессия с своими куками).

✅ **Идеальный ответ:**

> «Multi-page сценарий — тест, работающий с **несколькими страницами (вкладками/окнами) одновременно**. Иерархия в Playwright: Browser → BrowserContext (изолированная сессия: свои cookies, storage) → Page (вкладка).
> Два случая:
> 1. **Несколько страниц в одном контексте** — общая сессия: клик открыл новую вкладку (ловим `context.waitForEvent('page')`), попап оплаты. Обе вкладки видят одни куки — это один залогиненный пользователь.
> 2. **Несколько контекстов** — полная изоляция: классический пример — **два пользователя в одном тесте** (чат, звонок, совместное редактирование): создаём два контекста с разными storageState (userA.json, userB.json), в каждом свою page, и проверяем взаимодействие — А отправил сообщение, Б его увидел.
> Ответ на вопрос интервьюера: контекст **может быть и один, и несколько** — зависит от того, нужна ли тесту общая сессия (вкладки одного пользователя) или изоляция (разные пользователи).»

✅ **Идеальный ответ:**

> «Смотря что считать поддержкой:

### Вопрос 35. Какие метрики сервера анализировать при нагрузке?

🗣 **Ответ кандидата:**
Сначала снова про RPS и latency (клиентские). После наводящих вопросов («что у сервера нагружается?») назвал: **CPU, оперативная память, кэш/постоянная память, пропускная способность сети**.

⚠️ **Анализ ошибок:**
1. В итоге перечислил правильно (CPU, RAM, диск, сеть) — но **только по цепочке наводящих вопросов**; сам стартовал с клиентских метрик, хотя спрашивали именно про сервер.

✅ **Идеальный ответ:**

> «Четыре базовых ресурса сервера:
> 1. **CPU** — утилизация; стабильно >80–90% — узкое место;
> 2. **Память (RAM)** — потребление, swap; рост без выхода на плато при постоянной нагрузке — признак утечки;

> - открытые соединения/сокеты, размер пула соединений к БД;
> - очереди запросов (backlog), тред-пулы;

> Смысл анализа — сопоставить клиентскую картину (растёт p99, появились 5xx) с серверной и найти **узкое место**: упёрлись в CPU → масштабировать/профилировать; память течёт → чинить утечку; диск — оптимизировать запросы/индексы. Инструменты: Grafana + Prometheus, ELK, APM (например, Jaeger/Zipkin для трейсинга).»

## Главные системные проблемы кандидата

### 1. Разрыв «делаю руками — не знаю, как называется»
Кандидат реально пользуется фикстурами, POM, воркерами, storageState — но не может назвать ни `page.route`, ни `storageState`, ни stages, ни query parameters, ни consumer group. На скрининге проверяют именно словарь и понимание концепций: «работал, но не назову» засчитывается как «не знает».

### 2. Непонимание вместо незапоминания
Часть ошибок — не про термины, а про модель мира: «очистка через garbage collector», «Kafka слушает и сама отдаёт», «параметризация — это if/else в тесте», «мокирование — это запросы к реальному эндпоинту». Это концептуальные пробелы, которые не закрываются зубрёжкой — нужно разобраться в механике.

### 3. Ответ не на заданный вопрос
Систематически: спрашивают про структуру проекта — рассказывает про бизнес-логику; про параллелизацию — про POM; про тестовые данные — про импорты. Интервьюер трижды-четырежды повторял одни и те же вопросы. Правило: **сначала прямой ответ одним предложением, потом детали.**

### 4. Речь и подача
«Ну», «получается», «э-э», «как сказать» в каждой фразе; термины коверкаются («ЗОТ», «TLC», «текстуры»); мысли обрываются. При равных знаниях структурированная речь даёт +1 к грейду в глазах интервьюера, каша — −1.

### 5. Неумение работать с незнанием
Долгие попытки угадать («трейдинг, корутины, докер...») хуже, чем честная формула: «Точный термин не вспомню, но по смыслу это X, применяется для Y». Единственный хороший скип — Consumer Group; и отдельный плюс — кандидат в конце сам спросил правильные ответы (XDист, Consumer Group): любознательность интервьюеры ценят.

## Дополнение: SPA, async/defer и события загрузки страницы

Понятия из вопроса «что происходит между вводом URL и отрисовкой страницы» — разбор терминов, которые часто уточняют отдельно.

### SPA (Single Page Application)
«Одностраничное приложение» — сайт с одной HTML-страницей, где весь контент дальше отрисовывает JavaScript прямо в браузере, без полной перезагрузки. При переходах по разделам страница не перезагружается целиком: JS подменяет нужный кусок и подтягивает данные запросами (AJAX/fetch). Фреймворки: React, Vue, Angular. Примеры: почта, Trello, соцсети.

**Следствие для тестировщика:** первичный HTML у SPA почти пустой (каркас), реальный контент появляется только после выполнения JS. Поэтому нельзя проверять сразу после загрузки — нужно **дожидаться появления элемента** после отрисовки, иначе тест словит пустоту и будет флакать.

**AJAX** — техника, когда JS в фоне (без перезагрузки) делает запрос на сервер и обновляет часть контента. Основа интерактивности SPA.

### async и defer
Атрибуты тега `<script>`, управляющие загрузкой и выполнением внешнего JS. По умолчанию скрипт **блокирует парсинг HTML**: браузер останавливает построение страницы, качает и выполняет скрипт, потом продолжает — это тормозит отрисовку.

- **`async`** — скрипт качается параллельно с парсингом и выполняется **сразу, как загрузился** (парсинг на этот момент прерывается). Порядок выполнения не гарантирован. Подходит для независимых скриптов (аналитика, счётчики).
- **`defer`** — скрипт качается параллельно, но выполняется **после полного парсинга HTML**, в **порядке подключения**. Подходит для скриптов, которым нужен готовый DOM и важен порядок.

```html
<script src="a.js"></script>          <!-- блокирует парсинг -->
<script src="b.js" async></script>    <!-- параллельно, выполнить как только скачался -->
<script src="c.js" defer></script>    <!-- параллельно, выполнить после парсинга, по порядку -->
```

### DOMContentLoaded и load
- **`DOMContentLoaded`** — HTML полностью распарсен и **DOM построен**; картинки/стили могут ещё грузиться. Наступает раньше. `defer`-скрипты выполняются как раз перед этим событием.
- **`load`** — загружено **всё**: DOM + картинки, стили, шрифты, iframe. Наступает позже, страница полностью готова.

**На практике:** нужен только готовый DOM — ориентир `DOMContentLoaded`; нужны загруженные ресурсы — `load`. Но для SPA даже `load` не гарантирует, что контент отрисован (его дорисует JS после AJAX), поэтому в автотестах ждут не эти события, а **конкретный элемент на экране**.

## Дополнение: параметризация тестов в Playwright (Python и TypeScript)

**Параметризация** (data-driven testing) — запуск одного и того же теста на разных наборах входных данных, где каждый набор считается отдельным кейсом. Зачем: не копипастить один тест под каждое значение, покрыть классы эквивалентности и граничные значения компактно, получить в отчёте отдельный результат по каждому набору.

#### Ответ для интервью (как сказать вслух)

> «Параметризация — это когда мы пишем **один тест**, а запускаем его на **множестве наборов входных данных**, и каждый набор — отдельный кейс в отчёте. Логика теста одна, меняются только данные и ожидаемый результат.
>
> Нужна, чтобы **не дублировать** один и тот же тест ради разных значений, компактно покрыть **классы эквивалентности и граничные значения**, и чтобы при падении было видно, **на каком именно наборе** — а не "тест упал" в общем.
>
> Например, проверка валидации поля email: один тест и таблица данных — пустое поле, без "@", валидный адрес — прогоняется тремя отдельными кейсами.
>
> Реализуется по-разному: в **Playwright + Python** через pytest — декоратор `@pytest.mark.parametrize`; в **Playwright + TypeScript** встроенного `each` нет, поэтому оборачиваем `test()` в цикл по массиву данных.»

**Ключевые тезисы, если попросят короче:** один тест → много данных → каждый набор отдельный кейс; убирает дублирование; удобно для эквивалентности/границ; видно, какой именно набор упал.

Реализуется по-разному, потому что у Playwright для Python и для TS **разные раннеры**:
- Python → тесты гоняет **pytest** (плагин `pytest-playwright`) → параметризация средствами pytest.
- TypeScript → встроенный раннер **`@playwright/test`** → своего `each` нет, параметризация через цикл.

---

### Playwright + Python (pytest)

#### 1. Основной способ — `@pytest.mark.parametrize`

```python
import pytest

@pytest.mark.parametrize("email, expected_error", [
    ("",         "Введите email"),
    ("invalid",  "Некорректный email"),
    ("a@b.c",    None),
])
def test_login_validation(page, email, expected_error):
    page.goto("/login")
    page.fill("#email", email)
    page.click("#submit")
    if expected_error:
        assert page.inner_text(".error") == expected_error
```

Тест прогонится 3 раза, каждый набор — отдельный кейс в отчёте.

#### 2. Читаемые имена кейсов — `ids` / `pytest.param`

По умолчанию pytest генерирует имена автоматически, но их удобнее задать явно:

```python
@pytest.mark.parametrize(
    "email, expected_error",
    [
        pytest.param("",        "Введите email",       id="empty_email"),
        pytest.param("invalid", "Некорректный email",  id="no_at_sign"),
        pytest.param("a@b.c",   None,                  id="valid_email"),
    ],
)
def test_login_validation(page, email, expected_error):
    ...
```

В отчёте будет `test_login_validation[empty_email]` — сразу понятно, что упало.

#### 3. Пометки на отдельный набор — `marks`

Можно пометить конкретный кейс как `xfail` (ожидаемо падает) или `skip`:

```python
@pytest.mark.parametrize("value", [
    1,
    2,
    pytest.param(0, marks=pytest.mark.xfail(reason="деление на ноль, известный баг")),
])
def test_divide(value):
    assert 10 / value
```

#### 4. Стекинг декораторов — все комбинации (декартово произведение)

Несколько `parametrize` перемножаются:

```python
@pytest.mark.parametrize("width", [1920, 375])
@pytest.mark.parametrize("theme", ["light", "dark"])
def test_layout(page, width, theme):   # 2 × 2 = 4 прогона
    ...
```

#### 5. Параметризация фикстуры — `@pytest.fixture(params=[...])`

Когда набор данных нужен многим тестам, параметризуют саму фикстуру — тогда **каждый** тест, использующий её, размножится по наборам:

```python
@pytest.fixture(params=["admin", "user", "guest"])
def role(request):
    return request.param

def test_access(page, role):    # запустится для admin, user, guest
    ...
```

**Что такое `request` и `request.param`.** `request` — встроенная фикстура pytest, дающая доступ к **контексту текущего запуска** (какой тест, с какими параметрами, какой конфиг). Её не создают — просто добавляют аргументом, pytest подставит. `request.param` — **текущее значение параметра**, когда фикстура параметризована через `params=[...]`: pytest запускает фикстуру по разу на каждый элемент и на каждой итерации кладёт очередной в `request.param` (сначала `"admin"`, потом `"user"`, потом `"guest"`). Итог — `test_access` выполняется 3 раза.

⚠️ `request.param` существует **только если фикстура параметризована**. Без `params=...` обращение к нему упадёт с `AttributeError`.

Что ещё умеет `request`:

- **`request.param`** — значение параметра (в параметризованной фикстуре).
- **`request.node`** — объект теста (`request.node.name` — его имя).
- **`request.config`** — конфиг pytest, чтение CLI-опций: `request.config.getoption("--env")`.
- **`request.getfixturevalue("name")`** — получить другую фикстуру динамически по имени.
- **`request.addfinalizer(func)`** — зарегистрировать teardown (аналог кода после `yield`).

**Косвенная параметризация (`indirect=True`)** — приём, когда значение из теста прокидывается **в** фикстуру через тот же `request.param`, чтобы она успела что-то подготовить (например, создать пользователя нужной роли до теста):

```python
@pytest.fixture
def user(request):
    role = request.param                  # значение придёт из теста
    return create_user(role=role)

@pytest.mark.parametrize("user", ["admin", "guest"], indirect=True)
def test_access(user):
    ...
```

`indirect=True` = не передавай значения прямо в тест, а сначала пропусти через фикстуру `user` (она получит их в `request.param`).

#### Зачем нужна косвенная параметризация

Обычный `parametrize` отдаёт значение прямо в тест «как есть». `indirect=True` нужен, когда параметр — это **сырьё, которое надо сначала обработать через фикстуру** (что-то создать, поднять, залогинить) до старта теста, и в тест приходит уже результат её работы.

Причины использовать:

1. **Setup зависит от параметра.** Строка `"admin"` бесполезна сама по себе — тесту нужен реальный залогиненный пользователь с этой ролью. Фикстура создаёт его в setup, логика «создать пользователя» живёт в одном месте, а не копируется в каждый тест.
2. **Нужен teardown (уборка).** Фикстура через `yield` может не только создать, но и удалить за собой — обычный `parametrize` так не умеет, у него нет жизненного цикла:

```python
@pytest.fixture
def user(request):
    u = create_user(role=request.param)
    yield u                    # отдаём в тест
    delete_user(u)             # уборка после теста
```

3. **Переиспользование и читаемость.** Одна фикстура с indirect используется многими тестами; тела тестов чистые — вся подготовка спрятана.
4. **Параметризация окружения.** Классика — прокинуть параметр в фикстуру, поднимающую разные конфигурации (например, `db` = postgres / sqlite), и прогнать тест на обеих.

**Частичный indirect** — часть параметров через фикстуры, часть напрямую:

```python
@pytest.mark.parametrize("user, page_url", [("admin", "/panel")], indirect=["user"])
```

Здесь `user` идёт через фикстуру, а `page_url` — прямо в тест.

Коротко: обычный `parametrize` = «подставь значение в тест»; `indirect=True` = «сначала прогони значение через фикстуру, потом отдай результат». Нужна, когда параметр требует **предобработки, ресурса или уборки (setup/teardown)**.

### Это pipeline или нет?

Важно не путать два разных значения слова.

**Фикстуры — это НЕ CI/CD pipeline.** Pipeline (пайплайн) в контексте CI/CD — это автоматизированная цепочка шагов сборки/тестирования/деплоя в системе вроде GitLab CI, GitHub Actions, Jenkins (описывается в `.gitlab-ci.yml` / workflow-файле): `checkout → установка зависимостей → линт → запуск автотестов → сборка → деплой`. Это про инфраструктуру запуска, а не про код теста.

**Фикстуры — это lifecycle подготовки данных для теста** (setup → тест → teardown). Фикстуры **могут зависеть друг от друга**, образуя цепочку подготовки, которую иногда неформально называют «конвейером подготовки»:

```python
@pytest.fixture
def api_client(): ...            # шаг 1: клиент

@pytest.fixture
def auth_token(api_client): ...  # шаг 2: логин через клиент

@pytest.fixture
def user(auth_token): ...        # шаг 3: создать пользователя с токеном

def test_x(user): ...            # тест получает конец цепочки
```

Здесь pytest сам выстраивает порядок: `api_client → auth_token → user → test`, а на выходе разворачивает teardown в обратном порядке. Это **цепочка зависимостей фикстур**, а не CI/CD-пайплайн.

Как отвечать на собесе, если спросят: «Фикстуры — это механизм подготовки/уборки данных теста с поддержкой зависимостей между собой; это не путать с CI/CD-пайплайном, который оркестрирует запуск самих тестов в системе непрерывной интеграции».

### Реальный простой автотест с параметризацией фикстуры

Рабочий пример на **Playwright + Python (pytest)**, который реально запускается против публичного тренировочного сайта [the-internet.herokuapp.com](https://the-internet.herokuapp.com/login). Проверяем форму логина на трёх сценариях, данные приходят из **параметризованной фикстуры**.

```python
# test_login.py
import pytest


# --- параметризованная фикстура: 3 набора (логин, пароль, ожидаемое сообщение) ---
@pytest.fixture(params=[
    ("tomsmith", "SuperSecretPassword!", "You logged into a secure area!"),
    ("wrong_user", "SuperSecretPassword!", "Your username is invalid!"),
    ("tomsmith", "wrong_pass", "Your password is invalid!"),
], ids=["valid", "bad_username", "bad_password"])
def credentials(request):
    # request.param — текущий набор из списка params
    return request.param


# page — фикстура из плагина pytest-playwright (сама открывает/закрывает браузер)
def test_login(page, credentials):
    username, password, expected_message = credentials

    page.goto("https://the-internet.herokuapp.com/login")
    page.fill("#username", username)
    page.fill("#password", password)
    page.click("button[type=submit]")

    # на этом сайте сообщение появляется в блоке #flash
    assert expected_message in page.inner_text("#flash")
```

**Как запустить:**

```bash
pip install pytest-playwright        # ставит pytest + playwright + плагин
playwright install                    # скачивает браузеры
pytest test_login.py -v               # запуск; -v показывает каждый кейс
```

**Что выведет** (фикстура размножила тест на 3 кейса благодаря `params` + `ids`):

```
test_login.py::test_login[valid] PASSED
test_login.py::test_login[bad_username] PASSED
test_login.py::test_login[bad_password] PASSED
```

**Что здесь важно для собеса:**
- параметризация сделана на **фикстуре** (`@pytest.fixture(params=[...])`), а не на тесте — так набор данных легко переиспользовать в других тестах;
- `request.param` отдаёт текущий набор;
- `ids=[...]` дал читаемые имена кейсов (`[valid]`, `[bad_username]`, `[bad_password]`) — сразу видно, что упало;
- `page` — встроенная фикстура `pytest-playwright`, которая сама поднимает и гасит браузер (это её setup/teardown lifecycle).

## Зачем параметризация нужна в автотестах (Python и TS)

Причины **общие** для обоих языков — сама идея одна, различается только синтаксис реализации. Ниже — зачем она нужна и что говорить на собесе.

### 1. Убрать дублирование кода (DRY)
Без параметризации на каждое значение пишется отдельный тест-близнец:

```python
def test_login_empty():    # копия 1
    ...
def test_login_invalid():  # копия 2 — почти то же
    ...
```

С параметризацией — **один тест, много данных**. Меняешь логику проверки в одном месте, а не в десяти копиях. Меньше кода → меньше багов в самих тестах → дешевле поддержка.

### 2. Компактно покрыть тест-дизайн (эквивалентность и границы)
Параметризация — прямой инструмент под техники тест-дизайна:
- **классы эквивалентности** — по одному представителю на класс (пустое / невалидное / валидное);
- **граничные значения** — `0, 1, 2` и `99, 100, 101` одной таблицей данных.

Это связывает автоматизацию с теорией тестирования — сильный аргумент на собесе: «параметризацией я покрываю классы эквивалентности и границы, не плодя копий».

### 3. Понятная диагностика — видно, какой набор упал
Каждый набор — **отдельный кейс в отчёте** (`test_login[bad_password]`), а не «тест упал». Сразу ясно, на каких данных сломалось, без раскопок. Один параметризованный тест с 10 наборами при падении покажет ровно проблемный, остальные 9 останутся зелёными — в отличие от одного теста с 10 проверками внутри, где падение первой скрывает остальные.

### 4. Масштабируемость и data-driven подход
Данные отделены от логики теста. Добавить сценарий = добавить строку в таблицу, а не писать новый тест. Данные можно вынести во внешний источник (JSON/CSV/БД) и генерировать наборы динамически — тесты растут без разрастания кода.

### 5. Матрица окружений
Тем же механизмом гоняют один набор тестов под разные браузеры/вьюпорты/конфигурации:
- Python — CLI `--browser chromium --browser firefox` или параметризованные фикстуры;
- TS — `projects` в `playwright.config.ts`.

### Как это выглядит в двух экосистемах (одна цель — разный синтаксис)

| Зачем | Python (pytest) | TypeScript (`@playwright/test`) |
|---|---|---|
| DRY / data-driven | `@pytest.mark.parametrize` или `params` у фикстуры | цикл `for...of` вокруг `test()` |
| Диагностика набора | авто-`id` или `ids=` / `pytest.param(id=...)` | данные в заголовке `test()` |
| Динамические данные | `pytest_generate_tests`, чтение из файла | цикл по массиву/файлу |
| Матрица окружений | CLI `--browser`, фикстуры | `projects` в конфиге |
| Подготовка/уборка на набор | `indirect=True` + фикстура с `yield` | фикстуры `test.extend` |

### Ответ для интервью (коротко)

> «Параметризация нужна, чтобы **не дублировать** тесты ради разных данных: одна логика — много наборов. Она компактно покрывает **классы эквивалентности и граничные значения**, а в отчёте каждый набор — отдельный кейс, поэтому сразу видно, на каких данных упало. Данные отделены от логики — это data-driven подход, наборы легко расширять и выносить в файлы. Идея одинаковая в Python и TS, разный только синтаксис: в Python это декоратор `@pytest.mark.parametrize` (или `params` у фикстуры), в TS встроенного `each` нет — оборачиваем `test()` в цикл по массиву данных.»

## Зачем нужны фикстуры в автотестах (Python и TS)

**Фикстура** — это механизм подготовки того, что тесту нужно для работы (браузер, страница, залогиненный пользователь, тестовые данные, соединение с БД), и уборки после него. Тест получает готовое окружение аргументом и занимается только проверкой, а не рутиной подготовки.

### 1. Setup и teardown в одном месте (главное «зачем»)
У теста есть жизненный цикл: **подготовить → выполнить → убрать за собой**. Фикстура инкапсулирует setup и teardown, чтобы тест не занимался этим сам:

```python
@pytest.fixture
def db():
    conn = connect()      # setup — до теста
    yield conn            # отдаём в тест
    conn.close()          # teardown — после теста, даже если тест упал
```

Уборка (`teardown`) гарантированно выполнится, даже если тест упал с ошибкой, — соединения/данные не «протекут».

### 2. Убрать дублирование подготовки (DRY)
Одна и та же подготовка (логин, открытие браузера, создание пользователя) нужна десяткам тестов. Без фикстур это копипастится в каждый; с фикстурами — пишется один раз и переиспользуется:

```python
def test_a(logged_in_user): ...   # оба получают готового
def test_b(logged_in_user): ...   # залогиненного пользователя
```

#### Реалистичный пример: фикстура `logged_in_user`

Рабочий пример на **Playwright + Python (pytest)** против публичного демо-магазина [saucedemo.com](https://www.saucedemo.com) (стандартный логин `standard_user` / `secret_sauce`). Фикстура логинится один раз и отдаёт в тест **уже авторизованную страницу**, а тесты сразу проверяют, что им нужно, не повторяя логин.

```python
# conftest.py  — общие фикстуры лежат здесь, доступны всем тестам
import pytest


@pytest.fixture
def logged_in_user(page):
    """Логинится в saucedemo и отдаёт в тест авторизованную страницу."""
    # --- SETUP: подготовка до теста ---
    page.goto("https://www.saucedemo.com/")
    page.fill("#user-name", "standard_user")
    page.fill("#password", "secret_sauce")
    page.click("#login-button")

    # убеждаемся, что логин реально прошёл (мы на странице товаров)
    page.wait_for_url("**/inventory.html")

    yield page          # <-- отдаём готовую (залогиненную) страницу в тест

    # --- TEARDOWN: уборка после теста (выполнится, даже если тест упал) ---
    # разлогиниваемся через бургер-меню, если оно доступно
    if page.is_visible("#react-burger-menu-btn"):
        page.click("#react-burger-menu-btn")
        page.click("#logout_sidebar_link")
```

```python
# test_shop.py — сами тесты; логин уже сделан фикстурой
def test_inventory_visible(logged_in_user):
    page = logged_in_user                      # это уже авторизованная страница
    assert page.is_visible(".inventory_list")
    assert page.locator(".inventory_item").count() == 6


def test_add_to_cart(logged_in_user):
    page = logged_in_user
    page.click("[data-test='add-to-cart-sauce-labs-backpack']")
    assert page.inner_text(".shopping_cart_badge") == "1"


def test_open_cart(logged_in_user):
    page = logged_in_user
    page.click(".shopping_cart_link")
    assert "cart" in page.url
```

**Что здесь происходит по шагам:**
1. Тест запрашивает аргумент `logged_in_user` → pytest видит фикстуру с таким именем и запускает её **до** теста.
2. Фикстура сама запрашивает встроенную фикстуру `page` (из `pytest-playwright`) — это **композиция**: `page → logged_in_user → test`.
3. Код до `yield` — **setup**: открыть сайт, залогиниться, проверить, что вошли.
4. `yield page` отдаёт в тест **уже авторизованную** страницу.
5. Тело теста работает с готовым состоянием — никакого повторного логина.
6. Код после `yield` — **teardown**: разлогин, выполнится даже если тест упал.

**Что это даёт:** логин написан **один раз** в фикстуре, а не скопирован в каждый из трёх тестов (DRY). Каждый тест получает **свежую авторизованную сессию** (изоляция). Тесты читаются чисто — видно только суть проверки, а не рутину подготовки.

**Вариант: фикстура отдаёт данные пользователя, а не страницу.**
Иногда удобнее вернуть объект пользователя (например, при API-подготовке), а не UI-страницу:

```python
@pytest.fixture
def logged_in_user(page):
    user = {"username": "standard_user", "password": "secret_sauce"}
    page.goto("https://www.saucedemo.com/")
    page.fill("#user-name", user["username"])
    page.fill("#password", user["password"])
    page.click("#login-button")
    page.wait_for_url("**/inventory.html")
    return {"page": page, "user": user}        # отдаём и страницу, и данные

def test_greeting(logged_in_user):
    page = logged_in_user["page"]
    assert logged_in_user["user"]["username"] == "standard_user"
    assert page.is_visible(".inventory_list")
```

**Аналог на TypeScript (`@playwright/test`)** — та же идея через `test.extend`, где `await use(page)` играет роль `yield`:

```typescript
import { test as base, expect, Page } from '@playwright/test';

const test = base.extend<{ loggedInUser: Page }>({
  loggedInUser: async ({ page }, use) => {
    // SETUP
    await page.goto('https://www.saucedemo.com/');
    await page.fill('#user-name', 'standard_user');
    await page.fill('#password', 'secret_sauce');
    await page.click('#login-button');
    await page.waitForURL('**/inventory.html');

    await use(page);   // отдаём авторизованную страницу в тест (аналог yield)

    // TEARDOWN
    if (await page.isVisible('#react-burger-menu-btn')) {
      await page.click('#react-burger-menu-btn');
      await page.click('#logout_sidebar_link');
    }
  },
});

test('добавление в корзину', async ({ loggedInUser }) => {
  await loggedInUser.click("[data-test='add-to-cart-sauce-labs-backpack']");
  await expect(loggedInUser.locator('.shopping_cart_badge')).toHaveText('1');
});
```

Запуск Python-версии: `pip install pytest-playwright && playwright install && pytest -v`.

#### Разбор синтаксиса `test.extend` (TypeScript)

Строка с `test.extend` пугает нагромождением скобок — но каждая скобка отвечает за своё.

```typescript
const test = base.extend<{ loggedInUser: Page }>({
  loggedInUser: async ({ page }, use) => {
```

**1. `<{ loggedInUser: Page }>` — дженерик-тип.**
`extend<...>()` — дженерик-метод, в угловых скобках `<>` передаём **тип** новых фикстур. `{ loggedInUser: Page }` внутри — **объектный тип** (описание формы): «есть поле `loggedInUser` типа `Page`». Фигурные скобки тут описывают **тип**, а не значение. Если фикстур несколько: `<{ loggedInUser: Page; adminToken: string }>`.

**2. `({ ... })` — круглые скобки вызова + объект-значение.**
После дженерика идёт вызов `(...)`, а внутри `{ ... }` — **объект-значение** с реализациями фикстур («имя → функция подготовки»):

```typescript
base.extend<...>({           // ← ( вызов, { объект-значение
  loggedInUser: async (...) => {...},
});
```

Итого: `<{ loggedInUser: Page }>` — **тип** (что за фикстура), `({ loggedInUser: ... })` — **значение** (как её приготовить).

**3. `async ({ page }, use) => {` — два аргумента функции.**
- Первый аргумент — объект со всеми доступными фикстурами Playwright (`page`, `context`, `browser`...). Запись `{ page }` — **деструктуризация**: «достань из этого объекта поле `page`». Без неё было бы `async (fixtures, use) => { const page = fixtures.page; ... }`.
- Второй аргумент `use` — функция, через которую фикстура **отдаёт значение в тест** (`await use(page)`): до `use` — setup, после — teardown. Это TS-аналог `yield` из pytest.

**Какая скобка за что отвечает:**

| Скобка | Что это |
|---|---|
| `<{ ... }>` | дженерик — **тип** новых фикстур |
| `(...)` | круглые — **вызов** метода `extend` |
| `{ loggedInUser: ... }` внутри `()` | объект-**значение** с реализациями |
| `{ page }` в аргументе функции | **деструктуризация** — достаём `page` из объекта фикстур |

Правило чтения: **угловые `<>`** — про типы (TypeScript), **круглые `()`** — вызов, **фигурные `{}`** — объект (тип или значение) либо деструктуризация, смотря по месту.

### 3. Изоляция и чистота тестов
Каждый тест получает **свежее, чистое окружение** и свои данные, чтобы тесты не влияли друг на друга и не зависели от порядка запуска. Это основа стабильных, неслетающих (не флакающих) тестов.

### 4. Управление областью видимости (scope)
Фикстуру можно готовить с разной «частотой»: на каждый тест, на модуль, на всю сессию. Дорогой ресурс (поднять БД, залогиниться) создаётся один раз и переиспользуется — экономит время прогона:

```python
@pytest.fixture(scope="session")   # один раз на весь прогон
def api_client(): ...
```

#### Области видимости (scope) фикстур — подробно

`scope` определяет, **как часто фикстура создаётся заново и как долго живёт**. Чем шире scope, тем реже setup/teardown и тем больше тестов делят один экземпляр. Пять уровней, от узкого к широкому:

**1. `function` (по умолчанию)** — создаётся **заново на каждый тест**, teardown сразу после. Максимальная изоляция, самый безопасный вариант. Для данных/состояния, которое тест меняет (свой пользователь, свежая страница).

```python
@pytest.fixture              # scope="function" по умолчанию
def data(): ...
```

**2. `class`** — один раз **на класс тестов**, переиспользуется всеми его методами.

```python
@pytest.fixture(scope="class")
def db_table(): ...
```

**3. `module`** — один раз **на файл** (`.py`), живёт для всех тестов файла. Для дорогого, что нужно всем тестам одного модуля (тестовый сервер, набор данных).

```python
@pytest.fixture(scope="module")
def server(): ...
```

**4. `package`** — один раз **на пакет** (папку с тестами). Используется реже остальных.

**5. `session`** — один раз **на весь прогон pytest**, переиспособируется всеми тестами. Для очень дорогих ресурсов: соединение с БД, авторизация/токен, запуск контейнера, конфиг. Экономит больше всего времени.

```python
@pytest.fixture(scope="session")
def api_client(): ...
```

**Время жизни наглядно:**

```
session   ├──────────────────────────────────────────────┤   (1 раз на всё)
module    ├───────────────┤ ├──────────────┤                  (на каждый файл)
class     ├──────┤ ├──────┤   ...                             (на каждый класс)
function  ├─┤├─┤├─┤├─┤├─┤├─┤   ...                            (на каждый тест)
```

**Главный компромисс — скорость vs изоляция:**
- узкий scope (`function`) — медленнее (готовим на каждый тест), но максимальная изоляция и стабильность;
- широкий scope (`session`) — быстрее (готовим один раз), но тесты **делят общий экземпляр**; если один тест его испортит (изменит состояние), поедут другие → флак и зависимость от порядка.

**Правило: бери самый узкий scope, который достаточен.** Расширяй только ради дорогих ресурсов, которые тесты **не мутируют**:

```python
@pytest.fixture(scope="session")
def api_client():
    client = ApiClient()          # дорого — поднимаем один раз
    yield client
    client.close()

@pytest.fixture                    # function — дёшево и изолированно
def user(api_client):
    u = api_client.create_user()   # свой пользователь на каждый тест
    yield u
    api_client.delete_user(u)
```

Клиент один на сессию (не мутируется), пользователь — свежий на каждый тест (мутируется). Типичная связка.

**Нюансы:**
- **Зависимость по scope:** фикстура может зависеть только от фикстур **своего или более широкого** scope. `session`-фикстура не может использовать `function`-фикстуру (та живёт короче). Наоборот — можно.
- **Порядок teardown** — обратный setup: созданное последним убирается первым (как стек).
- Встроенные фикстуры уже имеют scope (`tmp_path` — function и т.д.).

**Аналог в Playwright (TS)** — не пять уровней, а по сути два:
- **`test`** (по умолчанию) — на каждый тест, аналог `function`;
- **`worker`** — один раз на воркер (параллельный процесс), близко к `session` при параллельном прогоне.

```typescript
const test = base.extend<{}, { apiClient: ApiClient }>({
  apiClient: [async ({}, use) => {
    const client = new ApiClient();
    await use(client);
    await client.close();
  }, { scope: 'worker' }],   // ← один на воркер
});
```

**Про два generic-параметра `extend` и пустые `{}`.** `test.extend` — дженерик с **двумя** типовыми параметрами:

```typescript
base.extend< TestFixtures , WorkerFixtures >(...)
//           ^1-й: scope "test"  ^2-й: scope "worker"
```

- **Первый** `<...>` — фикстуры со scope **`test`** (на каждый тест, аналог pytest `function`).
- **Второй** `<...>` — фикстуры со scope **`worker`** (раз на воркер, аналог `session`).

В примере `<{}, { apiClient: ApiClient }>`: пустой `{}` (пустой объектный тип, «объект без полей») означает «test-scoped фикстур не добавляю», а все новые фикстуры — worker-scoped. Пропустить первый параметр нельзя: раз нужен второй (`worker`), первый обязан стоять на месте — его заполняют пустышкой `{}`.

Сравни с примером логина выше: `base.extend<{ loggedInUser: Page }>({...})` — там только первый параметр, потому что `loggedInUser` нужен свежий на каждый тест (test-scoped).

| Позиция | Что описывает | В примере |
|---|---|---|
| 1-й `<...>` | фикстуры scope `test` (на каждый тест) | `{}` — нет таких |
| 2-й `<...>` | фикстуры scope `worker` (раз на воркер) | `{ apiClient: ApiClient }` |

Важно: тип во втором параметре говорит TypeScript, что фикстура worker-scoped, но **фактический scope в рантайме** задаётся в реализации — `[async (...) => {...}, { scope: 'worker' }]`. Тип (2-й generic) и значение (`{ scope: 'worker' }`) должны совпадать.

### 5. Композиция (фикстуры зависят от фикстур)
Фикстуры выстраиваются в цепочку зависимостей, и pytest сам разрешает порядок: `api_client → auth_token → user → test`. Сложное окружение собирается из простых кирпичиков.

### Как это устроено в двух экосистемах

**Python (pytest)** — фикстуры через декоратор `@pytest.fixture`, тест запрашивает их **по имени аргумента**; setup/teardown — через `yield`; общие фикстуры выносятся в `conftest.py`:

```python
@pytest.fixture
def user():
    u = create_user()
    yield u
    delete_user(u)

def test_profile(user):     # pytest подставит фикстуру по имени
    ...
```

**TypeScript (`@playwright/test`)** — своя мощная система фикстур через `test.extend`; тест получает их **через деструктуризацию** аргумента; встроенные фикстуры — `page`, `context`, `browser`:

```typescript
import { test as base } from '@playwright/test';

const test = base.extend<{ user: User }>({
  user: async ({}, use) => {
    const u = await createUser();   // setup
    await use(u);                    // отдаём в тест (аналог yield)
    await deleteUser(u);             // teardown
  },
});

test('profile', async ({ page, user }) => {   // получаем page и user
  ...
});
```

Обрати внимание: `await use(value)` в Playwright — прямой аналог `yield` в pytest (до `use` — setup, после — teardown).

| Аспект | Python (pytest) | TypeScript (`@playwright/test`) |
|---|---|---|
| Объявление | `@pytest.fixture` | `test.extend({...})` |
| Получение в тесте | по имени аргумента | деструктуризация `{ page, user }` |
| Setup/teardown | `yield` | `await use(value)` |
| Общие фикстуры | `conftest.py` | отдельный файл с расширенным `test` |
| Scope | `function/class/module/session` | worker / test |
| Встроенные | `page` (pytest-playwright) | `page`, `context`, `browser` |

 ### Фикстуры vs параметризация — не путать

- **Фикстура** отвечает на вопрос «**что** подготовить для теста» (окружение, ресурсы, данные) и как убрать.
- **Параметризация** — «**на каких данных** прогнать тест».

Они **сочетаются**: параметризованная фикстура (`@pytest.fixture(params=[...])`) готовит разное окружение под каждый набор — это и есть их пересечение (см. раздел про indirect и реальный автотест выше).

### Ответ для интервью (коротко)

> «Фикстуры нужны, чтобы вынести из теста **подготовку и уборку** окружения: открыть браузер, залогиниться, создать данные — и гарантированно убрать за собой через teardown, даже если тест упал. Это убирает дублирование (одна подготовка на много тестов), даёт **изоляцию** (каждый тест получает чистое окружение — основа стабильности) и управление scope (дорогой ресурс поднимается один раз). Идея одна в Python и TS: в pytest это `@pytest.fixture` с `yield`, запрашивается по имени аргумента; в Playwright для TS — `test.extend` с `await use()`, приходит через деструктуризацию. А параметризованная фикстура объединяет фикстуры и параметризацию — готовит разное окружение под каждый набор данных.»

#### 6. Динамические данные — `pytest_generate_tests`

Хук для генерации параметров на лету (например, читать кейсы из JSON/CSV/БД):

```python
def pytest_generate_tests(metafunc):
    if "case" in metafunc.fixturenames:
        cases = load_cases_from_json("data.json")
        metafunc.parametrize("case", cases)
```

**Что такое `metafunc`.** Это не «метафункция», а объект-**описание тестовой функции** на этапе её сбора (класс `Metafunc`). Приставка «meta» = «данные о функции»: это не сам тест, а информация о нём, через которую управляют параметризацией. Хук `pytest_generate_tests(metafunc)` pytest вызывает **для каждой** тестовой функции на этапе коллекции (до запуска) и передаёт туда `metafunc`.

Основное внутри `metafunc`:

- **`metafunc.fixturenames`** — список имён аргументов/фикстур, которые запрашивает тест. `if "case" in metafunc.fixturenames` — проверка «этот тест вообще принимает аргумент `case`?»; если нет — не трогаем его.
- **`metafunc.parametrize("case", cases)`** — программный аналог декоратора `@pytest.mark.parametrize`: «для аргумента `case` создай по кейсу на каждый элемент `cases`».
- **`metafunc.function`** — сама тестовая функция; **`metafunc.module` / `metafunc.cls`** — где она лежит.
- **`metafunc.config`** — конфиг pytest (можно читать CLI-опции: `metafunc.config.getoption("--env")`).

По шагам: pytest дошёл до теста → зашёл в хук → увидел, что тест ждёт `case` → подгрузил кейсы из JSON → сгенерировал по отдельному тесту на каждый:

```python
def test_something(case):   # запустится N раз, по числу элементов в data.json
    assert case["input"] == case["expected"]
```

**Зачем это, если есть декоратор `@parametrize`:** `pytest_generate_tests` нужен, когда наборы **неизвестны заранее** и вычисляются динамически — читаются из файла/БД/API, генерируются по условию или зависят от CLI-опции. Декоратор так не умеет — в нём данные прописываются статически прямо в коде.

Прогон по браузерам в pytest-playwright задаётся **не** параметризацией, а CLI-опцией:
`pytest --browser chromium --browser firefox --browser webkit`.

### Playwright + TypeScript (`@playwright/test`)

У встроенного раннера **нет** аналога `test.each` (как в Jest). Параметризация делается **обычным циклом по массиву**, внутри которого вызывается `test()`.

#### 1. Основной способ — цикл `for...of` вокруг `test()`

```typescript
import { test, expect } from '@playwright/test';

const cases = [
  { email: '',        error: 'Введите email' },
  { email: 'invalid', error: 'Некорректный email' },
  { email: 'a@b.c',   error: null },
];

for (const { email, error } of cases) {
  test(`валидация логина: "${email}"`, async ({ page }) => {
    await page.goto('/login');
    await page.fill('#email', email);
    await page.click('#submit');
    if (error) {
      await expect(page.locator('.error')).toHaveText(error);
    }
  });
}
```

⚠️ **Важно:** имя каждого теста должно быть **уникальным** — поэтому в заголовок подставляют значение из данных (`${email}`). Одинаковые имена → Playwright ругается на дубли.

#### 2. Группировка — цикл вокруг `test.describe`

Если на каждый набор нужно несколько проверок:

```typescript
for (const user of ['admin', 'guest']) {
  test.describe(`роль: ${user}`, () => {
    test('видит дашборд', async ({ page }) => { /* ... */ });
    test('видит настройки', async ({ page }) => { /* ... */ });
  });
}
```

#### 3. Параметризация по окружениям — `projects` в `playwright.config.ts`

Один и тот же набор тестов гоняется под разные браузеры/вьюпорты/URL — это «параметризация окружения», а не данных:

```typescript
// playwright.config.ts
import { defineConfig, devices } from '@playwright/test';

export default defineConfig({
  projects: [
    { name: 'chromium', use: { ...devices['Desktop Chrome'] } },
    { name: 'firefox',  use: { ...devices['Desktop Firefox'] } },
    { name: 'mobile',   use: { ...devices['iPhone 13'] } },
  ],
});
```

#### 4. Параметризованные опции через `test.extend`

Кастомный параметр (например, роль) объявляют как option-фикстуру и переопределяют на уровне project или `describe`:

```typescript
import { test as base } from '@playwright/test';

type Options = { role: string };

export const test = base.extend<Options>({
  role: ['guest', { option: true }],   // значение по умолчанию
});

// далее в конфиге можно задать разный role для разных projects:
// use: { role: 'admin' }
```

#### 5. Данные из файла

Читается обычными средствами Node и так же проходится циклом:

```typescript
import cases from './data.json';

for (const c of cases) {
  test(`${c.name}`, async ({ page }) => { /* ... */ });
}
```

### Сводка

| Аспект | Playwright + Python | Playwright + TS |
|---|---|---|
| Раннер | pytest (`pytest-playwright`) | `@playwright/test` |
| Data-driven | `@pytest.mark.parametrize`, `params` у фикстур | цикл `for...of` вокруг `test()` |
| Имена кейсов | `ids=` / `pytest.param(id=...)` | подставлять данные в заголовок (уникальность!) |
| Все комбинации | стекинг декораторов `parametrize` | вложенные циклы |
| Пометки на набор | `marks=` (xfail/skip) | `test.skip()` / `test.fixme()` внутри |
| По окружениям (браузеры) | CLI `--browser` | `projects` в конфиге |
| Динамические данные | `pytest_generate_tests` | цикл по массиву/файлу |

**Главное отличие для собеса:** в Python параметризация **декларативная** (декоратор pytest), в TS — **императивная** (встроенного `each` нет, оборачиваешь `test()` в цикл, следя за уникальностью имён). Матрица браузеров: в Python — через CLI-опцию, в TS — через `projects` в конфиге.

## Дополнение: корнер-кейсы (corner cases) — что это

**Корнер-кейс** — баг/ситуация, которая возникает при **совпадении нескольких редких/крайних условий одновременно**, в отличие от эдж-кейса, где на границе **один** параметр.

**Отличие от эдж-кейса:**

| | Эдж-кейс (edge) | Корнер-кейс (corner) |
|---|---|---|
| Сколько условий | **одно** на границе | **несколько** на границах одновременно |
| Пример | поле 1-100 → проверяем 0, 1, 100, 101 | максимальная сумма + нулевой остаток + гонка + истекающая сессия вместе |
| Аналогия | край одной оси | угол, где сходятся несколько краёв |

**Примеры:**
- **Перевод денег:** максимально допустимая сумма + на счету ровно столько же до копейки + одновременное списание комиссии по другой операции (гонка) + сессия истекает через секунду. Каждое условие безобидно, вместе — перевод в минус / задвоение.
- **Из банковского домена:** клиент со скорингом БКИ ровно на пороге одобрения + активное ограничение ФНС + статус, при котором должна всплыть модалка про лимит — что победит, предложение или блокировка?
- **Загрузка файла:** файл максимального размера + эмодзи в имени + медленный интернет + сессия почти истекла + «отмена» в момент завершения.
- **Корзина:** последний товар на складе + два пользователя покупают в одну секунду + промокод истекает в эту же секунду.
- **Дата:** операция в момент перехода через полночь + смена часового пояса + переход на летнее время.

**Практический вывод (связь с чисткой регресса):** корнер-кейсов **бесконечно много** — комбинаций редких условий сколько угодно. Поэтому в регрессе их ревизуют: держат те, где **цена ошибки высока** (гонки на денежных операциях, граничные состояния счёта), а «экзотику ради экзотики» (эмодзи в комментарии к архивному заказу) выкидывают. Именно неактуальные корнер-кейсы раздувают регресс, если не чистить.

**Формула для собеса:** корнер-кейс = стечение нескольких крайних/редких условий одновременно; часто именно там прячутся самые дорогие баги — гонки, граничные состояния, рассинхроны.
