## Часть 2. Вопросы скрининга + идеальные ответы

### 1. Какие виды тестирования знаешь? Структурированно, по группам.

**Идеальный ответ — раскладываем по классификациям, а не списком вперемешку:**

**По доступу к коду / знанию системы:**
- **Чёрный ящик (black box)** — тестируем без знания внутренней реализации, по требованиям и интерфейсу.
- **Белый ящик (white box)** — с доступом к коду и знанием внутренней логики.
- **Серый ящик (grey box)** — частичное знание реализации (например, знаем структуру БД/API, но тестируем через UI).

**По уровню (пирамида тестирования):**
- **Модульные (unit)** — отдельные функции/классы.
- **Интеграционные** — взаимодействие модулей/сервисов между собой.
- **Системные / E2E** — вся система целиком по пользовательским сценариям.
- **Приёмочные (acceptance)** — соответствие бизнес-требованиям.

**По функциональности:**
- **Функциональное** — проверяем, что система делает то, что должна.
- **Нефункциональное** — производительность/нагрузка, безопасность, юзабилити, совместимость, надёжность, локализация, доступность.

**По целям / по запуску кода:**
- **Позитивное / негативное**.
- **Статическое** (без запуска — ревью кода, анализ требований, линтеры) и **динамическое** (с запуском).
- **Дымовое (smoke)**, **санитарное (sanity)**, **регрессионное**, **повторное (re-testing)**.

**По степени автоматизации:** ручное и автоматизированное.

> Совет: интервьюеру достаточно общего понимания — важно показать, что ты мыслишь классификациями, а не вываливаешь термины кучей.

### 2. Какие техники тест-дизайна знаешь?

**Идеальный ответ:**
- **Классы эквивалентности (equivalence partitioning)** — разбиваем входные данные на группы, где система ведёт себя одинаково, и тестируем по одному представителю из каждого класса. Сокращает число тестов без потери покрытия.
- **Граничные значения (boundary value analysis)** — проверяем значения на границах диапазонов (см. вопрос 3).
- **Таблица решений (decision table)** — для комбинаций условий и соответствующих действий.
- **Попарное тестирование / pairwise (например, метод «pairwise»/allpairs)** — покрываем все пары значений параметров вместо полного перебора комбинаций.
- **Диаграмма состояний и переходов (state transition)** — когда поведение зависит от текущего состояния системы.
- **Причина-следствие (cause-effect)**.
- **Предугадывание ошибок (error guessing)** — на основе опыта.
- **Тестирование на основе сценариев использования (use case testing)**.

---

### 3. При граничных значениях какая техника используется?

**Идеальный ответ:**
Граничные значения (**boundary value analysis**) почти всегда применяются **вместе с классами эквивалентности**. Сначала разбиваем данные на классы эквивалентности, затем для каждого класса проверяем **границы** — потому что ошибки чаще всего возникают именно на краях диапазонов (`< > <= >=`, off-by-one).

Проверяем **три точки** на границе: значение **на границе**, **на 1 меньше** и **на 1 больше**.
Пример: поле принимает от 1 до 100 → тестируем `0, 1, 2` и `99, 100, 101`.

### 4. Много ли автотестов писал? / Выведи характеристики хорошего автотеста.

**Идеальный ответ — характеристики хорошего автотеста:**
- **Детерминированность / стабильность** — тест не «флакает», при одинаковых условиях всегда даёт одинаковый результат. Никаких случайных падений.
- **Независимость (изоляция)** — не зависит от других тестов и от порядка запуска; сам готовит и убирает свои данные (setup/teardown).
- **Атомарность** — проверяет одну вещь/один сценарий; при падении сразу понятно, что сломалось.
- **Быстрый** — выполняется быстро, чтобы можно было гонять в CI на каждый коммит.
- **Читаемый и поддерживаемый** — понятное название, структура **Arrange-Act-Assert** (Given-When-Then), без «магических» значений.
- **Осмысленные ассерты** — проверяет именно нужный результат, падает с понятным сообщением.
- **Повторяемость и переносимость** — одинаково работает локально и в CI, на любом окружении.
- **Без хардкода** — данные и конфиги вынесены (переменные окружения, фикстуры, тест-данные).
- **Идемпотентность** — можно запустить много раз без «загрязнения» окружения.

### 6. Из чего состоит HTTP-запрос?

**Идеальный ответ — запрос состоит из:**
1. **Стартовая строка (request line):**
   - **Метод** — `GET`, `POST`, `PUT`, `PATCH`, `DELETE`, `HEAD`, `OPTIONS`.
   - **URL / путь (адрес ресурса)** — куда направлен запрос (по этому адресу метод «понимает, куда идти»).
   - **Версия протокола** — например `HTTP/1.1`.
2. **Заголовки (headers)** — метаданные запроса: `Host`, `Content-Type`, `Authorization`, `Accept`, `User-Agent`, `Cookie` и т.д.
3. **Тело (body)** — данные запроса (для `POST`/`PUT`/`PATCH`): JSON, форма, файл. У `GET` тела обычно нет.

**Ответ (HTTP-response) состоит из:** статусной строки (**код ответа** — 2xx успех, 3xx редирект, 4xx ошибка клиента, 5xx ошибка сервера), **заголовков** и **тела**.

### 7. Python: пустой класс `C`. Создаём два экземпляра в разные переменные и сравниваем их — что будет?

**Идеальный ответ:**
```python
class C:
    pass

a = C()
b = C()
print(a == b)   # False
```
Будет **`False`**. По умолчанию у объекта нет своего `__eq__`, поэтому сравнение `==` падает на **сравнение по идентичности** (как `is`) — сравниваются **ссылки/адреса в памяти**. Это два разных объекта в разных ячейках памяти → не равны.

**Нюансы:**
- `a is b` тоже `False` — это разные объекты.
- `a == a` → `True`.
- В **JavaScript** для сравнения объектов было бы аналогично `false` (объекты сравниваются по ссылке). *(В транскрипте была оговорка про «три» — речь про `===` строгое сравнение, но суть та же: разные объекты не равны.)*
- Чтобы сравнивать по содержимому — нужно определить `__eq__` (и обычно `__hash__`), либо использовать `@dataclass`.

### 8. Какие переменные в Python передаются по ссылке, а какие по значению?

**Идеальный ответ (формально — Python использует «передачу по ссылке на объект», но на практике различие сводится к изменяемости):**

- **Неизменяемые (immutable)** объекты ведут себя как **передача по значению**: `int`, `float`, `bool`, `str`, `tuple`, `frozenset`, `bytes`. Их нельзя изменить на месте — при «изменении» создаётся новый объект.
- **Изменяемые (mutable)** объекты ведут себя как **передача по ссылке**: `list`, `dict`, `set`, а также пользовательские объекты. Изменения внутри функции видны снаружи.

**Ключевой момент про кортеж (tuple):** относится к **неизменяемым** → по значению. Строка (`str`) — тоже неизменяемая, по значению.

**Строго говоря:** в Python всё — это **ссылки на объекты** («call by object reference» / «call by sharing»). Разница в поведении возникает не из способа передачи, а из **изменяемости** самого объекта.

```python
def f(x):
    x += 1          # int неизменяем → снаружи не меняется
def g(lst):
    lst.append(1)   # list изменяем → снаружи меняется
```

### 9. Что происходит между вводом URL в браузер и полной отрисовкой страницы?

> **Как отвечать на интервью.** Это классический вопрос «What happens when you type google.com and press Enter». Проверяют не зубрёжку, а понимание всей цепочки: сеть → сервер → браузер → рендеринг. Хорошая стратегия: сначала назвать этапы верхнеуровнево одним предложением («сначала браузер находит сервер через DNS, устанавливает соединение, отправляет HTTP-запрос, получает HTML и рендерит его»), а потом раскрывать каждый по мере интереса интервьюера. Обязательно уточни: *«Насколько подробно раскрывать — по сети или по рендерингу?»* — это показывает зрелость.

**Верхнеуровнево цепочка такая:** разбор URL → DNS → TCP/TLS → HTTP-запрос → ответ сервера → парсинг и рендеринг → выполнение JS → страница готова.

Теперь по каждому этапу подробно.

---

#### Этап 1. Разбор URL (парсинг адреса)
Браузер разбирает введённую строку на составляющие:
- **схема/протокол** — `https://` (или браузер сам подставит и попробует HTTPS);
- **домен (хост)** — `www.ozon.ru`;
- **порт** — по умолчанию 443 для HTTPS, 80 для HTTP;
- **путь** — `/category/...`;
- **query-параметры** — `?id=123`;
- **фрагмент (якорь)** — `#section`, он не отправляется на сервер, обрабатывается локально.

Попутно браузер проверяет **HSTS-список** (нужно ли принудительно идти по HTTPS) и решает, это вообще URL или поисковый запрос в адресной строке.

*На интервью:* «Браузер сначала парсит URL на протокол, домен, порт, путь и параметры, чтобы понять, куда и как идти».

---

#### Этап 2. DNS-резолвинг (находим IP по домену)
Домен — это для людей, а сети нужен **IP-адрес**. Браузер ищет его, последовательно проверяя кэши, чтобы не бегать в интернет лишний раз:
1. **кэш браузера**;
2. **кэш ОС** (+ файл `hosts`);
3. **кэш роутера**;
4. **DNS-сервер провайдера** (рекурсивный резолвер), который при необходимости обходит цепочку: **корневой сервер → TLD-сервер (`.ru`) → авторитативный сервер домена**.

В ответ приходит IP (например, `IPv4` или `IPv6`).

*На интервью:* «DNS — это как телефонная книга интернета: превращает имя домена в IP-адрес, при этом на каждом уровне есть кэш ради скорости».

---

#### Этап 3. Установка соединения (TCP + TLS)
- **TCP three-way handshake** — три пакета `SYN → SYN-ACK → ACK`. Так клиент и сервер договариваются, что готовы обмениваться данными, и синхронизируют номера последовательности.
- Для **HTTPS** дополнительно **TLS-handshake**: сервер присылает **сертификат**, браузер проверяет его (кем выдан, не истёк ли, соответствует ли домену), затем стороны согласуют версию TLS и **сеансовые ключи шифрования**. Дальше весь трафик шифруется.

*На интервью:* «TCP-хэндшейк устанавливает надёжное соединение, а TLS поверх него добавляет шифрование и проверку подлинности сервера через сертификат».

---

#### Этап 4. Отправка HTTP-запроса
Браузер формирует и отправляет **HTTP-запрос** (обычно метод `GET`):
- **стартовая строка**: метод + путь + версия (`GET /path HTTP/1.1`);
- **заголовки**: `Host`, `User-Agent`, `Accept`, `Cookie`, `Accept-Encoding` и т.д.;
- **тело**: у `GET` обычно отсутствует.

*На интервью:* здесь удобно связать с прошлым вопросом про состав HTTP-запроса.

---

#### Этап 5. Обработка на сервере
Запрос может пройти через **балансировщик нагрузки**, **CDN**, дойти до **бэкенда**, который сходит в **базу данных / другие микросервисы** (в Озоне — микросервисная архитектура) и соберёт ответ.
Сервер возвращает **HTTP-ответ**:
- **статус-код** (2xx успех, 3xx редирект, 4xx ошибка клиента, 5xx ошибка сервера);
- **заголовки** (`Content-Type`, `Set-Cookie`, `Cache-Control`);
- **тело** — обычно HTML-документ (или JSON для API).

Если пришёл редирект (301/302) — браузер повторяет запрос по новому адресу.

---

#### Этап 6. Получение ответа и начало парсинга
Браузер получает HTML (часто по частям — потоково) и запускает **парсер**, не дожидаясь полной загрузки.

---

#### Этап 7. Рендеринг — как HTML превращается в картинку (Critical Rendering Path)
Это ключевая часть для веб-тестировщика:
1. **Парсинг HTML → DOM** (Document Object Model) — дерево элементов страницы.
2. **Парсинг CSS → CSSOM** (CSS Object Model) — дерево стилей. CSS **блокирует рендеринг**, пока не загружен.
3. **Render Tree** — объединение DOM + CSSOM только из **видимых** элементов (например, `display:none` в дерево не попадает).
4. **Layout (Reflow)** — расчёт **геометрии**: где какой элемент, какого размера, координаты в пикселях.
5. **Paint** — заливка пикселей: цвета, текст, границы, тени.
6. **Compositing** — сборка **слоёв** воедино (часть работы уходит на GPU), после чего кадр выводится на экран.

*На интервью:* «Браузер строит DOM из HTML и CSSOM из CSS, объединяет их в Render Tree, считает layout — геометрию, затем paint — отрисовку, и composite — сборку слоёв».

---

#### Этап 8. Загрузка и влияние ресурсов (CSS, JS, картинки, шрифты)
Параллельно подгружаются внешние ресурсы. Важные нюансы, которые любят спрашивать:
- **CSS** блокирует рендеринг (render-blocking), поэтому его подключают в `<head>`.
- **JS** по умолчанию блокирует парсинг HTML (**parser-blocking**), потому что может менять DOM. Решается атрибутами:
  - `async` — скрипт грузится параллельно и выполняется сразу как загрузится;
  - `defer` — грузится параллельно, но выполняется после полного парсинга HTML, в порядке подключения.
- Картинки и шрифты не блокируют парсинг, но влияют на финальную отрисовку и метрики скорости.

---

#### Этап 9. Выполнение JavaScript и интерактивность
JS-движок исполняет скрипты: навешивает обработчики событий, может делать дополнительные **асинхронные запросы** (**AJAX / fetch / XHR**) и динамически дорисовывать контент (характерно для SPA на React/Vue — там первичный HTML почти пустой, а страницу строит JS уже в браузере).

---

#### Этап 10. Готовность страницы (события загрузки)
- **`DOMContentLoaded`** — HTML распарсен и DOM построен (не ждём картинки).
- **`load`** — загружены все ресурсы (картинки, стили, шрифты).
После этого страница считается полностью отрисованной и готовой к взаимодействию.

---

**Мини-резюме одним абзацем (если нужно ответить кратко):**
Браузер парсит URL, через DNS находит IP сервера, устанавливает TCP- и (для HTTPS) TLS-соединение, отправляет HTTP-запрос, получает от сервера HTML; затем строит DOM и CSSOM, объединяет их в Render Tree, выполняет layout и paint, подгружает и исполняет CSS/JS/ресурсы, после чего страница отрисовывается и по событиям `DOMContentLoaded` / `load` становится готова.

**Почему это важно для AQA:** понимание этой цепочки помогает осознанно ставить **ожидания (waits)** в автотестах — например, дожидаться не просто загрузки DOM, а появления элемента после AJAX-запроса; отличать, почему элемент «есть в DOM, но не виден»; и грамотно диагностировать флаки-тесты, связанные с гонками при рендеринге.

## Часть 3. Итоги и следующий этап

- Интервьюер заполнит отчёт с обратной связью, HR вернётся в ближайшие дни.
- При позитивном фидбеке — **техсобес ~1.5 часа**: задания сложнее, возможно живое кодирование в своей IDE (с подсказками и запуском кода).
- Бэкенд-тестирование будет в меньшей степени; документация по API есть (Swagger/спека).

### Что подтянуть к техническому собесу
- Python углублённо: ООП, коллекции, генераторы, декораторы, исключения, GIL/потоки vs процессы.
- Playwright / Selenium: селекторы, ожидания (waits), Page Object Model, параллельный запуск.
- API-тестирование: `requests`/`httpx`, статус-коды, работа со Swagger, авторизация (токены).
- SQL: `JOIN`, `GROUP BY`, подзапросы, агрегаты.
- Основы CI/CD, Docker, Allure-отчёты.
- Алгоритмы/лайвкодинг: строки, списки, словари, простые задачки на logic.
