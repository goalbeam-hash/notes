# Глава 1. Query-параметры, URL, Origin, SOP и CORS

*Связана с вопросом 23 основного разбора («Как передаём данные через GET? Из чего состоит HTTP-запрос?»).*

## 1.1. Анатомия URL

```text
https://api.example.com:443/v1/users/42?status=active&page=2#section-3
└─┬─┘   └───────┬───────┘└┬┘└────┬────┘└──────────┬─────────┘└───┬───┘
scheme        host       port   path            query        fragment
```

| Компонент | Что это | Нюанс для собеседования |
|---|---|---|
| **Scheme** | Протокол: `https`, `http`, `ws`, `ftp` | Определяет дефолтный порт |
| **Host** | Домен или IP | Поддомен — это **другой origin** |
| **Port** | Порт сервера | Если не указан: 80 для HTTP, 443 для HTTPS |
| **Path** | Путь к ресурсу: `/v1/users/42` | Идентифицирует ресурс (path parameters) |
| **Query string** | Всё после `?`: пары `ключ=значение` через `&` | Фильтры, сортировка, пагинация |
| **Fragment** | Всё после `#` | **На сервер не отправляется никогда** — обрабатывается только браузером (якоря, роутинг SPA) |

### 1.1.1. URL Fragment (`#...`) — подробный разбор

**Fragment** (ещё называют **hash**, **anchor**, **якорь**, **hash-часть URL**) — это всё, что идёт в URL **после символа `#`**. Официальное имя в RFC — **fragment identifier** (идентификатор фрагмента).

```text
https://shop.example.com/catalog?category=phones#product-42
└────────────── path ──────────┘└── query ──┘└ fragment ┘
                                              ↑
                         сервер видит только до сюда (path + query)
                         fragment остаётся в браузере
```

**Примеры fragment:**

- `https://docs.example.com/guide#installation` — прокрутить к заголовку «Installation»
- `https://app.example.com/orders#42` — SPA открывает заказ №42
- `https://oauth.example.com/callback#access_token=eyJ...` — OAuth implicit flow (устаревший): токен в fragment **специально**, чтобы не попал на сервер

---

#### Отправляется ли fragment на сервер?

**Нет, никогда.** Это один из самых частых вопросов на собеседовании — и ответ всегда однозначный.

При HTTP-запросе браузер формирует **request line** только из метода, **path + query** и версии протокола:

```text
GET /catalog?category=phones HTTP/1.1    ← fragment (#product-42) здесь НЕТ
Host: shop.example.com
```

Fragment **не попадает**:

- в HTTP-запрос к серверу;
- в логи веб-сервера, nginx, балансировщика;
- в `Referer` целиком — по политике браузера fragment часто **обрезается** (зависит от `Referrer-Policy`).

Fragment **остаётся**:

- в адресной строке браузера;
- в истории браузера (полный URL с `#...`);
- в закладках;
- в JavaScript: `window.location.hash`, `window.location.href`.

**Почему так устроено.** Изначально fragment задумывался как **ссылка на место внутри уже загруженного документа** (якорь `<a id="installation">`). Сервер отдаёт страницу целиком, браузер сам прокручивает к нужному элементу — серверу знать про `#installation` не нужно.

---

#### Fragment vs Query — чем отличаются

| | Query (`?key=value`) | Fragment (`#value`) |
|---|---|---|
| Разделитель | `?` (первый), далее `&` | `#` |
| Видит сервер | ✅ Да | ❌ Нет |
| Влияет на ответ сервера | Может (фильтры, пагинация) | Нет |
| Логируется на сервере | ✅ Да | ❌ Нет |
| Кэшируется CDN по ключу URL | ✅ Да (вместе с query) | ❌ Fragment не влияет на cache key сервера |
| Меняет без перезагрузки страницы | Обычно нет (новый запрос) | ✅ Да (`hashchange` event) |
| Типичное использование | API-параметры, фильтры | Якоря, SPA-роутинг, OAuth-токены |

---

#### Для чего fragment используют на практике

**1. Якоря в статических страницах (классика HTML).**

```html
<h2 id="installation">Установка</h2>
<a href="#installation">Перейти к установке</a>
```

Браузер прокручивает страницу к элементу с `id="installation"`. Сервер отдал ту же страницу — с fragment или без.

**2. SPA-роутинг (Single Page Application).**

React Router, Vue Router и др. могут использовать **hash-routing**:

```text
https://app.example.com/#/orders/42
https://app.example.com/#/profile/settings
```

Всё после `#` читает **JavaScript на клиенте** — сервер всегда отдаёт один `index.html`. Альтернатива — **History API** (`/orders/42` без `#`), тогда path виден серверу (нужен fallback на index.html на сервере).

**3. OAuth / OpenID — токен в fragment (legacy).**

В implicit flow токен возвращался в URL:

```text
https://app.example.com/callback#access_token=eyJ...&token_type=Bearer
```

Fragment выбран **намеренно**: токен не уходит на сервер приложения через HTTP-запрос (его обрабатывает только JS на клиенте). Сейчас implicit flow **deprecated** — рекомендуют Authorization Code + PKCE, но вопрос на собеседованиях про «почему токен в #, а не в ?» всё ещё встречается.

**4. Состояние UI без запроса на сервер.**

`#tab=settings`, `#modal=payment` — некоторые приложения хранят состояние вкладок/модалок в hash, чтобы можно было поделиться ссылкой без бэкенд-логики.

---

#### Fragment глазами AQA — что проверять в тестах

**Проверка URL с hash в Playwright:**

```typescript
// Переход по ссылке с якорем
await page.click('a[href="#installation"]');
await expect(page).toHaveURL(/#installation/);

// Прямой goto с fragment
await page.goto('/catalog#product-42');
expect(page.url()).toContain('#product-42');

// SPA hash-routing
await page.goto('/#/orders');
await page.click('text=Заказ 42');
await expect(page).toHaveURL(/#\/orders\/42/);
```

**Что важно помнить:**

- `page.goto('https://site.com/page#section')` — сервер получит запрос **без** `#section`; если тест падает «страница не та» — проблема не в fragment, а в path/query.
- Hash-навигация **не вызывает полную перезагрузку** — нужно слушать `hashchange` или ждать конкретный элемент, а не `load`.
- В Network DevTools запросы к API **не содержат** fragment — если тестируете API через `request.get()`, hash в URL бессмысленен.
- OAuth-тесты: если приложение ждёт токен в `#access_token=...`, проверяйте `window.location.hash` через `page.evaluate()` или что приложение корректно его парсит.

**Типовые вопросы и ответы:**

- *«Отправится ли `#...` на сервер?»* — **Нет.** Request line содержит только path и query; fragment обрабатывается исключительно браузером после получения ответа.
- *«Чем fragment отличается от query?»* — Query сервер видит и может менять ответ; fragment — только клиент (прокрутка, JS-роутинг, хранение токена без утечки на сервер).
- *«Виден ли fragment в логах nginx?»* — **Нет.** Виден в истории браузера и в `location.hash`.
- *«Почему OAuth клали токен в fragment?»* — Чтобы access token не попал в server-side логи и Referer; его забирает только клиентский JS.

**Одна фраза для собеседования:** *«Fragment — часть URL после `#`, которую сервер никогда не получает; браузер использует её для якорной прокрутки, SPA-роутинга или передачи данных (например, OAuth-токена) только на клиент.»*

## 1.2. Query-параметры vs path-параметры

- **Path parameters** (`/users/42`) — идентификация конкретного ресурса, часть иерархии. Убрать нельзя — изменится смысл URL.
- **Query parameters** (`?status=active&page=2`) — необязательные уточнения: фильтрация, сортировка, пагинация, поиск. Порядок не важен, любой параметр можно опустить.

**Правило REST-дизайна, которое ждут в ответе:** path — «что за ресурс», query — «как его отдать».

```text
GET /users/42/orders?status=paid&sort=date&limit=20
    └──────┬───────┘ └──────────────┬───────────────┘
      какой ресурс         как его отдать
```

## 1.3. Массивы и повторяющиеся ключи

Единого стандарта нет — хороший ответ, показывающий опыт:

- повторение ключа: `?tag=a&tag=b`;
- скобки (PHP/Rails-стиль): `?tag[]=a&tag[]=b`;
- через запятую: `?tag=a,b`.

Как API парсит дубликаты (`?id=1&id=2` — первое значение, последнее или список?) — зависит от фреймворка и **не стандартизовано**. Это:

1. обязательный тест-кейс при тестировании API;
2. источник уязвимости **HTTP Parameter Pollution** — когда фронтовый валидатор и бэкенд читают разные значения одного параметра.

## 1.4. URL-кодирование (percent-encoding)

В URL разрешён ограниченный набор символов. Всё остальное кодируется как `%XX` — hex-код байта в UTF-8:

- пробел → `%20` (в query исторически ещё `+`);
- `Иван` → `%D0%98%D0%B2%D0%B0%D0%BD`;
- зарезервированные символы внутри **значений** обязательно кодировать: `&` → `%26`, `=` → `%3D`, `?` → `%3F`, `#` → `%23`, `+` → `%2B`.

**Классический баг-кейс:** пользователь ищет строку `black&white`. Если `&` не закодировать, сервер увидит два параметра: `black` и `white=`.

Инструменты:

- JS: `encodeURIComponent()` — для значений; `encodeURI()` — для целого URL (не трогает `&`, `=`, `?`);
- Python: `urllib.parse.quote` / `urlencode`;
- HTTP-клиенты (axios, requests, Playwright `APIRequestContext`) кодируют параметры автоматически, если передавать их объектом `params`, а не конкатенацией строк.

## 1.5. Ограничение длины URL

Стандарт длину не ограничивает, но на практике браузеры и серверы режут примерно на 2000–8000 символах (IE — 2083; у nginx есть лимит на размер строки запроса). Поэтому большие наборы данных передают в теле POST, а не в query.

## 1.6. Безопасность query-параметров

Чувствительные данные (пароли, токены, ПДн) в query передавать **нельзя**, потому что URL:

1. пишется в **логи** серверов, прокси, балансировщиков;
2. сохраняется в **истории браузера**;
3. утекает через заголовок **Referer** при переходе на другой сайт;
4. **кэшируется** (браузером, CDN);
5. виден в аналитике и трекерах.

HTTPS шифрует URL в канале, но не спасает от логов и истории. Правильно: секреты — в заголовках (`Authorization: Bearer ...`) или в теле POST.

## 1.7. Query-параметры и кэширование

URL вместе с query-строкой — это **ключ кэша**: `?page=1` и `?page=2` кэшируются отдельно.

- Приём **cache busting**: добавление `?v=123` к статике, чтобы сбросить кэш после релиза.
- Обратная сторона: случайный/лишний параметр «пробивает» CDN-кэш и создаёт лишнюю нагрузку на origin-сервер.

## 1.8. Что такое origin

**Origin = схема + хост + порт.** Все три компонента должны совпадать:

| URL 1 | URL 2 | Один origin? |
|---|---|---|
| `https://example.com` | `https://example.com/page` | ✅ Да (path не считается) |
| `https://example.com` | `http://example.com` | ❌ Нет (схема) |
| `https://example.com` | `https://api.example.com` | ❌ Нет (поддомен — другой origin) |
| `https://example.com` | `https://example.com:8080` | ❌ Нет (порт) |

## 1.9. Same-Origin Policy (SOP)

Фундаментальный механизм безопасности браузера: **скрипт со страницы одного origin не может читать ответы запросов к другому origin**, а также чужие куки, localStorage и DOM другого окна.

Зачем: без SOP любой сайт в соседней вкладке мог бы JS-ом сходить в ваш интернет-банк с вашими куками и прочитать баланс.

**Нюанс-ловушка:** SOP ограничивает **чтение ответа**, а не отправку запроса — `<img>`, `<form>`, `<script>` с чужого домена работали всегда. Именно поэтому существует CSRF (см. 1.13).

## 1.10. Заголовок Origin

HTTP-заголовок, который **браузер добавляет автоматически** (из JS подменить нельзя) к кросс-доменным запросам и ко всем POST. Содержит только origin страницы-источника:

```text
Origin: https://app.example.com
```

Зачем серверу:

1. **CORS** — по Origin сервер решает, разрешить ли кросс-доменный доступ;
2. **Защита от CSRF** — сервер сверяет Origin с ожидаемым: запрос на перевод денег с `Origin: https://evil.com` отклоняется.

## 1.11. Origin vs Referer vs Host

| Заголовок | Что содержит | Пример |
|---|---|---|
| `Origin` | Только схема+хост+порт источника запроса | `https://app.example.com` |
| `Referer` | Полный URL страницы-источника (с path и query) | `https://app.example.com/orders?id=5` |
| `Host` | Куда идёт запрос (домен из URL запроса) | `api.example.com` |

- Origin приватнее Referer (не светит путь и параметры) и надёжнее для security-решений.
- Referer может отсутствовать или урезаться политикой `Referrer-Policy`.
- `Referer` — официально закреплённая опечатка в спецификации (должно было быть Referrer).

## 1.12. CORS — Cross-Origin Resource Sharing

Механизм, которым сервер **ослабляет** SOP: явно сообщает браузеру, каким чужим origin разрешено читать его ответы.

### Простые запросы

GET/HEAD/POST с обычными заголовками: браузер шлёт запрос сразу, добавляя `Origin`. Сервер отвечает:

```text
Access-Control-Allow-Origin: https://app.example.com
```

- Origin совпал → браузер отдаёт ответ скрипту.
- Заголовка нет / не совпал → браузер **блокирует чтение ответа**.
- **Вопрос-ловушка:** запрос при этом до сервера дошёл и **выполнился** — CORS блокирует только чтение результата.

### Preflight-запросы

Если запрос «непростой» (PUT/PATCH/DELETE, заголовок `Authorization`, `Content-Type: application/json`), браузер сначала сам отправляет **OPTIONS**:

```text
OPTIONS /api/users HTTP/1.1
Origin: https://app.example.com
Access-Control-Request-Method: PUT
Access-Control-Request-Headers: content-type, authorization
```

Сервер отвечает, что разрешено:

```text
Access-Control-Allow-Origin: https://app.example.com
Access-Control-Allow-Methods: GET, POST, PUT, DELETE
Access-Control-Allow-Headers: content-type, authorization
Access-Control-Max-Age: 86400
```

Только после этого браузер шлёт настоящий запрос. `Max-Age` — кэш preflight, чтобы не гонять OPTIONS перед каждым запросом. Отсюда «лишние» OPTIONS во вкладке Network — частый вопрос.

### Куки в кросс-доменных запросах

По умолчанию **не отправляются**. Нужно:

- на клиенте: `fetch(..., { credentials: 'include' })`;
- на сервере: `Access-Control-Allow-Credentials: true`, и тогда `Allow-Origin` **не может быть `*`** — только конкретный origin.

### Ключевые факты для собеседования

1. CORS работает **только в браузере**. curl, Postman, API-тесты (Playwright `APIRequestContext`, Python requests) CORS не проверяют. «В Postman работает, а на фронте CORS error» — это штатное поведение, а не баг бэкенда как такового.
2. CORS — **не защита сервера** от запросов (запрос доходит и выполняется). Это защита **пользователя браузера** от чтения его данных чужими сайтами.
3. Ошибка CORS видна только в консоли браузера; сервер о ней «не знает».

## 1.13. Связка с CSRF

**CSRF (Cross-Site Request Forgery)** — злой сайт заставляет браузер жертвы отправить запрос на доверенный сайт с её куками (например, автосабмит скрытой формы на `bank.com/transfer`). Работает, потому что SOP не запрещает **отправку** кросс-доменных запросов.

Защиты:

1. **CSRF-токены** — уникальный токен в форме/заголовке; злой сайт не может его узнать (как раз из-за SOP);
2. **Проверка Origin/Referer** на сервере;
3. **Куки SameSite:**
   - `SameSite=Lax` — дефолт в современных браузерах: куки не идут с кросс-сайтовыми POST;
   - `SameSite=Strict` — куки не идут ни с какими кросс-сайтовыми запросами;
   - `SameSite=None; Secure` — куки идут везде (для легитимных кросс-доменных сценариев, только по HTTPS).

## 1.14. Смежные вопросы, которые задают в связке

**«Чем query-параметры отличаются от параметров в теле запроса?»**
Query — часть URL: видна, логируется, кэшируется, ограничена по длине; для чтения/фильтрации. Body — полезная нагрузка POST/PUT/PATCH: не светится в URL, без практического лимита; для передачи данных. Формат тела задаёт `Content-Type`:

- `application/json` — JSON;
- `application/x-www-form-urlencoded` — те же пары `key=value`, но в теле;
- `multipart/form-data` — файлы и смешанные данные.

**«Отправится ли fragment (#...) на сервер?»**
**Нет, никогда** — подробный разбор: см. **раздел 1.1.1** (якоря, SPA hash-routing, OAuth-токен в `#`, отличие от query, проверки в Playwright).

**«Можно ли тело у GET-запроса?»**
Спецификация не запрещает, но семантики у него нет; многие серверы и прокси его игнорируют или отбрасывают. На практике не используется; для больших поисковых запросов — POST (или новый метод QUERY, пока в драфтах).

**«Что будет, если два параметра с одним именем?»**
Не стандартизовано: первый, последний или список — зависит от сервера. Тест-кейс + потенциальная уязвимость (HTTP Parameter Pollution).

**«Как в Playwright работать с query-параметрами?»**

```typescript
// API-тесты: params кодируются автоматически
const resp = await request.get('/api/users', {
  params: { status: 'active', page: 2 },
});

// UI-тесты: проверка URL после навигации
await expect(page).toHaveURL(/status=active/);

// Перехват запросов с нужными параметрами
await page.route('**/api/users?*', route => { ... });
```

**«Почему перед моим PUT летит OPTIONS?»**
Это CORS preflight: браузер спрашивает у сервера разрешение на непростой кросс-доменный запрос; сервер отвечает списком разрешённых методов и заголовков; ответ кэшируется на `Access-Control-Max-Age`.

# Глава 2. HTTP-заголовки — исчерпывающий справочник

## 2.1. Что такое заголовки и зачем они нужны

Заголовки — это метаданные запроса и ответа в формате `Имя: значение`, по одному на строку, после стартовой строки и до пустой строки-разделителя. Они управляют всем «вокруг» полезной нагрузки: форматом данных, аутентификацией, кэшированием, соединением, безопасностью.

Свойства, о которых спрашивают:

- имена заголовков **регистронезависимы** (`content-type` = `Content-Type`);
- заголовок может повторяться (например, несколько `Set-Cookie`);
- кастомные заголовки — просто нестандартные имена; исторический префикс `X-` (`X-Request-Id`) официально устарел, но повсеместно жив.

Категории:

| Категория | Где встречается | Примеры |
|---|---|---|
| Заголовки запроса | Только в запросе | `Host`, `Authorization`, `Accept`, `User-Agent`, `Origin`, `Referer` |
| Заголовки ответа | Только в ответе | `Set-Cookie`, `Location`, `Server`, `Access-Control-Allow-Origin` |
| Заголовки представления (entity) | Обе стороны, описывают тело | `Content-Type`, `Content-Length`, `Content-Encoding` |
| Общие | Обе стороны | `Cache-Control`, `Connection`, `Date` |

## 2.2. Важнейшие заголовки запроса

**`Host: api.example.com`** — обязателен с HTTP/1.1. На одном IP живут десятки сайтов (virtual hosting) — сервер по Host понимает, к какому сайту запрос.

**`Content-Type: application/json`** — формат **тела запроса**. Классические значения:

- `application/json` — JSON (API);
- `application/x-www-form-urlencoded` — пары key=value (классические HTML-формы);
- `multipart/form-data; boundary=...` — файлы и смешанные данные;
- `text/plain`, `application/xml` и т.д.

Типовой баг: фронт шлёт JSON без `Content-Type: application/json` — сервер отвечает 400/415, потому что не понимает, как парсить тело.

**`Accept: application/json`** — какой формат **ответа** клиент готов принять (content negotiation). Пара для собеседования: `Content-Type` — «что я тебе шлю», `Accept` — «что я хочу получить».

**`Authorization`** — учётные данные:

- `Authorization: Bearer <JWT/opaque token>` — самый частый вариант в API;
- `Authorization: Basic base64(login:password)` — Base64 — это **кодирование, не шифрование**; без HTTPS равно передаче пароля открытым текстом (типовой вопрос-ловушка).

**`Cookie: session_id=abc; theme=dark`** — все куки, подходящие под домен/путь, браузер прикрепляет автоматически.

**`User-Agent`** — идентификация клиента (браузер, версия, ОС). Используется для аналитики и — плохая практика — для ветвления логики.

**`Origin`, `Referer`** — см. главу 1 (разделы 1.10–1.11).

**`Accept-Encoding: gzip, br`** — какие сжатия клиент понимает; сервер отвечает сжатым телом с `Content-Encoding: gzip`.

**`If-None-Match` / `If-Modified-Since`** — условные запросы для кэш-валидации (см. 2.5).

**`X-Request-Id` / `traceparent`** — сквозной идентификатор запроса для трейсинга по логам микросервисов. Для тестировщика — главный инструмент: упавший E2E-тест → взять request id → найти всю цепочку в ELK/Jaeger.

## 2.3. Важнейшие заголовки ответа

**`Content-Type`** — формат тела ответа (браузер по нему решает: отрендерить HTML, распарсить JSON, скачать файл).

**`Set-Cookie: session=abc; HttpOnly; Secure; SameSite=Lax; Max-Age=3600; Path=/; Domain=example.com`** — установка куки. Атрибуты — любимая тема собеседований:

| Атрибут | Что делает |
|---|---|
| `HttpOnly` | Кука недоступна из JS (`document.cookie`) — защита от кражи через XSS |
| `Secure` | Кука отправляется только по HTTPS |
| `SameSite=Lax/Strict/None` | Отправка в кросс-сайтовых запросах — защита от CSRF (см. 3.7) |
| `Max-Age` / `Expires` | Время жизни; без них — session cookie (до закрытия браузера) |
| `Path`, `Domain` | Область действия куки |

**`Location: /users/42`** — куда идти: в 3xx-редиректах и в `201 Created` (адрес созданного ресурса).

**`Cache-Control`** — правила кэширования (см. 2.5).

**`WWW-Authenticate`** — приходит с 401: какой схемой аутентифицироваться.

**`Retry-After: 30`** — приходит с 429/503: через сколько повторить (важно для тестов на rate limiting).

## 2.4. Security-заголовки (спрашивают на позициях с уклоном в security)

| Заголовок | Защита |
|---|---|
| `Strict-Transport-Security` (HSTS) | Браузер ходит на сайт только по HTTPS заданное время, даже если юзер набрал http:// |
| `Content-Security-Policy` (CSP) | Белый список источников скриптов/стилей/картинок — главная защита от XSS |
| `X-Content-Type-Options: nosniff` | Запрет браузеру «угадывать» тип содержимого вопреки Content-Type |
| `X-Frame-Options: DENY` / CSP `frame-ancestors` | Запрет встраивания сайта в iframe — защита от clickjacking |
| `Referrer-Policy` | Сколько информации уходит в Referer |

## 2.5. Кэширование через заголовки (частый блок вопросов)

**`Cache-Control`** — основной механизм:

- `no-store` — не кэшировать вообще (чувствительные данные);
- `no-cache` — кэшировать можно, но перед использованием **валидировать** у сервера (имя обманчиво — ловушка на собеседовании);
- `max-age=3600` — свежесть в секундах;
- `public` / `private` — можно ли кэшировать общим кэшам (CDN, прокси) или только браузеру.

**Валидация кэша:**

1. Сервер отдаёт ресурс с `ETag: "v42"` (хэш-версия) или `Last-Modified`.
2. Когда кэш устарел, браузер спрашивает: `If-None-Match: "v42"`.
3. Не изменилось → сервер отвечает **`304 Not Modified` без тела** (экономия трафика); изменилось → `200` с новым телом и новым ETag.

## 2.6. Заголовки глазами AQA — как это спрашивают

**«Как проверить заголовки в Playwright?»**

```typescript
// API-тест: заголовки ответа
const resp = await request.get('/api/users');
expect(resp.headers()['content-type']).toContain('application/json');

// Добавить заголовки всем запросам контекста
const context = await browser.newContext({
  extraHTTPHeaders: { Authorization: `Bearer ${token}`, 'X-Test-Run': 'e2e' },
});

// Перехватить и проверить заголовки исходящего запроса
const reqPromise = page.waitForRequest('**/api/orders');
await page.click('#submit');
const req = await reqPromise;
expect(req.headers()['content-type']).toBe('application/json');
```

### 2.6.1. Что здесь происходит под капотом — разбор построчно

Всё выше — не сторонние библиотеки, а **встроенные объекты самого Playwright**. Никаких axios/fetch подключать не нужно.

**`request` — это фикстура типа `APIRequestContext`.** Playwright Test встраивает в каждый тест набор готовых фикстур, которые запрашиваются деструктуризацией в аргументах теста:

```typescript
import { test, expect } from '@playwright/test';

test('пример', async ({ page, context, browser, request }) => {
  //                    └─┬─┘ └──┬───┘ └──┬───┘ └──┬───┘
  //                     Page BrowserContext Browser APIRequestContext
});
```

- `request` — HTTP-клиент, работающий **мимо браузера**: запрос уходит прямо из Node.js-процесса тест-раннера. Поэтому он быстрый, не требует открытой страницы и не подчиняется CORS (браузерных ограничений нет — см. 3.4).
- Методы повторяют HTTP: `request.get(url, options)`, `.post()`, `.put()`, `.patch()`, `.delete()`. В `options` — `params` (query), `headers`, `data` (тело JSON), `form`, `multipart`.
- Возвращают `APIResponse` с методами `status()`, `headers()`, `json()`, `text()`, `ok()`.
- `baseURL` берётся из конфига — поэтому в тестах пишут относительный путь `/api/users`.

```typescript
// typическая связка в API-тесте
const resp = await request.post('/api/users', {
  headers: { Authorization: `Bearer ${token}` },
  data: { name: 'Ivan' },              // сам сериализует и поставит Content-Type: application/json
});
expect(resp.status()).toBe(201);
const body = await resp.json();
```

Свой независимый клиент (вне фикстуры) создаётся фабрикой: `const api = await playwright.request.newContext({ baseURL, extraHTTPHeaders })` — так делают API-клиенты в фикстурах подготовки данных.

**`browser.newContext(options)` — фабрика браузерных контекстов.** Иерархия объектов (та же, что в главе 13):

```text
Browser  ──.newContext()──▶  BrowserContext  ──.newPage()──▶  Page
(процесс браузера)           (изолированная сессия)           (вкладка)
```

`newContext()` создаёт «чистый профиль инкогнито» за миллисекунды: свои cookies, storage, кэш. Всё поведение сессии задаётся **опциями при создании**:

```typescript
const context = await browser.newContext({
  extraHTTPHeaders: { 'X-Test-Run': 'e2e' },   // заголовки ко ВСЕМ запросам контекста
  storageState: '.auth/user.json',             // готовая сессия (глава 11)
  baseURL: 'https://stage.example.com',
  viewport: { width: 390, height: 844 },       // или ...devices['iPhone 15']
  locale: 'ru-RU',
  ignoreHTTPSErrors: true,                     // самоподписанные сертификаты стенда
});
const page = await context.newPage();
```

Важная деталь: в обычных тестах `browser.newContext()` руками почти не вызывают — Playwright Test сам создаёт свежий контекст на каждый тест (отсюда изоляция), а опции задаются декларативно в `use` конфига или через `test.use({...})` в файле. Руками контексты создают в особых случаях: второй пользователь в одном тесте (глава 13), нестандартные опции для одного теста.

**`page.waitForRequest(pattern)` — подписка на событие сети.** Page эмитит события `request` / `response` для всего трафика страницы; `waitForRequest` / `waitForResponse` возвращают промис, который резолвится первым совпавшим запросом. Паттерн — glob/регулярка/предикат, как у `route`. Ключевой паттерн использования — **подписаться до действия** (иначе гонка: запрос улетит раньше подписки), поэтому промис сохраняется в переменную без `await`, а `await` ставится после клика.

Сводка «кто есть кто» одним взглядом:

| Объект | Что это | Откуда берётся | Типовое применение |
|---|---|---|---|
| `browser` | Инстанс браузера | Фикстура | Руками нужен редко — создать особый контекст |
| `context` | Изолированная сессия | Фикстура (свежий на тест) | Куки, storageState, `context.route`, второй пользователь |
| `page` | Вкладка | Фикстура | Основные UI-действия, `page.route`, `waitForRequest` |
| `request` | HTTP-клиент вне браузера | Фикстура | API-тесты, подготовка данных, проверка заголовков/статусов |

**«Что проверить в API-тесте кроме тела?»** — статус-код, `Content-Type`, критичные бизнес-заголовки (`Location` у 201, `Retry-After` у 429), время ответа, схему тела.

# Глава 3. CORS и CSRF — углублённо

*База — в главе 1 (разделы 1.8–1.13). Здесь — полная механика, edge-кейсы и вопросы «на подумать».*

## 3.1. CORS: полный список заголовков

**Запрос (ставит браузер, руками не подменить):**

| Заголовок | Когда | Содержимое |
|---|---|---|
| `Origin` | Все кросс-доменные запросы и POST | Схема+хост+порт источника |
| `Access-Control-Request-Method` | Только в preflight | Метод будущего запроса |
| `Access-Control-Request-Headers` | Только в preflight | Нестандартные заголовки будущего запроса |

**Ответ (ставит сервер):**

| Заголовок | Что разрешает |
|---|---|
| `Access-Control-Allow-Origin` | Конкретный origin или `*` (нельзя `*` вместе с credentials) |
| `Access-Control-Allow-Methods` | Методы (для preflight) |
| `Access-Control-Allow-Headers` | Заголовки, которые клиент может слать |
| `Access-Control-Allow-Credentials: true` | Разрешить куки/HTTP-авторизацию |
| `Access-Control-Expose-Headers` | Какие заголовки ответа JS сможет **прочитать** (по умолчанию видны только простые: Content-Type, Cache-Control и ещё несколько) |
| `Access-Control-Max-Age` | Сколько секунд кэшировать preflight |

`Access-Control-Expose-Headers` — редко кто называет, а это готовый плюс в оценку: без него JS не прочитает, например, кастомный `X-Total-Count` из ответа, даже если CORS «настроен».

## 3.2. Критерии «простого» запроса (когда preflight НЕ летит)

Все условия одновременно:

1. Метод — только `GET`, `HEAD` или `POST`;
2. Заголовки — только автоматические плюс `Accept`, `Accept-Language`, `Content-Language`, `Content-Type`;
3. `Content-Type` — только `text/plain`, `application/x-www-form-urlencoded` или `multipart/form-data`.

Следствия-ловушки:

- `POST` с `Content-Type: application/json` — **непростой** → preflight;
- добавили `Authorization` — непростой → preflight;
- обычная HTML-форма (`x-www-form-urlencoded`) — простая → preflight не летит → **CORS не защищает от CSRF через формы** (мостик к 3.5).

## 3.3. Типовые CORS-ошибки и их причины

| Ошибка в консоли | Причина |
|---|---|
| `No 'Access-Control-Allow-Origin' header is present` | Сервер вообще не настроил CORS (или упал и отдал ошибку без CORS-заголовков — частный случай: «CORS-ошибка» маскирует 500) |
| `The value of the header ... does not match` | Origin не в белом списке сервера |
| `Response to preflight request doesn't pass` | OPTIONS не обработан (роутер не знает OPTIONS, или auth-middleware требует токен даже для preflight) |
| `... when the request's credentials mode is 'include'` | `Allow-Origin: *` вместе с куками — запрещённая комбинация |

Практический совет для дебага: смотреть в Network не только сам запрос, но и **OPTIONS перед ним** — чаще всего ломается именно он.

## 3.4. CORS и тестирование — вопросы с подвохом

**«Нужно ли тестировать CORS API-тестами?»** — Прямо — нельзя: API-клиенты CORS не проверяют. Но можно проверить **конфигурацию сервера**: отправить запрос с заголовком `Origin: https://evil.com` и проверить, что в ответе нет `Access-Control-Allow-Origin: https://evil.com` (и тем более не отражается любой присланный origin — распространённая мисконфигурация «reflected origin»).

**«Тест в Playwright падает с CORS, а руками работает. Почему?»** — Частые причины: тест ходит на другой стенд/порт (другой origin), чем сконфигурирован фронт; или мок через `page.route` отдаёт ответ без CORS-заголовков для кросс-доменного запроса.

## 3.5. CSRF: анатомия атаки по шагам

1. Жертва залогинена на `bank.com` — в браузере живёт сессионная кука.
2. Жертва открывает `evil.com`, где лежит:

```html
<form action="https://bank.com/transfer" method="POST" id="f">
  <input type="hidden" name="to" value="attacker" />
  <input type="hidden" name="amount" value="100000" />
</form>
<script>document.getElementById('f').submit();</script>
```

3. Браузер отправляет POST на `bank.com` **и прикладывает куки** (так работают куки — по домену назначения).
4. Сервер видит валидную сессию и выполняет перевод.

Ключевая суть: **атакующий не крадёт куку и не читает ответ — он лишь заставляет браузер жертвы выполнить действие.** Поэтому CSRF работает только против кук/basic-auth (автоматически прикладываемых кред), и **не работает против `Authorization: Bearer`** — токен из localStorage чужой сайт приложить не может. Это главный вопрос-развилка: «если аутентификация по JWT в заголовке — актуален ли CSRF?» — нет (зато актуален XSS, который может украсть токен из localStorage; куки с HttpOnly от кражи защищены — симметрия, которую любят спрашивать).

## 3.6. Защиты от CSRF — подробно

**1. Synchronizer token (классические CSRF-токены).** Сервер генерирует случайный токен, привязанный к сессии, вкладывает в форму/страницу. Каждый мутирующий запрос должен вернуть токен (поле формы или заголовок `X-CSRF-Token`). Злой сайт токен узнать не может — SOP не даст прочитать чужую страницу.

**2. Double submit cookie.** Токен кладётся в куку и дублируется в заголовке; сервер сверяет — чужой сайт куку прочитать и продублировать не может.

**3. Проверка `Origin`/`Referer`** — дёшево и сердито, работает потому, что эти заголовки браузер ставит сам.

**4. `SameSite` куки** (основная современная защита):

- `Lax` (дефолт в Chrome с 2020) — кука идёт в кросс-сайтовых **top-level GET-переходах** (клик по ссылке), но не идёт с POST/iframe/fetch;
- `Strict` — не идёт ни с какими кросс-сайтовыми запросами (побочный эффект: перешёл по ссылке на сайт — оказался разлогинен в первом запросе);
- `None; Secure` — идёт всегда, только по HTTPS (нужно для встраиваемых виджетов, SSO).

**Как AQA тестирует CSRF-защиту:** отправить мутирующий запрос без токена / с чужим токеном / с валидной кукой, но «чужим» Origin — ожидаем 403; проверить атрибуты сессионной куки (`HttpOnly`, `Secure`, `SameSite`) в DevTools или через `context.cookies()` в Playwright.

## 3.7. CORS vs CSRF — сравнение одним блоком (просят почти всегда)

| | CORS | CSRF |
|---|---|---|
| Что это | Механизм **разрешения** кросс-доменного чтения | **Атака** подделкой кросс-сайтового запроса |
| Кто защищается | Пользователь: чужой сайт не прочитает его данные | Сервер/пользователь: чужой сайт не выполнит действие от его имени |
| Что контролирует | **Чтение ответа** | **Выполнение запроса** |
| Связь | CORS **не защищает** от CSRF: простые запросы и формы уходят без preflight; защита от CSRF — токены и SameSite | |

# Глава 4. Kafka и брокеры сообщений *(вопросы 14, 16–18 основного разбора)*

## 4.1. Зачем вообще брокер сообщений

Проблема: микросервис A должен сообщить о событии сервисам B, C, D. Прямые HTTP-вызовы дают жёсткую связность: B упал — A должен ретраить, появился E — переписываем A.

Решение — **асинхронный обмен через брокера**: A публикует событие «платёж создан» и забывает; заинтересованные сервисы читают в своём темпе. Получаем: слабую связность, устойчивость к падению потребителей, сглаживание пиков нагрузки (буфер), возможность добавлять потребителей без изменения продюсера.

## 4.2. Архитектура Kafka: словарь терминов

```text
Producer ──▶ Topic "payments"                        Consumer Group "fraud"
             ├── Partition 0: [m0][m1][m2][m3] ◀──── consumer A (партиции 0,1)
             ├── Partition 1: [m0][m1][m2]     ◀──── 
             └── Partition 2: [m0][m1]         ◀──── consumer B (партиция 2)
                       ▲ offset — позиция чтения      Consumer Group "notifications"
                                                       ◀──── читает те же партиции независимо
```

- **Broker** — сервер Kafka; кластер = несколько брокеров.
- **Topic** — именованный поток событий («payments», «user-registrations»).
- **Partition** — топик разбит на партиции: упорядоченные **append-only журналы**. Порядок сообщений гарантируется **только внутри партиции**, не по топику в целом.
- **Ключ сообщения** определяет партицию (hash(key) % N). Одинаковый ключ → одна партиция → строгий порядок событий одной сущности. Пример: все события `client_id=42` идут в одну партицию — «пополнение» никогда не обгонит «открытие счёта».
- **Offset** — порядковый номер сообщения в партиции; позиция чтения консюмера.
- **Retention** — сообщения **не удаляются после прочтения**, хранятся заданное время/объём (например, 7 дней). Kafka — это лог, а не очередь.
- **Replication** — каждая партиция реплицируется на несколько брокеров (лидер + фолловеры); при падении брокера лидерство переезжает.

## 4.3. Producer: как пишутся сообщения

Продюсер отправляет `(key, value)` в топик; сам решает партицию (по ключу или round-robin, если ключа нет). Уровень надёжности — параметр `acks`:

- `acks=0` — «выстрелил и забыл» (можно потерять);
- `acks=1` — подтвердил лидер партиции;
- `acks=all` — подтвердили все синхронные реплики (максимальная надёжность).

## 4.4. Consumer: pull-модель (вопрос 17 — где кандидат ошибся)

Kafka — **pull**: консюмер сам, в цикле, вызывает `poll()` — «дай мне сообщения из моих партиций начиная с моего offset». Прочитал пачку → обработал → **закоммитил offset** (запомнил позицию).

Почему pull, а не push:

1. консюмер сам управляет темпом — брокер не завалит медленного потребителя (естественный backpressure);
2. эффективные батчи — забирать пачками выгоднее;
3. перечитывание истории — offset под контролем консюмера: сдвинул назад и переобработал (реплей после бага, прогрев нового сервиса).

Чтобы pull не превращался в пустой опрос, `poll` работает как long polling — ждёт данных до таймаута.

## 4.5. Consumer Group: масштабирование чтения (вопрос 18)

**Consumer group** — консюмеры с общим `group.id`, совместно читающие топик:

- **внутри группы** каждая партиция назначена ровно одному консюмеру → сообщение обрабатывается группой один раз → распределение нагрузки: 6 партиций и 3 консюмера — по 2 партиции каждому;
- **между группами** — независимость: каждая группа получает весь поток со своими offset'ами. Топик `payments` целиком читают и группа `fraud-detection`, и группа `notifications`;
- **rebalance** — консюмер упал/добавился → партиции перераспределяются между живыми. Даёт отказоустойчивость, но на время ребаланса группа приостанавливает чтение (источник продовых инцидентов);
- консюмеров больше, чем партиций → лишние простаивают. **Число партиций = потолок параллелизма чтения.**

Одной фразой для собеседования: *«Consumer — один читатель; consumer group — механизм горизонтального масштабирования и отказоустойчивости: партиции топика делятся между членами группы, каждая группа видит весь поток независимо от других».*

## 4.6. Семантики доставки (вопрос со звёздочкой)

- **At-most-once** — коммит offset до обработки: упал после коммита — сообщение потеряно;
- **At-least-once** — коммит после обработки (типовой вариант): упал между обработкой и коммитом — после рестарта сообщение придёт **повторно**;
- **Exactly-once** — транзакции Kafka + идемпотентный продюсер; дорого и сложно.

Практический вывод, который ждут: **консюмер должен быть идемпотентным** — повторная обработка того же события не должна дублировать эффект (см. идемпотентность в главе 6 — темы связаны).

## 4.7. Kafka vs RabbitMQ (вопрос 14)

| | Kafka | RabbitMQ |
|---|---|---|
| Модель | Распределённый **лог** | Классическая **очередь** |
| Доставка | **Pull** — консюмер опрашивает | **Push** — брокер заталкивает |
| После прочтения | Сообщение остаётся (retention), можно перечитать | Сообщение удаляется после ack |
| Маршрутизация | Простая: топик → партиции по ключу | Богатая: exchanges (direct, topic, fanout, headers) |
| Порядок | Внутри партиции | Внутри очереди |
| Сильные стороны | Стриминг событий, огромный throughput, много независимых групп читателей, реплей | Очереди задач, RPC, сложный роутинг, приоритеты, TTL, dead-letter |

## 4.8. Kafka глазами AQA — что реально спрашивают у тестировщика

**«Как ты тестируешь функциональность с Kafka?»**

1. **Тест через событие:** тест выполняет действие (UI/API) → проверяет, что в топик прилетело событие с правильной схемой и полями. Технически: тестовый консюмер в фикстуре (kafkajs для TS, confluent-kafka для Python) подписывается на топик и ждёт сообщение с нужным ключом.
2. **Тест от события:** тест сам публикует событие в топик → проверяет реакцию системы (изменился статус, пришла нотификация, перерисовался UI).
3. **Eventual consistency:** после события состояние обновляется **не мгновенно** — в тестах нельзя делать `sleep(5)`, нужен **polling с таймаутом**: `expect.poll(() => getStatus(id)).toBe('processed')` в Playwright.
4. Изоляция: уникальные ключи/сущности на тест, чтобы параллельные тесты не ловили чужие события.

**«Сообщение в топике есть, а сервис его "не видит". Куда смотреть?»** — консюмер жив? group.id тот? offset не укатился вперёд (auto.offset.reset)? не залип rebalance? ошибка десериализации (сообщение уходит в DLQ/лог)?

# Глава 5. Клиент-серверное взаимодействие, REST и статус-коды *(вопросы 19, 23)*

## 5.0. Зачем нужен каждый заголовок — ответ для собеседования

Когда на собеседовании просят «назови заголовки и зачем они», ждут не перечисление имён, а связку **заголовок → проблему, которую он решает**. Шпаргалка по каждому (детальный справочник — в главе 2):

**В запросе:**

| Заголовок | Зачем нужен — формулировка для ответа |
|---|---|
| `Host` | На одном IP живут десятки сайтов — сервер по Host понимает, к какому из них запрос. Без него виртуальный хостинг невозможен, поэтому он обязателен с HTTP/1.1 |
| `Content-Type` | Говорит серверу, **как парсить тело запроса**: JSON, форма, файл. Без него сервер получает байты и не знает, что с ними делать → 400/415 |
| `Accept` | Обратная сторона: **в каком формате клиент хочет ответ** (content negotiation). Один эндпоинт может отдавать и JSON, и XML — Accept выбирает |
| `Authorization` | **Кто делает запрос**: токен (`Bearer`) или логин-пароль (`Basic`). HTTP stateless — сервер не помнит клиента, поэтому подтверждать личность нужно в каждом запросе |
| `Cookie` | Второй способ решить ту же проблему stateless: браузер сам прикладывает сессионные куки, сервер по ним восстанавливает «кто это» |
| `User-Agent` | Идентификация клиента (браузер/версия/ОС) — для аналитики, статистики, редко — адаптации ответа |
| `Origin` | Откуда (схема+хост+порт) пришёл запрос — сервер по нему принимает CORS-решения и отсекает CSRF |
| `Referer` | Полный URL страницы-источника — аналитика переходов, антифрод |
| `Accept-Encoding` | Какое сжатие клиент умеет распаковать (gzip, br) — экономия трафика |
| `If-None-Match` / `If-Modified-Since` | Условные запросы: «отдай, только если изменилось» — экономия трафика через кэш-валидацию (ответ 304 без тела) |
| `X-Request-Id` | Сквозной идентификатор для трейсинга запроса по логам всех микросервисов — главный друг тестировщика при разборе падений |

**В ответе:**

| Заголовок | Зачем нужен |
|---|---|
| `Content-Type` | Как клиенту интерпретировать тело ответа: отрендерить HTML, распарсить JSON, скачать файл |
| `Set-Cookie` | Установить клиенту куку (сессия после логина) с атрибутами безопасности: `HttpOnly`, `Secure`, `SameSite` |
| `Location` | Куда идти дальше: адрес при редиректе 3xx или URL созданного ресурса при 201 |
| `Cache-Control` / `ETag` | Правила кэширования: что можно кэшировать, на сколько, как проверять свежесть |
| `Access-Control-Allow-*` | CORS: каким чужим origin разрешено читать этот ответ |
| `WWW-Authenticate` | Приходит с 401 — подсказывает, какой схемой аутентифицироваться |
| `Retry-After` | Приходит с 429/503 — через сколько секунд можно повторить запрос |

Короткая версия ответа, если просят «в двух словах»: *«Заголовки — это метаданные, которые решают всё вокруг полезной нагрузки: формат тела (`Content-Type`/`Accept`), личность клиента (`Authorization`/`Cookie`) — потому что HTTP stateless, маршрутизацию (`Host`), кэширование (`Cache-Control`/`ETag`), безопасность кросс-доменных запросов (`Origin` + CORS-заголовки) и служебную диагностику (`X-Request-Id`)».*

## 5.1. Полный жизненный цикл HTTP-запроса

Что происходит от «нажал Enter» до отрисовки — классика собеседований:

1. **DNS-резолв:** имя `api.example.com` → IP (кэш браузера → ОС → DNS-сервер).
2. **TCP-соединение:** three-way handshake (SYN → SYN-ACK → ACK).
3. **TLS handshake** (для HTTPS): проверка сертификата, согласование ключей (подробно — 6.5).
4. **HTTP-запрос:** стартовая строка + заголовки + [тело].
5. **Обработка на сервере:** балансировщик → роутинг → middleware (auth, rate limit) → контроллер → БД/другие сервисы.
6. **HTTP-ответ:** статус-код + заголовки + [тело].
7. Соединение переиспользуется (keep-alive); в HTTP/2 — много параллельных потоков в одном соединении.

**HTTP — stateless:** сервер не помнит клиента между запросами. Состояние переносится клиентом: кука с session id или токен в `Authorization`.

## 5.2. Структура запроса и ответа (шпаргалка к вопросу 23)

```text
POST /api/users?notify=true HTTP/1.1        ← request line: метод + URI + версия
Host: api.example.com                        ← headers
Content-Type: application/json
Authorization: Bearer eyJhbG...
                                             ← пустая строка-разделитель
{"name": "Ivan", "role": "admin"}            ← body

HTTP/1.1 201 Created                         ← status line: версия + код + фраза
Location: /api/users/42
Content-Type: application/json

{"id": 42, "name": "Ivan"}
```

## 5.3. Статус-коды: что обязан знать AQA

**Группы:** 1xx — информационные; 2xx — успех; 3xx — редиректы; 4xx — ошибка клиента; 5xx — ошибка сервера.

| Код | Смысл | Нюанс для собеседования |
|---|---|---|
| 200 OK | Успех | |
| 201 Created | Создано | Обычно + `Location` нового ресурса |
| 204 No Content | Успех без тела | Типично для DELETE |
| 301 / 302 | Постоянный / временный редирект | 301 кэшируется браузером |
| 304 Not Modified | Ресурс не менялся | Ответ на условный запрос, без тела (см. 2.5) |
| 400 Bad Request | Невалидный запрос | Сломанный JSON, неверные параметры |
| **401 Unauthorized** | **Не аутентифицирован** («кто ты?») | Имя обманчиво — код про аутентификацию |
| **403 Forbidden** | **Не авторизован** («тебе нельзя») | Аутентифицирован, но прав нет. Пара 401/403 — топ-вопрос |
| 404 Not Found | Ресурса нет | Иногда отдают вместо 403, чтобы не раскрывать существование ресурса |
| 405 Method Not Allowed | Метод не поддерживается | POST на read-only эндпоинт |
| 409 Conflict | Конфликт состояния | Дубль уникального значения, optimistic locking |
| 415 Unsupported Media Type | Неподдерживаемый Content-Type | |
| 422 Unprocessable Entity | Синтаксис ок, семантика — нет | Валидация бизнес-правил |
| **429 Too Many Requests** | Rate limit | + `Retry-After`; всплывает в нагрузочном и в параллельных автотестах |
| 500 Internal Server Error | Необработанное исключение | |
| 502 Bad Gateway | Прокси получил мусор от апстрима | Бэкенд за nginx упал |
| 503 Service Unavailable | Сервис перегружен/на обслуживании | |
| 504 Gateway Timeout | Апстрим не ответил вовремя | Частый спутник нагрузочных тестов |

## 5.4. REST: принципы, а не только методы

REST — архитектурный стиль. Признаки RESTful API, которые стоит назвать:

1. **Ресурсы в URL, действия в методах:** `GET /orders/42`, а не `POST /getOrder`;
2. **Единообразный интерфейс:** предсказуемая семантика методов (GET читает, POST создаёт, PUT заменяет, PATCH изменяет, DELETE удаляет);
3. **Stateless:** каждый запрос самодостаточен;
4. **Кэшируемость** ответов, где уместно;
5. Правильные статус-коды, версионирование (`/v1/...`).

**PUT vs PATCH (любимое уточнение):** PUT — полная замена ресурса (шлёшь весь объект; пропустил поле — оно затрётся), PATCH — частичное изменение (шлёшь только изменяемые поля).

## 5.5. Что проверяет API-тест — чек-лист

1. Статус-код; 2. Схема ответа (контракт: типы, обязательные поля — Zod/pydantic); 3. Значения бизнес-полей; 4. Заголовки (Content-Type, Location); 5. Негативные кейсы: невалидное тело → 400/422, без токена → 401, чужой ресурс → 403/404, неверный метод → 405; 6. Идемпотентность повторного запроса; 7. Побочные эффекты (запись реально создана — проверка GET-ом или в БД).

# Глава 6. Идемпотентность, safe-методы, HTTP vs HTTPS *(вопросы 20–22)*

## 6.1. Два независимых свойства методов

- **Safe (безопасный)** — метод **не изменяет** состояние сервера (только чтение).
- **Идемпотентный** — N одинаковых запросов приводят сервер **в то же состояние**, что и один (повтор не меняет результат).

Всякий safe — идемпотентен; обратное неверно (DELETE идемпотентен, но не safe).

| Метод | Safe | Идемпотентный | Пояснение |
|---|---|---|---|
| GET, HEAD, OPTIONS | ✅ | ✅ | Только чтение |
| PUT | ❌ | ✅ | Полная замена: сколько ни повторяй — итог тот же |
| DELETE | ❌ | ✅ | Ресурс удалён; повтор состояние не меняет (ответ может стать 404 — идемпотентность про **состояние**, не про код ответа) |
| POST | ❌ | ❌ | Каждый вызов создаёт новую сущность |
| PATCH | ❌ | ❌ (не гарантированно) | Патч может быть относительным («добавить элемент», «+10») — повтор изменит результат |

## 6.2. Зачем это на практике (то, что отличает мидла)

**Ретраи.** Сеть моргнула, ответ не дошёл — можно ли повторить запрос? Идемпотентный — безопасно (браузеры, прокси и HTTP-клиенты автоматически ретраят только их). POST повторять опасно — дубль платежа.

**Idempotency keys.** Как делают POST безопасным для ретраев: клиент шлёт `Idempotency-Key: <uuid>`; сервер хранит результат первого запроса с этим ключом и на повтор возвращает его же, не создавая дубль. Стандарт в платёжных API (Stripe и т.п.). Отличный тест-кейс: двойной POST с одним ключом → одна сущность.

**Автотесты.** Идемпотентность нужна и самим тестам: перезапуск упавшего теста не должен ломаться об данные, созданные первой попыткой.

## 6.3. Safe GET и передача данных (вопрос 22 — полный ответ)

GET — safe по спецификации: только чтение. Но передавать в нём секреты нельзя — параметры URL оседают в логах, истории, Referer, кэшах (подробно — 1.6). Если разработчик сделал изменение данных по GET — это нарушение семантики и реальный баг: поисковый краулер или prefetch браузера, проходя по ссылкам, «понажимает» действия.

## 6.4. HTTP vs HTTPS (вопрос 21 — развёрнуто)

HTTPS = HTTP поверх **TLS**. TLS даёт три гарантии:

1. **Конфиденциальность** — трафик зашифрован (пароли и токены не идут открытым текстом);
2. **Целостность** — данные нельзя незаметно изменить по пути;
3. **Аутентификация сервера** — сертификат подтверждает, что мы говорим с настоящим сервером (защита от man-in-the-middle).

## 6.5. TLS handshake на пальцах

1. Клиент: «привет, поддерживаю такие-то версии TLS и шифры» (ClientHello).
2. Сервер: выбирает шифры, отдаёт **сертификат** (публичный ключ + подпись центра сертификации).
3. Клиент **проверяет сертификат**: подписан доверенным CA (цепочка до корневого в хранилище ОС/браузера)? домен совпадает? срок не истёк?
4. Обмен ключами (асимметричная криптография) → обе стороны получают общий **сессионный ключ**.
5. Дальше весь трафик шифруется **симметрично** сессионным ключом (быстро).

Асимметричная криптография — только для рукопожатия, симметричная — для данных: это «почему так» ждут в хорошем ответе. Версии: актуальны TLS 1.2 и 1.3; SSL и TLS 1.0/1.1 — deprecated. Порты: HTTP — 80, HTTPS — 443.

**След в автотестах:** самоподписанные сертификаты тестовых стендов → ошибка проверки → флаг `ignoreHTTPSErrors: true` в Playwright (и понимание, почему в проде так нельзя).

# Глава 7. Мокирование: теория и Playwright *(вопросы 15, 24)*

## 7.1. Словарь тестовых двойников (test doubles)

| Термин | Что делает |
|---|---|
| **Stub (заглушка)** | Возвращает заранее заданные данные. Пассивен |
| **Mock** | Стаб + **проверка взаимодействия**: с какими аргументами и сколько раз вызван |
| **Fake** | Упрощённая рабочая реализация (in-memory БД вместо PostgreSQL) |
| **Spy** | Пропускает вызов в реальную реализацию, но записывает факты вызовов |
| **Dummy** | Объект-пустышка для заполнения обязательного параметра |

В разговорной речи всё называют «моками» — на собеседовании различие stub/mock стоит проговорить: *стаб отвечает на вопрос «что вернуть», мок — «как меня вызвали»*.

## 7.2. Зачем мокировать — и зачем НЕ мокировать

**За:** изоляция от нестабильных/платных/недоступных внешних сервисов; воспроизведение труднодостижимых состояний (500-е, таймауты, пустые списки, миллионные значения); скорость; детерминированность.

**Против (важно сказать!):** замокали всё — перестали тестировать реальную интеграцию. E2E-тест с замоканным бэкендом — уже не E2E. Баланс: критические пути — на реальной интеграции, edge-кейсы и ошибки — на моках.

## 7.3. `page.route()` — полный арсенал

```typescript
// 1. Замокать ответ: запрос до сервера НЕ дойдёт
await page.route('**/api/operations*', route =>
  route.fulfill({
    status: 200,
    contentType: 'application/json',
    body: JSON.stringify({ items: [], total: 0 }),   // кейс «пустой список»
  }),
);

// 2. Симулировать ошибку сервера — главный use case моков в UI-тестах
await page.route('**/api/payment', route =>
  route.fulfill({ status: 500, body: JSON.stringify({ error: 'Internal' }) }),
);
// → проверяем, что UI показал человеческое сообщение, а не белый экран

// 3. Симулировать сетевой сбой
await page.route('**/api/**', route => route.abort('failed'));

// 4. Пропустить, изменив запрос (подмена заголовка/тела)
await page.route('**/api/**', route =>
  route.continue({ headers: { ...route.request().headers(), 'X-Debug': '1' } }),
);

// 5. Подсмотреть реальный ответ и подменить его часть
await page.route('**/api/user', async route => {
  const response = await route.fetch();               // реальный запрос
  const json = await response.json();
  json.balance = 999999999;                           // кейс «огромный баланс»
  await route.fulfill({ response, json });
});
```

Дополнительно: `context.route()` — на весь контекст сразу; `page.unroute()` — снять перехват; порядок — последний зарегистрированный обработчик срабатывает первым, `route.fallback()` передаёт следующему.

**Как работает `context.route()`.** API идентичен `page.route()`, но перехват вешается на **весь BrowserContext**: под него попадают запросы всех страниц контекста — уже открытых и тех, что откроются позже (новые вкладки, попапы). `page.route()` же действует только на одну конкретную вкладку.

```typescript
// Перехват на уровне контекста: действует на ВСЕ страницы
const context = await browser.newContext();
await context.route('**/api/feature-flags', route =>
  route.fulfill({ json: { darkMode: true, newCheckout: false } }),
);
await context.route('**/*.{png,jpg,woff2}', route => route.abort()); // ускорение: режем статику

const page = await context.newPage();      // уже под перехватом
const popup = await context.newPage();     // и эта тоже — ничего вешать заново не надо

// Приоритет: роуты страницы проверяются раньше роутов контекста —
// на конкретной вкладке можно точечно переопределить общий мок
await page.route('**/api/feature-flags', route =>
  route.fulfill({ json: { darkMode: false } }),
);
```

Когда что выбирать:

- **`context.route()`** — сквозные вещи на весь тест или весь проект: фичефлаги, блокировка аналитики/рекламы/тяжёлой статики, общий мок нестабильного сервиса. Удобно вешать в фикстуре контекста — тогда мок автоматически действует во всех тестах;
- **`page.route()`** — точечный мок под конкретный шаг конкретного теста (симулировать 500 именно при оплате);
- в multi-page сценариях (попап оплаты, вторая вкладка) `context.route()` обязателен: попап — новая page, и её запросы `page.route()` родительской вкладки не перехватит;
- снятие — симметрично: `context.unroute()` / `page.unroute()`.

### 7.3.1. Как устроен `page.route()` — синтаксис и принцип работы

**Сигнатура:**

```typescript
await page.route(urlPattern, handler);
//               └────┬────┘ └───┬──┘
//     что перехватываем    что с этим делать
```

**Первый аргумент — паттерн URL**, три варианта:

```typescript
await page.route('**/api/users', handler);          // glob-строка: ** — любое число сегментов, * — один
await page.route(/\/api\/users\/\d+$/, handler);    // регулярное выражение
await page.route(url => url.pathname.startsWith('/api/'), handler);  // функция-предикат
```

**Второй аргумент — обработчик**, получает два параметра:

- **`route`** — «пульт управления» перехваченным запросом. Именно у него вызывается ровно **один** из методов-решений: `fulfill` / `abort` / `continue` / `fallback` / `fetch`+`fulfill`;
- **`request`** — объект запроса только для чтения: `request.url()`, `request.method()`, `request.headers()`, `request.postDataJSON()`.

**Принцип работы:** Playwright встраивается между браузером и сетью. Когда страница отправляет запрос, подходящий под паттерн, запрос **замораживается** и управление передаётся вашему обработчику. Пока вы не вызовете один из методов `route`, запрос никуда не уходит — вы становитесь «сервером» для этого запроса.

```text
Страница ──запрос──▶ [перехват page.route] ──┬── route.fulfill()  → ответ из теста, сервер не участвует
                                             ├── route.abort()    → сетевой сбой для страницы
                                             ├── route.continue() → запрос идёт дальше (можно изменив)
                                             └── route.fetch() + fulfill() → сходить на сервер, подменить часть ответа
```

**Три правила, которые надо проговорить:**

1. **Регистрировать до действия.** Перехват ставится **до** `page.goto()` / клика, который порождает запрос — иначе запрос успеет уйти на реальный сервер.
2. **Одно решение на запрос.** В обработчике вызывается ровно один метод `route`; не вызвать ничего = запрос зависнет до таймаута.
3. **Мок живёт на уровне страницы/контекста** до `unroute()` или конца теста — он перехватит и повторные запросы под тот же паттерн.

### 7.3.2. `route.fulfill()` — синтаксис ответа

`fulfill` собирает HTTP-ответ, который получит страница, — вы описываете его теми же частями, из которых состоит настоящий ответ (глава 5.2):

```typescript
await route.fulfill({
  status: 200,                                  // статус-код (по умолчанию 200)
  contentType: 'application/json',              // шорткат для заголовка Content-Type
  headers: { 'X-Total-Count': '0' },            // остальные заголовки ответа
  body: JSON.stringify({ items: [] }),          // тело: строка или Buffer
  // json: { items: [] },                       // альтернатива body — сам сериализует и поставит Content-Type
  // path: 'fixtures/users.json',               // альтернатива — тело из файла
  // response,                                  // база — реальный ответ от route.fetch(), поверх — переопределения
});
```

Нюансы, которые ценят на интервью:

- `json: {...}` — современный шорткат: не нужно ни `JSON.stringify`, ни `contentType`;
- `path` — удобно держать большие мок-ответы файлами-фикстурами рядом с тестами;
- комбинация `response + json` (пример 5 выше) — «частичный мок»: реальный ответ сервера с точечной подменой одного поля;
- если фронт и мок на разных origin — в мок-ответ нужно добавить CORS-заголовки, иначе браузер заблокирует чтение (связка с главой 3).

### 7.3.3. Как рассказать это на интервью — последовательность действий

Отвечать удобно как алгоритм из пяти шагов на конкретном сценарии («проверяю, что UI переживает 500 от бэкенда»):

1. **«Регистрирую перехват до действия»** — `await page.route('**/api/payment', ...)` до клика по кнопке оплаты; паттерн — glob, регулярка или предикат.
2. **«Playwright замораживает подходящий запрос** и отдаёт мне `route` и `request`; запрос никуда не уходит, пока я не приму решение».
3. **«Принимаю одно из решений»:** `fulfill` — ответить самому (мок), `abort` — симулировать сетевой сбой, `continue` — пропустить, при желании изменив заголовки/тело, `fetch`+`fulfill` — получить реальный ответ и подменить его часть.
4. **«Описываю ответ в `fulfill`** как настоящий HTTP-ответ: статус, заголовки, тело (`json`/`body`/`path` из файла)».
5. **«Выполняю действие и проверяю реакцию UI»** — кликаю оплату, ассертю, что показано человеческое сообщение об ошибке, а не белый экран; при необходимости снимаю перехват `unroute` для следующих шагов.

Такой ответ показывает сразу три вещи: знание API, понимание механики перехвата (почему регистрация — до действия) и тестовое мышление (мок ради конкретного проверяемого кейса, а не «мокаю всё подряд»).

## 7.4. HAR: запись и воспроизведение трафика

```typescript
// Запись реального трафика в файл
await context.routeFromHAR('network.har', { update: true });
// Воспроизведение: тесты работают без бэкенда, ответы из HAR
```

## 7.5. Ожидание запросов/ответов (соседняя тема, спрашивают сразу после моков)

```typescript
// Дождаться конкретного ответа после действия — правильная замена sleep
const respPromise = page.waitForResponse(
  r => r.url().includes('/api/transfer') && r.status() === 200,
);
await page.click('#submit');
const resp = await respPromise;
expect((await resp.json()).status).toBe('processed');
```

Паттерн «подписаться до действия, дождаться после» — важно: если кликнуть, а потом подписываться, ответ можно пропустить (race condition).

# Глава 8. Git: merge, rebase и повседневная работа *(вопросы 25–26)*

## 8.1. Ментальная модель: три зоны и указатели

- **Working directory** (рабочие файлы) → `git add` → **staging/index** → `git commit` → **репозиторий** (граф коммитов).
- Коммит — снапшот + ссылка на родителя(ей); **ветка — просто подвижный указатель на коммит**; HEAD — указатель на текущую ветку.
- Хэш коммита считается от содержимого и родителя → **изменить коммит нельзя, только создать новый** (ключ к пониманию rebase).

## 8.2. Merge vs rebase — с картинками

Исходная ситуация: main ушёл вперёд (C), ваша ветка feature от B (D, E):

```text
        A───B───C        (main)
             \
              D───E      (feature)
```

**Merge** (`git checkout main && git merge feature`) — создаётся merge-коммит M с **двумя родителями** (C и E); история сохраняет реальное ветвление:

```text
        A───B───C───────M   (main)
             \         /
              D───E───┘     (feature)
```

**Rebase** (`git checkout feature && git rebase main`) — Git берёт D и E и **повторно применяет** их поверх C. Это **новые коммиты D' и E'** (новые хэши!); история линейная:

```text
        A───B───C───D'───E'   (feature)
                └ main
```

| | Merge | Rebase |
|---|---|---|
| История | Правдивая, с ветвлениями («ромбы») | Линейная, «переписанная» |
| Коммиты | Не изменяются | Пересоздаются (новые хэши) |
| Конфликты | Один раз, в merge-коммите | По каждому переносимому коммиту |
| Где уместен | Общие ветки, вливание в main | Свои локальные ветки, актуализация перед MR |

**Золотое правило: не ребейзить опубликованные общие ветки.** Rebase переписывает историю; у коллег останутся старые хэши — их ветки «разъедутся» с origin. После rebase своей ветки пуш — только `--force-with-lease` (безопаснее `--force`: не затрёт чужие свежие коммиты).

**Типовой флоу:** feature-ветка → работа → `git rebase main` (актуализация + чистая история) → push → MR → в main через merge (часто squash merge — вся ветка одним коммитом).

## 8.3. Команды, которые надо знать глубже, чем «слышал»

| Команда | Что делает | Нюанс |
|---|---|---|
| `git status` | Состояние working dir и staging | НЕ «инициализирован ли репозиторий» (ошибка кандидата) |
| `git fetch` vs `git pull` | fetch — скачать изменения **без применения**; pull = fetch + merge (или rebase с `--rebase`) | Классический вопрос на различие |
| `git stash` / `stash pop` | Отложить незакоммиченные изменения | Срочно переключиться на другую ветку |
| `git cherry-pick <hash>` | Перенести один коммит в текущую ветку | Хотфикс в релизную ветку |
| `git revert <hash>` | **Новый** коммит, отменяющий изменения | Безопасен для общих веток |
| `git reset --soft/--mixed/--hard` | Сдвинуть ветку назад: soft — изменения в staging, mixed — в working dir, hard — **удалить** | Только для локальной истории |
| `git log --oneline --graph` | История графом | Как раз чтобы «увидеть» merge vs rebase |
| `git bisect` | Бинарный поиск коммита, сломавшего тест | Киллер-фича для AQA: найти коммит-виновник за log₂(N) шагов |

**revert vs reset — постоянный вопрос:** revert добавляет отменяющий коммит (история цела — можно на общих ветках), reset стирает коммиты из истории (только локально).

# Глава 9. CI/CD-пайплайн для автотестов *(вопрос 27)*

## 9.1. Термины: CI, CD и CD

- **CI (Continuous Integration)** — каждый пуш автоматически собирается и тестируется;
- **CD (Continuous Delivery)** — артефакт всегда готов к выкатке, релиз по кнопке;
- **CD (Continuous Deployment)** — выкатка в прод автоматическая, без кнопки.

## 9.2. Иерархия пайплайна (те самые «квадратики»)

```text
Pipeline (запуск по триггеру)
└── Stages — последовательные стадии:   build → test → e2e → deploy
    └── Jobs — задачи внутри стадии, идут ПАРАЛЛЕЛЬНО (шарды тестов)
        └── Steps/script — команды внутри джобы
```

- **Триггеры:** push, merge request, расписание (nightly regress), ручной запуск, вызов по API, тег.
- Стадия начинается после успеха предыдущей; джобы внутри стадии параллельны.
- **Runner/agent** — машина (обычно Docker-контейнер), исполняющая джобу.
- **Самое первое действие любой джобы — checkout:** клонирование репозитория на раннер (в GitHub Actions — явный шаг `actions/checkout`, в GitLab — автоматически). Именно это не вспомнил кандидат.

## 9.3. Эталонный пайплайн E2E-тестов

```yaml
# GitLab CI — скелет
stages: [lint, test]

e2e:
  stage: test
  image: mcr.microsoft.com/playwright:v1.54.0-jammy   # браузеры уже внутри
  parallel: 4                                          # 4 шарда
  script:
    - npm ci                                           # чистая установка по lock-файлу
    - npx playwright test --shard=$CI_NODE_INDEX/$CI_NODE_TOTAL
  artifacts:
    when: always                                       # отчёты и при падении!
    paths: [playwright-report/, test-results/]
  rules:
    - if: $CI_PIPELINE_SOURCE == "merge_request_event"
```

Пояснения, которые показывают понимание:

- **`npm ci`, а не `npm install`** — ставит строго по lock-файлу, воспроизводимо;

  > **Что такое lock-файл.** В `package.json` версии зависимостей задаются **диапазонами**: `"playwright": "^1.54.0"` означает «любая 1.x не ниже 1.54.0» — сегодня поставится 1.54.0, через месяц 1.56.2. **`package-lock.json`** — автоматически генерируемый снимок того, что реально установилось: точные версии **всего дерева** зависимостей (включая зависимости зависимостей) плюс контрольные суммы пакетов.
  >
  > Зачем это в CI: без lock-файла прогон в понедельник и прогон в пятницу могут идти на разных версиях библиотек — тест падает «сам по себе», хотя код не менялся. Разница команд:
  >
  > - `npm install` — разрешает диапазоны из `package.json` заново и **может обновить** lock-файл → недетерминированно;
  > - `npm ci` — удаляет `node_modules`, ставит **строго по lock-файлу** и падает, если lock рассинхронизирован с `package.json` → каждый прогон CI на идентичных версиях, как у всех разработчиков.
  >
  > Поэтому lock-файл **обязательно коммитится в репозиторий** — это часть воспроизводимости сборки, а не мусор. Аналоги в других экосистемах: `yarn.lock`, `pnpm-lock.yaml`, в Python — `poetry.lock` / `uv.lock` (или пины версий в `requirements.txt`). Бонус: по хэшу lock-файла CI кэширует `node_modules` — lock не менялся, значит зависимости можно не скачивать заново.

- **готовый Playwright-образ** — не тратим время на установку браузеров;
- **кэш зависимостей** между запусками (`cache: node_modules` по хэшу lock-файла);
- **artifacts `when: always`** — трейсы, скриншоты и видео нужны именно у упавших прогонов;
- **секреты** — в CI-переменных (masked/protected), никогда в репозитории;
- после шардов — `npx playwright merge-reports` в отдельной джобе.

## 9.4. Куда встраивать автотесты — стратегия

| Когда | Что гонять | Почему |
|---|---|---|
| На каждый MR | Линт + юниты + smoke E2E (5–10 мин) | Быстрая обратная связь, не блокировать ревью часами |
| После merge в main | Расширенный набор | Ловим интеграционные эффекты |
| Ночью (schedule) | Полный регресс + нагрузочные | Времени не жалко |
| После деплоя на стенд | Smoke по живому стенду | Проверка, что выкатка не сломала критичное |

Плюс понятие **quality gate**: красные тесты блокируют merge (required check).

# Глава 10. Нагрузочное тестирование *(вопросы 28, 29, 35)*

## 10.1. Виды тестирования производительности

> **Что такое SLA.** **SLA (Service Level Agreement)** — соглашение об уровне сервиса: формально зафиксированные обязательства по качеству работы системы, обычно в цифрах. Примеры: «доступность 99,9% в месяц», «p95 времени ответа API < 500 мс», «error rate < 0,1%». Именно против этих цифр и гоняется нагрузочное тестирование: SLA превращается в критерии прохождения теста (passed/failed).
>
> Рядом два термина, различие которых любят спрашивать:
>
> - **SLI (Service Level Indicator)** — сама измеряемая метрика (латентность, доля ошибок, аптайм);
> - **SLO (Service Level Objective)** — внутренняя целевая планка по этой метрике («p95 < 400 мс»), обычно строже внешнего SLA, чтобы был запас;
> - **SLA** — внешнее обязательство перед клиентом, часто с финансовой ответственностью за нарушение.
>
> Одной фразой: *SLI — что меряем, SLO — какую цель себе ставим, SLA — что пообещали клиенту.*

| Вид                        | Нагрузка                             | Вопрос, на который отвечает                                         |
| -------------------------- | ------------------------------------ | ------------------------------------------------------------------- |
| **Load**                   | Ожидаемая (обычная и пиковая)        | Выдерживаем ли SLA при штатном трафике?                             |
| **Stress**                 | Выше ожидаемой, до предела и за него | Где предел? Как деградируем и восстанавливаемся?                    |
| **Soak / endurance**       | Умеренная, но **долго** (часы/сутки) | Утечки памяти, деградация со временем, переполнение логов/дисков    |
| **Spike**                  | Резкие скачки                        | Переживём ли залп трафика (реклама, рассылка)?                      |
| **Capacity / scalability** | Ступенчатый рост                     | Максимальная ёмкость при соблюдении SLA; линейно ли масштабируемся? |

Дифференциатор load vs stress — **уровень нагрузки относительно ожидаемой** (тот самый «один основной параметр» из вопроса интервьюера).

## 10.2. Клиентские метрики (сторона нагрузки)

- **RPS/TPS** — пропускная способность (запросов/транзакций в секунду);
- **Response time / latency** — обязательно **перцентили**: p50 (медиана), p95, p99. Почему не среднее: среднее скрывает хвосты — при среднем 200 мс p99 может быть 5 секунд, и 1% пользователей страдает. Формулировка: *«p95 = 800 мс значит, что 95% запросов быстрее 800 мс»*;
- **Error rate** — доля 5xx/таймаутов при росте нагрузки;
- **VU (virtual users)** — конкурентные виртуальные пользователи.

**Ключевые точки на графике «нагрузка → отклик»:**

- **Saturation point (точка насыщения)** — рост нагрузки перестаёт увеличивать throughput, латентность начинает расти (упёрлись в ресурс) — слово, которое не вспомнил кандидат;
- **Breaking point (точка отказа)** — система начинает массово ошибаться или падает.

## 10.3. Серверные метрики (вопрос 35)

Четыре базовых ресурса + прикладной уровень:

1. **CPU** — стабильно выше 80–90% → узкое место;
2. **RAM** — потребление, swap; рост без плато при постоянной нагрузке = утечка памяти (ловится soak-тестом);
3. **Диск I/O** — латентность диска, очередь операций — критично для БД;
4. **Сеть** — пропускная способность, ошибки, ретрансмиссии;
5. Прикладное: соединения/сокеты, пул соединений БД, очереди запросов, тред-пулы, GC-паузы (JVM/.NET), медленные запросы и блокировки БД.

Суть анализа — **корреляция**: клиентская картина (растёт p99, полезли 5xx) сопоставляется с серверной (CPU упёрся? пул БД исчерпан?) → найдено узкое место → оптимизация → повторный прогон.

## 10.4. Инструменты и методика

- **Инструменты:** JMeter (GUI, классика), Gatling (Scala, отчёты), **k6** (сценарии на JS, удобен в CI), Locust (Python), Яндекс.Танк.
- **Мониторинг:** Grafana + Prometheus, APM (трейсинг — Jaeger/Zipkin), ELK.
- **Методика, которую ждут в ответе:** определить цели и SLA (например, «p95 < 500 мс при 1000 RPS») → подготовить профиль нагрузки по реальному трафику (какие эндпоинты в каких пропорциях) → изолированный стенд, сопоставимый с продом → **ramp-up** (плавный рост, а не сразу залп) → мониторить обе стороны → анализ, отчёт, повтор после фиксов.
- Типовая ошибка: генератор нагрузки сам упёрся в CPU/сеть — и «деградация сервера» оказывается деградацией генератора. Мониторить надо и его.

# Глава 11. Аутентификация в Playwright и storageState *(вопрос 30)*

## 11.1. Где браузер хранит состояние сессии

| Хранилище | Что хранит | Уходит на сервер? | В storageState? |
|---|---|---|---|
| **Cookies** | Session id, токены (`HttpOnly`) | Да, автоматически | ✅ |
| **localStorage** | JWT, настройки; живёт до очистки | Нет (только JS руками) | ✅ |
| **sessionStorage** | То же, но живёт до закрытия вкладки | Нет | ❌ (не сохраняется!) |
| **IndexedDB** | Структурированные данные; MSAL и другие auth-библиотеки хранят токены тут | Нет | ✅ (в свежих версиях) |

Тот самый «третий вид», который не вспомнил кандидат, — **IndexedDB**.

## 11.2. Эталонная схема: логин один раз, использование везде

```typescript
// playwright.config.ts
projects: [
  { name: 'setup', testMatch: /auth\.setup\.ts/ },
  {
    name: 'chromium',
    dependencies: ['setup'],                          // сначала — логин
    use: { storageState: 'playwright/.auth/user.json' },
  },
],

// auth.setup.ts
setup('authenticate', async ({ page }) => {
  await page.goto('/login');
  await page.getByLabel('Логин').fill(process.env.USER!);
  await page.getByLabel('Пароль').fill(process.env.PASS!);
  await page.getByRole('button', { name: 'Войти' }).click();
  await expect(page.getByTestId('profile')).toBeVisible();   // дождаться завершения логина!
  await page.context().storageState({ path: 'playwright/.auth/user.json' });
});
```

Каждый тест стартует **уже залогиненным** — экономия 5–15 секунд на тест, минус флаки самой формы логина.

## 11.3. Продвинутые варианты (то, что отличает мидла)

- **Логин через API вместо UI** — быстрее и стабильнее: POST на auth-эндпоинт → положить полученные куки в контекст `context.addCookies()` или токен в localStorage через `page.addInitScript()`. UI-форму логина тестируем отдельным одним тестом.
- **Несколько ролей** — несколько файлов состояния (`admin.json`, `user.json`) + фикстуры/проекты на роль; в одном тесте два пользователя = два контекста с разными storageState (см. главу 13).
- **API-тесты** — токен в `extraHTTPHeaders` у `APIRequestContext`.
- **Параллельность:** один аккаунт на все воркеры может ломаться (одна сессия, лимиты) — паттерн «аккаунт на воркер» через worker-scoped фикстуру и `workerIndex`.
- **Протухание сессии:** setup-проект перелогинивается на каждый прогон; в CI файл состояния не должен попадать в репозиторий (секрет + мусор).

# Глава 12. Параметризация тестов и фикстур *(вопрос 31)*

## 12.1. Суть и главное правило

**Параметризация** — прогон одной тестовой логики с разными входными данными без дублирования кода. Каждый набор данных = **отдельный независимый тест** в отчёте (падает, ретраится и фильтруется сам по себе).

**Антипаттерн, на котором засыпался кандидат:** if/else внутри одного теста — это НЕ параметризация. Тест должен быть линейным и детерминированным; ветвление = несколько тестов, склеенных в один, с нечитаемым отчётом.

## 12.2. Параметризация тестов в Playwright

```typescript
const roles = [
  { role: 'admin',   canExport: true  },
  { role: 'viewer',  canExport: false },
];

for (const { role, canExport } of roles) {
  test(`кнопка экспорта для роли ${role}`, async ({ page }) => {
    await loginAs(page, role);
    await expect(page.getByRole('button', { name: 'Экспорт' }))
      .toBeVisible({ visible: canExport });
  });
}
```

В отчёте — два теста с говорящими именами. В pytest — то же самое декоратором:

```python
@pytest.mark.parametrize("role, can_export", [("admin", True), ("viewer", False)])
def test_export_button(role, can_export): ...
```

## 12.3. Параметризация фикстур и окружений

**Projects в конфиге** — параметризация всего прогона: одни и те же тесты × разные браузеры/устройства/стенды:

```typescript
projects: [
  { name: 'chromium', use: { ...devices['Desktop Chrome'] } },
  { name: 'mobile',   use: { ...devices['iPhone 15'] } },
],
```

**Option-фикстуры** — параметр, переопределяемый на уровне проекта или группы тестов:

```typescript
export const test = base.extend<{ userRole: string }>({
  userRole: ['viewer', { option: true }],           // дефолт
});
// в тест-файле: test.use({ userRole: 'admin' });
```

В pytest параметризация фикстуры — `@pytest.fixture(params=[...])`: каждый тест, использующий фикстуру, прогонится с каждым param.

## 12.4. Разница одной фразой (то, что хотел услышать интервьюер)

*«Параметризация теста множит тесты по **данным** (один сценарий × N наборов), параметризация фикстур/проектов множит прогоны по **окружениям и предусловиям** (все сценарии × N конфигураций). В обоих случаях получается несколько независимых тестов в отчёте — а не один тест с if/else внутри».*

# Глава 13. Multi-page сценарии, контексты и вкладки *(вопрос 32)*

## 13.1. Иерархия изоляции в Playwright

```text
Browser (процесс браузера)
└── BrowserContext (изолированная сессия: свои cookies, storage, кэш)
    └── Page (вкладка)
```

- **Контекст** = профиль «инкогнито»: создаётся за миллисекунды, контексты не видят куки друг друга. Каждый тест по умолчанию получает свежий контекст — вот откуда изоляция тестов.
- **Page** = вкладка внутри контекста; вкладки одного контекста **разделяют сессию**.

## 13.2. Случай 1: несколько вкладок, один пользователь (один контекст)

Клик открывает новую вкладку (target=_blank, окно оплаты, popup OAuth):

```typescript
const pagePromise = context.waitForEvent('page');   // подписка ДО клика!
await page.getByRole('link', { name: 'Оферта' }).click();
const newPage = await pagePromise;
await newPage.waitForLoadState();
await expect(newPage).toHaveURL(/offer/);
```

Обе вкладки видят одни куки — это один залогиненный пользователь.

## 13.3. Случай 2: несколько пользователей (несколько контекстов)

Классика — чат/звонок/совместное редактирование, проверка «А отправил — Б увидел»:

```typescript
const ctxA = await browser.newContext({ storageState: '.auth/userA.json' });
const ctxB = await browser.newContext({ storageState: '.auth/userB.json' });
const [pageA, pageB] = [await ctxA.newPage(), await ctxB.newPage()];

await pageA.goto('/chat/42');
await pageB.goto('/chat/42');
await pageA.getByRole('textbox').fill('Привет!');
await pageA.keyboard.press('Enter');
await expect(pageB.getByText('Привет!')).toBeVisible();   // авто-ожидание — WebSocket доедет

await ctxA.close(); await ctxB.close();
```

## 13.4. Ответ на вопрос интервьюера про контекст

Контекст в multi-page сценарии **может быть и один, и несколько — это выбор по задаче**: общая сессия (вкладки одного пользователя) → один контекст; изоляция сессий (разные пользователи, разные роли) → разные контексты. Плюс частные случаи: iframe — это не отдельная page, а `frameLocator` внутри той же страницы; новое «окно» браузера в Playwright — та же сущность page.

# Глава 14. Мобильное тестирование: Playwright, эмуляторы, симуляторы *(вопросы 33–34)*

## 14.1. Поддерживает ли Playwright мобильные платформы (правильный ответ на вопрос 33)

Разделяем три вещи:

1. **Мобильный веб через эмуляцию — да, полноценно.** Device descriptors: viewport, user agent, `deviceScaleFactor`, `hasTouch`, `isMobile`; плюс эмуляция геолокации, локали, таймзоны, тёмной темы, permissions:

```typescript
projects: [
  { name: 'iphone', use: { ...devices['iPhone 15'] } },
  { name: 'pixel',  use: { ...devices['Pixel 7'] } },
],
// точечно: тест на геолокацию
test.use({ geolocation: { latitude: 55.75, longitude: 37.61 }, permissions: ['geolocation'] });
```

Честная оговорка: это **эмуляция браузером на десктопе** — реальное железо, реальная сеть и жесты не воспроизводятся точно.

2. **Реальный Android — экспериментально:** Chrome на устройстве и WebView через ADB.
3. **Нативные приложения (iOS/Android) — нет.** Для них: **Appium** (кроссплатформенно, WebDriver-протокол), **Espresso** (Android, от Google), **XCUITest** (iOS, от Apple).

Ответ кандидата «не поддерживает» — неверный: для mobile web Playwright — штатный инструмент.

## 14.2. Эмулятор vs симулятор (вопрос 34 — эталонная формулировка)

| | Эмулятор | Симулятор |
|---|---|---|
| Что воспроизводит | **Железо + настоящую ОС** (Android Emulator исполняет реальный образ Android, эмулируя ARM/x86-устройство) | Только **программную среду/API** (iOS Simulator исполняет приложение как процесс поверх macOS) |
| Точность поведения | Высокая: настоящая ОС, сенсоры, реалистичная производительность | Средняя: имитация окружения, не настоящий iPhone |
| Скорость | Медленнее (виртуализация) | Быстрее |
| Что ближе к реальному девайсу | **Эмулятор** | |

Обязательное дополнение: **оба не заменяют реальные устройства** — батарея, реальная сеть (3G, обрывы), вендорские прошивки (MIUI, One UI), реальная производительность и жесты проверяются только на девайсах или девайс-фермах (BrowserStack, Sauce Labs, Firebase Test Lab).

## 14.3. Специфика мобильного тестирования (если копнут глубже)

- **Пирамида для мобилок:** unit → интеграционные → UI на эмуляторах в CI → smoke на реальных девайсах.
- Особые кейсы: прерывания (звонок, push, сворачивание), смена ориентации, потеря сети и офлайн-режим, deep links, разрешения (камера, гео), обновление приложения с сохранением данных.
- Responsive web vs нативное приложение vs WebView-гибрид — разные объекты тестирования и разные инструменты.
