# Глава 2. Зачем нужна Kafka — проблема и решение

## Проблема без брокера

Сервис A должен сообщить сервисам B, C, D: «создан заказ №123».

```
A ──HTTP──▶ B
A ──HTTP──▶ C
A ──HTTP──▶ D
```

Минусы:
- A знает про всех получателей — **жёсткая связность**;
- B упал — A должен ретраить, усложняется код;
- появился E — меняем A;
- пик нагрузки — A и B падают одновременно.

## Решение — асинхронный обмен через Kafka

```
A ──publish──▶ [ Topic: orders ] ──▶ B (consumer group "billing")
                                 ──▶ C (consumer group "notifications")
                                 ──▶ D (consumer group "analytics")
```

- A **публикует событие** и не ждёт ответа;
- B, C, D **читают в своём темпе**;
- Kafka **буферизует** сообщения — сглаживает пики;
- новый сервис E — просто подписывается на тот же топик, A не меняется.

**Одна фраза для собеседования:** *Kafka — распределённый брокер сообщений, построенный как append-only журнал (commit log), для асинхронного обмена событиями между микросервисами.*

# Глава 3. Словарь терминов — все ключевые понятия

## 3.1. Базовые сущности

| Термин                   | Что это                                                     | Аналогия                                            |
| ------------------------ | ----------------------------------------------------------- | --------------------------------------------------- |
| **Message (сообщение)**  | Единица данных: key + value + headers + timestamp           | Строка в таблице                                    |
| **Key (ключ)**           | Опциональный идентификатор; определяет **партицию**         | «Номер клиента» — все его события в одну партицию   |
| **Value (значение)**     | Полезная нагрузка (JSON, Avro, строка, байты)               | Само событие: `{"orderId": 123, "status": "paid"}`  |
| **Headers**              | Метаданные сообщения (content-type, trace-id)               | HTTP-заголовки                                      |
| **Topic (топик)**        | Именованный поток сообщений одного типа                     | «Канал» или «таблица» `orders`                      |
| **Partition (партиция)** | Топик разбит на N упорядоченных **журналов**                | Шард / сегмент таблицы                              |
| **Offset (оффсет)**      | Порядковый номер сообщения **внутри партиции** (0, 1, 2...) | Номер строки в журнале                              |
| **Broker (брокер)**      | Сервер Kafka, хранит партиции                               | Один узел кластера                                  |
| **Cluster (кластер)**    | Несколько брокеров, работающих вместе                       | Весь Kafka-кластер                                  |
| **Producer (продюсер)**  | Кто **пишет** сообщения в топик                             | Отправитель                                         |
| **Consumer (консюмер)**  | Кто **читает** сообщения из топика                          | Получатель                                          |
| **Consumer Group**       | Группа консюмеров, **совместно** читающих топик             | Команда воркеров на одну задачу                     |
| **Zookeeper / KRaft**    | Координация кластера (метаданные, лидеры)                   | «Мозг» кластера; у тебя — **KRaft** (без Zookeeper) |

### Брокер vs кластер vs контроллер — чтобы не путать

Три соседних понятия, которые легко смешать:

- **Брокер** = **один процесс Kafka** (один JVM-процесс с уникальным `node.id`). Хранит партиции (лидеры и реплики) и обслуживает клиентов. **Один Docker-контейнер с Kafka = один брокер.**
- **Кластер** = **группа брокеров, работающих как одна система**: общее пространство топиков, единая согласованная картина (кто хранит какую партицию, кто лидер, кто в ISR), совместное распределение нагрузки и взаимная подстраховка. Топик создаётся «в кластере», а не «на брокере» — кластер сам раскладывает его партиции и реплики по брокерам. Три Kafka, которые не настроены знать друг о друге, — это не кластер, а три одиночки; кластером их делает **общая конфигурация координации** (единый кворум).
- **Контроллер** = **роль**, которая управляет метаданными кластера (назначает лидеров, отслеживает состав, ISR). В **KRaft** это встроенная роль брокеров (заменяет внешний Zookeeper). У тебя `KAFKA_PROCESS_ROLES: broker,controller` — один процесс совмещает обе роли, но это по-прежнему **один брокер**, просто он ещё и контроллер.

**Про твой стенд:** один контейнер `kafka` (`node.id=1`) — это **кластер из одного брокера**. Формально кластер, но узел один: делить и реплицировать не с кем, поэтому `replication-factor` максимум 1 и все лидеры сидят на нём. Чтобы получить настоящий кластер (RF=3, реплики на разных узлах), нужно **несколько процессов Kafka** — обычно несколько сервисов в compose с разными `node.id`.

```text
Кластер
 ├── Broker 1 (процесс, node.id=1) ── хранит часть партиций (лидеры + реплики)
 ├── Broker 2 (процесс, node.id=2) ── хранит часть партиций
 └── Broker 3 (процесс, node.id=3) ── хранит часть партиций
      ▲ связаны через контроллер (KRaft) = единая согласованная система
```

**Аналогия:** брокер — один музыкант; кластер — оркестр, играющий по общей партитуре под управлением дирижёра (контроллера). Один музыкант тоже играет, но оркестром не становится.

### Узел (node), node.id и роли

**Узел (node)** — общее слово для «одного участника кластера»: один процесс Kafka на сервере/в контейнере со своим уникальным **`node.id`**. По сути узел = брокер (в KRaft — брокер и/или контроллер). Тот самый `node.id` виден в `--describe` как `Leader: 1`.

- **`node.id`** — идентификатор узла в кластере (в конфиге стенда — `KAFKA_NODE_ID: 1`). Историческое имя настройки — `broker.id`; с приходом KRaft её обобщили до `node.id`, потому что узел может быть не только брокером.
- **Роли узла** (`KAFKA_PROCESS_ROLES`):
  - `broker` — хранит партиции и обслуживает клиентов (брокер в обычном смысле);
  - `controller` — ведёт метаданные кластера (лидеры, ISR), заменяет Zookeeper;
  - `broker,controller` — **совмещённый** узел (как на твоём стенде): один процесс и хранит данные, и координирует. В больших кластерах контроллеры выносят на отдельные узлы.

**Узел vs брокер.** Строго: узел — процесс-участник кластера; брокер — узел **в роли брокера**. На одно-узловом стенде это одно и то же — один узел `node.id=1`, совмещающий обе роли.

```text
Кластер = несколько узлов (nodes)
  └─ Узел (node.id) = один процесс Kafka на сервере/в контейнере
       ├─ роль broker     → хранит партиции, обслуживает клиентов
       └─ роль controller → ведёт метаданные кластера (вместо Zookeeper)
```

**Формула на собес:** *узел (node) — один экземпляр Kafka в кластере со своим `node.id`; в роли брокера хранит данные, в роли контроллера управляет метаданными, а в KRaft может совмещать обе.*

## 3.2. Термины хранения и надёжности

| Термин                       | Что это                                                                                                    |
| ---------------------------- | ---------------------------------------------------------------------------------------------------------- |
| **Commit log (журнал)**      | Kafka хранит сообщения как append-only лог — только дописывает в конец                                     |
| **Retention (удержание)**    | Сколько хранить сообщения: по времени (7 дней) или размеру (10 ГБ на партицию)                             |
| **Replication (репликация)** | Каждая партиция копируется на несколько брокеров (лидер + реплики)                                         |
| **Leader / Follower**        | Лидер партиции принимает запись/чтение; фолловеры реплицируют                                              |
| **ISR (In-Sync Replicas)**   | Реплики, успевшие синхронизироваться с лидером                                                             |
| **acks**                     | Уровень подтверждения записи продюсером: `0`, `1`, `all`                                                   |
| **Consumer offset commit**   | Консюмер запоминает, до какого offset прочитал                                                             |
| **Replication factor (RF)**  | Сколько копий держит каждая партиция. RF=1 — одна копия (стенд), RF=3 — три на разных брокерах             |
| **Replicas (список реплик)** | Полный список брокеров, которым **назначено** хранить копию партиции («как задумано»)                      |
| **TopicId**                  | Неизменный уникальный id топика (base64 UUID), генерируется при создании; при пересоздании топика меняется |

### Replicas vs ISR, RF и TopicId — детали из `--describe`

**Replication factor (RF)** — сколько копий у **каждой** партиции. Топик с 3 партициями и RF=3 = 9 копий на дисках. RF — рычаг надёжности: при RF=3 переживаешь падение до 2 брокеров. На одно-брокерном стенде RF максимум 1.

**Replicas ≠ ISR** — обе про копии, но это разные вещи:

- **Replicas** — *полный назначенный* список брокеров с копией (статический план, «как задумано»).
- **ISR (In-Sync Replicas)** — *подмножество*, которое **сейчас догнало лидера** (динамическое состояние, «как есть»).

Разница видна, когда копия отстаёт (RF=3):

```text
здоров:                 Replicas: 1,2,3   Isr: 1,2,3
брокер 2 тормозит/упал:  Replicas: 1,2,3   Isr: 1,3     ← копия на 2 выпала из ISR
```

Почему важно: новым лидером может стать **только** член ISR (иначе потеряли бы свежие данные); `acks=all` ждёт подтверждения от ISR, а `min.insync.replicas` требует минимум N в ISR. **`Replicas` > `Isr` = under-replicated** — красный флаг мониторинга. При RF=1 они выглядят одинаково (`1` и `1`) просто потому, что копия одна.

**TopicId** — уникальный id, который кластер генерирует при создании топика; неизменен всю его жизнь. Имя может совпадать у разных «поколений», а id — нет: удалил и создал топик с тем же именем → **TopicId другой**. Зачем: Kafka использует id (а не имя) в метаданных и в именах каталогов на диске (KRaft), чтобы не перепутать старый топик с новым одноимённым. Как использовать тебе — диагностика: сравнил TopicId в двух `--describe`, поменялся → топик пересоздавали (частая причина «данные пропали, имя то же»); удобен для корреляции логов/метрик.

## 3.3. Термины поведения консюмеров

| Термин                      | Что это                                                                               |
| --------------------------- | ------------------------------------------------------------------------------------- |
| **Poll**                    | Консюмер вызывает `poll()` — «дай мне пачку сообщений» (pull-модель)                  |
| **Rebalance**               | Перераспределение партиций между консюмерами группы (кто-то упал/добавился)           |
| **Lag (отставание)**        | Разница между последним offset в партиции и offset консюмера — «сколько не прочитано» |
| **Dead Letter Queue (DLQ)** | Отдельный топик для сообщений, которые не удалось обработать                          |
| **Partition key**           | Ключ, по которому сообщение попадает в конкретную партицию                            |

## 3.4. Термины, которые любят на собеседовании

| Термин                     | Коротко                                                           |     |
| -------------------------- | ----------------------------------------------------------------- | --- |
| **Event streaming**        | Непрерывный поток событий, а не разовая доставка «задачи»         |     |
| **Event sourcing**         | Состояние системы = replay всех событий из лога                   |     |
| **Backpressure**           | Консюмер сам регулирует темп чтения (pull) — брокер не заваливает |     |
| **Idempotent producer**    | Продюсер не создаёт дубликаты при ретраях                         |     |
| **Transactional producer** | Атомарная запись в несколько топиков                              |     |
| **Schema Registry**        | Хранилище схем (Avro/Protobuf) для контрактов сообщений           |     |

### Разбор терминов: зачем нужно, в чём выражается, как устроено

**Event streaming (потоковая обработка событий).**

*Что это.* Модель, где данные — это **непрерывный поток событий-фактов** («заказ создан», «клик», «платёж прошёл»), которые публикуются и обрабатываются по мере поступления, а не разовые «задачи», которые взял-выполнил-выкинул.

*В чём выражается.* Продюсеры непрерывно пишут в топик, консюмеры непрерывно читают; поверх потока строят фильтрацию/агрегацию в реальном времени (Kafka Streams, Flink) — например «сумма продаж за последние 5 минут по каждому магазину».

*Зачем и как устроено (инженерно).* Противоположность батч-обработке (раз в сутки прогнать выгрузку). Поток даёт **низкую задержку** (реакция сразу) и **развязку**: источник не знает потребителей. Технически это работает благодаря тому, что топик — это устойчивый лог: события копятся, их читают много потребителей, можно перечитать. Пример-цепочка: `clicks` → стрим-процессор считает счётчики по товарам → пишет в топик `top-products` → дашборд читает его почти в реальном времени.

*Что значит «развязка» (decoupling) в этом контексте.* Развязка — это когда **источник события и его потребители ничего не знают друг о друге** и не зависят друг от друга. Продюсер просто кладёт событие в топик и идёт дальше; кто, когда и сколько раз его прочитает — не его забота. Топик стоит **посередине как буфер-посредник** и разрывает прямую связь. Развязка проявляется сразу в нескольких измерениях:

- **По адресатам (кто):** продюсер не держит список получателей и не вызывает их. Появился новый потребитель (`fraud`, `analytics`) — он просто подписывается на топик, продюсер **не меняется** и даже не знает о нём.
- **По времени (когда):** продюсер и консюмер не обязаны работать одновременно. Консюмер лежал на деплое — события ждут его в логе, прочитает позже. В синхронном HTTP так нельзя: получатель недоступен → вызов падает.
- **По скорости (как быстро):** продюсер пишет в своём темпе, консюмер читает в своём; разрыв безопасно копится в партиции (это и есть backpressure). Медленный потребитель не тормозит быстрый источник.
- **По сбоям:** упал один потребитель — остальные и продюсер работают как ни в чём не бывало; ошибка не расходится по цепочке.

*Контраст.* Без развязки (прямой HTTP `A→B→C→D`) сервис A **жёстко связан** со всеми: знает их адреса, ждёт ответа, обрабатывает их падения, а при добавлении E его нужно править. С Kafka A публикует одно событие — и связь с конкретными B/C/D/E разорвана. Это и есть смысл «источник не знает потребителей»: единственный, кого знает продюсер, — это **топик**, а не сервисы за ним.

**Event sourcing.**

*Что это.* Паттерн хранения, где **состояние системы = результат проигрывания (replay) всех событий из лога**, а не «текущий снимок» в таблице. Хранишь не «баланс = 100», а всю ленту: `+50, +70, −20`.

*В чём выражается.* Kafka-топик становится **источником истины**: каждое изменение — событие, добавленное в конец. Текущее состояние получают, прочитав события с начала и «свернув» их. Для быстрых снимков используют compacted-топики или проекции в БД.

*Зачем и как устроено (инженерно).* Даёт **полный аудит** (видно каждое изменение и его причину), **машину времени** (восстановить состояние на любой момент), возможность **пересчитать** проекцию по-новому после изменения логики (перечитал лог — построил другую вьюху). Держится на append-only логе и retention/compaction. Обратная сторона — сложнее читать «текущее значение» (нужно свернуть события) и управлять эволюцией схемы событий.

**Backpressure (обратное давление).**

*Что это.* Свойство, при котором **потребитель сам регулирует темп** получения данных, и быстрый источник не может его «завалить».

*В чём выражается.* В Kafka это следствие pull-модели: консюмер вызывает `poll()` тогда и в том объёме (`max.poll.records`), в каком готов обработать. Отстаёт — просто растёт lag, а сообщения ждут в логе.

*Зачем и как устроено (инженерно).* В push-системах (брокер заталкивает) медленный потребитель переполняется — растут очереди в памяти, риск OOM и потерь. Kafka переносит «буфер» в устойчивый лог на диске: продюсер пишет со своей скоростью, консюмер читает со своей, а разрыв безопасно копится в партиции (в пределах retention). Это развязывает скорость producer и consumer — ключ к устойчивости под пиками нагрузки.

**Idempotent producer (идемпотентный продюсер).**

*Что это.* Режим продюсера, при котором **повторная отправка из-за ретрая не создаёт дубликат** в партиции.

*В чём выражается.* Включается `enable.idempotence=true` (в новых клиентах — по умолчанию). Проблема, которую решает: продюсер отправил сообщение, брокер записал, но ответ `ack` потерялся по сети → продюсер ретраит → без идемпотентности запись задвоится.

*Зачем и как устроено (инженерно).* Брокер присваивает продюсеру **PID (producer id)** и нумерует сообщения **sequence number** на партицию. Если приходит сообщение с уже виденным номером — брокер его отбрасывает (дедупликация на записи). Так `acks=all` + идемпотентность дают «записал ровно один раз» на стороне продюсера, без дублей от ретраев. Это фундамент exactly-once на участке producer→broker.

**Transactional producer (транзакционный продюсер).**

*Что это.* Механизм **атомарной записи**: несколько сообщений (в один или разные топики/партиции) + коммит offset'ов становятся видимы потребителям **всё-или-ничего**.

*В чём выражается.* Продюсер оборачивает работу в `beginTransaction() … commitTransaction()` (или `abortTransaction()`). Консюмеры с `isolation.level=read_committed` видят сообщения только после коммита; при аборте — не видят вообще.

*Зачем и как устроено (инженерно).* Нужен для паттерна **read-process-write** (Kafka Streams): «прочитал из топика A → обработал → записал в топик B и сдвинул offset A» должно быть атомарно, иначе при сбое получишь либо дубли, либо потерю. Технически — транзакционный координатор на брокере, маркеры commit/abort в логе, привязка offset-коммита к той же транзакции. Это и есть основа **exactly-once** внутри Kafka (Kafka→Kafka). На внешние системы (БД, HTTP) гарантия не распространяется.

**Schema Registry.**

*Что это.* Отдельный сервис — **хранилище схем сообщений** (Avro / Protobuf / JSON Schema), которое обеспечивает единый **контракт** между продюсерами и консюмерами.

*В чём выражается.* Продюсер регистрирует схему; в сообщение кладётся не вся схема, а маленький **schema id**. Консюмер по id достаёт схему из реестра и десериализует. Реестр проверяет **совместимость** новых версий (backward/forward): нельзя выкатить схему, которая сломает существующих потребителей.

*Зачем и как устроено (инженерно).* Решает главную боль событийных систем — **эволюцию контракта**: продюсер и консюмер деплоятся независимо, и без реестра продюсер может случайно начать слать несовместимый формат, а консюмеры — падать на десериализации. Реестр не даёт зарегистрировать несовместимую схему. Бонус — компактность (в сообщении id вместо схемы) и строгая типизация вместо «сырого JSON на честном слове». Для AQA это точка контроля: тест валидирует, что событие соответствует зарегистрированной схеме.

## 3.5. Продвинутые термины (спрашивают на мидла)

| Термин                          | Что это                                                                                                                                                                                           |
| ------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Replication factor (RF)**     | Сколько копий каждой партиции держит кластер. RF=3 → лидер + 2 фолловера на разных брокерах. У тебя на локальном стенде RF=1 (одна копия, отказоустойчивости нет).                                |
| **Leader / Follower**           | Для каждой партиции один брокер — лидер (через него идут все запись и чтение), остальные — фолловеры, тянут данные с лидера. Если лидер падает — один из ISR-фолловеров становится новым лидером. |
| **High Watermark (HW)**         | Максимальный offset, до которого сообщение реплицировано на все ISR-реплики. Консюмер видит сообщения **только** до HW — гарантия, что читаешь то, что уже надёжно записано.                      |
| **LEO (Log End Offset)**        | Offset следующего сообщения, которое будет записано в партицию (конец лога).                                                                                                                      |
| **Log segment**                 | Партиция физически хранится не одним файлом, а нарезана на сегменты (по размеру/времени). Retention удаляет **целые старые сегменты**, а не отдельные сообщения.                                  |
| **Log compaction**              | Альтернатива retention по времени: Kafka хранит **последнее** значение для каждого key, старые версии удаляет. Для «снимка состояния» (актуальный профиль пользователя по его id).                |
| **Tombstone**                   | Сообщение с key и `value=null`. В compacted-топике означает «удалить этот key». Маркер удаления.                                                                                                  |
| **Partition assignor**          | Стратегия распределения партиций по консюмерам в группе: `range`, `round-robin`, `sticky`, `cooperative-sticky`.                                                                                  |
| **Cooperative rebalance**       | Современный «мягкий» rebalance: не останавливает всю группу (stop-the-world), а переназначает только затронутые партиции. Меньше простоя.                                                         |
| **min.insync.replicas**         | Минимум ISR-реплик, которые должны подтвердить запись при `acks=all`. Если живых реплик меньше — продюсер получает ошибку (защита от тихой потери данных).                                        |

| **Heartbeat / session.timeout** | Консюмер шлёт «я жив» координатору. Не пришёл heartbeat за `session.timeout.ms` → считается мёртвым → rebalance.                                                                                  |

### Разбор терминов: ситуация, пример, зачем существует

#### Группа A — репликация и надёжность

**Replication factor (RF).**
*Ситуация.* Партиция физически лежит на диске одного брокера. Брокер — это железо/процесс, который может упасть, перезагрузиться, потерять диск. Если копия одна — вместе с брокером пропадает доступ к данным, а то и сами данные.
*С какими сущностями работаем.* Партиция и её копии, брокеры кластера, ISR, контроллер (он назначает лидеров копий). RF относится к **каждой** партиции топика: топик из 6 партиций с RF=3 = 18 физических копий на дисках.
*Проблема без репликации (RF=1).* Любое падение брокера = недоступность части топика (все партиции, чей лидер жил на нём) и потенциальная потеря непрочитанных данных. Нет резерва — нет отказоустойчивости.
*Пример.* Топик `payments`, RF=3 на кластере из 3 брокеров: у каждой партиции лидер + 2 фолловера на разных узлах. Умер один брокер — контроллер переизбирает лидеров из ISR на живых брокерах, клиенты продолжают работать.
*Как устроено (теория/факты).* RF нельзя задать больше числа брокеров (`RF ≤ N брокеров`). Задаётся при создании топика; изменить постфактум можно только через переназначение реплик (`kafka-reassign-partitions.sh`), а не флагом. Служебные топики имеют собственный RF (`offsets.topic.replication.factor`, `transaction.state.log.replication.factor`) — в проде их тоже ставят 3, иначе смерть одного брокера уронит хранение offset'ов. Опасная настройка рядом — `unclean.leader.election.enable`: если `true`, лидером может стать **не** синхронная реплика (доступность ценой возможной потери данных); прод-безопасный вариант — `false`.
*Зачем (инженерно).* RF — главный рычаг **надёжности против стоимости**: RF=3 переживает падение 2 брокеров, но утраивает место на диске и добавляет трафик репликации между узлами. Прод-стандарт — RF=3. На твоём одно-брокерном стенде RF максимум 1 — копию класть некуда, отказоустойчивости нет by design.

**Leader / Follower.**
*Ситуация.* Копий партиции несколько (по RF). Если бы в любую копию можно было писать независимо, две копии приняли бы разные сообщения на один и тот же offset — рассинхрон, «split brain», непонятно, какая версия правильная.
*С какими сущностями работаем.* Реплики одной партиции, брокеры, контроллер (выбирает лидера), ISR, leader epoch (номер «поколения» лидерства).
*Проблема без выделенного лидера.* Мультимастер-запись = конфликты версий и потеря гарантии порядка внутри партиции — фундамент Kafka развалился бы.
*Пример.* P0: лидер на B1, фолловеры на B2 и B3. Все продюсеры пишут в B1, классически и консюмеры читают с B1; B2/B3 только тянут (`fetch`) данные с лидера, догоняя его.
*Как устроено (теория/факты).* Ровно **один лидер** на партицию в каждый момент. Исторически чтение шло только с лидера; позже появился `fetch-from-follower` (KIP-392) — консюмер может читать с ближайшей реплики ради экономии межзонального трафика, но лидер записи всё равно один. У каждой партиции есть **preferred leader** (первая реплика в списke) — контроллер периодически возвращает лидерство к нему (`auto.leader.rebalance.enable`), чтобы нагрузка не съезжала. При смене лидера растёт **leader epoch** — это защищает от того, чтобы «зомби»-фолловер со старыми данными не затёр новые (по epoch фолловеры понимают, до какого offset их лог валиден, и обрезают лишнее — log truncation).
*Зачем (инженерно).* Единая точка записи даёт **согласованность** (одна истина на партицию) и сохраняет порядок; фолловеры дают **отказоустойчивость** (горячий резерв). Упал лидер → контроллер за секунды назначает новым лидером одну из синхронных реплик (ISR). Так совмещаются согласованность и доступность.

**High Watermark (HW) и LEO.**
*Ситуация.* Продюсер дописал сообщение в лидера, но фолловеры ещё не скопировали его. Если сразу отдать это сообщение консюмеру, а лидер упадёт до репликации — новый лидер (из ISR) этого сообщения не имеет, и получается, что консюмер прочитал то, чего в кластере уже нет. Это «фантомное чтение» / потеря согласованности.
*С какими сущностями работаем.* Лог лидера, логи фолловеров, ISR, offset, консюмер. HW и LEO — это счётчики offset'ов, а не данные.
*Проблема без HW.* Консюмеры видели бы нереплицированные («грязные») записи; при failover данные под ними исчезали бы — гарантии «прочитал = существует» не было бы.
*Пример.* LEO лидера = 100 (последняя запись — offset 99), но реплики в ISR догнали только до 95 → **HW = 95**. Консюмер видит сообщения только до offset 94 (до HW); 95–99 «висят» невидимыми, пока ISR не подтянут их и HW не сдвинется.
*Как устроено (теория/факты).* **LEO (Log End Offset)** — у каждой реплики свой: offset следующей записи (конец её лога). **HW (High Watermark)** лидера = **минимум LEO по всем репликам в ISR**: до этой границы сообщение точно есть у всех синхронных копий. Консюмерский `fetch` **ограничен HW** — брокер не отдаст выше. HW двигается вперёд по мере того, как фолловеры репортят свой прогресс лидеру. При смене лидера новый лидер может **обрезать** свой лог до согласованной точки по leader epoch (log truncation), чтобы не разъехаться со старым. (Транзакции добавляют ещё одну границу — LSO, Last Stable Offset, до неё видны только закоммиченные транзакции при `read_committed`.)
*Зачем (инженерно).* HW — это механизм, который делает **чтение согласованным при асинхронной репликации**: видно только то, что уже надёжно лежит на всех ISR и переживёт падение лидера. Цена — небольшая задержка видимости (сообщение появляется для консюмера не мгновенно, а после репликации).

**min.insync.replicas.**
*Ситуация.* `acks=all` означает «подтвердили все синхронные реплики (ISR)». Но ISR — множество динамическое: реплики могут отставать и выпадать из него. Если фолловеры отвалились и в ISR остался только лидер, то «все ISR» = одна копия — запись подтвердится по одной копии, и падение этого брокера = тихая потеря данных.
*С какими сущностями работаем.* Продюсер (с `acks=all`), ISR, лидер партиции. `min.insync.replicas` — конфиг топика (или брокера по умолчанию).
*Проблема без него.* `acks=all` при схлопнувшемся ISR деградирует до `acks=1` незаметно — ложное чувство надёжности.
*Пример.* RF=3, `min.insync.replicas=2`. Отвалились 2 фолловера, в ISR остался только лидер (1 < 2) → продюсер получает `NotEnoughReplicas`/`NotEnoughReplicasAfterAppend`, запись **отклоняется**. Лучше явная ошибка (можно отретраить/поднять тревогу), чем молчаливая запись в единственную копию.
*Как устроено (теория/факты).* Настройка проверяется **только вместе с `acks=all`** — при `acks=0/1` она игнорируется. Ключевой момент — соотношение с RF: чтобы кластер и **писал, и был надёжен** при падении одного брокера, нужно `RF > min.insync.replicas` (классика: `RF=3`, `min.insync=2` — можно потерять 1 брокер и продолжать писать). Если поставить `min.insync = RF = 3`, то падение **любого** брокера уже блокирует запись (максимум надёжности ценой доступности) — это осознанный компромисс, а не «чем больше, тем лучше».
*Зачем (инженерно).* Это нижняя граница долговечности при `acks=all`: «не подтверждай запись, пока её не приняли минимум N копий». Связка **`acks=all` + `min.insync.replicas=2` + `RF=3`** — прод-стандарт для критичных данных (деньги, заказы): переживает падение одного брокера без потерь и без тихой записи в единственную реплику.
*К чему приведёт эта ошибка (последствия по цепочке).*
1. **Продюсер получает ошибку, а не «ок».** Запись в эту партицию не подтверждена, сообщение не считается отправленным. Ошибка **видимая** (приходит продюсеру), а не тихая.
2. **Продюсер ретраит.** Это retriable-ошибка: клиент повторяет отправку (в пределах `retries` / `delivery.timeout.ms`), ожидая, что ISR восстановится (отставшая реплика догонит лидера и вернётся в синхронные). Восстановился за окно ретраев — сообщение уходит, ты можешь даже не заметить просадку.
3. **Не восстановился за отведённое время** — ошибка отдаётся **в приложение** (исключение/колбэк при `send`). Дальше по коду: операция «создать заказ» падает / возвращает 5xx и событие не публикуется; если приложение ошибку проглотит — потеря уже на уровне бизнес-логики (дефект кода, не Kafka).
4. **Запись в партицию фактически заблокирована**, пока ISR не поднимется: страдает **доступность на запись именно этой партиции** (другие партиции со здоровым ISR продолжают принимать запись).

*Смысл — осознанный размен доступности на надёжность.* Настройка специально превращает потенциальную **тихую потерю данных** (записали в одну копию → брокер упал → данные исчезли молча) в **громкую ошибку записи**, которую видно, можно отретраить и на которую вешают алерт.

*Что делать при такой ошибке (эксплуатация).*
- это сигнал, что **реплики отвалились/отстают** — упал брокер, тормозит сеть/диск, идёт долгая репликация; смотрят under-replicated партиции и чинят/поднимают брокеры;
- на продюсере — вменяемые `retries` / `delivery.timeout.ms`, чтобы кратковременные просадки ISR переживались автоматически;
- проверить конфиг: должно быть **`RF > min.insync.replicas`** (классика `RF=3`, `min.insync=2`), иначе при `min.insync = RF` падение любого брокера сразу блокирует запись — частая причина «внезапно не пишется».

*Формула на собес:* *`NotEnoughReplicas` блокирует запись в партицию и заставляет продюсера ретраить/сообщить об ошибке — это намеренная защита: система выбирает временную недоступность записи вместо тихой потери данных.*

#### Группа B — устройство лога на диске

**Log segment (сегмент лога).**
*Ситуация.* Партиция — это бесконечно растущий append-only лог. Хранить его одним гигантским файлом невозможно: нельзя эффективно удалять старое из середины файла, тяжело искать по offset, файловая система не любит файлы на терабайты.
*С какими сущностями работаем.* Партиция, файлы на диске: `*.log` (данные), `*.index` (индекс offset→позиция), `*.timeindex` (индекс timestamp→offset), активный сегмент, закрытые сегменты.
*Проблема без сегментации.* Retention и compaction стали бы дорогими операциями «переписать весь файл»; поиск сообщения по offset — линейным сканом.
*Пример.* Партиция нарезана на сегменты (по размеру или времени): `00000000000000000000.log`, `...0000005000.log`, `...0000009000.log` (в имени — базовый offset). В **активный** (последний) сегмент идёт запись; остальные закрыты и неизменны.
*Как устроено (теория/факты).* Новый сегмент открывается при достижении `segment.bytes` (по умолчанию 1 ГБ) или `segment.ms` (по времени). К каждому сегменту идёт **разреженный индекс** (`index.interval.bytes`) — не на каждое сообщение, а раз в N байт, поэтому поиск по offset = «найти сегмент по базовому offset → прыгнуть по индексу → дочитать». Retention и compaction работают **только с закрытыми** сегментами — **активный сегмент никогда не удаляется и не компактится**. Отсюда неинтуитивное: даже с `retention.ms=1000` сообщение может лежать дольше, пока его сегмент активен и не закрылся.
*Зачем (инженерно).* Сегменты дают **дешёвое удаление** (retention сносит целый старый сегмент одним `unlink`, не трогая сообщения по одному), **быстрый поиск** по offset/времени и **последовательную запись** в один активный файл (максимум скорости диска). Практический вывод: и retention, и compaction работают с гранулярностью сегмента, а не отдельного сообщения.

**Log compaction.**
*Ситуация.* Иногда в топике нужен не поток событий, а **актуальное состояние по ключу**: последний профиль пользователя, текущая цена товара, свежая конфигурация. Обычный retention по времени тут плох: удалишь по сроку — потеряешь последнее известное значение старого, но всё ещё нужного ключа; не удаляй — храни бесконечную историю правок.
*С какими сущностями работаем.* Ключ сообщения, compacted-топик, фоновый поток-уборщик (**log cleaner**), проекции состояния (Kafka Streams KTable, кэши сервисов).
*Проблема без compaction.* Для «снимка состояния» пришлось бы либо терять данные по retention, либо реплеить километровую историю правок при каждом старте потребителя.
*Пример.* Топик `user-profiles`, `cleanup.policy=compact`. Для `key=user-42` было 5 обновлений — compaction со временем оставит только **последнее** значение, старые версии удалит. Новый консюмер читает топик с начала и получает актуальный снимок по всем пользователям, а не всю историю.
*Как устроено (теория/факты).* `cleanup.policy` бывает `delete` (по умолчанию), `compact`, или `compact,delete` (и снимок, и ограничение по времени). Cleaner делит лог на «tail» (уже сжатую часть) и «head» (свежую); чистка запускается, когда доля «грязных» записей превышает `min.cleanable.dirty.ratio` (по умолчанию 0.5). Compaction гарантирует, что для каждого ключа останется **как минимум последнее** значение (может временно оставаться и больше — это не «ровно одно немедленно»). Важное требование — у сообщений **должен быть ключ** (записи с `key=null` в compacted-топике недопустимы). Сама Kafka использует compaction для служебного `__consumer_offsets` — там как раз нужно «последнее закоммиченное значение на группу+партицию».
*Зачем (инженерно).* Превращает лог в **таблицу «ключ → последнее значение»**, не теряя достоинств Kafka (реплей снимка, чтение многими группами, репликация). Это основа хранения состояния и материализованных вью. Отличие от `delete`-retention: там критерий удаления — «старое по времени/размеру», тут — «есть ли более новое значение для этого же ключа».

**Tombstone (надгробие).**
*Ситуация.* В compacted-топике, который хранит «последнее значение на ключ», иногда ключ надо **удалить совсем** (пользователь удалён, товар снят). Но лог — append-only: физически стереть запись из середины нельзя, можно только дописать в конец.
*С какими сущностями работаем.* Compacted-топик, ключ, значение `null`, log cleaner, потребители снимка.
*Проблема без tombstone.* Раз удалять нельзя, а можно только дописывать — ключ жил бы в compacted-топике вечно, снимок состояния «протёк» бы удалёнными сущностями.
*Пример.* Пишем `key=user-42, value=null`. Это и есть tombstone — «надгробие» для ключа. Потребители, читающие снимок, трактуют `null` как «этого ключа больше нет» и убирают его из своей проекции/кэша.
*Как устроено (теория/факты).* Compaction, встретив tombstone, удаляет все прежние записи этого ключа. Сам маркер живёт ещё окно `delete.retention.ms` (по умолчанию ~24 ч) — специально, чтобы **отставшие консюмеры успели увидеть факт удаления**, а не пропустили его; после этого окна удаляется и сам tombstone. Отсюда важность окна: слишком маленькое — медленный консюмер не узнает про удаление и оставит «зомби»-ключ у себя.
*Зачем (инженерно).* Tombstone — единственный способ выразить удаление в append-only логе: удаление становится обычной записью-маркером. Для AQA: `value=null` в compacted-топике — не баг и не «пустое сообщение», а осмысленный сигнал «удали ключ»; тест должен это учитывать.

#### Группа C — группа консюмеров и rebalance

**Partition assignor (стратегия назначения).**
*Ситуация.* В группе N консюмеров и M партиций — кто-то должен решить, кто какие партиции читает, и пересчитывать это при каждом изменении состава. Причём делать это ровно (без перекоса) и по возможности без лишних «переездов».
*С какими сущностями работаем.* Consumer group, партиции всех подписанных топиков, group coordinator (брокер) и **group leader** — это один из консюмеров, а не брокер: именно он вычисляет раскладку, координатор лишь раздаёт результат.
*Проблема без продуманной стратегии.* Перекос (один консюмер держит вдвое больше партиций) или тотальная тасовка на каждом rebalance (все партиции переезжают, консюмеры сбрасывают кэши/состояние).
*Пример.* `range` — раздаёт подряд идущие партиции **по каждому топику** отдельно (при нескольких топиках перекашивает: первый консюмер собирает P0 всех топиков); `round-robin` — раскидывает все партиции по кругу (ровнее); `sticky` — как round-robin, но старается **сохранить прежние** назначения; `cooperative-sticky` — то же + инкрементальный (кооперативный) протокол rebalance.
*Как устроено (теория/факты).* Задаётся `partition.assignment.strategy`. Исторический дефолт — `range`; современные клиенты по умолчанию — `cooperative-sticky`. Раскладку считает group leader по алгоритму ассайнора и рассылает через координатора (фаза SyncGroup). «Липкость» (sticky) минимизирует число партиций, сменивших владельца, — это прямо экономит прогрев состояния у stateful-консюмеров.
*Зачем (инженерно).* От выбора зависят **равномерность** нагрузки и **стоимость rebalance**. `sticky` уменьшает «переезды» (меньше сброса кэшей/состояния), `cooperative-sticky` — вдобавок не останавливает всю группу (см. ниже). Для stateful-обработки это критично.

**Cooperative rebalance.**
*Ситуация.* Классический (eager) rebalance при любом изменении состава **отзывает все** партиции у всех консюмеров и раздаёт заново. Пока идёт пересчёт, вся группа не читает — «stop-the-world». В большой группе, где rebalance случается часто, это ощутимые регулярные паузы и скачки lag.
*С какими сущностями работаем.* Consumer group, координатор, фазы rebalance (revoke → assign), ассайнор `cooperative-sticky`.
*Проблема с eager-протоколом.* Даже добавление/удаление одного консюмера роняет чтение у **всех** — простой пропорционален размеру группы, а не масштабу изменения.
*Пример.* 10 консюмеров, добавили 11-го. Eager: все 10 бросают свои партиции, пересчёт, все берут заново (общая пауза). Cooperative: отзываются только те несколько партиций, что переезжают к новому консюмеру; остальные 9–10 продолжают читать **без паузы**.
*Как устроено (теория/факты).* Кооперативный протокол (KIP-429) делает rebalance в **два прохода**: сначала отзываются только партиции, которые реально должны сменить владельца, затем они назначаются — без глобальной остановки. Требует ассайнора `cooperative-sticky`. Рядом стоит **static membership** (`group.instance.id`, KIP-345): консюмер с фиксированным id при коротком рестарте (в пределах `session.timeout`) **не** вызывает rebalance вовсе — координатор ждёт его возвращения. Вместе они резко снижают и частоту, и стоимость перебалансировок.
*Зачем (инженерно).* Убирает главную операционную боль больших групп — простой на каждом rebalance. Переназначается только «дельта». Критично для stateful-консюмеров (дорогой прогрев состояния) и сервисов с требованием к минимальной задержке.

**Group coordinator (координатор группы).**
*Ситуация.* Группе нужен «дирижёр»: помнить, кто в составе, хранить offset'ы, замечать павших консюмеров, запускать и разруливать rebalance. Если бы консюмеры пытались договариваться между собой напрямую — это распределённый консенсус на клиентах, хрупко и сложно.
*С какими сущностями работаем.* Consumer group, брокер-координатор, служебный топик `__consumer_offsets` (по умолчанию 50 партиций), протокол группы (JoinGroup/SyncGroup/Heartbeat/OffsetCommit).
*Проблема без координатора.* Некому централизованно детектировать падения и назначать партиции; offset'ы негде надёжно хранить.
*Пример.* Для группы `billing` координатором становится конкретный брокер — тот, что является лидером партиции `__consumer_offsets`, в которую попадает `hash(group.id) % 50`. Консюмеры шлют ему heartbeat, запросы JoinGroup при старте и OffsetCommit по мере чтения; он инициирует rebalance при изменении состава.
*Как устроено (теория/факты).* Координатор **вычисляется детерминированно** из `group.id` — поэтому все консюмеры одной группы находят одного и того же координатора. Это **не** то же самое, что кластерный **контроллер** (тот заведует метаданными кластера и лидерами партиций) — координатор заведует одной группой. Важный нюанс: сам координатор состояние группы (offset'ы, метаданные членов) держит **в логе** `__consumer_offsets`, а не в памяти «в себе» — поэтому при его падении другой брокер (новый лидер этой offsets-партиции) поднимает состояние из лога и становится координатором. Раскладку партиций при этом считает **group leader** (консюмер), а координатор её лишь распространяет.
*Зачем (инженерно).* Единая точка управления группой убирает клиентский консенсус и делает поведение предсказуемым. Хранение состояния в реплицируемом логе даёт координатору **отказоустойчивость** — группа переживает падение своего координатора.

**Heartbeat / session.timeout.**
*Ситуация.* Консюмер может упасть, потерять сеть или зависнуть молча — без явного «я ухожу». Координатору нужно как-то понять, что консюмера больше нет, отдать его партиции живым и при этом не ждать вечно и не дёргаться на каждую микропаузу.
*С какими сущностями работаем.* Консюмер (его фоновый heartbeat-поток), координатор, таймеры `heartbeat.interval.ms`, `session.timeout.ms`, `max.poll.interval.ms`.
*Проблема без механизма живости.* Либо «мёртвые» консюмеры вечно держат свои партиции (их никто не читает, lag растёт), либо приходится грубо ждать фиксированный таймаут на всё.
*Пример.* Консюмер шлёт heartbeat каждые `heartbeat.interval.ms` (напр. 3 c). Если координатор не получил ни одного за `session.timeout.ms` (напр. 10 c) — считает консюмера мёртвым, исключает из группы и запускает rebalance; его партиции уходят живым.
*Как устроено (теория/факты).* Heartbeat идёт в **фоновом потоке**, независимо от обработки, и его интервал обычно берут ≈ 1/3 от `session.timeout.ms` (чтобы за окно успело пройти несколько ударов). `session.timeout.ms` зажат серверными границами `group.min.session.timeout.ms` / `group.max.session.timeout.ms`. Отдельная, часто путаемая настройка — **`max.poll.interval.ms`**: она ловит «консюмер жив (heartbeat идёт), но завис в обработке и не зовёт `poll()`». Если между вызовами `poll()` прошло больше этого лимита — консюмер сам покидает группу (это и есть механизм, порождающий «rebalance storm» при слишком долгой обработке; лечится ускорением обработки, меньшим `max.poll.records` или бо́льшим лимитом). Комплементарно — static membership (`group.instance.id`): короткий рестарт в пределах session.timeout не вызывает rebalance.
*Зачем (инженерно).* Это **детектор живости** с балансом скорости реакции и стабильности: маленький `session.timeout` → ложные срабатывания на паузах GC/сети → лишние rebalance; большой → долго не замечаем реальные падения, растёт lag. Два таймера разводят два разных отказа: «процесс умер» (heartbeat) и «процесс жив, но завис» (poll interval).

## 3.6. Пирамида хранения vs логические абстракции

![|797](https://raw.githubusercontent.com/goalbeam-hash/notes/main/assets/kafka-diagram-1.png)
Все сущности Kafka удобно разложить на **две оси**: что физически **хранит данные** и с какими **логическими абстракциями работают клиенты** (продюсеры/консюмеры). Их часто путают — топик кажется «уровнем хранения», а это логика.

### Ось 1 — физическое хранение (вложенность = «содержит»)

```text
Кластер            ← группа брокеров = единая система (несколько контейнеров)
  └─ Брокер        ← 1 JVM-процесс = 1 контейнер (хранит партиции на диске)
       └─ Партиция ← append-only лог: единица параллелизма, порядка, хранения
            └─ Сегмент   ← партиция нарезана на файлы (retention чистит целыми сегментами)
                 └─ Сообщение ← конкретная запись @ offset

  ⟂ Реплика — стоит СБОКУ от иерархии: копия партиции на ДРУГОМ брокере.
    Именно она даёт отказоустойчивость (leader + followers, ISR), а не сама партиция.
```

| Уровень | Что это | Единица чего |
|---|---|---|
| **Кластер** | Группа брокеров как одна система | Масштаб и координация |
| **Брокер** | Один процесс Kafka (= контейнер) | Хранения и обслуживания клиентов |
| **Партиция** | Append-only лог на диске брокера | **Параллелизма и порядка** |
| **Сегмент** | Файлы, на которые нарезана партиция | Физического хранения / retention |
| **Сообщение** | Запись `key+value+headers` по offset | Данных |
| **Реплика** | Копия партиции на другом брокере | **Отказоустойчивости** |

### Ось 2 — логические абстракции (с ними работают клиенты)

Продюсеры и консюмеры — это **клиенты снаружи** кластера, они не часть пирамиды хранения. Они оперируют логическими понятиями, которые «ложатся» на физические партиции.

| Абстракция | Что это | Зачем клиенту |
|---|---|---|
| **Producer** | Клиент, который пишет | Публикует события в топик (в лидера партиции) |
| **Consumer** | Клиент, который читает | Забирает события из топика (pull, с лидера) |
| **Топик** | Именованный набор партиций | «Домен данных»; логическая обёртка над партициями |
| **Ключ (key)** | Идентификатор сообщения | Маршрут в партицию + порядок для сущности |
| **Consumer Group** | Группа читателей с общим `group.id` | Делёж партиций (параллелизм) + fan-out между группами |
| **Offset** | Позиция чтения группы | Закладка «докуда прочитал», прогресс |
| **Message** | key + value + headers + timestamp | Единица данных, которой обмениваются |

### Как логика ложится на хранение

- **Топик** → его **партиции** на брокерах (топик сам ничего не хранит);
- **Key** → выбор **партиции** (`hash(key) % N`);
- **Offset** → позиция внутри конкретной **партиции**;
- **Consumer Group** → чьи это offset'ы (у каждой группы свои).

**Частые ошибки, которые это снимает:**

- «Кластер — это контейнер» ❌ → контейнер = один **брокер**; кластер = несколько брокеров.
- «Партиция — единица отказоустойчивости» ⚠️ → партиция = параллелизм/порядок; отказоустойчивость даёт **реплика**.
- «Топик — уровень хранения» ❌ → топик **логический**, хранят партиции.
- «Есть топики продюсеров и топики консюмеров» ❌ → топик один; продюсер его пишет, консюмер читает. (Единственный служебный «консюмерский» топик — внутренний `__consumer_offsets`, куда Kafka сама пишет offset'ы групп.)

## 3.7. Логика клиентов — подробно

Это раздел про **логическую сторону** Kafka: то, чем оперируют продюсеры и консюмеры, поверх физического хранения из 3.6. Здесь нет «магии брокера» — есть несколько простых правил, из которых складывается вся мощь.

### 3.7.1. Message — что реально едет

Сообщение (record) — это не «строка текста», а структура:

| Поле                                       | Смысл                                                     | Кто использует                                   |     |
| ------------------------------------------ | --------------------------------------------------------- | ------------------------------------------------ | --- |
| **key**                                    | идентификатор для партиционирования (может быть `null`)   | продюсер (выбор партиции), compaction            |     |
| **value**                                  | полезная нагрузка (JSON/Avro/байты)                       | бизнес-логика консюмера                          |     |
| **headers**                                | метаданные (`trace-id`, `content-type`, `schema-version`) | трассировка, маршрутизация на стороне приложения |     |
| **timestamp**                              | время события/записи                                      | seek-by-time, оконные агрегации                  |     |
| *(добавляет брокер)* **offset, partition** | адрес записи                                              | позиционирование консюмера                       |     |

Ключевая мысль: **key и value — разные вещи**. Value — это «что произошло», key — «к чему это относится» (по нему считается партиция). Можно слать value без key (`key=null`) — тогда теряется привязка к партиции и порядок между такими сообщениями.

### 3.7.2. Топик — как выбирают по смыслу

Топик — это логический **тип потока событий**, «канал» под один смысл. Практические правила, по которым проектируют топики:

- **Один топик = один тип события с общей схемой и жизненным циклом.** `orders`, `payments`, `shipments` — раздельно, потому что у них разные потребители, retention, права, схема. Смешивать разнородное в один топик = каша (консюмер вынужден фильтровать чужое, схема размывается).
- **Гранулярность — по «кто это потребляет и как долго хранить».** Если у двух типов событий разные сроки хранения (клики — 1 день, заказы — 30 дней) или разные читатели — это два топика.
- **Не плодить лишнего.** Тысяча почти пустых топиков = накладные расходы на метаданные и партиции. Ориентир: топик оправдан, когда у него свой смысл, свои потребители и свой контракт.
- **Именование как неймспейс.** Часто используют префиксы-домены: `billing.orders`, `billing.invoices`, `analytics.clicks` — это не «группа топиков» (такой сущности нет), а соглашение об именах + ACL по маске.

Пример логики: «сервис платежей эмитит событие успешной оплаты» → нужен топик, который читают биллинг, уведомления и аналитика, с retention 7–30 дней → создаём `payments` (не кладём это в общий `events`).

### 3.7.3. Consumer group и group.id — почему это единица параллелизма

**Consumer group** — набор консюмеров с одинаковым `group.id`. `group.id` — это строка-идентификатор, которая говорит Kafka: «эти процессы — одна логическая команда, дели работу между ними и веди для них общий прогресс (offset'ы)».

Почему группа — **единица параллелизма**:

- Kafka делит партиции топика **между членами группы**: каждая партиция → ровно одному консюмеру. Значит, чтобы читать топик в K потоков, ты просто запускаешь K консюмеров с одним `group.id` — Kafka сама раскидает партиции. Масштабирование чтения = добавить консюмер в группу (до числа партиций).
- Потолок параллелизма группы = **число партиций**. 6 партиций → максимум 6 полезных консюмеров, 7-й простаивает.
- Прогресс (offset) ведётся **на группу**, а не на отдельного консюмера — поэтому падение/замена консюмера не теряет позицию: новый владелец партиции продолжит с общего committed offset.

**Что такое `group.id` технически.** Это **настройка консюмера** (одна строка в конфиге клиента), например `group.id="billing"`. При старте консюмер сообщает её брокеру-координатору при запросе JoinGroup — так Kafka понимает, к какой группе его приписать. Группа **не создаётся заранее** отдельной командой: она возникает автоматически, когда первый консюмер с таким `group.id` подключился, и «умирает» (становится `Empty`, а потом чистится), когда все ушли и истёк срок хранения offset'ов. То есть группа — это не объект, который ты администрируешь, а **живое состояние**: члены + их offset'ы в `__consumer_offsets`.

> **Кто такие «члены» (members).** Член группы = один **подключённый консюмер** (активный экземпляр, сделавший JoinGroup и держащий сессию heartbeat'ами; у него свой `member id`). Именно между членами координатор делит партиции. Нюансы: член ≠ сервис/процесс — один процесс может создать несколько консюмеров с одним `group.id` (обычно всё же 1 инстанс = 1 консюмер = 1 член); в `--describe` и в Kafka UI (вкладка **Members**) члены видны как строки с `CONSUMER-ID`/`HOST`. Члены — **динамическая** часть группы (приходят и уходят); когда живых членов 0, группа переходит в `Empty`, но её **offset'ы сохраняются** (пока не истечёт `offsets.retention.minutes`) — поэтому новый консюмер с тем же `group.id` продолжит с сохранённой закладки.

**Как выбирают/создают группы по логике** (важно на собесе):

- **Одна логическая обязанность = одна группа.** «Сервис биллинга» — это группа `billing` (сколько бы инстансов сервиса ни крутилось — у всех один `group.id`, они делят партиции). «Сервис уведомлений» — отдельная группа `notifications`.
- **Разные группы для разных реакций на одно событие** (это и есть fan-out, ниже).
- **`group.id` = стабильное имя роли, а не имя инстанса.** Если каждый инстанс поставит свой уникальный `group.id`, они перестанут делить работу — каждый прочитает весь топик целиком (частая ошибка: «почему каждое сообщение обрабатывается 5 раз?» → 5 инстансов с разными group.id вместо одного общего).

> **Что такое «инстанс».** Инстанс (instance) — это **один запущенный экземпляр твоего сервиса/приложения**: отдельный процесс, обычно в своём контейнере/поде. Когда сервис масштабируют, его запускают в нескольких копиях ради нагрузки и отказоустойчивости — например, 5 подов `billing-service` в Kubernetes. Это и есть «5 инстансов»: один и тот же код, 5 работающих копий. Каждый инстанс поднимает внутри себя консюмер Kafka.
>
> Смысл правила: все инстансы одной роли должны использовать **один и тот же `group.id`** (имя роли, напр. `"billing"`), тогда Kafka увидит их как одну группу из 5 членов и **поделит партиции между ними** — каждое сообщение обработает только один инстанс. Если же каждому инстансу дать **уникальный** `group.id` (например, подставить hostname/pod-имя), Kafka решит, что это 5 **разных** групп по одному члену — и каждая группа получит **весь** поток (fan-out), то есть каждое сообщение обработается 5 раз (списание денег 5 раз — авария).
>
> Практика: `group.id` берут из **имени роли/сервиса** (конфиг, одинаковый для всех реплик), а НЕ из уникальных признаков инстанса (hostname, pod name, случайный id). Уникальный per-инстанс идентификатор нужен в другом месте — `group.instance.id` для static membership, но `group.id` при этом общий.

```text
ПРАВИЛЬНО: 5 инстансов, один group.id="billing"    ОШИБКА: 5 инстансов, у каждого свой group.id
   ┌ billing-pod-1 ┐                                   billing-pod-1 (group "billing-1") ← весь топик
   ├ billing-pod-2 ┤  один group "billing"             billing-pod-2 (group "billing-2") ← весь топик
   ├ billing-pod-3 ┤  → партиции ПОДЕЛЕНЫ,              billing-pod-3 (group "billing-3") ← весь топик
   ├ billing-pod-4 ┤    сообщение обработано 1 раз      billing-pod-4 (group "billing-4") ← весь топик
   └ billing-pod-5 ┘                                    billing-pod-5 (group "billing-5") ← весь топик
                                                        = каждое сообщение обработано 5 раз!
```

**Как это выглядит в коде (subscribe = работа через группу).**

```typescript
// kafkajs: консюмер в группе billing
const consumer = kafka.consumer({ groupId: 'billing' });   // ← group.id
await consumer.connect();
await consumer.subscribe({ topic: 'payments', fromBeginning: false });
await consumer.run({
  eachMessage: async ({ topic, partition, message }) => {
    process(message);        // Kafka сама назначила партиции и ведёт offset группы
  },
});
// запустишь 3 таких процесса с groupId:'billing' → партиции разделятся между ними
```

**Команды для работы с группами (CLI).**

```powershell
# список всех групп
docker exec kafka /opt/kafka/bin/kafka-consumer-groups.sh --bootstrap-server localhost:9092 --list
# детали группы: члены, назначение партиций, current/end offset, LAG
docker exec kafka /opt/kafka/bin/kafka-consumer-groups.sh --bootstrap-server localhost:9092 --group billing --describe
# перемотать offset группы на начало (replay); группа должна быть без активных консюмеров
docker exec kafka /opt/kafka/bin/kafka-consumer-groups.sh --bootstrap-server localhost:9092 `
  --group billing --topic payments --reset-offsets --to-earliest --execute
# удалить группу (когда она Empty)
docker exec kafka /opt/kafka/bin/kafka-consumer-groups.sh --bootstrap-server localhost:9092 --group billing --delete
```

> Кстати, `kafka-console-consumer.sh` без `--group` не «читает без группы» — он молча создаёт **временную случайную группу** `console-consumer-XXXXX`. Полноценное «без группы» — это другой режим (ниже).

### 3.7.3.1. Можно ли использовать консюмер БЕЗ группы?

Да — и это важный кейс. У консюмера есть **два режима подписки**:

| Режим | Метод | Кто назначает партиции | Rebalance | Offset ведёт |
|---|---|---|---|---|
| **С группой** | `subscribe(topics)` | Kafka (координатор + ассайнор) | да | группа (в `__consumer_offsets`) |
| **Без координации группы** | `assign(partitions)` | **ты сам, вручную** | нет | ты сам (seek / внешнее хранилище) |

При `assign()` ты **явно указываешь**, какие партиции читать, и сам управляешь позицией через `seek()`. Координатор группы, дележ партиций и rebalance при этом **не задействованы** — это «ручной» консюмер.

```typescript
// «Ручной» режим: читаем конкретную партицию с конкретного offset, без группы
const consumer = kafka.consumer({ groupId: 'adhoc-tool' }); // groupId может требоваться клиентом, но координация не используется
await consumer.connect();
// назначаем партиции сами — никакого дележа и rebalance
await consumer.assign([{ topic: 'orders', partition: 4 }]);
await consumer.seek({ topic: 'orders', partition: 4, offset: '42' }); // читаем ровно с offset 42
```

**Когда НЕ нужна consumer group (используем `assign` / ручной режим):**

- **Утилиты и разовые задачи:** «прочитать партицию 4 с offset 42 и посмотреть содержимое», отладка, дамп топика. Дележ и rebalance тут только мешают.
- **Полный детерминизм:** нужно, чтобы **этот** процесс читал **строго определённые** партиции (например, шардирование обработки по внешней логике), а не «как назначит Kafka».
- **Свой учёт offset:** offset хранишь во внешней системе (в той же БД, что и результат обработки) ради строгой согласованности/exactly-once — тогда `__consumer_offsets` не нужен, позицию задаёшь через `seek()`.
- **Один читатель, которому нужны ВСЕ партиции сразу** и не нужна балансировка между инстансами.
- **Replay точечно:** перечитать конкретный диапазон offset'ов без влияния на прод-группу.

**Когда группа НУЖНА (используем `subscribe`):**

- нужно **масштабировать** чтение несколькими инстансами и чтобы Kafka сама делила партиции;
- нужна **отказоустойчивость**: упал инстанс — его партиции автоматически перешли живым;
- нужно, чтобы Kafka **вела прогресс** за тебя (committed offset), и рестарт продолжал с места остановки;
- нужен **fan-out** (несколько независимых потребителей одного топика — каждый своей группой).

Правило: **сервис в проде → почти всегда группа** (масштаб + отказоустойчивость + авто-offset). **Инструмент/скрипт/спец-логика с ручным контролем → `assign` без координации.**

### 3.7.3.2. «На что делятся партиции?» — частая путаница режимов

Важно не смешать два режима: в `subscribe` (с группой) партиции **никогда не указываются вручную** — их раздаёт Kafka. Ручное указание партиций — это другой режим (`assign`), и там дележа нет вообще.

- **`assign()`** — ты сам прописываешь партиции → **никакого дележа**, группа не участвует.
- **`subscribe()`** — ты подписываешься на **топик**, а Kafka сама раздаёт партиции этого топика между членами группы. Вручную ничего не назначаешь.

**«На что делятся?»** Партиции у топика уже существуют — их число зафиксировано при создании (например, 6). «Делить» = **раздать эти 6 существующих партиций между консюмерами группы**, каждая — ровно одному.

```text
Топик orders = 6 партиций (P0..P5) — число задано при создании

1 консюмер в группе:   C1 ← P0,P1,P2,P3,P4,P5   (все 6 ему)
2 консюмера:           C1 ← P0,P1,P2   C2 ← P3,P4,P5
3 консюмера:           C1 ← P0,P1  C2 ← P2,P3  C3 ← P4,P5
```

**«Как делим?»** Руками — никак. Раскладку считает Kafka (group leader по стратегии ассайнора, раздаёт координатор). Ты только запускаешь/останавливаешь консюмеры с одним `group.id`, а rebalance пересчитывает назначение автоматически.

**Когда возникает запрос на масштабирование чтения.** Главный триггер — **растёт consumer lag**: продюсер пишет быстрее, чем группа успевает читать, необработанные сообщения копятся, данные в UI/БД отстают. Ситуации: пик трафика (распродажа, массовая рассылка), тяжёлая обработка каждого сообщения, backlog после простоя сервиса. Сигнал — колонка `LAG` в `--describe` стабильно растёт. Реакция — добавить консюмеров в группу (до числа партиций).

**Команды — дележ и масштабирование вживую.**

```powershell
# топик на 6 партиций
docker exec kafka /opt/kafka/bin/kafka-topics.sh --bootstrap-server localhost:9092 `
  --create --topic orders --partitions 6 --replication-factor 1 --if-not-exists

# Терминал 1 — один консюмер группы workers (заберёт все 6 партиций)
docker exec -it kafka /opt/kafka/bin/kafka-console-consumer.sh `
  --bootstrap-server localhost:9092 --topic orders --group workers

# смотрим раскладку и lag
docker exec kafka /opt/kafka/bin/kafka-consumer-groups.sh `
  --bootstrap-server localhost:9092 --group workers --describe
```

Пока консюмер один — все партиции на нём, lag растёт:

```text
TOPIC   PARTITION  CURRENT-OFFSET  LOG-END-OFFSET  LAG    CONSUMER-ID
orders  0..5       ...             ...             ~12000 consumer-1   ← один тянет все 6, не справляется
```

Масштабируем — запускаем ещё 2 консюмера с ТЕМ ЖЕ `--group workers` (Терминалы 2 и 3):

```powershell
docker exec -it kafka /opt/kafka/bin/kafka-console-consumer.sh `
  --bootstrap-server localhost:9092 --topic orders --group workers
```

После подключения — rebalance, снова `--describe`:

```text
TOPIC   PARTITION  ...  LAG   CONSUMER-ID
orders  0,1        ...  ~200  consumer-1
orders  2,3        ...  ~150  consumer-2
orders  4,5        ...  ~110  consumer-3     ← по 2 партиции на консюмера, LAG падает
```

Партиции автоматически поделились 2/2/2 — ты нигде не писал «consumer-2, читай P2,P3». Потолок: масштаб упирается в число партиций — 7-й консюмер при 6 партициях **простаивает**. Поэтому партиции закладывают с запасом.

### 3.7.4. Дележ партиций в группе — как именно происходит параллелизм

```text
Topic "orders" — 6 партиций          Group "billing" — 3 консюмера
P0 P1 P2 P3 P4 P5

Consumer A ← P0, P1
Consumer B ← P2, P3
Consumer C ← P4, P5
```

Правила:

- каждая партиция назначена **ровно одному** консюмеру группы (никогда двум — иначе сломались бы порядок и общий offset);
- назначение считает **group leader** (один из консюмеров) по стратегии ассайнора, раздаёт координатор;
- изменился состав (упал/добавился консюмер, поменялось число партиций) → **rebalance** пересчитывает раскладку;
- консюмеров больше, чем партиций → лишние в резерве (подхватят при падении).

Внутри группы это **competing consumers**: сообщение обрабатывается один раз (кем-то одним из группы) — так делится нагрузка.

### 3.7.5. Fan-out — одно событие, много независимых реакций

**Fan-out** — когда одно и то же событие независимо получают **несколько разных групп**. Между группами партиции **не делятся** — каждая группа читает **весь** поток целиком, со своими offset'ами.

```text
                    ┌─▶ Group "billing"        (списать деньги)
Topic "payments" ───┼─▶ Group "notifications"  (отправить письмо)
                    └─▶ Group "analytics"      (обновить дашборд)
     один поток        каждая группа видит ВСЕ сообщения, независимо
```

Два уровня распределения, которые нельзя путать:

- **внутри группы** — партиции делятся (параллелизм, каждое сообщение обработано в группе один раз);
- **между группами** — ничего не делится (fan-out, каждая группа получает копию всего потока).

Зачем: развязка потребителей (добавил группу `fraud` — продюсер не тронут), изоляция скорости и сбоев (медленная analytics не тормозит billing). Держится на том, что сообщения не удаляются после чтения (retention) и offset принадлежит группе.

### 3.7.6. Offset — закладка группы и логика коммита

**Offset** — порядковый номер сообщения внутри партиции (0,1,2…). Но как *логика клиента* важнее другое: **committed offset** — это «докуда дочитала группа», её **закладка**. Она принадлежит группе и хранится в `__consumer_offsets`.

Инженерная логика проведения записи по offset (главное!):

```text
Партиция P0:  [0][1][2][3][4][5][6][7]  ← LEO = 8 (конец лога)
                          ▲
                    committed offset группы = 5
                    (0–4 обработаны и зафиксированы, следующим читаем 5)
   Lag = LEO − committed = 8 − 5 = 3   (сколько ещё не прочитано)
```

Цикл консюмера и момент коммита определяют семантику доставки:

```text
while true:
    records = poll()          # взяли пачку начиная с committed offset
    for r in records:
        process(r)            # бизнес-обработка
    commit(offset = last + 1) # сдвинули закладку

commit ПОСЛЕ обработки → at-least-once (упал до commit → перечитаем → дубль)
commit ДО   обработки → at-most-once  (упал в обработке → offset уже сдвинут → потеря)
auto-commit по таймеру → удобно, но менее предсказуемо
```

Ключевые свойства offset как логики:

- **сдвигается только вперёд** при нормальной работе, но его можно **перемотать назад** (reset) — это и есть replay;
- **у каждой группы свой** — поэтому две группы читают один топик независимо;
- **переживает рестарт** — новый консюмер той же группы продолжит с закладки, а не с нуля;
- у новой группы без закладки старт определяется `auto.offset.reset` (`earliest` — с начала, `latest` — только новые).

### 3.7.7. Сквозной инженерный пример — сообщение через все уровни

Проследим **один** заказ от продюсера до эффекта, касаясь и логики клиентов, и физического хранения. Кластер: 3 брокера, топик `orders` — 6 партиций, RF=3. Группа `billing` — 3 консюмера.

**Шаг 1 — продюсер формирует сообщение (логика).**
Сервис заказов создаёт запись: `key="order-1001"`, `value={"orderId":1001,"status":"created","amount":5000}`, `headers={correlationId: "abc-123"}`, timestamp = сейчас.

**Шаг 2 — выбор партиции (логика → адрес).**
Продюсер считает `partition = murmur2("order-1001") % 6 = 4`. Значит, все события этого заказа всегда пойдут в **P4** → порядок для заказа сохранён.

**Шаг 3 — батчинг и отправка (клиент → сеть).**
Сообщение кладётся в батч для P4 (ждёт до `linger.ms` или заполнения `batch.size`), сжимается и отправляется **лидеру P4** — это, скажем, брокер B2.

**Шаг 4 — запись в лог и репликация (физическое хранение).**
Лидер P4 на B2 дописывает сообщение в конец активного **сегмента** партиции, присваивая **offset = 42** (LEO становится 43). Фолловеры P4 на B1 и B3 тянут запись к себе. Когда обе ISR-реплики подтвердили — при `acks=all` продюсер получает `ack`, а **High Watermark** P4 сдвигается до 43 (сообщение стало видимым для консюмеров). `min.insync.replicas=2` гарантировал, что копий было достаточно.

**Шаг 5 — сообщение лежит и ждёт (хранение + логика).**
Запись теперь физически существует в трёх копиях (лидер + 2 реплики), в сегменте на диске, под offset 42 в P4. Она **не удалится** после чтения — живёт по retention. Её могут читать сколько угодно групп.

**Шаг 6 — группа billing распределила партиции (логика группы).**
В группе `billing` 3 консюмера, 6 партиций: Consumer C назначен на P4 и P5 (раскладку посчитал group leader, раздал координатор — брокер, ответственный за `hash("billing") % 50`).

**Шаг 7 — консюмер C читает (pull, логика offset).**
Consumer C в цикле зовёт `poll()`, забирает пачку из P4 начиная со своей закладки. Доходит до offset 42 — получает наш заказ (брокер отдаёт только до HW, то есть до надёжно реплицированного).

**Шаг 8 — обработка и эффект (бизнес-логика).**
C списывает деньги по заказу 1001, обновляет статус в БД. Побочный эффект применён.

**Шаг 9 — коммит offset (логика прогресса).**
C коммитит `offset=43` для группы `billing`, партиция P4 → запись уходит в `__consumer_offsets`. Теперь `Lag` группы по P4 = 0. Если C упадёт — новый владелец P4 продолжит с 43, не переобрабатывая заказ 1001.

**Шаг 10 — fan-out (логика групп).**
Параллельно то же сообщение (offset 42 в P4) **независимо** читают группы `notifications` (шлёт письмо) и `analytics` (пишет в хранилище) — у каждой свой committed offset в `__consumer_offsets`, они не мешают billing и друг другу.

Итоговая раскладка «кто на каком уровне»:

```text
ЛОГИКА КЛИЕНТОВ                         ФИЗИЧЕСКОЕ ХРАНЕНИЕ
key "order-1001" ─hash%6─▶ P4           P4 (лидер на B2) + реплики на B1,B3
value {...} = что произошло             запись в активном сегменте, offset 42
Topic "orders" = домен                  6 партиций, размазаны по 3 брокерам
Group "billing" делит P0..P5            offset'ы группы в __consumer_offsets
  Consumer C ← P4 (pull, poll)          fetch ограничен High Watermark
committed offset 43 = закладка          RF=3 + acks=all + min.insync=2 = надёжно
Fan-out: notifications, analytics       тот же лог читают много групп (retention)
```

Одной фразой: *ключ сообщения выбирает партицию → партиция физически живёт (лидер + реплики) на брокерах и хранит запись под offset → топик логически группирует партиции → группа консюмеров делит партиции между собой (параллелизм) и ведёт свою закладку-offset → разные группы читают тот же лог независимо (fan-out).*

### 3.7.8. Polling и батчирование — как клиенты реально общаются с брокером

Оба механизма — про **эффективность обмена по сети**. Kafka почти всё делает пачками, а не по одному сообщению; в этом секрет её пропускной способности.

#### Polling (опрос) — как читает консюмер

**Polling** — это модель, при которой **консюмер сам, в цикле, запрашивает у брокера новую порцию сообщений** через метод `poll()`. Брокер ничего не «пушит» — он пассивно хранит лог и отдаёт данные по запросу.

Как выглядит цикл:

```text
while running:
    records = consumer.poll(timeout=100ms)   # «дай сообщения начиная с моего offset»
    for r in records:                         # records — это ПАЧКА, а не одно сообщение
        process(r)
    consumer.commit()                          # сдвинули закладку-offset
```

Что происходит на каждом `poll()`:

1. консюмер шлёт брокеру-лидеру `Fetch`-запрос: «дай данные из моих партиций начиная с offset X»;
2. брокер возвращает **пачку** сообщений (сколько — регулируется настройками, см. ниже);
3. консюмер обрабатывает пачку в своём коде и двигает offset.

Важные факты про `poll()`:

- **`poll()` возвращает пачку, а не одно сообщение** — обрабатываешь их в цикле.
- **`poll()` — это ещё и «пульс» членства.** Между вызовами `poll()` не должно проходить больше `max.poll.interval.ms` — иначе координатор решит, что консюмер завис, и выкинет его из группы (rebalance). Отсюда правило: не делай слишком долгую обработку внутри одной итерации, либо уменьшай размер пачки `max.poll.records`.
- **`timeout` в `poll()`** — сколько ждать данных, если их пока нет (чтобы не крутить пустой цикл на 100% CPU).

Настройки, управляющие чтением:

| Настройка | Что делает |
|---|---|
| `max.poll.records` | сколько максимум сообщений вернёт один `poll()` (напр. 500) |
| `fetch.min.bytes` | сколько байт брокер накопит, прежде чем ответить (батч на стороне брокера) |
| `fetch.max.wait.ms` | сколько брокер ждёт накопления `fetch.min.bytes`, прежде чем всё же ответить |
| `max.poll.interval.ms` | предельная пауза между `poll()`, иначе консюмер выбывает из группы |

*Зачем pull, а не push (инженерно).* Консюмер сам задаёт темп — это **backpressure**: медленный потребитель просто реже опрашивает, сообщения ждут в логе, и его нельзя «завалить». Плюс pull даёт эффективное батчирование и replay (запросить со старого offset).

#### Батчирование (batching) — как пишет продюсер (и читает консюмер)

**Батч (batch)** — это **пачка сообщений, сгруппированных вместе для отправки/чтения одним куском** вместо по одному. Сеть и диск ненавидят много мелких операций: одна отправка из 1000 сообщений в разы дешевле, чем 1000 отдельных.

**На стороне продюсера.** Продюсер не шлёт каждое сообщение сразу — копит в буфере и отправляет группой:

| Настройка | Что делает |
|---|---|
| `batch.size` | максимальный размер батча в байтах на партицию (по умолчанию ~16 КБ). Набрался — шлём |
| `linger.ms` | сколько ждать, добивая батч, прежде чем отправить (по умолчанию 0). Больше → крупнее батчи, выше throughput, но выше задержка |
| `compression.type` | сжатие батча целиком (`gzip`/`snappy`/`lz4`/`zstd`) — ещё меньше по сети и на диске |

```text
Producer:  msg,msg,msg... ─┐
                           ├─ копятся в батч по партиции P4 (до batch.size или linger.ms)
                           ├─ батч сжимается целиком
                           └─▶ отправляется лидеру P4 одним запросом → пишется в лог как одна запись
```

**На стороне консюмера.** Симметрично: `poll()` возвращает батч, а `fetch.min.bytes`/`fetch.max.wait.ms` управляют тем, сколько брокер накопит перед отдачей.

*Зачем (инженерно).* Батчирование — главный рычаг компромисса **throughput против latency**: крупнее батчи → выше пропускная способность (меньше сетевых round-trip'ов, лучше сжатие), но чуть больше задержка (сообщение может «полежать» в батче до `linger.ms`). Для AQA это ещё один довод в пользу polling вместо `sleep`: событие уходит не мгновенно, а после формирования батча.

**Связь polling ↔ батчирование:** и то, и другое — про то, чтобы **не дёргать сеть по одному сообщению**. Продюсер копит батч на запись; брокер копит данные под `fetch.min.bytes`; консюмер забирает всё это одним `poll()` и обрабатывает пачкой. Одна фраза на собес: *Kafka быстрая, потому что общается пачками — продюсер батчит запись, консюмер по pull забирает пачку за `poll()`; настройками (`linger.ms`, `batch.size`, `max.poll.records`) ты крутишь баланс «скорость против задержки».*

# Глава 4. Архитектура: как Kafka работает изнутри

## 4.1. Схема потока данных

```text
Producer ──write──▶ Topic "payments"
                      ├── Partition 0: [msg0][msg1][msg2]  offset: 0,1,2
                      ├── Partition 1: [msg0][msg1]        offset: 0,1
                      └── Partition 2: [msg0]              offset: 0
                           ▲
Consumer Group "fraud" ────┘ (читает все партиции, распределяя между собой)
Consumer Group "notify" ───┘ (читает тот же топик независимо)
```

## 4.2. Ключевые правила (выучить наизусть)

1. **Порядок гарантируется только внутри одной партиции**, не по всему топику.
2. **Одинаковый key → одна партиция** → порядок событий одной сущности сохраняется.
3. **Сообщения не удаляются после чтения** — хранятся по retention; консюмер двигает свой offset.
4. **Pull, не push** — консюмер сам опрашивает брокер (`poll()`).
5. **Разные consumer groups** читают один топик **независимо** — каждая видит все сообщения.

### Разбор каждого правила: пример, ситуация, зачем это нужно

**Правило 1. Порядок — только внутри партиции.**

*Пример.* Топик `orders` на 3 партиции. Продюсер без ключа шлёт 6 событий — они раскидываются round-robin по партициям. Консюмер читает P0, P1, P2 параллельно и видит события **не** в том глобальном порядке, в котором их слали.

```powershell
# отправляем без ключа — уйдут в разные партиции
docker exec -it kafka /opt/kafka/bin/kafka-console-producer.sh `
  --bootstrap-server localhost:9092 --topic orders
# читаем с указанием партиции и offset — видно, что порядок глобально не сохранён
docker exec kafka /opt/kafka/bin/kafka-console-consumer.sh `
  --bootstrap-server localhost:9092 --topic orders --from-beginning `
  --property print.partition=true --property print.offset=true --max-messages 6
```

*Ситуация.* Внутри каждой партиции offset строго растёт (0,1,2…), но между партициями Kafka **не** упорядочивает — они читаются независимо и параллельно.

*Зачем так (инженерно).* Глобальный порядок по всему топику потребовал бы единой точки сериализации всех сообщений = один поток = потолок производительности и никакого масштабирования. Kafka сознательно жертвует глобальным порядком ради параллелизма: партиции независимы, поэтому их можно раскидать по брокерам и читать одновременно. Порядок остаётся там, где он реально нужен, — внутри партиции (правило 2).

**Правило 2. Одинаковый key → одна партиция → порядок сущности сохранён.**

*Пример.* События одного заказа обязаны идти по порядку: `created → paid → shipped`. Шлём их с `key = order-1001`.

```powershell
docker exec -it kafka /opt/kafka/bin/kafka-console-producer.sh `
  --bootstrap-server localhost:9092 --topic orders `
  --property parse.key=true --property key.separator=:
# order-1001:created
# order-1001:paid
# order-1001:shipped   ← все три с одним key → одна партиция → порядок гарантирован
```

*Ситуация.* `hash("order-1001") % N` всегда даёт одну и ту же партицию, поэтому все три события лягут подряд в один лог, и консюмер прочитает их строго по порядку. При этом события **другого** заказа (`order-2002`) уедут, возможно, в другую партицию и будут обрабатываться параллельно.

*Зачем так (инженерно).* Это способ получить **и порядок, и параллелизм одновременно**: порядок — на уровне сущности (ключа), параллелизм — между разными сущностями (разные ключи → разные партиции). Классический приём: `key = userId / orderId / accountId`. Обратная сторона — плохой ключ (все события с одним значением) создаёт hot partition (см. 4.4).

**Правило 3. Сообщения не удаляются после чтения (retention).**

*Пример.* Консюмер уже прочитал топик, но данные на месте — их может перечитать новая группа или тот же консюмер после сброса offset.

```powershell
# смотрим retention (по умолчанию 7 дней)
docker exec kafka /opt/kafka/bin/kafka-configs.sh --bootstrap-server localhost:9092 `
  --entity-type topics --entity-name orders --describe
# новая группа читает ВСЮ историю с нуля — сообщения никуда не делись
docker exec kafka /opt/kafka/bin/kafka-console-consumer.sh `
  --bootstrap-server localhost:9092 --topic orders --group fresh --from-beginning --max-messages 10
```

*Ситуация.* Чтение не «съедает» сообщение (в отличие от очереди). Сообщение живёт заданный retention-период независимо от того, прочитано оно или нет; удаляются лишь старые сегменты по истечении срока.

*Зачем так (инженерно).* Это фундамент ключевых возможностей Kafka: **replay** (перечитать историю после бага или для прогрева нового сервиса), **добавление новых потребителей** задним числом (новая группа увидит всю историю), **аудит и event sourcing** (состояние = проигрывание лога). Плюс развязка скорости: медленный консюмер не теряет данные — они ждут его в логе. Подвох для AQA: отставший больше retention консюмер **потеряет** непрочитанное — за lag и retention следят вместе.

**Правило 4. Pull, не push — консюмер сам опрашивает брокер.**

*Пример.* Консюмер в цикле вызывает `poll()` и забирает столько, сколько готов обработать.

```powershell
# console-consumer под капотом крутит poll() и тянет сообщения пачками
docker exec -it kafka /opt/kafka/bin/kafka-console-consumer.sh `
  --bootstrap-server localhost:9092 --topic orders --group workers
```

*Ситуация.* Брокер не «заталкивает» сообщения — он пассивно хранит лог и отдаёт диапазоны по запросу. Темп чтения задаёт сам консюмер.

*Зачем так (инженерно).* Это даёт **backpressure**: медленный консюмер не захлёбывается — он просто реже опрашивает, а сообщения ждут в логе. Push-модель (как в RabbitMQ) рискует завалить слабого потребителя. Pull также даёт эффективное **батчирование** (взять пачку за раз) и **replay** (запросить со старого offset). Цена — небольшая задержка на опрос и необходимость настраивать размер пачки (`max.poll.records`).

**Правило 5. Разные consumer groups читают топик независимо.**

*Пример.* Один топик `payments` читают три группы, и каждая получает **весь** поток.

```powershell
# группа billing — читает всё
docker exec kafka /opt/kafka/bin/kafka-console-consumer.sh `
  --bootstrap-server localhost:9092 --topic payments --group billing --from-beginning --max-messages 5
# группа analytics — те же сообщения, свои offset, независимо
docker exec kafka /opt/kafka/bin/kafka-console-consumer.sh `
  --bootstrap-server localhost:9092 --topic payments --group analytics --from-beginning --max-messages 5
```

*Ситуация.* Внутри группы партиции делятся между консюмерами (каждое сообщение обработано один раз в группе); между группами ничего не делится — у каждой свои offset'ы в `__consumer_offsets`, каждая видит поток целиком.

*Зачем так (инженерно).* Это механизм **fan-out**: одно событие независимо получают разные подсистемы (billing спишет деньги, notifications пошлёт письмо, analytics обновит дашборд) без дублирования данных и без связности. Добавить потребителя = завести новую группу, продюсер и остальные не меняются. Изоляция сбоев и скорости: упала/тормозит одна группа — остальные читают как ни в чём не бывало.

## 4.4. Как продюсер выбирает партицию

```
if (key != null):
    partition = hash(key) % num_partitions   # один key → одна партиция
else:
    partition = round-robin / sticky         # равномерное распределение
```

**Пример:** все события `client_id=42` → одна партиция → порядок «открытие счёта → пополнение → перевод» сохранён.

### Подробно: приоритетная лестница выбора партиции

Продюсер выбирает партицию по четырём уровням, сверху вниз — срабатывает первый подходящий:

```
1. partition задан явно         → пишем прямо в него (key игнорируется)
2. задан кастомный partitioner  → решает его логика (partitioner.class)
3. key != null                  → toPositive(murmur2(keyBytes)) % num_partitions
4. key == null                  → sticky partitioner (2.4+) / round-robin (старые версии)
```

1. **Партиция указана явно.** Если при отправке задан номер партиции (`ProducerRecord(topic, partition, key, value)`), сообщение идёт ровно туда, key и всё остальное не учитываются. Высший приоритет.

2. **Кастомный партиционер.** Можно подключить свой класс через `partitioner.class` (реализует интерфейс `Partitioner`) и написать любую логику — например «VIP-клиентов в отдельную партицию» или геошардинг. Если задан — решает он.

3. **Есть key → хеширование (детерминированно).** Дефолт с ключом. Детали, которые прячет упрощённое `hash(key) % N`:
   - хешируются **сериализованные байты ключа**, и не встроенным `hashCode`, а алгоритмом **murmur2** — стабильным и одинаковым на всех клиентах и языках (Java, Python, Go дают тот же результат);
   - точнее формула: `toPositive(murmur2(keyBytes)) % num_partitions`;
   - отсюда **детерминизм**: один и тот же key при неизменном числе партиций всегда попадает в одну партицию — это и держит порядок событий одной сущности.

4. **Key = null → sticky / round-robin (равномерно).** Поведение зависит от версии Kafka:
   - **до 2.4** — чистый round-robin: каждое сообщение в следующую партицию по кругу. Равномерно, но много мелких батчей → хуже throughput;
   - **2.4+ (sticky partitioner)** — продюсер «прилипает» к одной партиции и льёт в неё, пока не наберётся батч (`batch.size`/`linger.ms`), затем переключается. Распределение всё равно равномерное, но батчи крупнее → выше пропускная способность;
   - **3.3+ (uniform sticky, KIP-794)** — та же идея, но с учётом нагрузки брокеров (больше льёт в те, что успевают).

**Подвох для собеса:** хеш берётся **по модулю числа партиций**. Если топику добавить партиций, `hash(key) % N` изменится — и тот же `client_id=42`, раньше шедший в партицию 1, для новых сообщений может уйти в партицию 3. Старые сообщения останутся на месте, новые уедут в другую партицию → **порядок для этого ключа нарушится**. Поэтому число партиций стараются не менять на живых топиках, где важен порядок (и партиции можно только увеличивать, но обычно этого избегают).

### Зачем вообще нужно равномерное распределение (key = null)

Равномерное распределение существует, чтобы **выжать максимум параллелизма и не создать перекос нагрузки, когда порядок сообщений между собой не важен.**

```text
БЕЗ КЛЮЧА → равномерно (хорошо)        ОДИН key НА ВСЁ → hot partition (плохо)

Producer (key=null)                    Producer (key="X")
   │    │    │                                   │
   ▼    ▼    ▼                                   ▼
 P0[■■] C0 ✓ ровно                     P0[■■■■■■] C0 ⚠ перегружен, lag растёт
 P1[■■] C1 ✓ ровно                     P1[      ] C1 zzz простаивает
 P2[■■] C2 ✓ ровно                     P2[      ] C2 zzz простаивает

 → все партиции и консюмеры заняты      → работает только один консюмер,
   максимум throughput                    параллелизм не используется
```

Почему это нужно, по пунктам:

1. **Партиция — единица параллелизма, её надо загружать ровно.** Одну партицию в группе читает ровно один консюмер. Скорость обработки топика упирается в то, насколько ровно сообщения размазаны по партициям. Раскидал поровну → все консюмеры работают, throughput максимальный. Свалил всё в одну → один консюмер надрывается, остальные спят, и хоть партиций три — по скорости как с одной.

2. **Защита от hot partition.** Если бы ключ был обязателен и все сообщения шли с одинаковым ключом, `hash(key) % N` всегда давал бы одну партицию — она переполняется, по ней растёт lag, остальные простаивают. Равномерное распределение гарантированно этого избегает, когда осмысленного ключа для шардирования нет.

3. **Большинству событий порядок между собой не нужен.** Ключ (и привязка к одной партиции) нужен только для порядка событий **одной сущности** (события одного клиента). Но клики, метрики, логи, независимые уведомления — между ними порядок не важен. Навязывать им ключ и сажать в одну партицию — значит добровольно отказаться от параллелизма без выгоды. Отсюда дефолт «нет ключа → раскидываем ровно».

4. **Почему sticky, а не чистый round-robin (в новых версиях).** Чистый round-robin шлёт каждое сообщение в новую партицию → распределение идеальное, но батчи мелкие, а это бьёт по throughput (см. Б3 про батчинг). Sticky «прилипает» к партиции, набивает полный батч, потом переключается. По итогу распределение всё равно ровное, но батчи крупные — сеть и диск используются эффективнее.

**Одна фраза для собеса:** *Ключ = порядок для сущности, но риск hot partition. Без ключа = равномерная нагрузка и максимальный параллелизм, но порядок между сообщениями не гарантируется. Ключ выбираешь только там, где реально нужен порядок; всё остальное льёшь без ключа, чтобы Kafka сама размазала нагрузку.*

# Глава 5. Consumer Group, offset и rebalance

## 5.1. Consumer Group — главная идея масштабирования

**Consumer group** — набор консюмеров с общим `group.id`, которые **делят между собой партиции** топика.

```text
Topic "orders" — 6 партиций
Consumer Group "processors" — 3 консюмера

Consumer A ← partition 0, 1
Consumer B ← partition 2, 3
Consumer C ← partition 4, 5
```

**Правила:**
- каждая партиция в группе читается **ровно одним** консюмером;
- консюмеров **больше**, чем партиций → лишние **простаивают**;
- **разные группы** не мешают друг другу — обе получают весь поток.

## 5.2. Offset — позиция чтения

```text
Partition 0:  [0][1][2][3][4][5][6][7]
                              ▲
                         committed offset = 5
                         (прочитаны 0–4, следующее — 5)
```

- Offset **коммитится** консюмером (в топик `__consumer_offsets` или вручную);
- после рестарта консюмер **продолжает с offset** — не теряет прогресс;
- можно **сдвинуть offset назад** — перечитать историю (replay).

## 5.3. Rebalance — что происходит

**Rebalance** — перераспределение партиций, когда:
- консюмер **упал**;
- **добавился** новый консюмер в группу;
- **изменилось** число партиций топика.

На время rebalance группа **приостанавливает чтение** → возможны задержки и дубликаты (at-least-once).

**Для собеседования:** rebalance — нормальное поведение, но источник продовых инцидентов при плохой настройке (слишком частый rebalance, долгая обработка сообщения).

# Глава 6. Семантики доставки и надёжность

## 6.1. Три семантики

| Семантика | Что значит | Как достигается | Риск |
|---|---|---|---|
| **At-most-once** | Сообщение доставлено **не более одного раза** | Commit offset **до** обработки | Потеря сообщений |
| **At-least-once** | Сообщение доставлено **минимум один раз** | Commit offset **после** обработки | Дубликаты при падении |
| **Exactly-once** | Ровно один раз | Транзакции Kafka + идемпотентный консюмер | Сложно, дорого |

**На практике:** at-least-once + **идемпотентный консюмер** (повторная обработка не ломает систему) — самый частый выбор.

## 6.2. acks у продюсера

`acks` (acknowledgements) — настройка **продюсера**: какого уровня подтверждения записи он ждёт от брокера, прежде чем считать сообщение отправленным. Это компромисс «надёжность против скорости».

| acks | Поведение | Надёжность | Скорость |
|---|---|---|---|
| `0` | Не ждёт подтверждения | Низкая | Максимальная |
| `1` | Подтвердил лидер партиции | Средняя | Средняя |
| `all` / `-1` | Подтвердили лидер + все ISR-реплики | Высокая | Медленнее |

### Что именно значит `acks=all`

`acks=all` (то же самое, что `acks=-1`) — самый надёжный уровень: запись считается успешной, только когда её подтвердили **лидер И все синхронные реплики (ISR)**. То есть сообщение легло не в одну копию, а во все актуальные копии партиции на разных брокерах.

По шагам:

1. продюсер шлёт сообщение лидеру партиции;
2. лидер записывает его к себе в лог;
3. лидер ждёт, пока все реплики из ISR **притянут** это сообщение;
4. только теперь лидер отвечает продюсеру «ок».

Зачем: если сразу после подтверждения **упадёт лидер**, новым лидером станет реплика из ISR — а у неё сообщение уже есть (шаг 3). Данные не потеряны. Это и есть гарантия «записал = переживёт падение брокера». Цена — лишний сетевой раунд ожидания реплик, поэтому чуть медленнее.

Для сравнения: `acks=1` ждёт **только лидера** — если лидер упадёт до того, как реплики скопировали, сообщение потеряется. `acks=0` не ждёт ничего — максимум скорости, но потерю даже не заметишь.

**Важно — `acks=all` работает в паре с `min.insync.replicas`.** Сам по себе `all` = «все синхронные реплики»; но если синхронной осталась только одна, то «все» = одна копия, и гарантия слабеет. Поэтому при RF=3 ставят `min.insync.replicas=2`: если живых синхронных реплик меньше двух — брокер **отклонит** запись с ошибкой, а не запишет тихо в единственную копию. Стандарт для критичных данных (деньги, заказы): **`acks=all` + `min.insync.replicas≥2` + `RF≥3`**.

> На одно-брокерном стенде `acks=all` фактически = «подтвердил единственный брокер»: ISR состоит из одной копии, реального резерва нет. Полный смысл флаг раскрывает только на кластере из нескольких брокеров.

**Фраза на собес:** *`acks=all` — продюсер ждёт подтверждения от лидера и всех синхронных реплик (ISR), что гарантирует сохранность сообщения при падении брокера; вместе с `min.insync.replicas` это защита от тихой потери данных ценой небольшой задержки.*

## 6.3. Связь с AQA

- **Eventual consistency:** после события в Kafka состояние UI/API обновляется **не мгновенно** — в тестах нужен polling, не `sleep(5)`.
- **Дубликаты:** при at-least-once одно действие может обработаться дважды — проверяй идемпотентность.
- **Порядок:** если тест шлёт события A→B→C с одним key — они попадут в одну партицию и придут по порядку.

```powershell
docker exec kafka /opt/kafka/bin/kafka-topics.sh --bootstrap-server localhost:9092 `
  --describe --topic learning-orders
```

Ожидаемый вывод (в Kafka 3.9 добавлены колонки `Elr` / `LastKnownElr`):

```text
Topic: learning-orders  TopicId: 7bDx...Qa  PartitionCount: 3  ReplicationFactor: 1  Configs:
    Topic: learning-orders  Partition: 0  Leader: 1  Replicas: 1  Isr: 1  Elr:   LastKnownElr:
    Topic: learning-orders  Partition: 1  Leader: 1  Replicas: 1  Isr: 1  Elr:   LastKnownElr:
    Topic: learning-orders  Partition: 2  Leader: 1  Replicas: 1  Isr: 1  Elr:   LastKnownElr:
```

Как читать построчно:

- **PartitionCount: 3 / ReplicationFactor: 1** — подтверждение, что топик именно такой, как заказывали.
- **Partition: 0/1/2** — три независимых журнала. Порядок гарантируется внутри каждого, но не между ними.
- **Leader: 1** — через какой брокер идут запись и чтение этой партиции. У тебя один брокер, поэтому лидер везде один и тот же (его node id — может быть `1`, `0` или другой, смотри свой конфиг).
- **Replicas: 1** и **Isr: 1** — список брокеров с копией и список синхронных реплик (In-Sync Replicas). При RF=1 это один и тот же единственный брокер. **Если бы RF был 3**, здесь было бы, например, `Replicas: 1,2,3  Isr: 1,2,3`, и по расхождению этих списков ловят отставание репликации.
- **Elr / LastKnownElr** — пусто, это нормально (Eligible Leader Replicas, новая механика KIP-966; при RF=1 не задействована).

**Разбор трёх колонок подробнее (частые вопросы):**

- **ReplicationFactor** — сколько копий у **каждой** партиции. RF=1 → одна копия (у тебя), RF=3 → три на разных брокерах. RF задаёт, сколько брокеров может умереть без потери данных (RF=3 → до 2). На одно-брокерном стенде максимум RF=1 — копию некуда положить.
- **Replicas vs Isr — зачем показывают отдельно, если обе про копии.** Это разные понятия. **Replicas** — *назначенный* список брокеров с копией («как задумано», статично). **Isr** (In-Sync Replicas) — *подмножество*, которое **сейчас догнало лидера** («как есть», динамично). Разница проявляется, когда копия отстаёт:

  ```text
  RF=3 здоров:            Replicas: 1,2,3   Isr: 1,2,3
  RF=3, брокер 2 отстал:  Replicas: 1,2,3   Isr: 1,3     ← копия на 2 выпала из ISR
  ```

  Почему важно: новым лидером станет **только** член ISR (иначе потеряли бы свежие данные); `acks=all` ждёт подтверждения от ISR. **`Replicas` > `Isr` = under-replicated** — тревога мониторинга. У тебя `Replicas: 1  Isr: 1` совпадают только потому, что RF=1 и копия одна.
- **TopicId (`7bDx...Qa` / у тебя `XDvCDxYiTIKOBT8bFyYEwg`)** — уникальный неизменный id топика, кластер генерирует его при создании. Имя может совпадать у разных «поколений», а id — нет: удалил и создал топик с тем же именем → **id другой**. Нужен Kafka, чтобы в метаданных и в именах каталогов на диске (KRaft) не путать старый топик с новым одноимённым. Как использовать тебе — диагностика: сравнил TopicId в двух `--describe`, поменялся → топик пересоздавали (частая причина «данные пропали, а имя то же»); удобен для корреляции логов и метрик. В обычных CLI-командах ты его не передаёшь — работаешь по имени.

**Шаг 4. Проверь, что топик появился в списке.**

```powershell

```

Теперь в выводе есть строка `learning-orders`.

**Итог задачи 1 — что должно уложиться в голове:**

3. `--describe` показывает раскладку: лидер, реплики, ISR — язык, на котором говорят про надёжность.
4. Одно и то же состояние видно двумя способами — через CLI и через Kafka UI; на собесе полезно владеть обоими.

- **Isr: 1** — единственная реплика синхронна; при RF=1 отказоустойчивости нет (упадёт брокер — партиция недоступна).
- **Elr / LastKnownElr пустые** — ожидаемо для RF=1 (механика Eligible Leader Replicas не задействована).

Эта команда **создаёт новый топик `learning-orders` с 3 партициями и 1 репликой**. Разберём максимально подробно, по кусочкам.

Сначала про формат: обратная кавычка `` ` `` в конце первой строки — это в PowerShell **перенос длинной команды на следующую строку**. То есть обе строки — одна команда, просто разбитая для читаемости. (В Linux/bash ту же роль играет `\`.)

Теперь по частям:

**`docker exec kafka`**  
«Выполни команду внутри уже запущенного контейнера с именем `kafka`». Утилита `kafka-topics.sh` живёт внутри контейнера, поэтому мы не запускаем её на Windows, а «заходим» в контейнер и выполняем там.

**`/opt/kafka/bin/kafka-topics.sh`**  
Полный путь к CLI-скрипту управления топиками (тот самый launcher, что запускает Java-инструмент `TopicCommand`). Это то, что собственно исполняется внутри контейнера.

**`--bootstrap-server localhost:9092`**  
Адрес брокера, к которому подключиться. Скрипт — это клиент, он сам ничего не хранит; ему нужно сказать, куда идти. `localhost:9092` работает, потому что команда выполняется **внутри** контейнера `kafka`, где `localhost` — это сам брокер (у него слушает EXTERNAL-listener на 9092). Через bootstrap-сервер клиент узнаёт всю топологию кластера.

**`--create`**  
Действие — «создать топик». Альтернативы в этом же скрипте: `--list`, `--describe`, `--delete`, `--alter`.

**`--topic learning-orders`**  
Имя создаваемого топика. По этому имени к нему потом обращаются продюсеры и консюмеры.

**`--partitions 3`**  
Разбить топик на **3 партиции** (`learning-orders-0`, `-1`, `-2`). Это параллельные упорядоченные журналы: порядок гарантируется внутри каждой партиции, а три штуки позволяют читать топик параллельно (до 3 консюмеров в одной группе). Физически это три отдельные папки с логами на диске брокера. Важно: партиции потом можно только увеличить, уменьшить нельзя.

**`--replication-factor 1`**  
Сколько копий каждой партиции держать в кластере. `1` = одна копия, без резерва. Это единственный разумный вариант на твоём одно-брокерном стенде: чтобы поставить `2` или `3`, нужно 2–3 брокера. Обратная сторона — отказоустойчивости нет: упадёт брокер, партиция станет недоступна (в проде ставят `3`).

**Что произойдёт при выполнении:**

Скрипт подключится к брокеру, отправит админ-запрос «создай топик», брокер заведёт метаданные и нарежет 3 партиции с одной репликой каждая, после чего вернёт:

text

```text
Created topic learning-orders.
```

**На что обратить внимание:**

- Команда **не идемпотентна**: запустишь второй раз — получишь ошибку `TopicExistsException: Topic 'learning-orders' already exists`. Чтобы не падало в скриптах, добавляют `--if-not-exists`.
- Если брокер не поднят — будет `Connection ... could not be established` (не тот случай, что топик «не создался логически», а именно нет связи).
- Проверить результат: `--describe --topic learning-orders` (увидишь раскладку по партициям, как в твоём прогоне: Leader 1, Isr 1) либо `--list` (топик появится в списке), либо в Kafka UI → Topics.

Одной фразой: _зайти в контейнер kafka → запустить утилиту управления топиками → подключиться к брокеру на localhost:9092 → создать топик `learning-orders` из 3 партиций с 1 репликой._

# Глава 8. Типовые задачи и паттерны в Kafka

## 8.1. Какие задачи решают через Kafka

| Задача | Как Kafka помогает |
|---|---|
| **Интеграция микросервисов** | Слабая связность: сервисы общаются событиями, не HTTP-цепочками |
| **Event notification** | «Заказ создан» → email, SMS, аналитика — независимые consumer groups |
| **Event sourcing** | Состояние = replay всех событий из лога |
| **Log aggregation** | Сбор логов приложений в центральный топик → ELK |
| **Stream processing** | Kafka Streams / Flink читают поток и считают агрегаты в реальном времени |
| **Buffer / decoupling** | Пик нагрузки буферизуется — consumer обрабатывает когда успеет |
| **Audit trail** | Все события в логе — можно перечитать, кто что сделал |

## 8.2. Типовые паттерны

**Fire-and-forget (publish):** продюсер отправил — не ждёт ответа. Самый простой.

**Competing consumers:** N консюмеров в одной группе — параллельная обработка.

**Fan-out:** одно событие → несколько consumer groups (billing + notify + analytics).

**Replay:** сброс offset или новая consumer group — переобработать историю (после бага, прогрев нового сервиса).

**Dead Letter Topic:** сообщение не обработалось N раз → отправить в топик `orders.dlq` для ручного разбора.

**Outbox pattern:** транзакция в БД + запись в outbox-таблицу → отдельный процесс публикует в Kafka (гарантия «записали в БД = событие уйдёт»).

## 8.3. Типовые проблемы на проде (спрашивают «что может пойти не так»)

| Проблема | Симптом | Причина |
|---|---|---|
| **Consumer lag растёт** | Данные в UI устарели | Мало консюмеров / медленная обработка |
| **Дубликаты** | Два одинаковых email | At-least-once + повтор после падения |
| **Потеря сообщений** | Событие не обработано | acks=0, commit до обработки |
| **Нарушен порядок** | «Пополнение» раньше «открытия счёта» | Разные keys → разные партиции |
| **Rebalance storm** | Периодические паузы | Частые падения консюмеров, max.poll.interval |
| **Hot partition** | Одна партиция перегружена | Плохой key (все сообщения с одним key) |

## 8.4. Hot partition — разбор и диагностика

**Что это.** «Горячая партиция» — ситуация, когда **одна партиция получает непропорционально много нагрузки**: в неё летит большая часть сообщений, а остальные почти простаивают. Она превращается в узкое место всего топика.

**Почему это плохо (инженерно).** Партиция — единица параллелизма: её читает ровно один консюмер в группе. Значит скорость обработки всего топика упирается в самую загруженную партицию. Сделал 3 партиции ради параллелизма, но 90% трафика идёт в P0 → консюмер P0 захлёбывается и копит lag, а консюмеры P1/P2 простаивают. Плюс перекос по диску (P0 распухает) и по нагрузке на брокер, где лежит её лидер.

```text
key = "RU" (95% трафика)           key = orderId (высокая кардинальность)
P0 [■■■■■■■■■■] ← перегружена        P0 [■■■]
P1 [■]                              P1 [■■■]
P2 [ ]                              P2 [■■■]
= hot partition, перекос            = ровная нагрузка
```

**Откуда берётся — почти всегда плохой ключ** (`partition = hash(key) % N`):

- ключ с **малой кардинальностью** или перекосом: `key = country`, а 95% трафика из одной страны;
- «крупный» ключ: `key = tenantId`, и один клиент-гигант даёт львиную долю событий (skew);
- ключ фактически константа: всё шлётся с одним и тем же ключом.

**Как заметить — диагностика через CLI.** Смотрим offset'ы и lag по партициям: у горячей партиции числа резко больше.

```powershell
# 1. Раскладка по партициям: LOG-END-OFFSET и LAG по каждой
docker exec kafka /opt/kafka/bin/kafka-consumer-groups.sh `
  --bootstrap-server localhost:9092 --group workers --describe
```

```text
TOPIC   PARTITION  CURRENT-OFFSET  LOG-END-OFFSET  LAG   CONSUMER-ID
orders  0          1200            98000           96800  consumer-1   ← ГОРЯЧАЯ: offset и lag на порядок больше
orders  1          800             1000            200    consumer-2
orders  2          750             900             150    consumer-3
```

```powershell
# 2. Сколько всего сообщений в каждой партиции (сумма по разнице offset'ов)
docker exec kafka /opt/kafka/bin/kafka-run-class.sh kafka.tools.GetOffsetShell `
  --broker-list localhost:9092 --topic orders
# orders:0:98000   ← перекос виден сразу
# orders:1:1000
# orders:2:900
```

Признак hot partition: у одной партиции **LOG-END-OFFSET** и **LAG** на порядок выше остальных. В Kafka UI то же видно на вкладке Topic → Overview (Offset Max по партициям) и Consumers → группа → lag по партициям.

**Как лечить:**

- выбрать **ключ с высокой кардинальностью** и ровным распределением (`orderId`, `userId` вместо `country`/`region`);
- если порядок по «крупной» сущности не критичен — **убрать ключ** (sticky/round-robin размажет ровно) или сделать **составной ключ** (`tenantId:userId`);
- в крайнем случае — **соль/суффикс** к ключу (случайный хвост), но это ломает порядок для сущности, поэтому только где порядок не нужен;
- честно спросить себя, **нужен ли порядок именно по этому ключу** — часто ради ложного «порядка» жертвуют параллелизмом.

**Компромисс на собес:** *ключ даёт порядок для сущности, но при малой кардинальности создаёт hot partition; поэтому ключ выбирают осознанно — только там, где порядок реально нужен, и с достаточным разнообразием значений.*

### Что такое кардинальность ключа

**Кардинальность** — это количество **уникальных значений**, которые может принимать поле. «Высокая» = много разных значений, «низкая» = мало.

- **Высокая:** `orderId`, `userId`, `email`, `uuid` — тысячи/миллионы значений, почти каждое уникальное.
- **Низкая:** `country`, `status`, `gender`, `is_active` — единицы/десятки значений (`RU/US/DE`, `paid/pending`, `true/false`).

**Почему это важно для ключа.** Партиция выбирается как `hash(key) % N`. Чтобы сообщения размазались ровно, ключей должно быть **много** и встречаться они должны примерно **одинаково часто** — тогда хеш раскидывает их равномерно.

```text
key = orderId (высокая)         key = country (низкая, перекос)
P0 [■■■]                        P0 [■■■■■■■■■]  ← все "RU" сюда
P1 [■■■]                        P1 [■]
P2 [■■■]                        P2 [ ]
```

**Важный нюанс — одной высокой кардинальности мало, нужно ещё равномерное распределение.** `tenantId` может иметь тысячи значений (высокая кардинальность), но если один клиент-гигант даёт 80% событий — всё равно перекос. Это называется **skew** (перекос распределения). Идеальный ключ — и разнообразный, и без доминирующих значений.

**Правило выбора ключа:** бери поле, у которого много разных значений и ни одно не встречается сильно чаще других — тогда партиции грузятся ровно, а порядок для сущности (по этому ключу) сохраняется.

# Глава 9. Kafka vs RabbitMQ — сравнение для собеседования

## 9.1. Главная таблица

| Критерий | Kafka | RabbitMQ |
|---|---|---|
| **Модель** | Распределённый **лог** (commit log) | **Очередь** сообщений |
| **Доставка** | **Pull** — консюмер опрашивает | **Push** — брокер заталкивает |
| **После прочтения** | Сообщение **остаётся** (retention) | Сообщение **удаляется** после ack |
| **Перечитать историю** | ✅ Да (сдвиг offset) | ❌ Нет (уже удалено) |
| **Порядок** | Внутри **партиции** | Внутри **очереди** |
| **Маршрутизация** | Простая: topic → partition по key | Богатая: exchanges (direct, topic, fanout, headers) |
| **Throughput** | Очень высокий (миллионы msg/sec) | Умеренный |
| **Consumer groups** | Нативно — масштабирование чтения | Конкурентные consumers на queue |
| **Назначение** | Event streaming, event sourcing, логи | Task queues, RPC, сложный роутинг |
| **Сложность** | Выше (partitions, offsets, rebalance) | Ниже для простых кейсов |
| **TTL сообщений** | Retention по времени/размеру топика | Per-message TTL, DLX |

## 9.2. Когда что выбирать

**Kafka — если:**
- нужен **поток событий**, а не разовая задача;
- несколько независимых потребителей одного потока;
- нужен **replay** (перечитать историю);
- высокая пропускная способность;
- event sourcing / stream processing.

**RabbitMQ — если:**
- классическая **очередь задач** (обработай и удали);
- сложная **маршрутизация** (routing key, fanout, topic exchange);
- RPC-запросы с ответом;
- умеренный объём, проще в настройке.

## 9.3. Одна фраза для собеседования

*«Kafka — это pull-based распределённый лог для event streaming: сообщения хранятся, их можно перечитать, масштабирование через consumer groups и партиции. RabbitMQ — push-based очередь: сообщение доставляется и удаляется после ack, с гибкой маршрутизацией через exchanges. Kafka — для потоков событий и интеграции микросервисов; RabbitMQ — для task queues и RPC.»*

## 9.4. Вопрос-ловушка с интервью

**«Kafka слушает за микросервисами и подписана на события?»** — **Нет.** Kafka **не активный наблюдатель**. Продюсеры сами пишут в топик; консюмеры сами читают (pull). Брокер пассивно хранит лог.

# Глава 10. Kafka глазами AQA-тестировщика

## 10.1. Что тестировать

| Уровень | Что проверяем |
|---|---|
| **Контракт сообщения** | JSON-схема, обязательные поля, типы (Zod / pydantic) |
| **Наличие события** | После действия в UI/API — событие появилось в топике |
| **Содержимое события** | key, value, headers — правильные значения |
| **Побочный эффект** | Consumer обработал → статус в БД/UI изменился |
| **Порядок** | События одной сущности (один key) — в правильном порядке |
| **Негативные кейсы** | Битый JSON, пустой key, огромное сообщение |
| **Idempotency** | Повторная обработка того же события — без дубля эффекта |

## 10.2. Как тестировать — два подхода

**1. Test → проверка события (outbound):**
```
Действие в UI → тестовый consumer ждёт сообщение в топике → assert JSON
```

**2. Test ← событие (inbound):**
```
Тест публикует событие в топик → polling API/UI → assert состояние изменилось
```

## 10.3. Eventual consistency в тестах

```typescript
// ❌ Плохо
await page.click('#pay');
await page.waitForTimeout(5000);
await expect(page.getByText('Оплачено')).toBeVisible();

// ✅ Хорошо — polling с таймаутом
await page.click('#pay');
await expect.poll(async () => {
  const resp = await request.get(`/api/orders/${orderId}`);
  return (await resp.json()).status;
}, { timeout: 30_000 }).toBe('completed');
```

## 10.4. Изоляция параллельных тестов

- Уникальный **key** на тест: `test-${workerIndex}-${uuid}`;
- Уникальный **topic suffix** или фильтрация по key в consumer;
- **Cleanup** — не полагайся на автоудаление (Kafka хранит по retention).

## 10.5. Чек-лист «сообщение в топике есть, сервис не реагирует»

1. Consumer group жив? (`kafka-consumer-groups.sh --describe`)
2. Правильный `group.id`?
3. Offset не ушёл далеко вперёд?
4. Rebalance не завис?
5. Ошибка десериализации → сообщение в DLQ?
6. Consumer lag растёт?

# Глава 11. Вопросы на собеседовании + идеальные ответы

---

### В1. Что такое Kafka и зачем она нужна?

**Идеальный ответ:**
Kafka — распределённый брокер сообщений, построенный как append-only журнал (commit log). Используется для асинхронного обмена событиями между микросервисами: продюсер публикует событие в топик, консюмеры читают в своём темпе. Даёт слабую связность сервисов, буферизацию пиков нагрузки, возможность добавлять новых потребителей без изменения продюсера и replay истории событий.

---

### В2. Основные компоненты Kafka — перечисли.

**Идеальный ответ:**
- **Broker** — сервер, хранящий данные;
- **Topic** — именованный поток сообщений;
- **Partition** — топик разбит на упорядоченные журналы; порядок гарантируется внутри партиции;
- **Producer** — пишет сообщения;
- **Consumer** — читает сообщения (pull через `poll()`);
- **Consumer Group** — группа консюмеров, делящих партиции для масштабирования;
- **Offset** — позиция чтения в партиции;
- **Zookeeper / KRaft** — координация метаданных кластера (современные версии — KRaft без Zookeeper).

---

### В3. Чем топик отличается от партиции?

**Идеальный ответ:**
Topic — логическое имя потока (например, `orders`). Partition — физическое разбиение топика на N упорядоченных журналов для параллелизма. Сообщения с одинаковым key попадают в одну партицию — это сохраняет порядок событий одной сущности. Число партиций определяет максимальный параллелизм чтения в consumer group.

---

### В4. Push или pull? Как консюмер получает сообщения?

**Идеальный ответ:**
Kafka — **pull-модель**. Консюмер в цикле вызывает `poll()` и сам забирает пачку сообщений начиная со своего offset. Преимущества: консюмер управляет темпом (backpressure), эффективное батчирование, возможность replay. Брокер не «заваливает» медленного потребителя.

---

Round-robin — это способ распределения задач или сообщений по очереди, циклически, каждому получателю по одному.

В контексте Kafka: если у сообщения нет key, продюсер раскидывает сообщения по партициям топика последовательно — первое сообщение в партицию 0, второе в партицию 1, третье в партицию 2, потом снова в 0, и так по кругу. Из-за этого сообщения оказываются в разных партициях и порядок между ними не сохраняется — консьюмер может прочитать их не в том порядке, в котором они были отправлены.

Само название пошло от аналогии со спортивными турнирами circle round-robin, где каждый участник по очереди играет с каждым.


---

### В5. Что такое Consumer Group и зачем она нужна?

**Идеальный ответ:**
Consumer group — набор консюмеров с общим `group.id`, совместно читающих топик. Каждая партиция назначается ровно одному консюмеру в группе — это распределение нагрузки. Разные группы независимы: каждая получает весь поток со своими offset'ами. При падении/добавлении консюмера происходит rebalance — партиции перераспределяются. Число партиций = потолок параллелизма; лишние консюмеры простаивают.

---

### В6. Что такое offset?

**Идеальный ответ:**
Offset — порядковый номер сообщения внутри партиции (0, 1, 2...). Консюмер трекает свой offset — позицию, до которой прочитал. После обработки offset коммитится; при рестарте консюмер продолжает с места остановки. Offset можно сдвинуть назад — перечитать историю (replay). Хранится в служебном топике `__consumer_offsets`.

---

### В7. Гарантируется ли порядок сообщений?

**Идеальный ответ:**
Порядок гарантируется **только внутри одной партиции**, не по всему топику. Чтобы сохранить порядок событий одной сущности (например, одного клиента), используют **одинаковый key** — все его сообщения попадут в одну партицию. Без key сообщения распределяются round-robin — порядок между ними не гарантирован.

---

### В8. Удаляются ли сообщения после прочтения?

**Идеальный ответ:**
**Нет.** Kafka — это лог, а не очередь. Сообщения хранятся заданный **retention-период** (по времени или размеру) независимо от того, прочитаны они или нет. Это позволяет replay, добавление новых consumer groups, которые прочитают всю историю. В RabbitMQ сообщение удаляется после ack — это ключевое отличие.

---

### В9. At-most-once, at-least-once, exactly-once — в чём разница?

**Идеальный ответ:**
- **At-most-once:** commit offset до обработки — при падении сообщение потеряно;
- **At-least-once:** commit после обработки — при падении между обработкой и commit сообщение придёт повторно (дубликат);
- **Exactly-once:** транзакции Kafka + идемпотентный producer — сложно и дорого.
На практике: at-least-once + идемпотентный консюмер (повторная обработка безопасна).

---

### В10. Чем Kafka отличается от RabbitMQ?

**Идеальный ответ:** *(см. главу 9 — таблица)*

Kafka — pull-based лог для event streaming, хранит сообщения, replay, высокий throughput, consumer groups. RabbitMQ — push-based очередь, удаляет после ack, гибкая маршрутизация через exchanges, проще для task queues и RPC.

---

### В11. Что такое rebalance?

**Идеальный ответ:**
Rebalance — перераспределение партиций между консюмерами consumer group при изменении состава группы (консюмер упал, добавился, изменилось число партиций). На время rebalance чтение приостанавливается. Может вызывать задержки и дубликаты. Минимизируется стабильными консюмерами и правильной настройкой `session.timeout.ms`, `max.poll.interval.ms`.

---

### В12. Что такое acks у продюсера?

**Идеальный ответ:**
Уровень подтверждения записи: `acks=0` — не ждёт (можно потерять), `acks=1` — подтвердил лидер партиции, `acks=all` — подтвердили все in-sync реплики (максимальная надёжность, медленнее). Для критичных данных — `all`.

---

### В13. Как тестировать функциональность с Kafka (вопрос для AQA)?

**Идеальный ответ:**
Два направления: (1) после действия в UI/API — тестовый consumer проверяет, что событие появилось в топике с правильной схемой и полями; (2) тест сам публикует событие — polling проверяет изменение состояния (API/БД/UI). Учитывать eventual consistency — polling с таймаутом, не sleep. Изоляция: уникальные keys на тест. Консюмер должен быть идемпотентным — тестировать повторную обработку.

---

### В14. Сообщение в топике есть, сервис не реагирует — куда смотреть?

**Идеальный ответ:**
Consumer group жива? Правильный group.id? Offset не ушёл вперёд? Не завис rebalance? Ошибка десериализации (сообщение ушло в DLQ)? Consumer lag — растёт ли? Проверить через `kafka-consumer-groups.sh --describe` и логи консюмера.

---

### В15. Kafka «слушает» микросервисы и «подписана» на события?

**Идеальный ответ:**
**Нет.** Kafka — пассивный брокер. Продюсеры сами пишут в топик; консюмеры сами читают через poll. Kafka не «слушает» и не «подписана» — это pull-модель, не push и не pub/sub в классическом понимании RabbitMQ.

# Глава 12. GUI Kafka (Kafka UI) — подробный разбор интерфейса

> **Что это.** У тебя на стенде поднят **Kafka UI** (provectus/kafka-ui) на http://localhost:8090. Это веб-морда, которая по сети ходит в брокер (`localhost:9092`) и показывает то же, что CLI-команды, но визуально. GUI **ничего не хранит сам** — он лишь читает состояние кластера. Если что-то видно в UI — оно реально есть в брокере.

**Важно для собеседования:** GUI — удобный инструмент, но всё, что он показывает, можно получить и через `kafka-*.sh` скрипты. На интервью полезно уметь и то, и другое: «в UI я смотрю быстро, но за кулисами это `kafka-consumer-groups.sh --describe`».

## 12.1. Dashboard / Brokers — состояние кластера

Первый экран — обзор кластера. На что смотреть:

- **Brokers** — сколько брокеров живо. У тебя один (`localhost:9092`), в проде — 3+.
- **Version** — версия Kafka (у тебя 3.9, KRaft-режим — без Zookeeper).
- **Partitions / Replicas** — суммарное число партиций и их копий по кластеру.
- **Online / Offline partitions** — если есть offline-партиции, часть данных недоступна (упал брокер-лидер и нет живой реплики). На здоровом кластере offline = 0.
- **Under-replicated partitions** — партиции, у которых не все реплики в ISR. Красный флаг: репликация отстаёт.

**Вопрос на интервью:** «Как понять, что с кластером проблема?» → смотрю Under-replicated и Offline партиции; если они не ноль — брокер лёг или репликация не успевает.

## 12.2. Topics — главный экран

Список топиков. Для каждого видно: имя, число **партиций**, **replication factor**, суммарный **размер** на диске, число сообщений.

Провалившись в конкретный топик, ты видишь вкладки:

**Overview** — партиции топика с деталями по каждой:
- **Partition** — номер (0, 1, 2…).
- **Leader** — какой брокер сейчас лидер этой партиции.
- **Replicas / In Sync Replicas** — где лежат копии и сколько из них синхронны.
- **Offset Min / Max** — самый старый и самый новый offset в партиции. `Max − Min` ≈ сколько сообщений сейчас лежит (с поправкой на retention, который срезает старое).

**Messages** — просмотр самих сообщений. Здесь AQA проводит бóльшую часть времени:
- фильтр по **партиции**, по **offset**, по **времени** (seek to timestamp), по **ключу**;
- видно **key, value, headers, timestamp, partition, offset** каждого сообщения;
- можно листать от начала (oldest) или от конца (newest);
- есть режим «live» — новые сообщения появляются в реальном времени.
- **Как проверить, что событие дошло:** Topics → нужный топик → Messages → фильтр по своему тестовому key → видишь свой JSON.

**Consumers** — какие consumer groups читают этот топик и с каким lag.

**Settings / Configs** — конфиг топика: `retention.ms`, `cleanup.policy` (delete/compact), `max.message.bytes` и т.д. Здесь же на многих сборках можно топик редактировать/удалять.

**Как создать топик из UI:** кнопка «Add a Topic» → имя, число партиций, replication factor, retention. Это то же, что `kafka-topics.sh --create`.

## 12.3. Consumers (Consumer Groups) — самый важный экран для отладки

Список всех consumer groups. Для каждой:

- **Group ID** — идентификатор группы (тот самый `group.id`).
- **State** — состояние группы:
  - `Stable` — всё хорошо, партиции распределены, читают;
  - `Empty` — группа существует (есть закоммиченные offset), но **нет живых консюмеров** (никто не подключён);
  - `PreparingRebalance` / `CompletingRebalance` — идёт перераспределение партиций;
  - `Dead` — группа удалена/неактивна.
- **Members** — сколько консюмеров сейчас в группе.
- **Consumer Lag** — суммарное отставание группы (сколько сообщений не прочитано). **Ключевая метрика.**

Провалившись в группу, видишь **разбивку по партициям**:

| Колонка | Смысл |
|---|---|
| **Topic / Partition** | какую партицию какого топика читает |
| **Consumer ID / Host** | какой конкретный консюмер к ней назначен |
| **Log End Offset** | конец лога — последнее записанное в партицию (LEO) |
| **Current Offset** | до какого offset группа прочитала (committed) |
| **Lag** | `Log End Offset − Current Offset` — сколько не прочитано |

**Как читать эту таблицу (важнейший навык AQA):**
- `Lag = 0` по всем партициям → консюмер догнал, всё обработано.
- `Lag` растёт со временем → консюмер не справляется (медленный / мало консюмеров / завис).
- `State = Empty` + есть lag → консюмер **отвалился**, сообщения копятся, никто не читает. Классика «событие в топике есть, сервис не реагирует».
- Партиция есть, но **Consumer ID пустой** → эту партицию никто не читает (консюмеров меньше, чем партиций, или rebalance).

**Сброс offset из UI:** внутри группы обычно есть «Reset Offsets» — можно перемотать группу на earliest / latest / конкретный offset / по времени. Это GUI-эквивалент `kafka-consumer-groups.sh --reset-offsets`. Полезно для replay: перемотал группу на earliest — она перечитает всю историю.

## 12.4. Как GUI помогает в типичных AQA-сценариях

| Задача | Что делаю в UI |
|---|---|
| Проверить, что событие опубликовано | Topics → топик → Messages → фильтр по key/времени → вижу JSON |
| Проверить схему/поля события | Messages → открываю сообщение → смотрю value и headers |
| Проверить, что сервис обработал | Consumers → его группа → Lag должен стать 0 |
| Найти, почему сервис молчит | Consumers → группа: State=Empty? Members=0? Lag растёт? |
| Перечитать историю для нового теста | Consumers → Reset Offsets → earliest, ЛИБО новый group.id |
| Понять раскладку по партициям | Topic → Overview: сколько партиций, кто лидер |
| Убедиться, что один key = одна партиция | Messages → фильтрую по partition → все события этого key в одной |

## 12.5. Чего GUI НЕ делает (частая путаница)

- GUI **не является брокером** и **не хранит** сообщения — он их только показывает.
- GUI **не «подписан»** на события — он опрашивает кластер, как обычный клиент.
- Удаление сообщения из UI поштучно в Kafka **не предусмотрено** (Kafka — лог): можно удалить весь топик, настроить retention или compaction, но не «выделить строку и стереть». Это принципиальное отличие от очередей.

# Глава 13. Углублённый разбор сущностей: topic, partition, offset, consumer group

> Это ядро всех вопросов на собесе. Разберём каждую сущность так, чтобы можно было объяснить «на пальцах» и не поплыть на уточняющих вопросах.

## 13.1. Topic — что это на самом деле

Топик — это **именованный, разбитый на партиции, упорядоченный по времени журнал (лог) записей**. Ключевые свойства:

- Топик — **логическая абстракция**. Физически данные лежат в партициях, а партиции — на брокерах.
- Топик **многоподписчиковый**: сколько угодно consumer groups читают его независимо, не мешая друг другу и не «расходуя» сообщения.
- Топик задаётся при создании числом партиций и replication factor. **Партиции можно только увеличивать**, уменьшить — нельзя (пришлось бы пересобирать раскладку по key).
- Retention топика определяет, сколько живут сообщения: `cleanup.policy=delete` (по времени/размеру) или `compact` (последнее значение на key).

**Типичный уточняющий вопрос:** «Сколько партиций делать?» → зависит от нужного параллелизма чтения: число партиций = потолок числа полезных консюмеров в группе. Больше партиций = больше параллелизма, но и больше накладных расходов (файлы, метаданные, дольше rebalance). На старте — 3–6 на топик, дальше по нагрузке.

## 13.2. Partition — единица параллелизма и порядка

Партиция — это **упорядоченная, неизменяемая, append-only последовательность сообщений**. Всё самое важное в Kafka крутится вокруг партиций:

- **Порядок.** Гарантируется строго **внутри партиции**. Между партициями порядка нет. Если нужен порядок для сущности — шли её события с одним key.
- **Параллелизм.** Партиция — минимальная единица распараллеливания чтения. Одну партицию в группе читает ровно один консюмер. Хочешь читать в 6 потоков — нужно ≥6 партиций.
- **Хранение.** Партиция физически = папка на диске брокера, нарезанная на сегменты-файлы. Старые сегменты удаляются по retention целиком.
- **Репликация.** Копия партиции живёт на нескольких брокерах (по replication factor). Один — лидер, остальные догоняют.

**Как продюсер выбирает партицию:**

```
key задан      → partition = hash(key) % число_партиций   (детерминированно, один key → одна партиция)
key не задан    → sticky/round-robin                       (равномерно, порядок между сообщениями не важен)
partition задан явно → пишем прямо в неё
```

**Ловушка «hot partition»:** если key выбран плохо (например, у 90% событий один и тот же key), одна партиция перегружена, остальные простаивают. Решение — более «широкий» ключ.

## 13.3. Offset — позиция и прогресс

Offset — это **порядковый номер сообщения внутри партиции**, начиная с 0, монотонно растёт, никогда не переиспользуется. Важно различать три вещи:

- **Offset сообщения** — «адрес» записи в партиции. Неизменен.
- **Current / committed offset** — до какого места **дочитала конкретная consumer group**. Это состояние *группы*, а не сообщения. Хранится в служебном топике `__consumer_offsets`.
- **Log End Offset (LEO)** — offset следующей записи (конец лога).

`Lag = LEO − committed offset` — сколько группе осталось прочитать.

**Ключевая идея:** offset принадлежит **группе**, а не сообщению. Поэтому:
- две разные группы читают один топик со своими независимыми offset;
- «перечитать историю» = сдвинуть offset группы назад (reset) или создать новую группу с `auto.offset.reset=earliest`;
- удаление консюмера не двигает offset — при возврате он продолжит с закоммиченного места.

**Когда коммитить offset — и как это даёт семантику доставки:**
- коммит **до** обработки → at-most-once (упал в обработке → сообщение потеряно, offset уже сдвинут);
- коммит **после** обработки → at-least-once (упал до коммита → перечитаем → дубликат);
- авто-коммит (`enable.auto.commit=true`) по таймеру — удобно, но добавляет непредсказуемости (может коммитнуть до того, как ты реально обработал). Для надёжности часто выключают и коммитят вручную.

## 13.4. Consumer Group — масштабирование и отказоустойчивость

Consumer group — это **набор консюмеров с общим `group.id`, между которыми Kafka распределяет партиции топика**.

Три закона, которые надо знать наизусть:

1. **Одна партиция → ровно один консюмер в группе.** Не бывает, чтобы два консюмера одной группы читали одну партицию (иначе сломался бы порядок и offset). Это и есть механизм «конкурентной» обработки без дублей внутри группы.
2. **Партиций меньше, чем консюмеров → лишние простаивают.** Потолок полезного параллелизма = число партиций.
3. **Разные группы независимы.** Каждая группа получает **весь** поток топика и ведёт свои offset. Это механизм fan-out (billing, notifications, analytics читают одно и то же).

**Rebalance — как группа переживает изменения:**
- триггеры: консюмер упал (нет heartbeat), добавился новый, изменилось число партиций, консюмер завис дольше `max.poll.interval.ms`;
- **group coordinator** (брокер) заново раздаёт партиции по консюмерам;
- при «классическом» (eager) rebalance группа на миг **останавливает чтение** (stop-the-world) → возможны задержки и дубликаты;
- **cooperative** rebalance переназначает только затронутые партиции, простой меньше.

**Частая прод-проблема — «rebalance storm»:** обработка одного сообщения дольше `max.poll.interval.ms` → координатор думает, что консюмер завис → выкидывает его → rebalance → и по кругу. Лечится: обрабатывать быстрее, увеличить `max.poll.interval.ms`, брать меньше сообщений за `poll()` (`max.poll.records`).

**Как это связано:** topic (что читаем) → делится на partitions (единицы параллелизма и порядка) → consumer group распределяет партиции по консюмерам → каждый консюмер держит offset по своим партициям → lag показывает, догоняет ли группа. Это цепочка, вокруг которой строится 80% вопросов.

# Глава 14. Расширенный банк вопросов собеседования — человеческие ответы

> Формат «как бы ты ответил вслух». Отвечай **своими словами**, не заучивай дословно — интервьюер сразу слышит зубрёжку. Здесь ответы развёрнутые, с примерами.

### Б1. Объясни Kafka человеку, который её никогда не видел.

Представь общий журнал, куда одни сервисы дописывают события в конец, а другие читают их по порядку в своём темпе. Никто никого не ждёт: написал — пошёл дальше. Прочитал — запомнил, докуда дочитал. Сообщения не пропадают после чтения, лежат положенный срок, поэтому их можно перечитать или подключить нового читателя, который увидит всю историю. Вот это «общий устойчивый журнал событий» и есть Kafka. Она нужна, чтобы сервисы не были жёстко связаны друг с другом и переживали пики нагрузки.

### Б2. Почему не просто HTTP между сервисами?

По HTTP сервис A должен знать всех получателей, ждать их ответа и сам разруливать ретраи, если кто-то лёг. Появился новый потребитель — правь A. Пик нагрузки — A и B падают вместе. Kafka разрывает эту связь: A просто кладёт событие в топик и забывает. Кто подписан — их забота. Новый потребитель добавляется без единой правки в A. И Kafka работает буфером: если потребитель медленный, события накапливаются, а не теряются.

### Б3. Что физически происходит, когда продюсер отправляет сообщение?

Продюсер сериализует key и value, по ключу вычисляет партицию (`hash(key) % N`), группирует сообщения в батч и шлёт лидеру этой партиции. Лидер дописывает в конец лога, реплики подтягивают копию. В зависимости от `acks` продюсер получает подтверждение: при `acks=all` — только когда все in-sync реплики записали. Дальше сообщение просто лежит в партиции под своим offset и ждёт читателей.

**Про батчинг (важная деталь).** Продюсер не отправляет каждое сообщение по сети сразу — он **копит их в буфере и шлёт пачкой (батчем)**. Именно батчинг даёт Kafka высокую пропускную способность: одна отправка из 1000 сообщений в разы дешевле, чем 1000 отдельных. Батч формируется отдельно для каждой партиции и управляется двумя параметрами:

- **`batch.size`** — максимальный размер батча в байтах (по умолчанию ~16 КБ). Набрался — отправляем.
- **`linger.ms`** — сколько ждать, добивая батч, прежде чем отправить (по умолчанию `0` — шлём сразу). Небольшое увеличение (5–10 мс) делает батчи крупнее: throughput выше, но растёт задержка.

Батч по одной партиции сжимается целиком (`compression.type`: `gzip`/`snappy`/`lz4`/`zstd`) и пишется в лог как единая запись — эффективнее и по сети, и по диску. Отсюда важный для AQA вывод: сообщение может «полежать» в батче продюсера до `linger.ms` и уйти не мгновенно — ещё один довод в пользу polling вместо `sleep`. Симметрично на чтении: консюмер тоже получает сообщения **пачкой** — `poll()` возвращает батч (ограничен `max.poll.records`), а `fetch.min.bytes` / `fetch.max.wait.ms` управляют тем, сколько брокер накопит перед отдачей.

**Батчинг — это главный компромисс «throughput против latency»:** крупнее батчи → выше пропускная способность, но чуть больше задержка.

### Б4. Что значит «Kafka — это лог, а не очередь»?

В очереди (RabbitMQ) сообщение — это задача: доставили, обработали, ack — и оно исчезло. В Kafka сообщение — это факт в журнале: чтение его не удаляет. Оно лежит по retention, его могут прочитать сколько угодно разных групп, и каждая — с нуля. Отсюда replay, event sourcing, аналитика по истории. Читатель не «забирает» сообщение, а просто двигает свою закладку (offset).

### Б5. Зачем нужны партиции, если можно один большой лог?

Один лог = один поток записи и чтения, это потолок производительности и порядок «всё-или-ничего». Партиции разбивают топик на независимые журналы, которые лежат на разных брокерах и читаются параллельно разными консюмерами. Цена — порядок теперь только внутри партиции. Поэтому важные для порядка события шлют с одним key, чтобы они попали в одну партицию.

### Б6. Что будет, если консюмеров больше, чем партиций?

Лишние консюмеры будут простаивать без работы, потому что партиция назначается ровно одному консюмеру. 6 партиций и 8 консюмеров → 6 работают, 2 в резерве (подхватят, если кто-то упадёт). Значит, чтобы масштабировать чтение, надо закладывать достаточно партиций заранее.

### Б7. Что произойдёт, если консюмер упадёт в середине обработки?

Он не успел закоммитить offset. Координатор через `session.timeout` заметит пропажу heartbeat, запустит rebalance, отдаст его партиции другому консюмеру. Тот начнёт с последнего закоммиченного offset — то есть с сообщения, которое первый начал, но не закончил. Итог: сообщение обработается повторно (at-least-once, дубликат). Поэтому обработчик должен быть идемпотентным — повторная обработка не должна ломать данные.

### Б8. Что такое идемпотентность и как её добиться на стороне консюмера?

Идемпотентность — свойство, при котором повторная обработка того же события даёт тот же результат, без побочных дублей. Достигается так: хранить обработанные id событий и проверять перед действием (dedup-таблица); использовать upsert вместо insert; делать операции естественно идемпотентными («установить статус = paid», а не «увеличить счётчик»). Это главный практический способ жить с at-least-once.

### Б9. Что такое `__consumer_offsets`?

Служебный внутренний топик Kafka, куда группы коммитят свои offset. То есть прогресс чтения хранит сама Kafka, а не консюмер локально. Поэтому консюмер можно перезапустить или заменить — он подтянет offset из этого топика и продолжит с места остановки.

### Б10. Что видит новый консюмер: с какого места он начнёт читать?

Зависит от `auto.offset.reset`: `earliest` — с самого начала (вся история), `latest` — только новые сообщения, пришедшие после подключения. Это касается **только** случая, когда у группы ещё нет сохранённого offset. Если offset уже есть — продолжит с него, настройка не применяется.

### Б11. Как перечитать сообщения (replay)?

Два способа: сдвинуть offset существующей группы назад (`kafka-consumer-groups.sh --reset-offsets --to-earliest` или через UI Reset Offsets), либо подключить новую группу с `auto.offset.reset=earliest` — она прочитает всю сохранённую историю топика. Работает, потому что Kafka не удаляет сообщения после чтения.

### Б12. Что такое retention и что происходит, когда оно истекает?

Retention — правило, сколько хранить данные: по времени (`retention.ms`, по умолчанию 7 дней) или по размеру (`retention.bytes`). Когда сегмент лога старше срока — Kafka удаляет его целиком в фоне. Важно: удаляются старые **сегменты**, а не «прочитанные» сообщения; чтение вообще ни на что не влияет. Если консюмер отстал больше, чем retention, он может **потерять** непрочитанные сообщения — они удалятся раньше, чем он до них дойдёт.

### Б13. Чем log compaction отличается от обычного retention?

При `cleanup.policy=delete` Kafka чистит по времени/размеру. При `compact` — хранит **последнее** значение для каждого key бесконечно, удаляя старые версии этого же key. Это как «текущее состояние»: для key `user-42` останется только последнее событие. Удаление ключа делается tombstone-сообщением (`value=null`). Compaction используют для топиков-снимков состояния.

### Б14. Что такое ISR и почему это важно?

ISR (In-Sync Replicas) — реплики партиции, которые успевают за лидером. При `acks=all` продюсер ждёт подтверждения от всех ISR — это и есть гарантия надёжности. Если реплика отстала — она выпадает из ISR. Настройка `min.insync.replicas` задаёт минимум ISR: если живых меньше — запись отклоняется, чтобы не записать данные «в одну копию» и не потерять их при падении.

### Б15. Объясни acks=0/1/all на примере.

`acks=0` — продюсер бросил сообщение и не оглядывается: быстро, но если лидер лёг в этот момент — потеряли и не узнали. `acks=1` — ждём подтверждения лидера: если лидер записал, но упал до репликации — можем потерять. `acks=all` — ждём, пока запишут все in-sync реплики: медленнее, но сообщение точно переживёт падение одного брокера. Для денег/заказов — `all`, для метрик/логов, где потеря терпима — можно `1` или `0`.

### Б16. Как гарантировать порядок обработки заказов одного клиента?

Слать все события клиента с одним key (например, `client_id`). Тогда они попадут в одну партицию, а внутри партиции порядок гарантирован и читает её один консюмер. Нельзя параллелить обработку внутри одной партиции, если важен порядок. Если распараллелить по разным партициям — порядок между ними уже не гарантируется.

### Б17. Что такое exactly-once и реально ли оно?

Exactly-once — «ровно один раз», без потерь и без дублей. В Kafka достигается связкой: идемпотентный продюсер (не плодит дубли при ретраях) + транзакции (атомарная запись в несколько партиций/топиков + коммит offset в одной транзакции). Работает для сценария Kafka→обработка→Kafka (например, Kafka Streams). Но как только в цепочке появляется внешняя система (БД, HTTP) — гарантия на неё не распространяется, и на практике чаще берут at-least-once + идемпотентность.

### Б18. Что такое consumer lag и как на него реагировать?

Lag — разрыв между концом лога и позицией группы, то есть «сколько сообщений не прочитано». Небольшой ровный lag — норма. Растущий lag — тревога: консюмер не успевает. Реагируют так: добавить консюмеров (до числа партиций), ускорить обработку, увеличить число партиций, проверить, не завис ли консюмер в rebalance. Lag — метрика №1 для мониторинга здоровья потребителя.

### Б19. Что такое DLQ и когда её применяют?

Dead Letter Queue — отдельный топик, куда отправляют сообщения, которые не удалось обработать после N попыток (битый JSON, невалидные данные, ошибка бизнес-логики). Смысл — не блокировать всю партицию из-за одного «ядовитого» сообщения и не терять его молча. Потом такие сообщения разбирают вручную или отдельным процессом. В Kafka DLQ — это соглашение, реализуемое приложением, а не встроенная фича.

### Б20. Что делает ключ (key) сообщения?

Две вещи: определяет партицию (через hash) — а значит, порядок и локальность событий одной сущности; и служит ключом для log compaction (если топик compacted). Если key = null, сообщения раскидываются равномерно (round-robin/sticky) и порядок между ними не гарантируется.

### Б21. Zookeeper или KRaft — в чём разница?

Раньше Kafka хранила метаданные кластера (кто лидер, какие топики, ISR) во внешнем Zookeeper — это отдельный кластер, который надо поднимать и обслуживать. KRaft — новый режим, где Kafka сама управляет метаданными через встроенный Raft-консенсус, без Zookeeper. Меньше движущихся частей, быстрее восстановление, проще эксплуатация. Твой стенд на 3.9 — уже KRaft.

### Б22. Может ли Kafka потерять сообщения? Когда?

Да, при неаккуратной настройке: `acks=0` (продюсер не проверяет запись); `acks=1` + падение лидера до репликации; `min.insync.replicas` слишком мал; консюмер отстал больше retention — непрочитанное удалилось; авто-коммит offset до фактической обработки (потеря на стороне консюмера). Правильная связка для надёжности: `acks=all`, `min.insync.replicas≥2`, RF≥3, ручной коммит после обработки.

### Б23. Producer шлёт быстрее, чем consumer читает — что будет?

Ничего страшного не сломается сразу — в этом и сила Kafka как буфера. Сообщения копятся в партициях, растёт lag. Потребитель разгребёт, когда сможет (backpressure — он сам управляет темпом через pull). Опасность одна: если отставание превысит retention, старые непрочитанные сообщения удалятся. Поэтому за lag и retention следят вместе.

### Б24. Как устроено чтение — брокер шлёт или консюмер забирает?

Консюмер **забирает** (pull): в цикле вызывает `poll()`, получает пачку сообщений начиная со своего offset, обрабатывает, коммитит offset, повторяет. Брокер сам ничего не «пушит». Плюсы pull: консюмер контролирует темп (не захлебнётся), эффективное батчирование, легко делать replay. Это отличает Kafka от push-брокеров вроде RabbitMQ.

### Б25. Как тестировать сервис, который читает из Kafka (AQA)?

Тест выступает продюсером: публикую в топик событие с известным key/JSON, затем через polling проверяю побочный эффект — статус в API/БД/UI поменялся. Учитываю eventual consistency: не `sleep`, а `expect.poll` с таймаутом. Для изоляции параллельных тестов — уникальный key на тест. Проверяю негатив: битый JSON → сообщение уходит в DLQ, сервис не падает. И проверяю идемпотентность: публикую одно событие дважды — эффект должен быть один.

### Б26. Как тестировать сервис, который пишет в Kafka (AQA)?

Тест выступает консюмером: делаю действие в UI/API, затем тестовым консюмером читаю топик и проверяю, что событие появилось — правильный топик, key, схема value, headers. Опять же с ожиданием (событие приходит не мгновенно). Полезно читать с уникальной тестовой группой и `earliest`, чтобы не зависеть от чужого прогресса.

### Б27. «Событие в топике есть, а сервис не реагирует» — как дебажить?

Иду в Consumers (UI или `kafka-consumer-groups.sh --describe`) и по шагам: группа вообще существует и её State не Empty? Members > 0 (консюмер подключён)? Правильный ли `group.id` слушает сервис? Lag растёт? Партиция, куда легло сообщение, назначена живому консюмеру? Не завис ли rebalance? Нет ли ошибки десериализации (сообщение «ядовитое», ушло в DLQ / застряло)? Обычно проблема — мёртвая группа или неверный group.id.

### Б28. Сколько партиций выбрать для топика?

Отталкиваюсь от нужного параллелизма: партиций должно быть не меньше, чем максимальное число консюмеров в группе, которые я хочу нагрузить. Плюс запас на рост. Но не бесконечно: много партиций = больше файлов, дольше rebalance, больше нагрузка на метаданные. Практика: начать с 3–6, мониторить lag и throughput, при необходимости увеличить (уменьшить нельзя).

### Б29. Что такое headers и зачем они?

Headers — метаданные сообщения помимо key/value: например, `trace-id` для сквозной трассировки, `content-type`, `schema-version`, `source`. Не влияют на партиционирование, но полезны для маршрутизации на стороне приложения, отладки и версионирования схемы, не засоряя сам payload.

### Б30. Что такое Schema Registry и какую проблему он решает?

Это отдельный сервис-хранилище схем (Avro/Protobuf/JSON Schema). Продюсер и консюмер согласуют формат сообщения через схему, а не «на честном слове». Registry следит за совместимостью версий (можно ли добавить поле, не сломав старых консюмеров). Решает главную боль событийных систем — контракт между сервисами: продюсер не сможет случайно начать слать несовместимый формат.

### Б31. Kafka Streams / ksqlDB — что это в двух словах?

Библиотека/движок для обработки потоков поверх Kafka: читать топик, фильтровать/агрегировать/джойнить на лету и писать результат в другой топик. Например, «считать сумму заказов по каждому клиенту в реальном времени». Отличие от обычного консюмера — встроенное состояние, оконные агрегации и exactly-once внутри Kafka. Знать на уровне «что это и зачем» обычно достаточно.

### Б32. Один большой топик или много маленьких?

Зависит от смысла данных. Разные **типы** событий и разные контракты — разные топики (`orders`, `payments`, `shipments`): так проще управлять retention, доступами, схемами и потребителями. Много почти пустых топиков плодить тоже не стоит — накладные расходы на метаданные. Ориентир: топик = один логический тип событий с общей схемой и жизненным циклом.

# Глава 15. Kafka vs другие брокеры: RabbitMQ, ActiveMQ, SQS, NATS, Pulsar, Redis

## 15.1. Kafka vs RabbitMQ — углублённо

Это **главное** сравнение на собесе. Разбери его не как таблицу, а как две разные философии.

**RabbitMQ — «умный брокер, глупый потребитель».** Вся логика маршрутизации живёт в брокере: продюсер шлёт в **exchange**, тот по правилам (**bindings**) раскладывает сообщения по **очередям**, откуда их **пушит** потребителям. Сообщение — это задача: доставили, потребитель прислал **ack** — сообщение удалено. Если nack/таймаут — вернули в очередь или в DLX (dead-letter exchange). Богатая маршрутизация: `direct` (по точному ключу), `topic` (по маске `order.*.eu`), `fanout` (всем), `headers`. Идеально для очередей задач и сложного роутинга.

**Kafka — «глупый брокер, умный потребитель».** Брокер просто хранит упорядоченный лог и отдаёт байты по offset. Никакой маршрутизации — только топик и партиция по key. Потребитель сам решает, что и с какого места читать, сам двигает offset. Сообщение чтением **не удаляется**. Идеально для потоков событий, повторного чтения, множества независимых потребителей и высокого throughput.

| Критерий | Kafka | RabbitMQ |
|---|---|---|
| **Философия** | Глупый брокер, умный консюмер | Умный брокер, глупый консюмер |
| **Модель** | Распределённый лог (commit log) | Очереди + exchanges |
| **Доставка** | Pull (консюмер опрашивает `poll()`) | Push (брокер заталкивает) |
| **Судьба сообщения** | Остаётся по retention | Удаляется после ack |
| **Повторное чтение** | ✅ Да (сдвиг offset) | ❌ Нет (уже удалено) |
| **Порядок** | Внутри партиции | Внутри очереди (при 1 консюмере) |
| **Маршрутизация** | Простая: topic + key→partition | Богатая: 4 типа exchange, bindings |
| **Throughput** | Очень высокий (сотни тыс.–млн msg/s) | Умеренный (десятки тыс. msg/s) |
| **Масштабирование чтения** | Consumer groups + партиции | Несколько консюмеров на очередь |
| **Приоритеты сообщений** | ❌ Нет | ✅ Priority queues |
| **TTL / отложенная доставка** | Retention на топик | Per-message TTL, delayed exchange |
| **Типичное применение** | Event streaming, sourcing, логи, аналитика | Task queues, RPC, сложный роутинг |
| **Модель хранения** | Диск (лог), рассчитан на терабайты истории | В основном в памяти/до ack |

**Одна фраза:** *Kafka — это pull-based распределённый лог: сообщения хранятся, читаются многими группами независимо, можно перечитать, масштаб — через партиции. RabbitMQ — это push-based очередь с богатой маршрутизацией: сообщение доставляется и удаляется после ack. Kafka для потоков событий, RabbitMQ для очередей задач и роутинга.*

**Вопрос-ловушка:** «Kafka подписывается на события микросервисов и слушает их?» — **Нет.** Kafka пассивна: продюсеры сами пишут, консюмеры сами читают (pull). Она не наблюдатель и не подписчик — это просто хранилище-лог.

## 15.2. Когда что выбирать

**Бери Kafka, если:** нужен поток событий, а не разовые задачи; несколько независимых потребителей одного потока (fan-out); нужен replay/аудит/история; очень высокий объём; event sourcing или потоковая обработка (Streams/Flink).

**Бери RabbitMQ, если:** классическая очередь задач «обработал и забыл»; нужна сложная маршрутизация (routing key, fanout, topic exchange); RPC «запрос-ответ»; приоритеты сообщений; умеренный объём и хочется проще стартовать.

## 15.3. Остальные брокеры — коротко, чтобы не растеряться

| Брокер | Суть | Когда всплывает |
|---|---|---|
| **ActiveMQ / Artemis** | Классический JMS-брокер очередей (как RabbitMQ, но из Java/JMS-мира). Push, ack, очереди и топики (JMS-топики ≈ pub/sub). | Legacy Java-энтерпрайз, стандарт JMS |
| **Amazon SQS** | Полностью управляемая облачная очередь. Standard (at-least-once, без строгого порядка) и FIFO (порядок + exactly-once в пределах группы). Нет replay, нет consumer groups как в Kafka. | AWS, когда не хочется своей инфраструктуры |
| **Amazon Kinesis** | «Kafka от AWS»: шарды вместо партиций, лог с retention, replay. Управляемый. | AWS-стек, нужен стриминг без своей Kafka |
| **NATS / NATS JetStream** | Очень лёгкий и быстрый брокер. Core NATS — fire-and-forget pub/sub без хранения; JetStream добавляет персистентность и стримы (ближе к Kafka). | Микросервисы, IoT, низкая задержка |
| **Apache Pulsar** | Прямой конкурент Kafka: лог + очереди в одном, разделены хранение (BookKeeper) и обслуживание (broker), мультитенантность, гео-репликация из коробки. | Альтернатива Kafka, где нужны и очереди, и стримы |
| **Redis (Streams / Pub-Sub)** | Redis Pub/Sub — эфемерный (нет доставки офлайн-подписчикам). Redis Streams — лёгкий лог с consumer groups и offset, похоже на мини-Kafka в памяти. | Уже есть Redis, нужен простой стриминг без отдельной инфраструктуры |

**Как отвечать, если спросят про «другие»:** сгруппируй мысленно. Очереди-с-удалением-после-ack (RabbitMQ, ActiveMQ, SQS) — про доставку задач. Логи-с-retention-и-replay (Kafka, Kinesis, Pulsar, отчасти Redis Streams) — про потоки событий. Kafka — эталон второй группы: лог, pull, хранение, consumer groups, партиции.

# Глава 16. Шпаргалка одной страницей

```text
Producer ──write(key,value)──▶ Topic
                                  ├── Partition 0 [0][1][2]...
                                  ├── Partition 1 [0][1]...
                                  └── Partition 2 [0]...
                                       ▲ pull (poll)
Consumer Group "A" ──────────────────┘  (каждая partition → 1 consumer)
Consumer Group "B" ──────────────────┘  (независимо от A)

KEY RULES:
  • Порядок — только внутри partition
  • Один key → одна partition
  • Сообщения НЕ удаляются после чтения (retention)
  • Pull, не push
  • Разные consumer groups — каждая видит весь поток
  • Offset = позиция чтения; commit = запомнить прогресс
  • Rebalance = перераспределение partitions при изменении группы

KAFKA vs RABBITMQ:
  Kafka  = log, pull, хранит, replay, event streaming
  Rabbit = queue, push, удаляет после ack, task queues

AQA:
  • Polling вместо sleep (eventual consistency)
  • Test → event in topic OR event → state change
  • Unique keys per test for isolation
  • Schema validation (Zod/pydantic)
```

# Глава 17. Трекинг событий микросервисов через Kafka на AQA-проекте (с примерами кода)

> Здесь — как это реально выглядит на боевом проекте: как проследить путь события через несколько сервисов, как найти нужное сообщение по id, и рабочий код тестового helper'а, которым можно пользоваться в автотестах.

## 17.1. Реалистичная картина: что значит «трекать события»

На микросервисном проекте одно действие пользователя порождает **цепочку событий** в разных топиках. Пример «оформление заказа»:

```text
POST /orders  (UI/API)
      │
      ▼
[ topic: orders ]        order.created      ──▶ payment-service
      │                                            │
      │                                            ▼
[ topic: payments ]      payment.completed  ──▶ notification-service
      │                                            │
      ▼                                            ▼
[ topic: notifications ] email.sent          (письмо «отправлено»)
```

**«Трекать»** на AQA — это уметь ответить на вопросы:
- дошло ли событие `order.created` до топика после моего действия?
- правильные ли в нём поля (схема, значения)?
- породило ли оно `payment.completed`, а тот — `email.sent`?
- за какое время прошла вся цепочка, где застряло?

Ключевой приём — **сквозной идентификатор**. Хорошо спроектированные системы прокидывают через все события общий `correlationId` / `traceId` (в headers) и бизнес-id (`orderId` в key/value). По нему и «сшивается» вся цепочка в разных топиках.

## 17.2. По каким идентификаторам ищут сообщение

| Где лежит id | Что это обычно | Как искать |
|---|---|---|
| **key сообщения** | бизнес-id: `orderId`, `userId` | фильтр по ключу в UI/консюмере; ещё и определяет партицию |
| **headers** | `correlationId`, `traceId`, `eventId`, `messageId`, `schemaVersion` | фильтр по значению заголовка |
| **поле внутри value (JSON)** | `orderId`, `eventType`, `status` | распарсить JSON и сравнить поле |
| **offset + partition** | точный «адрес» записи | прямой seek к позиции |
| **timestamp** | когда произошло | seek by time (читать с момента X) |

**Практический вывод:** самый надёжный трекинг — по `correlationId` в headers (уникален на всю цепочку) плюс `orderId` в value. В тесте всегда генерируй **уникальный** id на прогон, чтобы не поймать чужое сообщение.

## 17.3. Способ 1 — поиск через Kafka UI (быстро, руками)

В provectus Kafka UI (localhost:8090) → Topics → нужный топик → **Messages**:
- **Seek Type**: Oldest / Newest / From offset / From timestamp — откуда начать читать;
- фильтр по **Key** — если бизнес-id лежит в ключе;
- **Smart Filter** — фильтр на JavaScript по содержимому каждого сообщения. Именно им ищут «по id внутри JSON» или «по заголовку».

Примеры Smart Filter (выполняется для каждого сообщения, доступны `key`, `value`, `headers`, `offset`, `partition`, `timestamp`):

```javascript
// найти по orderId внутри JSON-value
JSON.parse(value).orderId === 1001

// найти по correlationId в заголовке
headers['correlationId'] === 'test-run-8f3a12'

// все события конкретного типа за прогон
JSON.parse(value).eventType === 'payment.completed'
  && key.startsWith('order-1001')
```

## 17.5. Способ 3 — программно в автотесте (основной рабочий способ)

Идея helper'а: тестовый консюмер с **уникальной group.id** читает топик с `earliest`, складывает сообщения в буфер, а метод `waitForMessage(predicate, timeout)` ждёт (polling), пока не появится сообщение, удовлетворяющее условию — например «в value orderId === X» или «в headers correlationId === Y».

### TypeScript (kafkajs) — полноценный helper

```typescript
// kafka-test-client.ts
import { Kafka, logLevel, EachMessagePayload } from 'kafkajs';

export interface CapturedMessage {
  topic: string;
  partition: number;
  offset: string;
  key: string | null;
  value: any;                         // распарсенный JSON (или сырая строка)
  headers: Record<string, string>;
  timestamp: number;
}

export class KafkaTestClient {
  private kafka: Kafka;
  private consumer;
  private buffer: CapturedMessage[] = [];

  constructor(brokers = ['localhost:9092']) {
    this.kafka = new Kafka({
      clientId: 'aqa-tests',
      brokers,
      logLevel: logLevel.NOTHING,
    });
    // Уникальная группа на прогон → читаем независимо и с самого начала,
    // не мешая боевым консюмерам и не завися от их offset.
    this.consumer = this.kafka.consumer({
      groupId: `aqa-${Date.now()}-${Math.random().toString(36).slice(2)}`,
    });
  }

  /** Подписаться на топики и начать накапливать сообщения в буфер. */
  async start(topics: string[]) {
    await this.consumer.connect();
    for (const topic of topics) {
      await this.consumer.subscribe({ topic, fromBeginning: true });
    }
    await this.consumer.run({
      eachMessage: async ({ topic, partition, message }: EachMessagePayload) => {
        const raw = message.value?.toString() ?? '';
        let value: any = raw;
        try { value = JSON.parse(raw); } catch { /* оставим строкой */ }

        const headers: Record<string, string> = {};
        for (const [k, v] of Object.entries(message.headers ?? {})) {
          headers[k] = v?.toString() ?? '';
        }

        this.buffer.push({
          topic, partition,
          offset: message.offset,
          key: message.key?.toString() ?? null,
          value, headers,
          timestamp: Number(message.timestamp),
        });
      },
    });
  }

  /**
   * Ждать сообщение, удовлетворяющее предикату (polling с таймаутом).
   * Так учитывается eventual consistency — событие приходит НЕ мгновенно.
   */
  async waitForMessage(
    predicate: (m: CapturedMessage) => boolean,
    { timeoutMs = 30_000, intervalMs = 200 } = {},
  ): Promise<CapturedMessage> {
    const deadline = Date.now() + timeoutMs;
    while (Date.now() < deadline) {
      const found = this.buffer.find(predicate);
      if (found) return found;
      await new Promise((r) => setTimeout(r, intervalMs));
    }
    throw new Error(
      `Сообщение не найдено за ${timeoutMs}ms. В буфере: ${this.buffer.length} сообщений`,
    );
  }

  /** Отправить событие (тест как продюсер). */
  async publish(topic: string, key: string, value: object, headers: Record<string, string> = {}) {
    const producer = this.kafka.producer();
    await producer.connect();
    await producer.send({
      topic,
      messages: [{ key, value: JSON.stringify(value), headers }],
    });
    await producer.disconnect();
  }

  async stop() {
    await this.consumer.disconnect();
  }
}
```

Использование в тесте (Playwright / Jest):

```typescript
import { KafkaTestClient } from './kafka-test-client';
import { randomUUID } from 'crypto';

test('заказ порождает событие оплаты с правильными полями', async ({ request }) => {
  const kafka = new KafkaTestClient();
  await kafka.start(['orders', 'payments']);

  // Уникальный сквозной id на прогон — чтобы найти именно своё сообщение
  const correlationId = `test-${randomUUID()}`;

  // 1. Действие: создаём заказ через API
  const resp = await request.post('/api/orders', {
    data: { item: 'book', amount: 5000 },
    headers: { 'X-Correlation-Id': correlationId },
  });
  const { orderId } = await resp.json();

  // 2. Трекинг: ждём событие order.created в топике orders
  const created = await kafka.waitForMessage(
    (m) => m.topic === 'orders'
        && m.headers['correlationId'] === correlationId
        && m.value.orderId === orderId,
  );
  expect(created.value.status).toBe('created');
  expect(created.key).toBe(`order-${orderId}`);   // проверяем ключ = партиционирование

  // 3. Трекинг по цепочке: то же событие должно «дойти» до payments
  const paid = await kafka.waitForMessage(
    (m) => m.topic === 'payments'
        && m.headers['correlationId'] === correlationId,   // сшиваем по correlationId
    { timeoutMs: 30_000 },
  );
  expect(paid.value.eventType).toBe('payment.completed');
  expect(paid.value.orderId).toBe(orderId);

  await kafka.stop();
});
```

### Python (confluent-kafka) — тот же приём

```python
import json, time, uuid
from confluent_kafka import Consumer, Producer

BROKERS = "localhost:9092"

def make_consumer(topics):
    c = Consumer({
        "bootstrap.servers": BROKERS,
        # уникальная группа на прогон + читаем с начала
        "group.id": f"aqa-{uuid.uuid4()}",
        "auto.offset.reset": "earliest",
        "enable.auto.commit": False,
    })
    c.subscribe(topics)
    return c

def wait_for_message(consumer, predicate, timeout_s=30):
    """Polling до появления сообщения по условию (eventual consistency)."""
    deadline = time.time() + timeout_s
    while time.time() < deadline:
        msg = consumer.poll(0.5)
        if msg is None or msg.error():
            continue
        record = {
            "topic": msg.topic(),
            "partition": msg.partition(),
            "offset": msg.offset(),
            "key": msg.key().decode() if msg.key() else None,
            "value": json.loads(msg.value().decode()),
            "headers": {k: v.decode() for k, v in (msg.headers() or [])},
        }
        if predicate(record):
            return record
    raise AssertionError(f"Сообщение не найдено за {timeout_s}s")

def publish(topic, key, value, headers=None):
    p = Producer({"bootstrap.servers": BROKERS})
    p.produce(topic, key=key, value=json.dumps(value),
              headers=list((headers or {}).items()))
    p.flush()

# --- в тесте ---
def test_order_produces_payment_event(api_client):
    consumer = make_consumer(["orders", "payments"])
    corr = f"test-{uuid.uuid4()}"

    order_id = api_client.create_order(item="book", amount=5000,
                                       correlation_id=corr)["orderId"]

    created = wait_for_message(
        consumer,
        lambda m: m["topic"] == "orders"
                  and m["headers"].get("correlationId") == corr
                  and m["value"]["orderId"] == order_id,
    )
    assert created["value"]["status"] == "created"

    paid = wait_for_message(
        consumer,
        lambda m: m["topic"] == "payments"
                  and m["headers"].get("correlationId") == corr,
    )
    assert paid["value"]["eventType"] == "payment.completed"
    consumer.close()
```

## 17.6. Паттерн «сшивание цепочки по correlationId»

Когда нужно проверить весь путь события через N сервисов, собери все сообщения с одним `correlationId` из всех топиков и проверь состав и порядок этапов:

```typescript
// собрать все этапы цепочки по общему correlationId
async function collectTrace(kafka: KafkaTestClient, correlationId: string, expectedStages: number) {
  const trace: CapturedMessage[] = [];
  await kafka.waitForMessage((m) => {
    if (m.headers['correlationId'] === correlationId) trace.push(m);
    return trace.length >= expectedStages;   // ждём, пока соберутся все этапы
  }, { timeoutMs: 45_000 });
  return trace.sort((a, b) => a.timestamp - b.timestamp);
}

// в тесте: убеждаемся, что прошли все три этапа в правильном порядке
const trace = await collectTrace(kafka, correlationId, 3);
expect(trace.map((m) => m.value.eventType)).toEqual([
  'order.created',
  'payment.completed',
  'email.sent',
]);
```

Это и есть трекинг end-to-end: одно действие → проверяем, что оно корректно «прокатилось» через orders → payments → notifications, ничего не потерялось и порядок этапов верный.

## 17.7. Практические советы (чтобы тесты не флакали)

- **Уникальный id на прогон** (`uuid`) в key и/или headers — иначе поймаешь чужое сообщение из общего топика.
- **Уникальная group.id на тест** + `earliest` — тестовый консюмер читает независимо и с начала, не трогая offset боевых групп.
- **Polling, а не sleep** — событие приходит с задержкой (eventual consistency); ждать по условию с таймаутом, а не фиксированную паузу.
- **Подписывайся на топик ДО действия** — консюмеру нужно время подключиться и получить партиции; если опоздать, можно пропустить быстрое сообщение (или всегда читать `fromBeginning`).
- **Проверяй схему, а не только наличие** — валидируй value через Zod/pydantic: обязательные поля, типы, формат id.
- **Не полагайся на автоудаление** — Kafka хранит по retention; тестовые сообщения будут лежать. Изоляция — через уникальные id, а не через «чистый топик».
- **Таймауты с запасом** — сквозная цепочка через несколько сервисов дольше одиночного события; 30–45 c норм для E2E.
- **Идемпотентность** — при at-least-once одно и то же событие может прийти дважды; тест должен искать «хотя бы одно совпадение», а не «ровно одно», если это не проверка на дубли.

## 17.8. Что именно проверяет AQA при трекинге — чек-лист

1. Событие **появилось** в нужном топике после действия.
2. **Ключ** правильный (значит, партиционирование и порядок корректны).
3. **Схема и поля** value валидны (id, status, суммы, типы).
4. **Headers** содержат `correlationId`/`traceId` для сквозной трассировки.
5. Событие **породило** следующие в цепочке (payments, notifications).
6. **Порядок** этапов корректный (по timestamp / по offset внутри партиции).
7. **Побочный эффект** применился (статус в БД/UI изменился — проверяем polling'ом).
8. **Нет дублей** нежелательного эффекта (идемпотентность обработчика).
9. **Lag = 0** после обработки (сервис догнал, ничего не зависло в топике).

# Глава 18. Юниты Kafka и масштабирование: брокер, топик, партиция, реплика, группа — зачем и как связаны

![](https://raw.githubusercontent.com/goalbeam-hash/notes/main/assets/kafka-units-scaling-map.png)



## 18.1. Зачем нужны копии партиции (репликация) и что за роли

Партиция — это данные на диске одного брокера. Один брокер может **упасть, перезагрузиться, сгореть**. Если партиция существует в единственном экземпляре — вместе с брокером пропадает и доступ к данным (а то и сами данные). Чтобы этого не было, Kafka держит **несколько копий каждой партиции на разных брокерах**. Сколько копий — задаёт `replication-factor` (RF). RF=3 → три копии на трёх брокерах.

У копий — **две разные роли**:

- **Leader (лидер)** — «главная» копия партиции. Через неё идёт **вся** работа: продюсеры пишут только в лидера, консюмеры читают только с лидера. В каждый момент у партиции ровно один лидер.
- **Follower (фолловер / replica)** — «горячие копии» на других брокерах. Они **не обслуживают** клиентов, их единственная задача — постоянно тянуть новые записи с лидера и держать идентичную копию наготове.

Как это спасает: если брокер с лидером падает, кластер **выбирает нового лидера** из фолловеров, которые успевали синхронизироваться (они называются **ISR — In-Sync Replicas**). Клиенты переключаются на нового лидера, данные не потеряны, простой — секунды. Фолловер, который отстал от лидера, из ISR выпадает и в лидеры не годится (иначе потеряли бы свежие данные).

Связанная настройка — **`min.insync.replicas`**: при `acks=all` запись подтверждается, только когда её приняли минимум N синхронных копий. Это страховка «не записать данные в единственную копию» — иначе падение одного брокера сразу означало бы потерю.

**Что значит «одно-брокерный стенд».** Твой локальный стенд — это **один брокер** (один контейнер `kafka`, `KAFKA_NODE_ID: 1`). На одной машине держать «копию на другом брокере» физически негде — другого брокера нет. Поэтому:

- максимально возможный RF на стенде = **1** (одна копия, она же лидер, фолловеров нет);
- отказоустойчивости нет: упадёт единственный брокер — топик недоступен;
- для локального обучения это норм — репликация не про обучение, а про надёжность в проде, где брокеров 3+.

Чтобы иметь RF=3, нужно **три брокера** — и мы подходим к главному вопросу: зачем вообще несколько брокеров, топиков, партиций и групп. Ниже — карта юнитов и связей.

## 18.2. Схема связей (текстовая версия)

```text
                         Producer
                            │ пишет только в лидера
                            ▼
        ┌──────────── Topic: orders (4 партиции, RF=2) ───────────┐
        │                                                          │
   ═══════════════════ Kafka Cluster (3 брокера) ═══════════════════
   ┌── Broker 1 ──┐     ┌── Broker 2 ──┐      ┌── Broker 3 ──┐
   │ P0 · Leader  │     │ P1 · Leader  │      │ P2 · Leader  │
   │ P2 · replica │     │ P0 · replica │      │ P1 · replica │
   │ P3 · Leader  │     │              │      │ P3 · replica │
   └──────────────┘     └──────────────┘      └──────────────┘
        │  данные топика РАЗМАЗАНЫ по брокерам + у каждой партиции копия
        ▼                                   ▼
  Group "billing" (3 консюмера)      Group "analytics" (2 консюмера)
   C1←P0  C2←P1  C3←P2,P3             C1←P0,P2   C2←P1,P3
   каждая партиция — 1 консюмеру       тот же поток, свои offset,
   делят нагрузку = ПАРАЛЛЕЛИЗМ        читают НЕЗАВИСИМО = FAN-OUT

Legend: Leader — сюда идут запись/чтение; replica — горячая копия на другом брокере.
```

## 18.3. Юниты снизу вверх и цепочки связей

**Message (сообщение)** — единица данных: `key + value + headers + timestamp`. **key** решает две вещи: в какую партицию попадёт (`hash(key) % N`) и, как следствие, порядок событий одной сущности.
→ *связь:* `key` сообщения → выбор `partition` → гарантия порядка внутри неё.

**Partition (партиция)** — упорядоченный append-only журнал; **минимальная единица параллелизма и хранения**. Живёт на конкретном брокере, порядок гарантируется только внутри неё.
→ *связь:* число партиций = потолок числа полезных консюмеров в группе → определяет параллелизм чтения. Партиция ↔ брокер (где лежит) ↔ реплики (её копии).

**Topic (топик)** — именованный набор партиций, логический «тип потока» (`orders`, `payments`). Сам по себе ничего не хранит — хранят его партиции.
→ *связь:* topic → делится на N partitions → те распределяются по брокерам. Разные топики = разные домены данных со своим retention, схемой, доступами.

**Broker (брокер)** — сервер Kafka, физически хранит партиции (лидеры и реплики) и обслуживает клиентов. Кластер = несколько брокеров.
→ *связь:* brokers ↔ partitions (распределение хранения и нагрузки) ↔ replicas (копии на РАЗНЫХ брокерах для надёжности).


----

Да, именно так. В твоём стенде один контейнер `kafka` = один брокер.

Точнее, брокер — это **один запущенный процесс Kafka** (JVM-процесс, поднятый из `kafka-server-start` внутри образа `apache/kafka:3.9.0`). Контейнер оборачивает ровно один такой процесс, и у него один `KAFKA_NODE_ID: 1` — это и есть идентификатор брокера (тот самый `Leader: 1`, что ты видел в `--describe`). Один процесс с одним node id = один брокер.

Отсюда прямые следствия для твоего стенда:

**Кластер из одного брокера.** Формально это всё равно «кластер», просто из одного узла. Поэтому максимум `replication-factor = 1` — копию партиции физически некуда положить, другого брокера нет. И все лидеры всех партиций сидят на этом единственном брокере (балансировать не с кем).

**Чтобы получить 3 брокера — нужно 3 процесса Kafka.** Обычно это три сервиса в `docker-compose.yml` (`kafka-1`, `kafka-2`, `kafka-3`) с разными `KAFKA_NODE_ID` (1, 2, 3) и своими портами. Тогда появляется настоящий кластер, можно ставить RF=3, партиции и лидеры размажутся по узлам.

Один нюанс, чтобы не путаться: у тебя KRaft-режим и в конфиге `KAFKA_PROCESS_ROLES: broker,controller` — то есть этот **один процесс совмещает две роли**: он и брокер (хранит данные, обслуживает клиентов), и контроллер (управляет метаданными кластера, раньше это делал Zookeeper). Но это по-прежнему **один брокер** — просто он ещё подрабатывает контроллером. В больших кластерах контроллеры часто выносят на отдельные узлы.

Аналогия: брокер — как один сервер БД в кластере. Один контейнер поднимает один «сервер», хочешь кластер из трёх — поднимаешь три.

Хочешь, покажу, как переписать `docker-compose.yml` под 3-брокерный KRaft-кластер (чтобы поиграться с RF=3, репликами и настоящим rebalance лидеров)? Могу заодно добавить это в пособие как отдельный раздел.

**Consumer Group (группа консюмеров)** — набор консюмеров с общим `group.id`, между которыми Kafka делит партиции топика.
→ *связь:* group ↔ partitions (каждая — ровно одному консюмеру группы = масштаб чтения); разные groups ↔ один topic (каждая читает весь поток независимо = fan-out).

**Про «группу топиков».** В Kafka **нет** отдельной сущности «группа топиков». Топики группируют только логически — соглашением об именах (`billing.orders`, `billing.invoices` — префикс как неймспейс) и правами доступа (ACL на маску имён). Настоящая «группирующая» сущность в Kafka — это **consumer group** (группа читателей), а не группа топиков. Если на собесе слышишь «группа топиков» — почти всегда имеют в виду либо неймспейс по имени, либо путают с consumer group.

## 18.4. Компактные юзкейсы — каждый отвечает на «зачем»

**UC1. Трафик вырос — зачем несколько партиций и консюмеров.**
Один консюмер читает топик и не успевает, lag растёт. Одна партиция = один консюмер, быстрее не сделать. Решение: топик на 6 партиций + группа из 6 консюмеров. Kafka раздаёт по партиции на консюмера → читаем в 6 потоков.
*Цепочка:* нагрузка ↑ → больше **partitions** → больше консюмеров в **group** → **параллелизм** чтения. Потолок параллелизма = число партиций.

**UC2. На одно событие нужно несколько реакций — зачем несколько групп (fan-out).**
«Заказ оплачен» должен: списать деньги (billing), послать письмо (notifications), обновить дашборд (analytics). Не копируем событие трижды — три **разные consumer groups** читают один топик `payments`, каждая со своими offset, независимо.
*Цепочка:* один **topic** → N **consumer groups** → каждая видит весь поток → добавить потребителя = просто новая группа, продюсер не трогаем.

**UC3. Данные не влезают / брокер может упасть — зачем несколько брокеров и реплики.**
Терабайты событий на один сервер не помещаются, и один сервер = единая точка отказа. Ставим 3 **брокера**: партиции топика **распределяются** по ним (ёмкость и throughput ×3), а каждая партиция получает **копии** (RF=3) на разных брокерах.
*Цепочка:* объём/надёжность → несколько **brokers** → **partitions размазаны** по ним (масштаб) + **replicas** на других брокерах (лидер упал → фолловер из ISR становится лидером = отказоустойчивость).

**UC4. Разные типы событий — зачем несколько топиков.**
Клики, заказы и логи — разные данные с разным сроком хранения и потребителями. Мешать их в один топик = каша. Заводим отдельные **топики** `orders`, `clicks`, `logs`: у каждого свой retention, число партиций, схема, права.
*Цепочка:* разделение доменов → разные **topics** → независимые retention/партиционирование/доступ/потребители.

**UC5. Нужен порядок при параллельной обработке — зачем key → partition.**
Обрабатываем события заказов в 6 потоков, но события **одного** заказа обязаны идти по порядку (created → paid → shipped). Шлём их с `key = orderId`: один ключ всегда в одну партицию, внутри партиции порядок гарантирован и её читает один консюмер.
*Цепочка:* нужен порядок сущности → одинаковый **key** → одна **partition** → порядок сохранён, при этом разные заказы параллелятся по разным партициям.

## 18.5. Итоговая цепочка масштабирования (одним взглядом)

```text
СООБЩЕНИЕ (key) ──выбирает──▶ ПАРТИЦИЮ ──лежит на──▶ БРОКЕРЕ ──копируется в──▶ РЕПЛИКИ (на др. брокерах)
      │                          │                       │                         │
   порядок                  параллелизм              ёмкость и                 отказо-
   для сущности             (1 партиция =            throughput                устойчивость
                             1 консюмер)              кластера                  (leader→ISR)

ТОПИК = набор партиций (домен данных)      ГРУППА КОНСЮМЕРОВ = делит партиции (масштаб чтения)
Разные ТОПИКИ = разные домены              Разные ГРУППЫ на один топик = fan-out (независимые читатели)
```

**Зачем масштабировать, одной фразой на собес:** *Партиции дают параллелизм и распределение по брокерам; брокеры дают ёмкость и (через реплики) отказоустойчивость; consumer groups дают масштаб чтения и fan-out; ключ сообщения сохраняет порядок там, где он нужен. Всё вместе — это способ обрабатывать растущий поток событий, не теряя ни порядок, ни данные, ни доступность.*

## 18.6. Почему у одного брокера может быть несколько лидеров

На схеме у Broker 1 два лидера — P0 и P3. Это не ошибка, а следствие балансировки. Разложим по шагам:

- **Лидерство раздаётся по кругу.** 4 партиции на 3 брокера: P0→B1, P1→B2, P2→B3, а четвёртая P3 «оборачивается» назад на B1. 4 не делится на 3 нацело → один брокер получает 2 лидера, остальные по одному. Небольшой перекос (2 против 1) — нормален.
- **Зачем вообще размазывать лидеров.** Запись и чтение идут **только через лидера**. Если бы все лидеры сидели на одном брокере, он бы обрабатывал весь трафик топика, а остальные простаивали. Равномерное распределение лидеров = равномерная нагрузка на кластер.
- **Preferred leader.** У каждой партиции есть «предпочтительный лидер» — первый брокер в её списке реплик. После сбоев лидерство может съехать; Kafka периодически запускает **preferred leader election**, возвращая лидеров на свои места, чтобы баланс не уплывал.
- *Цепочка:* трафик идёт через лидеров → лидеров распределяют по брокерам для баланса → при неделимом числе один брокер берёт на себя лишний лидер → после падений баланс восстанавливается автоматически.

**Вывод:** число лидеров на брокере ≈ (число партиций / число брокеров), округление даёт небольшой перекос. Смотреть на это стоит: если один брокер держит **сильно** больше лидеров — он станет узким местом.

## 18.7. FAN-OUT — что это, зачем, с чем связано

**Fan-out** («веерная рассылка») — паттерн, когда **одно событие независимо получают несколько разных потребителей**. В Kafka это достигается не копированием сообщения, а тем, что топик читают **несколько разных consumer groups**, и каждая видит **весь** поток целиком со своими offset.

Ключ к пониманию — два уровня распределения партиций:

- **внутри одной группы** партиции **делятся** между консюмерами (competing consumers) → это масштаб/параллелизм, каждое сообщение обработано один раз в группе;
- **между разными группами** ничего не делится — **каждая группа получает копию всего потока** → это и есть fan-out.

```text
                       ┌─▶ Group "billing"       (списать деньги)
Topic "payments" ──────┼─▶ Group "notifications" (отправить письмо)
   (один поток)        └─▶ Group "analytics"     (обновить дашборд)
                          каждая группа читает ВСЕ сообщения, независимо,
                          со своим offset и в своём темпе
```

**Зачем нужен fan-out (инженерно):**

- **Развязка потребителей.** Продюсер `payments` не знает и не должен знать, кто читает событие. Появился четвёртый потребитель (антифрод) — просто заводим новую группу `fraud`, продюсер и остальные не меняются. Нулевая связность.
- **Изоляция скорости и сбоев.** Медленная `analytics` не тормозит быструю `billing` — у каждой группы свой offset и свой lag. Упала одна группа — остальные читают как ни в чём не бывало.
- **Разные сценарии из одного источника.** Один и тот же поток одновременно кормит онлайн-обработку (billing), уведомления и офлайн-аналитику — без дублирования данных и без лишних топиков.

**С чем связано:** fan-out напрямую держится на двух свойствах Kafka из предыдущих глав — сообщения **не удаляются после чтения** (retention), поэтому их может прочитать сколько угодно групп; и **offset принадлежит группе**, а не сообщению, поэтому группы не мешают друг другу.

**Пример-цепочка:** событие `payment.completed` в топик `payments` → группы `billing` / `notifications` / `analytics` читают его каждая целиком → billing списывает деньги, notifications шлёт письмо, analytics пишет в хранилище → добавили `fraud` → он тоже начал получать весь поток, ничего в системе не трогая.

**Контраст с RabbitMQ:** там для fan-out нужен специальный `fanout exchange`, который физически кладёт копию сообщения в каждую очередь. В Kafka копий нет — один лог читают много групп. Это дешевле и позволяет новым потребителям читать даже **историю** (с начала топика), а не только новые сообщения.

## 18.8. Юзкейс-разбор: Rebalance

**Ситуация.** Группа `orders-processors` из 3 консюмеров читает топик `orders` на 6 партиций — по 2 партиции на консюмера. Один консюмер падает (деплой, OOM, зависание).

**Что происходит по шагам:**

1. Упавший консюмер перестаёт слать heartbeat координатору группы.
2. Через `session.timeout.ms` координатор считает его мёртвым и объявляет **rebalance**.
3. Партиции переназначаются на живых: теперь 6 партиций на 2 консюмера = по 3 каждому.
4. При «классическом» (eager) протоколе на время шага 2–3 **вся группа приостанавливает чтение** (stop-the-world); при **cooperative** переназначаются только осиротевшие партиции, остальные читают дальше.

*Цепочка:* изменение состава группы → rebalance → перераспределение партиций → короткая пауза чтения (+ возможные дубли).

**Чем это опасно и на что смотреть (инженерно):**

- **Дубликаты.** Упавший консюмер мог обработать сообщения, но не успеть закоммитить offset. Новый владелец партиции начнёт с последнего коммита → часть сообщений обработается повторно (at-least-once). Отсюда требование **идемпотентности** обработчика.
- **Rebalance storm.** Если обработка одного `poll()` дольше `max.poll.interval.ms`, координатор решает, что консюмер завис, выкидывает его → rebalance → и по кругу. Симптом — периодические паузы и скачки lag.
- **Лечится:** обрабатывать быстрее / брать меньше за раз (`max.poll.records`), поднять `max.poll.interval.ms`, включить `cooperative-sticky` assignor (меньше «переездов» и без stop-the-world), не делать группы избыточно большими.

**Зачем это знать AQA:** во время rebalance тест может увидеть задержку доставки или повторную обработку — это не баг сервиса, а нормальное поведение. Проверяй идемпотентность и жди по условию (polling), а не фиксированной паузой.

## 18.9. Юзкейс-разбор: Семантики доставки

**Ситуация.** Консюмер `billing` читает `payment.completed` и списывает деньги. Ключевой инженерный выбор — **когда коммитить offset относительно обработки**. Именно он определяет семантику.

```text
Вариант A (commit ДО обработки):     poll → commit offset → обработка
   упал во время обработки → offset уже сдвинут → сообщение НЕ переобработается
   = AT-MOST-ONCE (риск ПОТЕРЯ: деньги не списаны, а событие «прочитано»)

Вариант B (commit ПОСЛЕ обработки):  poll → обработка → commit offset
   упал между обработкой и commit → новый владелец перечитает → обработка ПОВТОРНО
   = AT-LEAST-ONCE (риск ДУБЛЬ: деньги списаны дважды)

Вариант C (транзакции Kafka):        обработка + commit offset в ОДНОЙ транзакции
   = EXACTLY-ONCE (ровно один раз, но сложно и работает для Kafka→Kafka)
```

*Цепечка:* момент коммита offset → семантика доставки → требование к обработчику (нужна ли защита от дублей).

**Как выбирают на практике (инженерно):**

- **At-most-once** берут там, где потеря терпима, а дубль вреден или бессмыслен: метрики, телеметрия, «последнее известное значение».
- **At-least-once** — дефолт для бизнес-событий: лучше обработать дважды, чем потерять. Но обязателен **идемпотентный консюмер** — повторная обработка не должна списать деньги второй раз (dedup по `eventId`, upsert вместо insert, операции вида «установить статус = paid», а не «прибавить»).
- **Exactly-once** — когда дубль недопустим и вся цепочка внутри Kafka (Kafka Streams): идемпотентный продюсер + транзакции. Как только в цепочке появляется внешняя БД/HTTP — гарантия на неё не распространяется, и всё равно возвращаются к at-least-once + идемпотентность.

**Связь с продюсером.** Надёжность доставки — это не только про консюмера. `acks=all` + `min.insync.replicas≥2` + RF≥3 гарантируют, что сообщение вообще **доживёт** до чтения; а `enable.idempotence=true` у продюсера убирает дубли при его собственных ретраях. Полная картина: надёжный продюсер (не потерял и не задублировал на записи) + осознанный момент коммита у консюмера + идемпотентная обработка.

**Зачем это знать AQA:** большинство систем — at-least-once, значит дубли возможны штатно. Тест должен это учитывать: проверять, что повторная доставка того же события **не** удваивает эффект (идемпотентность), и не считать один дубль за баг, если система не заявляет exactly-once.
