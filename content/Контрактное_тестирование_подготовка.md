# Контрактное тестирование и интеграции — подготовка к собесу

> Концепции + инструменты + **честные формулировки ответов** под легенду Т-Банка (веб + API, sablead; schema-валидация через Zod, но НЕ полный Pact). Главный принцип: концепции знаю уверенно, прикладной опыт подаю честно, на незнакомое — не блефую.

---

## Часть 1. Концепции — что это

### Consumer-Driven Contract Testing (CDC)
Контракт между сервисами рождается **со стороны потребителя (consumer)**: потребитель описывает, что реально нужно от провайдера, а провайдер верифицирует, что не сломал это. Классика — **Pact**. Ловит breaking changes **до деплоя**, на стороне того, кто ломает. Даёт независимую деплоимость микросервисов.

### Contract as Code
Контракт хранится **как код/файл в репозитории** (JSON Schema, OpenAPI/Swagger, Pact-файл, Protobuf), версионируется в git, участвует в CI. Не «договорённость на словах», а исполняемый, проверяемый артефакт.

### Semantic Interoperability Testing
Проверка не только **структуры** (поля/типы), но и **смысла** данных: что `«Мужской»` на источнике = `«1»` в целевой системе = снова `«Мужской»` при обратной конвертации (round-trip). Системы не просто обмениваются форматом — они **одинаково понимают значения**. Критично в интеграциях, миграциях, госсистемах.

### Functional Contract Testing
Проверка, что при соблюдении контракта сервис **функционально ведёт себя правильно**: не только форма ответа корректна, но и логика/значения соответствуют бизнес-правилам.

### Golden records («золотые записи», эталонные данные)
Заранее выверенный набор «правильных» пар `источник → цель`, против которого прогоняют трансформацию. Основа для тестов маппинга атрибутов и трансформации значений (в т.ч. на 3000+ значений — data-driven по таблице маппинга, с проверкой round-trip в обе стороны).

### Debug / Traceability тесты
Автотесты, которые при падении **не просто «Fail», а указывают на конкретное правило маппинга / причину** — самодиагностируемые падения с трассировкой до бизнес-правила (ожидали X, получили Y, сломалось правило Z).

## Часть 2. Инструменты — что это

| Инструмент | Что делает |
|---|---|
| **Pact** | CDC-фреймворк: консьюмер описывает контракт, провайдер верифицирует; есть Pact Broker + гейт `can-i-deploy` |
| **Microcks** | Мокирование и контрактное тестирование API/событий по OpenAPI / AsyncAPI / Postman-коллекциям |
| **Prism** (Stoplight) | Mock-сервер и валидатор запросов/ответов по OpenAPI-спеке |
| **Spectral** | Линтер OpenAPI/JSON: проверяет саму спеку на соответствие правилам (стиль, обязательные поля) |
| **JSON Schema** | Стандарт описания структуры JSON; валидация ответов по схеме |
| **Zod** | TypeScript-библиотека валидации схем (schema/response validation на стороне консьюмера) |

**Важно не путать уровни:** Zod/JSON Schema — это **валидация схемы ответа** (односторонняя, у консьюмера). Pact — **двустороннее** consumer-driven contract testing с верификацией провайдера. Разные уровни, не синонимы.

## Часть 3. Честные формулировки ответов (под легенду Т-Банка)

### Про CDC / Contract-as-Code / semantic / functional
> «Понимание концепций есть, прикладной опыт — на уровне **schema/response validation**: на API-слое в Т-Банке валидировал структуру и типы ответов сервисов по согласованным контрактам через **Zod-схемы**, сверял с Swagger/спекой. Это по сути консьюмер-сайд контрактных проверок и Contract-as-Code через схемы в репозитории. С **полным Pact-стеком** (брокер, верификация на стороне провайдера, can-i-deploy) в проде не работал — понимаю, как устроено, но за плотный опыт не выдаю. Semantic interoperability с обратной конвертацией значений — концептуально знаю, на практике с маппингом enum'ов так глубоко не работал».

### Про golden records и маппинг 3000+ значений
> «Прямого опыта с "золотыми записями" и маппингом 3000+ значений enum'ов не было — это специфика data-миграций/интеграций, а мой фокус веб + API. Методологию понимаю: это data-driven тестирование по эталонной таблице маппинга с проверкой round-trip (прямая и обратная конвертация). Ближайшее из моего опыта — валидация полей/значений по схемам и параметризация по большим наборам (у нас много параметризации по бизнес-ролям и статусам). Механику освою быстро».

### Про Debug/Traceability (тут есть сильное)
> «Инструментов трассировки правил маппинга не делал, но принцип **самодиагностируемых падений** — моя постоянная практика. В Т-Банке добивался, чтобы тест падал с понятным сообщением и артефактами: для polling — "какую операцию ждали, сколько, последний статус"; в отчёте — trace, скрин, запрос/ответ. Эту же идею перенёс бы на маппинг: в ассерте выводить, какое правило и пара источник→цель не сошлись, с ожидаемым и фактическим значением».

### Про Pact / Microcks / Prism / Spectral / JSON Schema
> «С **JSON Schema** работал — валидация ответов по схемам (на TS через Zod, та же идея). С **Pact, Microcks, Prism, Spectral** плотного коммерческого опыта нет — понимаю назначение (Pact — CDC, Prism/Microcks — моки+валидация по спеке, Spectral — линтинг OpenAPI), но за рабочий опыт не выдаю. Освою целенаправленно — база схемной валидации есть».

## Часть 4. Вопросы-ловушки на честность

### Незнакомый/несуществующий инструмент (например «NaggEd»)
Иногда интервьюер называет инструмент, которого ты не знаешь (или которого не существует), — **проверка на блеф**. Единственно правильно — не выдумывать:

> «Честно — с таким инструментом не сталкивался и не уверен, что верно расслышал название. Если уточните, что это или какой класс инструмента, — скажу, работал ли с аналогом. Для API у меня Postman и встроенный `request` Playwright + схемная валидация; для Kafka — проверка сообщений по офсетам/топикам и polling статусов операций».

⚠️ **Никогда не говори «да, использовал» про незнакомый тул.** Кандидаты, которые блефуют, проваливаются мгновенно. Честное «не знаю такого, но вот мои аналоги» — сильнее и вызывает доверие.

**Реальные инструменты под API + Kafka (уместно назвать):** Postman/Newman, Karate, REST Assured, Playwright `request`; для Kafka — `kafka-console-consumer/producer`, Conduktor, AKHQ, тестовые consumer'ы, Testcontainers (поднять Kafka в тестах), Microcks (AsyncAPI).

## Часть 5. Стратегия на таком собесе

Вопросы про CDC/маппинг/golden records — из вакансии с уклоном в **интеграционное/контрактное тестирование и миграции данных** (не совсем профиль веб+API+sablead). Как держаться:

1. **Концепции** — объясняй уверенно (CDC, Contract-as-Code, semantic interoperability, golden records, schema validation, traceability).
2. **Прикладной опыт** — честно: schema/response validation (Zod, Swagger) — да; полный Pact / Microcks / маппинг 3000+ — нет, но методологию понимаю и освою.
3. **Опирайся на своё сильное**: самодиагностируемые падения (traceability), data-driven параметризация, работа с Kafka по офсетам, eventual consistency.
4. **На незнакомое — не блефуй.** «Не сталкивался, вот мои аналоги» = плюс к доверию.

**Красная нить:** «Контрактную тему я понимаю концептуально и практикую её облегчённую версию — schema-валидацию на API-слое. Полный CDC-стек — освою, база есть. А самодиагностируемые падения и data-driven подход, которые тут ключевые, — это ровно моя ежедневная практика».
