# Тестовое задание: автоматизация тестирования POS-терминалов

**Условия:** разобраться, что такое POS-терминалы и как их тестируют вручную. Нельзя использовать эмуляцию (подключение к компьютеру и отправку команд на терминал — это уже делается). Задача: максимально автоматизировать ручную работу ручных тестировщиков. Любые идеи, без ограничения бюджета.

---

## 1. Что такое POS-терминал и что делают ручные тестировщики

**POS-терминал** (point-of-sale) — устройство приёма платежей: читает карту (чип / магнитная полоса / NFC-бесконтакт), принимает PIN, связывается с банком (эквайринг), печатает чек.

**Ручная работа тестировщика — это три вида действий:**

1. **Физическое взаимодействие с железом:**
   - вставить чип / приложить NFC / протянуть магнитную полосу разными картами;
   - нажать физические кнопки PIN-пада (PIN, сумма, подтверждение/отмена);
   - оторвать/забрать чек.
2. **Наблюдение результата:**
   - смотреть на **экран** терминала (сумма, статус «Одобрено/Отклонено», код ошибки);
   - читать **распечатанный чек** (сумма, RRN, дата, маскированный PAN, тип операции);
   - слышать звуковые сигналы.
3. **Управление условиями:**
   - разные типы/банки карт, валюты, суммы (в т.ч. на границах лимитов);
   - сценарии: оплата, отмена, возврат, предавторизация, чаевые, оплата частями;
   - разные состояния сети (медленно, обрыв) и ответы банка (одобрение/отказ/лимит).

**Ключевая мысль:** ручной труд = **физические действия + наблюдение + управление условиями**. По условию задания эмуляция (слать команды на терминал) исключена — значит, автоматизируем именно **физику и наблюдение**, то есть чёрный ящик со стороны реального пользователя.

---

## 2. Стратегия: автоматизировать каждый из трёх пластов

### Пласт 1. Физические действия → робот-манипулятор
- **Роботизированная рука / стенд с актуаторами** (бюджет не ограничен — можно кастомный робо-стенд):
  - **картоприёмник-диспенсер** с набором реальных тест-карт (чип, NFC-фоны/стикеры, магнитные; разные банки, валюты, лимиты) — робот подаёт карту, вставляет / прикладывает / протягивает;
  - **актуаторы/соленоиды над клавиатурой** PIN-пада — физически нажимают кнопки: PIN, сумма, подтверждение, отмена.
- Робот воспроизводит **ровно то, что делает рука тестировщика**, без эмуляции команд.

### Пласт 2. Наблюдение результата → компьютерное зрение (CV + OCR)
- **Камера над экраном** терминала + **OCR** — распознаёт, что показано (сумма, статус, код ошибки), сравнивает с ожидаемым.
- **Камера/сканер на чек** + OCR — распознаёт распечатанный чек (сумма, RRN, маскированный PAN, тип операции) и валидирует.
- **Микрофон** (опц.) — проверка звуковых сигналов успех/ошибка.
- Это заменяет «глаза и уши» тестировщика — объективно и без усталости.

### Пласт 3. Управление условиями → контроль окружения
- **Управляемая сеть**: терминал ходит через контролируемый шлюз/роутер (или SIM-эмулятор для GPRS-терминалов) — программно вносим задержки, обрывы, потерю связи (это про сеть, а не про команды терминалу — правила соблюдены).
- **Тестовый банковский хост / стенд эквайринга** (обычно есть у платёжного бизнеса) — прогон одобрений/отказов/лимитов без реальных денег.

## 3. Архитектура системы

```
┌─────────────────── Оркестратор тестов (Python / TS) ───────────────────┐
│  ├─ управляет роботом-рукой (подача карты + нажатия кнопок)             │
│  ├─ читает камеру экрана → OCR → ассерт (статус, сумма, код)            │
│  ├─ читает камеру чека → OCR → ассерт (RRN, PAN, тип, сумма)            │
│  ├─ управляет сетевыми условиями (задержки, обрывы)                     │
│  ├─ управляет тестовым банковским хостом (одобрение/отказ/лимит)        │
│  └─ логирует + видео каждого прогона (traceability)                     │
└────────────────────────────────────────────────────────────────────────┘
        │ робот              │ камеры/OCR           │ сеть/хост
   [ PIN-пад + карты ]  [ экран + чек ]      [ роутер + эквайринг-стенд ]
                    [   РЕАЛЬНЫЙ POS-ТЕРМИНАЛ   ]
```

- **Оркестратор** — фреймворк, который гоняет тест-кейсы: «подай карту A → введи PIN → подтверди сумму 100 ₽ → дождись на экране "Одобрено" → распознай чек → проверь сумму и RRN».
- **Data-driven**: таблица `карта × сценарий × сумма × ожидаемый результат` — параметризация по сотням комбинаций (разные банки, типы карт, суммы на границах лимитов).
- **Traceability**: при падении — не «Ошибка», а **«карта VISA-chip, сценарий "возврат", сумма 5000: ожидали "Одобрено", на экране "Отклонён код 51"»** + фото/видео экрана и чека. Падение указывает на причину, а не просто на факт сбоя.

## 4. Приоритизация (по ROI — риск × частота × стоимость)

Автоматизировать не всё сразу, а по ценности:

1. **Сначала — самое частое и рутинное:** базовые сценарии оплаты по топовым типам карт (chip / NFC / magstripe). Это ~80% ручного времени — робот + камера закрывают их первыми и дают быстрый эффект.
2. **Потом — регресс и краевые случаи:** границы лимитов, отказы банка, плохая сеть, отмена/возврат, предавторизация.
3. **Оставить людям:** редкие экзотические сценарии, где физическая автоматизация дороже пользы (низкий ROI), и исследовательское тестирование новых фич.

---

## 5. Эффект и метрики

- **Скорость:** робот работает 24/7, без усталости и ошибок ввода — сотни комбинаций `карта × сценарий` за ночь.
- **Сокращение ручного регресса** — прямая экономия времени тестировщиков.
- **Воспроизводимость и объективность** — камера не «недосмотрит», результат стабилен.
- **Traceability** — интегратор/разработчик сразу видит, какой сценарий и на каком шаге сломался.
- **Метрики прогона:** покрытие матрицы карт/сценариев, доля автоматизированного регресса, пропущенные в прод дефекты, флак стенда.

---

## 6. Этапы внедрения (реалистично)

1. **Диагностика** — сесть с ручными тестировщиками, разложить их работу на действия/наблюдения/условия, собрать матрицу сценариев и приоритеты.
2. **PoC на одном стенде** — робот-рука + камера + OCR + оркестратор на самом частом сценарии оплаты. Доказать жизнеспособность подхода.
3. **Масштабирование** — расширить матрицу карт/сценариев, добавить OCR чека и управление сетью, распараллелить на нескольких стендах.
4. **Процессы и команда** — обучить команду, встроить в расписание/CI, дашборды и traceability-отчёты, поддержка стенда.

---

## 7. Риски и как их снять

| Риск | Решение |
|---|---|
| OCR ошибается на бликах/шрифтах | контролируемое освещение, калибровка, обучение модели на реальных экранах/чеках |
| Робот сбивает позиционирование карты/кнопок | фиксация терминала на стенде, калибровка координат, датчики позиции |
| Хрупкость физического стенда | резервные стенды, регулярная калибровка, мониторинг здоровья стенда |
| Реальные карты/деньги | тестовый банковский хост + тестовые карты, никаких реальных списаний |

---

## 8. Резюме (одним абзацем)

Раз эмуляция исключена, автоматизируем **физику и наблюдение**: робот-манипулятор с картоприёмником и актуаторами вместо рук; компьютерное зрение и OCR вместо глаз (экран + чек); управляемая сеть и тестовый эквайринг-хост вместо ручных условий. Сверху — оркестратор с data-driven матрицей `карта × сценарий`, приоритизацией по ROI и самодиагностируемыми падениями с traceability. Внедряем поэтапно: диагностика → PoC → масштабирование → процессы. Это переносит мой подход из веб-автоматизации (data-driven, приоритизация по риску, самодиагностика падений) на аппаратный стенд.
