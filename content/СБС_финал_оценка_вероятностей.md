# СБС (Страховой брокер Сбербанка) — оценка вероятностей на финал

## Как объяснять каждую зону — по шагам (реалистично)

Логика одна на все зоны: **тип занятости → почему параллельно → легальность → возврат к делу.** Коротко, ровно, без вины.

### Зона A — Дев Эволюшн + Почта (11.2021–02.2023)

1. **Назови тип занятости сразу:** «Дев Эволюшн — это ГПХ, удалённая автоматизация; Почта — локальная подработка на складе в Казани».
2. **Объясни, почему параллельно:** «ГПХ давал гибкий график и проектную, неполную загрузку — поэтому в тот период параллельно брал стабильную подработку, время было по доходу непростое».
3. **Закрой легальностью:** «Оба оформлены официально — ГПХ и трудовой договор, отчисления идут, по документам всё сходится».
4. **Верни к профессии:** «Профессионально я всё это время рос в автоматизации — склад был фоном, не карьерой».

### Зона B — Почта хвост + Трейд Стар (03.2023–04.2023)

1. **Обозначь стык:** «Тут короткий стык на пару месяцев — я уже начинал новый QA-контракт в Трейд Стар, а старая подработка ещё доходила до конца».
2. **Сними вопрос городов:** «Трейд Стар — московская компания, но работал удалённо из Казани, физически оставался там».
3. **Легальность + переход:** «Это переходный момент между подработкой и полной QA-загрузкой, всё официально».

### Зона C — Продторг + Трейд Стар (05.2023–08.2023)

1. **Тип и города:** «Трейд Стар — удалённый QA по ГПХ на московскую компанию, я в Казани; Продторг — локальная подработка на складе на 3–4 месяца».
2. **Почему подработка при наличии QA:** «QA-загрузка на новом контракте выходила на полную не сразу — пока разгонялась, закрывал доход локальной подработкой».
3. **Почему Продторг короткий:** «Как только QA вышел на полную занятость, подработку закрыл — она и была на переходный период».
4. **Легальность + возврат:** «Всё оформлено, по документам бьётся. А по профессии это уже был серьёзный рост — биржа, торговые сценарии, API».

## Мини-скрипт «если спросят вскользь» (дефолт)

> «В 2021–2023 у меня было совмещение: удалённые QA-контракты по ГПХ и локальная подработка на складе в переходный период. Всё официально, по документам сходится. Профессионально я всё это время рос в автоматизации».

15 секунд — и назад к техническому разговору.

---

## Два разных «гейта» — их нельзя путать

1. **Интервью (решение о найме).** Оценивают подачу, софт-скилы, технический фит под их боль (перенос ручного регресса в авто, API, Kafka). Хард выясняют в разговоре, а не грилят по теории.
2. **Проверка СБ перед офером.** Факт-чек: сходится ли резюме с трудовой/налоговой. Это не допрос, а сверка документов. Бинарно и по фактам, а не «по ощущениям».

Разные гейты — разные риски. Не мешать одно с другим.

## Вероятности (честно, без сглаживания)

| Что | Оценка | Почему |
|---|---|---|
| Пройти проверку СБ | **Высокая** | Резюме совпадает с реальными документами; пересечения — легальные ГПХ, не скрытые |
| Попасть «под лупу» на интервью | **Низкая, ~15–20%** | Культура не микроскопная, канал тёплый, 1-й этап сильный |
| Получить оффер | **Реальный при сильном собесе** | Тянет разговор + технический фит, а не резюме |

## Трудовая — калибровка (не катастрофа)

По шкале «насколько плохо» от 1 до 10:

- **9–10** — выдуманный работодатель, враньё, рушащееся при сверке, судимость/долги, увольнение по статье. Вот это топит.
- **6–7** — большой необъяснённый пробел, серия увольнений по инициативе работодателя.
- **Твой случай ≈ 3–4** — рвано, но **реально и documented**: легальные пересечения (ГПХ), склад как подработка/гэп-филлер, много ГПХ, титулы Т-банка не совпадают с ролью.

Вывод: это **лёгкий балласт, не дисквалификатор**. «Рвано, но правда» — самая частая категория трудовых, которую кадровики видят постоянно. В тёплом канале почти гасится.

Важно: раз резюме бьётся с документами — оставить пересечения было **правильно**. Вылизанная под красоту трудовая провалила бы сверку СБ; настоящая — проходит именно потому, что совпадает.

---

## Что в твоих руках (снижает вероятность «лупы»)

Уровень внимания к деталям во многом задаёшь ты сам. Лупу достают не от подозрительности, а в ответ на сигнал.

- **Не поднимать тему трудовой самому** — если не спрашивают, не объясняешь.
- **Держаться уверенно и сильно, как на 1-м этапе** — подача решает больше, чем бумага.
- **Консистентность формулировок** — свести к одному варианту: Selenium vs **Selenide**, стек Дев Эволюшн. На словах не расходиться с резюме.
- **Если спросят про совмещение** — 15-секундный спокойный ответ: «QA-контракты были по ГПХ и удалённо, поэтому шли параллельно; в отдельные периоды брал локальную подработку. Всё оформлено официально, по документам сходится». Без нервов, дальше по существу.

Что провоцирует лупу (избегать):
- сам начинаешь оправдываться → «а чего он это поднимает?»;
- расходишься на словах с резюме → «стоп, тут не сходится».

---

## Итог

Резюме тебя **не выиграет и не утопит.** Выигрывает сильный собес и технический фит под их боль. Проверку СБ проходишь, потому что всё правда. «Лупа» маловероятна (~15–20%) и в основном управляема тобой.

Формула на финал: **держаться как на первом этапе + не поднимать трудовую самому + консистентность + один спокойный ответ наготове.** Этого достаточно.

# На чём сосредоточиться на финале

Порядок по важности — сюда вкладывать энергию, а не в переживания о трудовой.

1. **Технический фит под их боль.** Их боли: много ручного регресса, перенос в авто, большой непокрытый API-слой, Kafka, релизгейты. Твой опыт ложится один в один — веди разговор туда. Это то, что реально продаёт.
2. **Подача как на 1-м этапе.** Коротко, структурно, тезисами. Лидерство подавать **через людей и процесс** (кросс-ревью, онбординги, фокусы), а не через селекторы.
3. **Мотивация «к чему-то».** Гринфилд, рост в грейде/менеджменте, новый стек (CI/CD, нагрузочное). Не «убегаю», а «иду к».
4. **Готовность к офису и быстрому выходу.** Первые недели очно, выход без отработки в течение недели — под горячую позицию это козырь.
5. **Консистентность стека.** До собеса зафиксировать один вариант (см. слабые стороны) и не расходиться с резюме на словах.

---

# Слабые стороны (честно, чтобы держать в уме)

- **Рваная трудовая** — пересечения дат, склад посреди QA, много ГПХ, короткие стажи. Управляется спокойным объяснением (ниже).
- **Стек на словах vs в резюме** — риск сказать «Selenium», где в резюме «Selenide» (это разные вещи), или разойтись по стеку Дев Эволюшн. Свести к одному варианту заранее.
- **Титулы Т-банка ≠ роль** — «менеджер по продажам», который пишет автотесты. Нужна короткая рамка про банковское оформление контрактников.
- **Глубина под нагрузкой** — если начнут копать очень глубоко в специфику Т-банка, держать один и тот же нарратив (домен, eventual consistency, ФНС/БКИ, Kafka, POM) без импровизаций, которые потом противоречат.
- **Смена городов** (Казань ↔ Москва) — снимается удалёнкой + релокацией.

# Связная история для объяснения нестыковок (несколько подходов)

Цель — **не оправдываться, а спокойно уложить реальные факты в понятную линию.** Ниже сквозной каркас и разные углы подачи под разный вопрос. Использовать только если спросят.

## Сквозной каркас (единая линия — держать её всегда одинаково)

> База — Казань. Автоматизацией начал заниматься по ГПХ и удалённо, потому что так было гибче. ГПХ-формат позволял в отдельные периоды параллельно брать локальную подработку, когда QA-загрузка была проектной и неполной. Позже перешёл в Т-банк, вырос до саблида; осенью 2025-го перевели по московскому юрлицу, но физически оставался в Казани и работал удалённо, а в Москву переехал недавно — в начале июля, окончательно. Всё оформлено официально — по трудовой, договорам и отчислениям всё сходится.

Из этого каркаса вытекают все ответы. Не отклоняться от него.

## Подход 1 — «Гибкость ГПХ» (если спросят про пересечения дат)

> «QA-контракты у меня были по ГПХ и удалённо — например, Трейд Стар московская компания, а я работал из Казани. Загрузка по ГПХ проектная, поэтому в отдельные периоды параллельно брал локальную подработку для стабильного дохода. Пересечения не скрытые — это “основное + подработка”, и по документам всё бьётся».

*Когда применять:* прямой вопрос «почему две работы одновременно / в разных городах».

## Подход 2 — «Восходящая линия в QA» (если сомневаются в профессионализме)

> «Если смотреть на профессиональную линию, она восходящая: начал автоматизацию в Дев Эволюшн, вырос на бирже в Трейд Стар — там уже сложные торговые сценарии, API, — и дальше Т-банк, где дошёл до саблида. Складские подработки — это фон в непростой период, а не карьера; профессия у меня одна — автоматизация тестирования».

*Когда применять:* если чувствуешь, что склад в трудовой размывает образ «преданного автоматизатора».

## Подход 3 — «Банковское оформление» (если спросят про титулы Т-банка)

> «В банке контрактников и штатных часто оформляют через позицию отдела — отсюда “младший специалист” или “менеджер”. Фактическая роль у меня всё время была инженер по автоматизированному тестированию, это видно по обязанностям. Смена записей — это внутренние переводы и ротации, а не смена профессии».

*Когда применять:* «почему менеджер по продажам пишет автотесты / три записи Т-банка».

## Подход 4 — «Релокация» (если спросят про города)

> «Родом из Казани, поэтому ранние роли там или удалённые на московские компании. Осенью 2025-го Т-банк перевёл меня по московскому юрлицу на нерегиональное направление, но физически я оставался в Казани и работал удалённо. В Москву переехал уже недавно, в начале июля, окончательно — хотел быть ближе к коллегам по Т-банку и к IT-среде, где у меня много знакомых. Сейчас в Москве, к офису на Ленинском готов».

*Когда применять:* «то Казань, то Москва — как так».

## Подход 5 — «Короткий и уверенный» (дефолт, если вопрос вскользь)

> «Там было совмещение по ГПХ и подработка в переходный период — всё официально, по документам сходится».

*Когда применять:* если вопрос задан вскользь и не стоит раздувать — закрыл одной фразой и вернулся к делу.

---

## Правила использования истории

- **Один каркас, разные углы.** Все пять подходов — про одни и те же факты, просто акцент под вопрос. Не выдумывать новых деталей в моменте — иначе разойдёшься сам с собой.
- **Не поднимать самому.** Если не спросили — не объясняешь.
- **15 секунд максимум.** Ответил спокойно — вернулся к техническому разговору, где ты силён.
- **Никакого негатива и извинений.** «Так сложилось, всё официально» — тон ровный, без вины.
- **Консистентность с бумагой.** Что говоришь — то и в резюме; стек назвать один раз и одинаково.

# Технический добор под СБС (PHP, Bitrix, ревью)

## Код-ревью vs кросс-ревью (быстро, если спросят про лидерство)

- **Код-ревью** — сама практика: проверка чужого кода перед вливанием в основную ветку (стиль, логика, локаторы, отсутствие лишнего, стандарты). Это «что делаем».
- **Кросс-ревью** — способ организации код-ревью: «кто кого ревьюит». Участники проверяют **друг друга взаимно** (по кругу), а не когда один лид ревьюит всех.

Это **частное и общее**: код-ревью — зонтичная практика, кросс-ревью — её схема (взаимная, децентрализованная).

| | Централизованное (лид всех) | Кросс-ревью (взаимно) |
|---|---|---|
| Риск | лид = узкое место, знание в одной голове | нагрузка распределена, растут все |
| Плюс | единый строгий стандарт | пропускная способность, нет единой точки отказа |

**Как подавать:** «Код-ревью я поставил, а кросс-ревью — как организовал, чтобы не быть бутылочным горлышком: подтянул коллегу до второго ревьюера, стали проверять друг друга». Показывает лид-мышление (убираешь себя как единую точку прохождения), а не «мы смотрим код».

## PHP — что знать минимально

**«PHP — некомпилируемый язык», как сказал Артём — это правда?**

**В практическом смысле — да, но с нюансом.**
- PHP — **интерпретируемый** язык: ты не собираешь отдельный бинарник/артефакт, который деплоишь (как в Go/Java/C++). Исходники выкладываются на сервер и выполняются движком PHP (Zend Engine) при каждом запросе.
- **Строго говоря, PHP всё же компилируется** — но не заранее в артефакт, а **на лету в опкоды (байткод)** движком Zend при выполнении; с **OPcache** эти опкоды кешируются (чтобы не пересобирать на каждый запрос), а в **PHP 8** есть **JIT** (Just-In-Time компиляция). То есть «вообще не компилируется» — неточно; правильнее «нет ahead-of-time компиляции в деплой-артефакт».
- **Практический вывод для QA (и он верный):** раз нет стадии сборки с артефактом, **автотесты нельзя погонять «на билде» — они запускаются только после выкатки исходников на среду** (test/preprod/prod). Именно это и имел в виду интервьюер про «в пайп встроить сложно».

**Как ответить, если зайдёт разговор:**
> «В практическом смысле да — PHP не компилируется в отдельный деплой-артефакт, код выполняется движком на сервере. Строго — Zend компилирует его в опкоды на лету, с OPcache кеширует, в PHP 8 есть JIT, но это компиляция во время выполнения, а не заранее. Для нас как QA важно следствие: тесты гоняются после выкатки на среду, а не на этапе сборки — поэтому и стратегию гейтов я строю вокруг прогонов на тестовой среде, а не в пайплайне сборки».

**Что ещё знать про PHP на минимуме (для QA на Bitrix-проекте):**
- Серверный, интерпретируемый, динамически типизированный; крутится на веб‑сервере (Nginx/Apache + PHP‑FPM).
- Бизнес-логика — на бэке в PHP; **ошибки чаще в логах сервера, а не в консоли браузера** — уметь читать PHP-стектрейсы в логах.
- Жизненный цикл запроса: браузер → веб‑сервер → PHP → БД (**у Bitrix — MySQL**) → ответ.
- **Bitrix работает на PHP + MySQL** — значит, SQL‑валидация данных актуальна.
- Деплой = выкладка исходников на сервер (нет бинарника). Зависимости — Composer (для QA не критично).
- Писать PHP тебе как QA обычно не надо — надо **понимать, где логика, как читать логи/ошибки и что деплой без сборки**.

## Bitrix — что знать заранее и какие вопросы подготовить

**Что такое Bitrix (главное):**
- **1С‑Битрикс / Битрикс24** — **коробочное платформенное решение** (CMS + CRM) от вендора 1С‑Битрикс. **Много функционала даёт сам вендор**, а не команда.
- Работает на **PHP + MySQL**, тяжёлая **админка**.
- Ключевые понятия: **инфоблоки** (infoblocks — абстракция хранения данных Bitrix), **компоненты**, **бизнес‑процессы**, **права доступа**, встроенные **чаты/уведомления (WebSocket)**, **REST API** для интеграций.

## Kafka — как работал, кейс из Т-банка + код

**Библиотека для TS:** **KafkaJS** — стандартный клиент Kafka для Node/TypeScript (продюсер/консюмер, headers, топики, офсеты). Для проверки «через API» — встроенный `request` Playwright.

### Ответ для собеса (монолог)

> «Домен банковский, с eventual consistency: операция инициируется на UI или через API, но реально проходит **асинхронно через Kafka**. Задача была — в E2E проверять не только что кнопка нажалась, а что операция реально **дошла через брокер и запроцессилась**, иначе получаешь ложно‑зелёные тесты. Делал так: при создании операции получал **correlation/message id**, который прокидывался в Kafka‑сообщение (в headers или в payload). Дальше два подхода.
>
> **Основной — через API:** девопсы с бэкендерами подняли тестовый endpoint, который по этому id возвращает статус операции — `started → processing → completed`. Я поллил его встроенным `request` Playwright через `expect.poll`, пока статус не станет `completed` или не выйдет таймаут. Polling вместо `sleep` — чтобы не флачило и ждать ровно до готовности.
>
> **Второй — прямое чтение Kafka:** через **KafkaJS** поднимал consumer на нужный топик, находил сообщение по `messageId` в заголовках, ассертил payload и статус. Проверял и порядок, и что сообщение вообще дошло. Библиотека — KafkaJS».

### Вариант А — проверка по id через API (основной, polling)

```ts
import { test, expect } from '@playwright/test';

test('операция доходит через Kafka и процессится', async ({ request }) => {
  // 1. Инициируем операцию, получаем correlation/message id
  const resp = await request.post('/api/operations', { data: { type: 'transfer', amount: 100 } });
  const { messageId } = await resp.json();

  // 2. Поллим тестовый эндпоинт по id, пока статус не станет completed
  await expect.poll(async () => {
    const r = await request.get(`/test/kafka/messages/${messageId}`);
    const msg = await r.json();
    return msg.status;                 // started -> processing -> completed
  }, {
    message: `Сообщение ${messageId} не запроцессилось за отведённое время`,
    timeout: 15_000,
    intervals: [500, 1000, 2000],      // нарастающие интервалы опроса
  }).toBe('completed');
});
```

### Вариант Б — прямое чтение из Kafka через KafkaJS

```ts
import { Kafka, logLevel } from 'kafkajs';

const kafka = new Kafka({
  clientId: 'e2e-tests',
  brokers: ['kafka:9092'],
  logLevel: logLevel.ERROR,
});

// Хелпер: дождаться сообщения по id в топике
export async function waitForMessageById(topic: string, messageId: string, timeoutMs = 15_000) {
  const consumer = kafka.consumer({ groupId: `e2e-${Date.now()}` });
  await consumer.connect();
  await consumer.subscribe({ topic, fromBeginning: true });

  return new Promise<any>((resolve, reject) => {
    const timer = setTimeout(async () => {
      await consumer.disconnect();
      reject(new Error(`Сообщение ${messageId} не найдено в ${topic} за ${timeoutMs}ms`));
    }, timeoutMs);

    consumer.run({
      eachMessage: async ({ message }) => {
        // id ищем в headers, либо в payload
        const id = message.headers?.messageId?.toString()
          ?? JSON.parse(message.value!.toString()).id;
        if (id === messageId) {
          clearTimeout(timer);
          const payload = JSON.parse(message.value!.toString());
          await consumer.disconnect();
          resolve(payload);
        }
      },
    });
  });
}
```

Использование в тесте:

```ts
import { test, expect } from '@playwright/test';
import { waitForMessageById } from './kafka';

test('сообщение дошло в топик и статус верный', async ({ request }) => {
  const { messageId } = await (await request.post('/api/operations', {
    data: { type: 'transfer', amount: 100 },
  })).json();

  const payload = await waitForMessageById('operations', messageId);

  expect(payload.status).toBe('completed');
  expect(payload.amount).toBe(100);
});
```

### Что подчеркнуть на собесе (тезисы)

- **Зачем вообще:** при eventual consistency UI обманчив — галочка есть, а операция ещё в пути или упала; проверка через Kafka ловит реальный результат.
- **Polling, не `sleep`:** ждём ровно до готовности статуса — стабильно и без флака.
- **По id/headers:** привязка к `messageId`/correlation‑id делает проверку точечной, а не «прочитал что попало».
- **KafkaJS** — библиотека; `expect.poll` + `request` — если проверяем через тестовый API.
- **Мостик к СБС:** у вас Kafka и RabbitMQ — логика та же (отправлено → доставлено → обработано); RabbitMQ отличается моделью (обменники/очереди/роутинг vs топики/офсеты), но подход к проверке идентичен.
